Die moderne Softwareentwicklung in Rust unterscheidet sich grundlegend von der Arbeit in älteren Sprachen. ## 2. Die Definition

* **Integrierte Entwicklungsumgebung (IDE)**: Eine Softwareanwendung, die Entwicklern umfassende Einrichtungen für die Softwareentwicklung zur Verfügung stellt. Im Kontext von Rust kombiniert sie einen Texteditor mit Syntaxhervorhebung, automatischer Code-Vervollständigung, Build-Automatisierung und integrierter Fehlerdiagnose.
* **rust-analyzer**: Das offizielle, hochperformante Language Server Protocol (LSP) Backend für die Programmiersprache Rust. Es analysiert den Quellcode während des Schreibens inkrementell im Hintergrund, baut einen abstrakten Syntaxbaum (AST) auf und liefert Fehlermeldungen, Autovervollständigung sowie Refactoring-Optionen.
* **Inlay Hints (Eingebettete Hinweise)**: Vom Editor generierte, visuelle Textsegmente, die nicht im eigentlichen Quelltext abgespeichert sind, sondern dynamisch eingeblendet werden. Sie zeigen beispielsweise den inferierten Typ einer Variable oder den Namen eines Funktionsparameters an der Aufrufstelle an.
* **Clippy**: Das offizielle Linting-Tool des Rust-Projekts. Es analysiert Ihren Code auf Häufigkeiten von Anti-Patterns, ineffizienten Algorithmen, Sicherheitsrisiken oder Verstößen gegen Designrichtlinien und schlägt konkrete, idiomatische Verbesserungen vor.
* **KI-gestützte Softwareentwicklung (LLM-Assisted Development)**: Die Integration von Modellen der künstlichen Intelligenz (wie Gemini oder Claude) in den Entwicklungsprozess, um durch Kontextanalyse Codefragmente zu generieren, Fehler zu erklären oder bestehende Implementierungen zu optimieren.
* **Prompt-Engineering**: Die systematische Gestaltung von Eingabemustern (Prompts), um ein Large Language Model (LLM) dazu zu bewegen, präzise, korrekte und auf Rust-Sicherheitsgarantien optimierte Antworten zu liefern.

### Die Fluglotse-und-Co-Pilot-Metapher

> [!NOTE]
> **Die Fluglotse-und-Co-Pilot-Metapher**: Stellen Sie sich vor, Sie fliegen ein hochmodernes Flugzeug (die Rust-Entwicklung). 
> 
> Der **rust-analyzer** ist Ihr **Fluglotse im Tower**. Er überwacht permanent die Flugdaten, warnt Sie vor turbulenten Winden (Borrow-Checker-Konflikten), zeigt Ihnen auf Ihren Instrumenten die genaue Flughöhe und Geschwindigkeit an (Inlay Hints) und markiert Hindernisse auf dem Radar mit roten Warnleuchten (Inline-Fehler). Er greift nicht selbst in die Steuerung ein, sorgt aber dafür, dass Sie niemals die Orientierung verlieren.
> 
> Die **KI (das LLM)** ist Ihr **Co-Pilot auf dem Sitz neben Ihnen**. Wenn Sie eine schwierige Flugroute planen müssen (komplizierte Algorithmen oder Speicherarchitekturen), können Sie diese Aufgabe an den Co-Piloten delegieren. Wenn Sie dem Co-Piloten jedoch nur zurufen: „Flieg uns irgendwohin, wo es warm ist!“, wird er planlos navigieren, veraltete Karten nutzen oder sogar gefährliche Manöver vorschlagen. Nur wenn Sie ihm präzise Navigationsanweisungen geben, den aktuellen Zustand der Triebwerke mitteilen und klare Limits setzen (Prompt-Engineering), steuert er die Maschine sicher durch den Sturm.

## 3. Das Problem & Die Motivation

Rust unterscheidet sich in einem wesentlichen Aspekt von vielen anderen Programmiersprachen: Die statische Typprüfung und die strikten Ownership-Regeln verschieben die Fehlererkennung fast vollständig von der Laufzeit (Runtime) in die Übersetzungszeit (Compilezeit). Was auf den ersten Blick wie ein Segen wirkt, kann im Entwicklungsalltag ohne die passenden Werkzeuge schnell zu Frustration führen:

1. **Die Unsichtbarkeit des Typsystems**: Rust nutzt eine starke Typinferenz. Das bedeutet, dass Sie Typen selten explizit hinschreiben müssen – der Compiler leitet sie selbstständig ab. Ohne eine IDE, die diese Typen visuell darstellt, arbeiten Sie im Blindflug. Sie wissen nicht genau, ob eine Variable nun ein `String`, eine Referenz `&str`, ein Smart Pointer `Rc<String>` oder ein Tupel ist.
2. **Die langsame Feedbackschleife**: Wenn Sie Code in einem simplen Texteditor schreiben, müssen Sie für jede Überprüfung manuell das Terminal öffnen, `cargo build` oder `cargo check` eingeben und die Ausgabe durchforsten. Dies unterbricht den kreativen Fluss („Flow-Zustand“) massiv.
3. **Die Komplexität des Borrow Checkers**: Fehlermeldungen bezüglich Lebensdauern (`lifetimes`) und Ausleihen (`borrowing`) sind mathematisch präzise, können aber für Einsteiger extrem kryptisch wirken. Ohne visuelle Führung im Code verliert man leicht den Überblick darüber, welche Variable wie lange gültig ist.
4. **Das Problem naiver KI-Anfragen**: Large Language Models wurden auf Milliarden von Zeilen Code trainiert – ein Großteil davon in C++, Java oder Python. Wenn Sie ein Rust-Problem mit einem unpräzisen Prompt an eine KI übergeben, neigt das Modell dazu, Konzepte aus diesen GC-basierten (Garbage Collected) oder manuell verwalteten Sprachen zu übertragen. Das Resultat ist Code, der zwar kompiliert, aber das Zero-Cost-Prinzip von Rust durch redundante Kopiervorgänge (`.clone()`) verletzt oder Sicherheitslücken mittels `unsafe` aufreißt.

Die Motivation für das perfekte Zusammenspiel von VS Code, `rust-analyzer` und strukturiertem KI-Einsatz liegt auf der Hand: Sie transformieren den Compiler von einem unbarmherzigen Richter in einen interaktiven Mentor. Sie sehen Fehler, bevor Sie kompilieren, verstehen das Speicherlayout auf einen Blick und nutzen KI-Assistenten als hochspezialisierte Experten statt als unsichere Raterunden.

## 4. Der naive Versuch

Betrachten wir das Szenario eines Anfängers, der versucht, eine Funktion zu schreiben, die die erste Hälfte eines Textes verarbeitet und eine Referenz auf diesen Teilbereich zurückgibt. Da der Entwickler weder Inlay-Hints aktiviert hat noch die genauen Lebensdauern versteht, schreibt er folgenden Code:

```rust
// Dieser Code soll die erste Hälfte eines übergebenen Texts ermitteln.
// Um Speicherallokationen zu vermeiden, soll ein Slice (&str) zurückgegeben werden.
fn get_first_half(text: &str) -> &str {
    let temp_string = text.to_string(); // Umwandlung in ein String-Objekt zur Bearbeitung
    let half_len = temp_string.len() / 2;
    let result = &temp_string[0..half_len]; // Erstellung des Slices
    result // Rückgabe des Slices
}

fn main() {
    let message = "Systemsteuerung";
    let first_part = get_first_half(message);
    println!("Die erste Hälfte lautet: {}", first_part);
}
```

### Der unpräzise KI-Prompt

Da der Code nicht kompiliert, kopiert der Entwickler die Fehlermeldung nicht einmal, sondern tippt einen kurzen, naiven Prompt in seinen KI-Chat:

> „Mein Rust-Code wirft einen Fehler, wenn ich eine Referenz auf einen String zurückgeben will. Wie kann ich das beheben? Hier ist die Funktion: [Code]“

### Die ungeeignete Antwort der KI

Das LLM, das keinen Kontext über Speicher- und Performanceanforderungen hat, schlägt folgende typische „Lösung“ vor:

```rust
// Vorschlag der naiven KI:
// Verwenden Sie einfach statische Lifetimes oder klonen Sie die Daten.
fn get_first_half(text: &'static str) -> &'static str {
    let temp_string = text.to_string();
    let half_len = temp_string.len() / 2;
    // Wir leaken den Speicher, damit er 'static wird!
    let leaked: &'static str = Box::leak(temp_string.into_boxed_str());
    &leaked[0..half_len]
}
```

## 5. Die Anatomie des Fehlers

### Das Compiler-Feedback zum naiven Versuch

Wenn wir den ursprünglichen Code aus Schritt 4 kompilieren, meldet der Rust-Compiler eine klare Verletzung der Speichersicherheit:

```text
error[E0515]: cannot return value referencing local variable `temp_string`
 --> src/main.rs:7:5
  |
6 |     let result = &temp_string[0..half_len];
  |                   ----------- `temp_string` is borrowed here
7 |     result
  |     ^^^^^^ returns a value referencing data owned by the current function
```

### Speicheranalyse und Blick hinter die Kulissen

Warum verweigert der Compiler hier den Dienst? Visualisieren wir die Situation im physischen Speicher (Stack und Heap) beim Verlassen der Funktion `get_first_half`:

```text
       STACK (Funktionsrahmen von `get_first_half`)
       +---------------------------------------------+
       | `text`: &str (Fat Pointer auf "System...")  |
       | `temp_string`: String (Besitzer auf Heap)    | ---> Zeigt auf Heap-Adresse 0x2000
       | `half_len`: usize (7)                       |
       | `result`: &str (Fat Pointer, ptr: 0x2000,   |
       |                 len: 7)                     |
       +---------------------------------------------+
                               |
                               | (Zeigt auf lokalen Heap-Speicher von temp_string)
                               v
       HEAP (Dynamischer Speicher)
       +---------------------------------------------+
       | 0x2000: "Systemsteuerung"                   |
       +---------------------------------------------+
```

Beim Erreichen des Funktionsendes (Zeile 8) passiert Folgendes:
1. Der Gültigkeitsbereich (Scope) von `get_first_half` endet.
2. Gemäß den Ownership-Gesetzen von Rust wird für alle Variablen, die Besitzer von Ressourcen sind, die `drop`-Funktion aufgerufen. `temp_string` ist der Besitzer des Heap-Speichers an Adresse `0x2000`.
3. Der Heap-Speicher an Adresse `0x2000` wird freigegeben (dealloziert) und steht dem Betriebssystem wieder zur Verfügung.
4. Die Funktion versucht jedoch, `result` (einen Fat Pointer, der auf eben diese Adresse `0x2000` zeigt) an die aufrufende Funktion `main` zurückzugeben.
5. Würde der Compiler dies zulassen, hätte `main` in der Variable `first_part` einen sogenannten **Dangling Pointer** (einen hängenden Zeiger). Der Zugriff darauf in `println!` wäre undefiniertes Verhalten (Undefined Behavior), da der Speicherbereich bereits freigegeben oder durch andere Daten überschrieben wurde.

### Die Fehlleistung des KI-Vorschlags

Der von der naiven KI vorgeschlagene Code löst das Kompilierungsproblem auf die denkbar schlechteste Weise:
* `Box::leak` umgeht das Ownership-System, indem es die automatische Freigabe des Speichers deaktiviert. Der Speicher an Adresse `0x2000` wird niemals freigegeben.
* Bei jedem Funktionsaufruf entsteht ein **Memory Leak** (Speicherleck). Läuft dieses Programm auf einem Server, wird der Arbeitsspeicher über kurz oder lang vollständig gefüllt sein, was zum Absturz des Systems führt. Dies bricht die Rust-Philosophie der sicheren, ressourcenschonenden Programmierung komplett.

## 6. Die Lösung

Um das Problem sauber, sicher und ohne Speicherlecks oder unnötige Kopien zu lösen, passen wir das Design an. Da wir die erste Hälfte eines bereits existierenden Strings extrahieren möchten, benötigen wir gar keine Zuweisung eines neuen `String`-Objekts auf dem Heap. Wir können direkt auf dem übergebenen `&str` arbeiten. Ein String-Slice `&str` is bereits eine Referenz auf einen bestehenden String im Speicher. Wir erstellen einfach ein neues Slice auf diesem vorhandenen Speicherbereich:

```rust
// Die saubere, idiomatische Lösung.
// Die Lebensdauer des Rückgabe-Slices ist an die Lebensdauer des Eingabe-Slices gebunden.
fn get_first_half(text: &str) -> &str {
    let half_len = text.len() / 2;
    
    // Wir erstellen ein neues Slice direkt auf dem Eingabe-String.
    // Es wird kein neuer Heap-Speicher alloziiert!
    &text[0..half_len]
}

fn main() {
    let message = "Systemsteuerung";
    let first_part = get_first_half(message);
    println!("Die erste Hälfte lautet: {}", first_part);
}
```

### Zeile-für-Zeile-Erklärung nach dem EVA-Prinzip

* **Eingabe (Input)**:
  Die Funktion `get_first_half` akzeptiert einen Parameter `text` vom Typ `&str` (ein unveränderliches String-Slice). Dieses Slice besitzt die Daten nicht, sondern referenziert sie nur (z. B. den statischen Text `"Systemsteuerung"` im Programmspeicher oder einen Heap-String in `main`).
* **Verarbeitung (Processing)**:
  1. `let half_len = text.len() / 2;`: Wir berechnen die Byte-Länge des halbierten Texts. Bei ASCII-Zeichen entspricht dies genau der halben Zeichenanzahl.
  2. `&text[0..half_len]`: Wir verwenden die Range-Syntax `0..half_len`, um eine Teilansicht des übergebenen Slices zu erzeugen.
* **Ausgabe (Output)**:
  Die Funktion gibt das neu erstellte String-Slice `&str` zurück. Dank der impliziten Lebensdauer-Regeln von Rust (Lifetime Elision) erkennt der Compiler automatisch, dass das zurückgegebene Slice exakt so lange leben darf wie das übergebene Eingabe-Slice `text`. Es wird kein temporärer String erzeugt und somit kein Speicher auf dem Heap reserviert oder freigegeben.

Einschränkungen & Anforderungen:

4. Gib mir den korrigierten, vollständigen und lauffähigen Code.
```

#### 3.2.2 Compiler-Fehlermeldungen auflösen

##### Schritt 6: Systematisches Auflösen eines Fehlers in der Praxis
Angenommen, Sie haben folgenden fehlerhaften Code in `src/main.rs` geschrieben:

```rust
fn main() {
    let mut names = vec!["Klaus", "Dieter", "Anna"];
    let first = names.first();
    names.push("Sabine"); // Fehler!
    println!("Erster Name: {:?}", first);
}
```

1. Ihr konfiguriertes VS Code markiert die Zeile `names.push(...)` sofort rot.
2. Führen Sie `cargo check` im Terminal aus, um die Fehlermeldung zu kopieren:
```text
error[E0502]: cannot borrow `names` as mutable because it is also borrowed as immutable
 --> src/main.rs:4:5
  |
3 |     let first = names.first();
  |                 ----- immutable borrow occurs here
4 |     names.push("Sabine");
  |     ^^^^^^^^^^^^^^^^^^^^ mutable borrow occurs here
5 |     println!("Erster Name: {:?}", first);
  |                                   ----- immutable borrow later used here
```
3. Kopieren Sie diese Fehlermeldung und Ihren Code in das Prompt-Template aus Schritt 5.
4. Die KI wird Ihnen erklären, dass `names.first()` eine unveränderliche Referenz hält und `names.push()` eine veränderliche Referenz benötigt, was gegen die Aliasing-Regeln verstößt. Sie schlägt Ihnen vor, die Reihenfolge zu ändern oder den Wert zu kopieren (falls es sich um primitive Typen handelt), oder den Scope der Ausleihe einzugrenzen.

## 8. Mentale Modelle & Deep Dive

### Das Language Server Protocol (LSP) in der Praxis

Um zu verstehen, wie `rust-analyzer` so blitzschnell auf jede Tastatureingabe reagieren kann, hilft ein Blick auf die zugrundeliegende Architektur. Traditionelle IDEs kompilierten bei jeder Änderung das gesamte Projekt im Hintergrund neu. Bei großen Rust-Projekten würde dies zu massiven Verzögerungen führen.

`rust-analyzer` nutzt stattdessen eine client-seitige Erweiterung (VS Code) und ein eigenständiges Server-Programm (das LSP-Backend), die über JSON-RPC-Nachrichten kommunizieren:

```text
+-----------------------+                    +-------------------------+
|     VS Code (Client)  |                    |  rust-analyzer (Server) |
+-----------------------+                    +-------------------------+
|                       |                    |                         |
| User tippt Buchstabe  |                    |                         |
|                       | -- didChange ----->| Analyse des AST         |
|                       |                    | (Inkrementeller Parser) |
|                       |                    |                         |
| Rote Wellenlinie      | <-- Diagnostics -- | Berechne Typen          |
|                       |                    |                         |
| Inlay Hints anzeigen  | <-- Inlay Hints -- | Liefert Typen           |
+-----------------------+                    +-------------------------+
```

Der Server hält ein internes Modell des Codes im Speicher. Sobald Sie ein Zeichen eintippen, aktualisiert er nur den betroffenen Teil des Syntaxbaums (inkrementelles Parsing). Erst wenn Sie die Datei speichern, wird im Hintergrund ein schneller `cargo check` oder `cargo clippy` ausgeführt, um tiefergehende semantische Fehler aufzudecken.

### Die Philosophie von Clippy

Clippy ist kein reiner Compiler-Hilfsdienst, sondern ein didaktisches Werkzeug. Es ist in vier Hauptkategorien (Lints) unterteilt:
1. **Style**: Code, der zwar korrekt ist, aber nicht den idiomatischen Rust-Konventionen entspricht.
2. **Correctness**: Code, der sehr wahrscheinlich zu Fehlern zur Laufzeit führt (z. B. Vergleiche von Fließkommazahlen auf exakte Gleichheit).
3. **Complexity**: Code, der unnötig kompliziert geschrieben ist und einfacher ausgedrückt werden kann (z. B. `if let` statt eines komplexen `match`).
4. **Performance**: Code, der unnötigen Speicher alloziiert oder CPU-Zyklen verschwendet (z. B. das Suchen in einem Vektor statt in einem HashSet).

### Detaillierte Konfigurationsreferenz

Im Folgenden sind alle relevanten Einstellungen der Entwicklungswerkzeuge aufgeführt, die Sie in Ihrer `settings.json` definieren können.

#### 1. `rust-analyzer.inlayHints.typeHints.enable`
* **Typ**: `boolean`
* **Standardwert**: `true`
* **Beschreibung**: Steuert die Anzeige von Typen für Variablenbindungen, bei denen kein Typ explizit angegeben wurde.
* **Performance-Auswirkung**: Geringer Speicher- und CPU-Overhead für das Rendering im Editor.
* **Beispiel**:
  ```json
  "rust-analyzer.inlayHints.typeHints.enable": true
  ```

#### 2. `rust-analyzer.inlayHints.parameterHints.enable`
* **Typ**: `boolean`
* **Standardwert**: `true`
* **Beschreibung**: Zeigt die Namen der Argumente an den Aufrufstellen von Funktionen und Methoden an.
* **Performance-Auswirkung**: Keine spürbaren Verzögerungen.
* **Beispiel**:
  ```json
  "rust-analyzer.inlayHints.parameterHints.enable": true
  ```

#### 3. `rust-analyzer.inlayHints.chainingHints.enable`
* **Typ**: `boolean`
* **Standardwert**: `true`
* **Beschreibung**: Zeigt die Typen der Zwischenergebnisse bei verketteten Methodenaufrufen (Method Chaining) an.
* **Performance-Auswirkung**: Extrem nützlich bei komplexen Iterator-Ketten, kann bei sehr langen Ketten das Editorbild optisch überladen.
* **Beispiel**:
  ```json
  "rust-analyzer.inlayHints.chainingHints.enable": true
  ```

#### 4. `rust-analyzer.check.command`
* **Typ**: `string`
* **Standardwert**: `"check"`
* **Beschreibung**: Bestimmt das Werkzeug, das beim Speichern einer Datei zur Validierung im Hintergrund aufgerufen wird. Gültige Werte sind `"check"` (für `cargo check`) oder `"clippy"` (für `cargo clippy`).
* **Performance-Auswirkung**: `"clippy"` benötigt minimal mehr Zeit als `"check"`, liefert dafür jedoch tiefgehende Qualitätsanalysen.
* **Beispiel**:
  ```json
  "rust-analyzer.check.command": "clippy"
  ```

#### 5. `rust-analyzer.check.extraArgs`
* **Typ**: `array of strings`
* **Standardwert**: `[]`
* **Beschreibung**: Zusätzliche Argumente, die an den Prüfbefehl übergeben werden. Oft genutzt, um Clippy-Warnungen als Fehler zu behandeln.
* **Performance-Auswirkung**: Keine.
* **Beispiel**:
  ```json
  "rust-analyzer.check.extraArgs": ["--", "-D", "warnings"]
  ```

#### 6. `rust-analyzer.cargo.buildScripts.enable`
* **Typ**: `boolean`
* **Standardwert**: `true`
* **Beschreibung**: Ermöglicht das Ausführen von Cargo-Build-Skripten (`build.rs`) zur Generierung von Hilfscode während der Analyse.
* **Performance-Auswirkung**: Kann beim ersten Laden eines Projekts mit vielen Abhängigkeiten zu Verzögerungen führen.
* **Beispiel**:
  ```json
  "rust-analyzer.cargo.buildScripts.enable": true
  ```

#### 7. `rust-analyzer.procMacro.enable`
* **Typ**: `boolean`
* **Standardwert**: `true`
* **Beschreibung**: Aktiviert die Expansion von prozeduralen Makros (wie `#[derive(Serialize)]`), damit Autovervollständigung und Typerkennung auch für makrogenerierten Code funktionieren.
* **Performance-Auswirkung**: Erhöhter CPU-Bedarf bei großen Makro-Bibliotheken.
* **Beispiel**:
  ```json
  "rust-analyzer.procMacro.enable": true
  ```

#### 8. `rust-analyzer.cargo.features`
* **Typ**: `string` oder `array`
* **Standardwert**: `"all"`
* **Beschreibung**: Definiert, welche Cargo-Features bei der Analyse berücksichtigt werden sollen.
* **Performance-Auswirkung**: Bei großen Monorepositories kann das Einschränken der Features die Ladezeit verkürzen.
* **Beispiel**:
  ```json
  "rust-analyzer.cargo.features": "all"
  ```

#### 9. `rust-analyzer.diagnostics.disabled`
* **Typ**: `array of strings`
* **Standardwert**: `[]`
* **Beschreibung**: Erlaubt das gezielte Deaktivieren von spezifischen Fehlern oder Warnungen, die vom rust-analyzer generiert werden.
* **Performance-Auswirkung**: Keine.
* **Beispiel**:
  ```json
  "rust-analyzer.diagnostics.disabled": ["unresolved-macro-call"]
  ```

#### 10. `rust-analyzer.hover.actions.references.enable`
* **Typ**: `boolean`
* **Standardwert**: `false`
* **Beschreibung**: Zeigt beim Hovern über ein Symbol an, wie oft und wo es im Projekt referenziert wird.
* **Performance-Auswirkung**: Kann bei sehr großen Codebasen zu Verzögerungen führen, daher standardmäßig deaktiviert.
* **Beispiel**:
  ```json
  "rust-analyzer.hover.actions.references.enable": true
  ```

## 9. Drei praktische Übungen

### Übung 1 (Leicht - VS Code & rust-analyzer Setup verifizieren)
* **Ziel**: Sicherstellen, dass das System voll funktionsfähig ist und Typinferenzen visuell dargestellt werden.
* **Aufgabe**: 
  1. Öffnen Sie ein neues Cargo-Projekt.
  2. Kopieren Sie folgenden Code in Ihre `src/main.rs`:
     ```rust
     fn main() {
         let number = 42;
         let text = "Hallo Rust";
         let values = vec![1.0, 2.0, 3.0];
         let mut doubled_values = values.iter().map(|x| x * 2.0);
         let result = doubled_values.next();
         println!("Wert: {:?}", result);
     }
     ```
  3. Prüfen Sie, ob VS Code Ihnen die Typen (`i32`, `&str`, `Vec<f64>`, etc.) in grauem Hilfstext neben den Variablennamen anzeigt.
  4. Fügen Sie absichtlich ein Semikolon am Ende einer Funktionsdefinition hinzu und beobachten Sie, ob Clippy Ihnen sofort eine Warnung on-save ausgibt.
* **Lösungshinweis**: Wenn die Typen nicht angezeigt werden, prüfen Sie in Ihrer `settings.json`, ob `"rust-analyzer.inlayHints.typeHints.enable": true` korrekt geschrieben ist und starten Sie den Language Server neu (`Ctrl+Shift+P` -> `Rust Analyzer: Restart Server`).

### Übung 2 (Mittel - Den Borrow Checker mit KI-Hilfe zähmen)
* **Ziel**: Systematisches Prompting zur Lösung eines Ownership-Konflikts anwenden.
* **Aufgabe**:
  Der folgende Code soll eine Funktion implementieren, die einen Vektor von Zahlen filtert und die verbleibenden Elemente verdoppelt. Der Code kompiliert jedoch aufgrund eines Borrowing-Konflikts nicht:
  ```rust
  fn filter_and_double(data: &mut Vec<i32>) -> Vec<&i32> {
      let mut result = Vec::new();
      for val in data.iter() {
          if *val > 10 {
              result.push(val);
          }
      }
      data.push(42); // Fehler tritt hier auf!
      result
  }

  fn main() {
      let mut numbers = vec![5, 12, 8, 20];
      let filtered = filter_and_double(&mut numbers);
      println!("Gefiltert: {:?}", filtered);
  }
  ```
  1. Kopieren Sie den Fehlercode aus `cargo check`.
  2. Formulieren Sie unter Verwendung des Prompt-Templates aus Schritt 7 eine Anfrage an ein LLM.
  3. Setzen Sie die vorgeschlagene Lösung um und verifizieren Sie, dass kein `.clone()` auf den Vektor angewendet wurde.
* **Lösungshinweis**: Das Problem ist, dass `result` unveränderliche Referenzen (`&i32`) auf Elemente in `data` hält, während `data.push(42)` eine veränderliche Referenz auf das gesamte Vektorelement erfordert. Eine saubere Lösung ist die Rückgabe von Werten (`Vec<i32>`) statt Referenzen, was durch Dereferenzierung und Kopieren der Zahlen gelöst wird (da `i32` das `Copy`-Trait implementiert).

### Übung 3 (Schwer - Zero-Cost-Refactoring eines KI-Vorschlags)
* **Ziel**: Einen ineffizienten Codevorschlag einer KI manuell in ein Zero-Cost-Design überführen.
* **Aufgabe**:
  Sie haben eine KI nach einem Parser gefragt, der den Domain-Namen aus einer E-Mail-Adresse extrahiert. Die KI hat Ihnen folgenden Code geliefert:
  ```rust
  // Dieser Code funktioniert zwar, alloziiert aber bei jedem Aufruf 
  // einen neuen String auf dem Heap, was ineffizient ist.
  fn extract_domain(email: String) -> String {
      let parts: Vec<String> = email.split('@').map(|s| s.to_string()).collect();
      if parts.len() == 2 {
          parts[1].clone()
      } else {
          "".to_string()
      }
  }

  fn main() {
      let email_address = String::from("entwickler@rust-kurs.de");
      let domain = extract_domain(email_address);
      println!("Domain: {}", domain);
  }
  ```
  1. Schreiben Sie diesen Code so um, dass er absolut **zero-cost** arbeitet. Das bedeutet:
     * Die Funktion `extract_domain` darf keinen `String` per Ownership übernehmen, sondern soll ein E-Mail-Slice (`&str`) als Parameter akzeptieren.
     * Sie darf keinen neuen `String` zurückgeben, sondern ein Slice (`Option<&str>`), das auf den ursprünglichen Speicherbereich verweist.
     * Es darf kein einziger Heap-Allokationsschritt (`.to_string()`, `.clone()`) ausgeführt werden.
  2. Erklären Sie das Speicherlayout vor und nach der Optimierung.
* **Lösungshinweis**: Nutzen Sie die Methode `email.split('@').nth(1)`, die direkt ein `Option<&str>` zurückgibt, ohne Speicher auf dem Heap zu reservieren.

## 11. Zusammenfassung

* **VS Code Setup**: Durch die Installation von `rust-analyzer` und die Aktivierung von Inlay Hints in der `settings.json` wird die implizite Typinferenz von Rust im Editor visuell sichtbar gemacht.
* **On-Save-Checks**: Die Umstellung des Analysebefehls auf `clippy` sorgt dafür, dass Stilfehler und Performance-Bremsen direkt beim Speichern markiert werden, noch bevor das Programm übersetzt wird.
* **KI-Kollaboration**: Naive Prompts führen bei LLMs oft zu nicht-idiomatischem Code (wie exzessivem Klonen). Strukturierte Prompts, die dem LLM eine Expertenrolle zuweisen und Speicher-Constraints vorgeben, erzeugen performante und sichere Lösungen.
* **Fehleranalyse**: Compiler-Meldungen enthalten wertvolle Traces. Das systematische Übergeben dieser Fehlermeldungen an KI-Assistenten beschleunigt das Lernen und Verstehen des Borrow Checkers.
* **Zero-Cost-Prinzip**: Das Beheben von Lifetime-Fehlern sollte primär durch präzises Lebensdauer-Design (z. B. Scopes und Slices) und nicht durch unreflektiertes Kopieren oder Umgehen der Sicherheitsprüfungen via `unsafe` erfolgen.
