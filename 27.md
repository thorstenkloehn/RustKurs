# Kapitel 27: Eigene Datentypen mit Structs strukturieren

> [!IMPORTANT]
> Structs sind der wichtigste Baustein, um aus einzelnen Werten ein fachliches Modell zu bauen. Sobald mehrere Werte immer zusammengehören, sollten Sie prüfen, ob ein eigener Struct-Typ die bessere Lösung ist.

## 27.1 Lernziele & Lernplan

Nach diesem Kapitel können Sie:

- Named-Field Structs, Tuple Structs und Unit-like Structs korrekt definieren und unterscheiden;
- Struct-Instanzen mit Feldnamen, Field-Init-Shorthand und Struct-Update-Syntax erzeugen;
- Methoden, verändernde Methoden und assoziierte Funktionen in `impl`-Blöcken schreiben;
- `self`, `&self` und `&mut self` anhand von Ownership und Mutabilität auswählen;
- erklären, wie Felder auf dem Stack liegen, wann Heap-Daten beteiligt sind und warum Alignment Padding erzeugen kann;
- Ownership bei Feldern, Moves, Kopien und partiellen Moves sicher vorhersagen;
- `derive`-Traits, Sichtbarkeit, Kapselung und einfache Best Practices für robuste Struct-APIs anwenden.

Lernplan:

| Schritt | Thema | Ergebnis |
|---|---|---|
| 1 | Definition | Sie kennen die drei Struct-Formen. |
| 2 | Motivation | Sie erkennen, wann lose Variablen und Tupel nicht mehr reichen. |
| 3 | Fehler | Sie sehen typische Anfängerfehler bei Structs bewusst scheitern. |
| 4 | Lösung | Sie bauen ein idiomatisches Struct mit Methoden. |
| 5 | Tutorial | Sie entwickeln ein kleines Konto-Modell Schritt für Schritt. |
| 6 | Deep Dive | Sie verstehen Speicherlayout, Ownership, Traits und Kapselung. |
| 7 | Übungen | Sie festigen die Regeln mit eigenen Structs. |

> [!TIP]
> Lesen Sie Struct-Code immer in zwei Ebenen: Die `struct`-Definition beschreibt die Daten. Die `impl`-Blöcke beschreiben das Verhalten.

## 27.2 Die Definition

Ein **Struct** ist ein selbst definierter zusammengesetzter Datentyp. Er fasst mehrere Felder zu einem neuen, benannten Typ zusammen. In Rust enthält die Struct-Definition nur Datenfelder. Verhalten wird separat in `impl`-Blöcken definiert.

Rust kennt drei Formen:

| Form | Syntax | Typischer Einsatz |
|---|---|---|
| Named-Field Struct | `struct User { name: String }` | Domänenmodelle mit klar benannten Feldern. |
| Tuple Struct | `struct Meter(f64);` | Kleine Wrapper, Newtype-Pattern, kompakte Werte. |
| Unit-like Struct | `struct JsonFormatter;` | Typen ohne Daten, Marker, zustandslose Implementierungen. |

Beispiel:

```rust
struct User {
    name: String,
    email: String,
    active: bool,
}

struct Meter(f64);

struct JsonFormatter;
```

Zeile-für-Zeile:

| Zeile | Erklärung |
|---|---|
| `struct User { Felder }` | Definiert einen neuen Typ mit benannten Feldern. |
| `name: String` | Das Feld besitzt einen `String`; das Struct wird Owner dieses Feldes. |
| `struct Meter(f64);` | Definiert einen eigenen Typ um einen einzelnen `f64`. |
| `struct JsonFormatter;` | Definiert einen Typ ohne Felder und ohne gespeicherte Daten. |

> [!NOTE]
> Structs sind keine Klassen. Es gibt keine Vererbung und keine versteckten Konstruktoren. Rust trennt Datenmodell, Methoden und Trait-Implementierungen bewusst.

## 27.3 Das Problem & die Motivation

Lose Variablen funktionieren nur, solange ein Programm sehr klein bleibt:

```rust
fn main() {
    let title = String::from("Rust Grundlagen");
    let pages = 320;
    let available = true;

    println!("{title}: {pages} Seiten, verfügbar: {available}");
}
```

Zeile-für-Zeile:

| Zeile | Erklärung |
|---|---|
| `title`, `pages`, `available` | Die Werte gehören fachlich zusammen, sind für den Compiler aber getrennte Variablen. |
| `println!` | Die Ausgabe muss alle Werte einzeln kennen. |

EVA:

| Phase | Beschreibung |
|---|---|
| Eingabe | Drei unabhängige Variablen. |
| Verarbeitung | Die Variablen werden manuell kombiniert. |
| Ausgabe | Eine Textzeile mit Buchdaten. |

Das Problem wird sichtbar, sobald Funktionen ins Spiel kommen:

```rust
fn print_book(title: String, pages: u32, available: bool) {
    println!("{title}: {pages} Seiten, verfügbar: {available}");
}
```

Diese Signatur ist technisch möglich, aber fachlich schwach:

- Die Reihenfolge der Parameter muss überall stimmen.
- Neue Eigenschaften vergrößern jede Funktionssignatur.
- Es gibt keinen eigenen Typ, der "Buch" ausdrückt.
- Besitzverhältnisse sind schwerer zu erkennen, weil einzelne Felder separat übergeben werden.

Ein Tupel verbessert die Gruppierung, verliert aber Namen:

```rust
fn main() {
    let book = (String::from("Rust Grundlagen"), 320, true);
    println!("{}: {} Seiten", book.0, book.1);
}
```

`book.0` und `book.1` sind kurz, aber nicht selbsterklärend. Ein Struct gibt dem Datenmodell Namen, Typidentität und später Methoden.

## 27.4 Der naive Versuch

Ein Anfänger möchte einen Benutzer modellieren, die E-Mail-Adresse ändern und danach eine Zusammenfassung ausgeben:

```rust
struct User {
    name: String,
    email: String,
    active: bool,
}

fn main() {
    let user = User {
        name: String::from("Ada"),
        email: String::from("ada@example.com"),
        active: true,
    };

    user.email = String::from("ada@rust.dev");

    println!("{} <{}>", user.name, user.email);
}
```

Zeile-für-Zeile:

| Zeile | Erklärung |
|---|---|
| `struct User` | Der Typ besitzt drei Felder. |
| `let user = User { Felder };` | Die Instanz wird unveränderlich gebunden. |
| `name: String::from("Ada")` | Der `String` liegt als Steuerblock im Struct und besitzt Heap-Daten. |
| `user.email = neuer_wert;` | Es wird versucht, ein Feld einer unveränderlichen Instanz zu ändern. |
| `println!` | Die Felder werden lesend verwendet. |

EVA:

| Phase | Beschreibung |
|---|---|
| Eingabe | Eine neue `User`-Instanz mit drei Feldern. |
| Verarbeitung | Die E-Mail-Adresse soll ersetzt werden. |
| Ausgabe | Name und E-Mail sollen ausgegeben werden. |

Der Code kompiliert nicht, weil `user` nicht veränderlich gebunden wurde.

Ein zweiter naiver Versuch betrifft Feld-Mutabilität direkt in der Definition:

```rust
struct User {
    name: String,
    mut email: String,
    active: bool,
}

fn main() {}
```

Dieser Code kompiliert ebenfalls nicht. In Rust ist `mut` keine Eigenschaft eines Struct-Feldes in der Typdefinition.

## 27.5 Die Anatomie des Fehlers

Der Compiler meldet beim ersten Beispiel sinngemäß:

```text
error[E0594]: cannot assign to `user.email`, as `user` is not declared as mutable
help: consider changing this to be mutable: `let mut user`
```

Was passiert im Speicher?

```text
Stack
user:
  name   -> ptr,len,cap ----> Heap: "Ada"
  email  -> ptr,len,cap ----> Heap: "ada@example.com"
  active -> bool

Bindung:
  user ist nicht mutabel.
  Deshalb darf kein Feld ersetzt werden.
```

Rust behandelt Mutabilität auf der Ebene der Bindung:

- `let user` erzeugt eine unveränderliche Bindung.
- `let mut user` erzeugt eine veränderliche Bindung.
- Wenn die Bindung veränderlich ist, dürfen Felder verändert werden.
- Wenn die Bindung unveränderlich ist, dürfen Felder nicht normal verändert werden.

Der zweite Fehler lautet sinngemäß:

```text
error: expected identifier, found keyword `mut`
```

`mut email: String` ist keine gültige Feldsyntax. Rust will nicht, dass einzelne Felder in der Typdefinition "immer mutabel" oder "immer unveränderlich" sind. Die API entscheidet über Methoden und Sichtbarkeit, welche Änderungen erlaubt sind.

> [!WARNING]
> `mut` gehört in den meisten Struct-Fällen an die Variable oder an eine Referenz: `let mut user` oder `fn change(user: &mut User)`. Es gehört nicht vor ein Feld in der `struct`-Definition.

## 27.6 Die Lösung

Eine idiomatische Lösung trennt Daten, Konstruktion und Verhalten:

```rust
#[derive(Debug)]
struct User {
    name: String,
    email: String,
    active: bool,
}

impl User {
    fn new(name: String, email: String) -> Self {
        Self {
            name,
            email,
            active: true,
        }
    }

    fn summary(&self) -> String {
        format!("{} <{}>", self.name, self.email)
    }

    fn change_email(&mut self, new_email: String) {
        self.email = new_email;
    }

    fn deactivate(self) -> Self {
        Self {
            active: false,
            ..self
        }
    }
}

fn main() {
    let mut user = User::new(
        String::from("Ada"),
        String::from("ada@example.com"),
    );

    user.change_email(String::from("ada@rust.dev"));
    println!("{}", user.summary());

    let user = user.deactivate();
    println!("{user:?}");
}
```

Zeile-für-Zeile:

| Zeile | Erklärung |
|---|---|
| `#[derive(Debug)]` | Der Compiler erzeugt eine Debug-Ausgabe für `User`. |
| `struct User` | Der Typ bündelt Name, E-Mail und Aktivstatus. |
| `impl User` | Ab hier werden Funktionen und Methoden für `User` definiert. |
| `fn new(name: String, email: String) -> Self` | Assoziierte Funktion, die eine neue Instanz erzeugt. |
| `Self { name, email, active: true }` | Field-Init-Shorthand übernimmt gleichnamige Parameter direkt. |
| `fn summary(&self)` | Methode mit lesendem Zugriff auf die Instanz. |
| `format!("{} <{}>", self.name, self.email)` | Erzeugt einen neuen `String`, ohne die Felder zu verschieben. |
| `fn change_email(&mut self, new_email: String)` | Methode mit exklusivem veränderlichem Zugriff. |
| `self.email = new_email` | Das alte Feld wird ersetzt und danach gedroppt. |
| `fn deactivate(self) -> Self` | Methode übernimmt Ownership der gesamten Instanz. |
| `..self` | Struct-Update-Syntax übernimmt die übrigen Felder aus `self`. |
| `let mut user` | Die Bindung ist veränderlich, deshalb darf `change_email` aufgerufen werden. |

EVA:

| Phase | Beschreibung |
|---|---|
| Eingabe | `new` erhält zwei besitzende `String`-Werte; `change_email` erhält einen neuen `String`. |
| Verarbeitung | Die Instanz wird erzeugt, verändert und anschließend in eine deaktivierte Instanz umgebaut. |
| Ausgabe | `summary` liefert einen neuen Text; `Debug` gibt die komplette Instanz aus. |

Warum dies funktioniert:

- `User::new` übernimmt Ownership an `name` und `email`.
- `summary(&self)` leiht die Instanz nur aus.
- `change_email(&mut self)` verlangt exklusiven Schreibzugriff.
- `deactivate(self)` darf `..self` verwenden, weil die Methode die Instanz besitzt.

> [!TIP]
> Verwenden Sie `Self` in `impl`-Blöcken, wenn Sie den aktuellen Typ meinen. Das bleibt auch dann lesbar, wenn der Typ später generisch oder länger wird.

## 27.7 Kleines Tutorial: Ein Konto-Modell bauen

In diesem Tutorial bauen Sie ein kleines Konto-Modell. Es zeigt Named-Field Structs, Tuple Structs, Unit-like Structs, Methoden, assoziierte Funktionen und Kapselung.

### Schritt 1: Fachliche Typen definieren

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
struct Cent(i64);

#[derive(Debug)]
struct Account {
    owner: String,
    balance: Cent,
    active: bool,
}

struct AuditLog;
```

Erklärung:

| Zeile | Erklärung |
|---|---|
| `struct Cent(i64);` | Tuple Struct als Newtype um Geldbeträge in Cent. |
| `Clone, Copy` | `Cent` darf kopiert werden, weil `i64` kopierbar ist. |
| `PartialEq, Eq` | Beträge können verglichen werden. |
| `struct Account` | Named-Field Struct für fachliche Kontodaten. |
| `struct AuditLog;` | Unit-like Struct ohne gespeicherte Daten. |

### Schritt 2: Konstruktor und lesende Methoden ergänzen

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
struct Cent(i64);

#[derive(Debug)]
struct Account {
    owner: String,
    balance: Cent,
    active: bool,
}

impl Account {
    fn new(owner: String) -> Self {
        Self {
            owner,
            balance: Cent(0),
            active: true,
        }
    }

    fn owner(&self) -> &str {
        &self.owner
    }

    fn balance(&self) -> Cent {
        self.balance
    }
}

fn main() {
    let account = Account::new(String::from("Grace"));
    println!("{}: {:?}", account.owner(), account.balance());
}
```

EVA:

| Phase | Beschreibung |
|---|---|
| Eingabe | `new` erhält einen besitzenden Namen. |
| Verarbeitung | Das Konto startet mit `Cent(0)` und `active: true`. |
| Ausgabe | `owner` gibt eine Referenz zurück; `balance` gibt eine Kopie von `Cent` zurück. |

### Schritt 3: Verändernde Methoden hinzufügen

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
struct Cent(i64);

#[derive(Debug)]
struct Account {
    owner: String,
    balance: Cent,
    active: bool,
}

impl Account {
    fn new(owner: String) -> Self {
        Self {
            owner,
            balance: Cent(0),
            active: true,
        }
    }

    fn deposit(&mut self, amount: Cent) {
        self.balance.0 += amount.0;
    }

    fn withdraw(&mut self, amount: Cent) -> bool {
        if self.balance.0 >= amount.0 {
            self.balance.0 -= amount.0;
            true
        } else {
            false
        }
    }
}

fn main() {
    let mut account = Account::new(String::from("Grace"));

    account.deposit(Cent(5_000));
    let success = account.withdraw(Cent(1_500));

    println!("{account:?}, Auszahlung erfolgreich: {success}");
}
```

Zeile-für-Zeile:

| Zeile | Erklärung |
|---|---|
| `fn deposit(&mut self, amount: Cent)` | Die Methode verändert den Kontostand und braucht `&mut self`. |
| `self.balance.0 += amount.0` | Zugriff auf das innere Feld des Tuple Structs. |
| `fn withdraw(&mut self, amount: Cent) -> bool` | Die Methode meldet Erfolg oder Misserfolg zurück. |
| `if self.balance.0 >= amount.0` | Prüfung, ob genug Guthaben vorhanden ist. |
| `let mut account` | Ohne `mut` wären `deposit` und `withdraw` nicht aufrufbar. |

### Schritt 4: Unit-like Struct für zustandsloses Verhalten nutzen

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
struct Cent(i64);

#[derive(Debug)]
struct Account {
    owner: String,
    balance: Cent,
    active: bool,
}

struct AuditLog;

impl AuditLog {
    fn record(message: &str) {
        println!("[audit] {message}");
    }
}

impl Account {
    fn new(owner: String) -> Self {
        Self {
            owner,
            balance: Cent(0),
            active: true,
        }
    }

    fn close(mut self) -> Self {
        self.active = false;
        AuditLog::record("Konto wurde geschlossen");
        self
    }
}

fn main() {
    let account = Account::new(String::from("Grace"));
    let account = account.close();

    println!("{account:?}");
}
```

`AuditLog::record` ist eine assoziierte Funktion. Sie hat keinen `self`-Parameter und wird deshalb mit `::` aufgerufen.

> [!NOTE]
> Eine Funktion in einem `impl`-Block ohne `self`, `&self` oder `&mut self` ist keine Methode, sondern eine assoziierte Funktion. Konstruktoren wie `new` sind in Rust nur Konvention, keine spezielle Spracheigenschaft.

## 27.8 Mentale Modelle & Deep Dive

### 27.8.1 Die drei Struct-Formen

Named-Field Struct:

```rust
struct Rectangle {
    width: u32,
    height: u32,
}

fn main() {
    let rect = Rectangle {
        width: 30,
        height: 50,
    };

    println!("{} x {}", rect.width, rect.height);
}
```

Verwenden Sie diese Form, wenn Feldnamen die Lesbarkeit erhöhen.

Tuple Struct:

```rust
struct UserId(u64);
struct OrderId(u64);

fn load_user(id: UserId) {
    println!("Benutzer-ID: {}", id.0);
}

fn main() {
    let user_id = UserId(42);
    let order_id = OrderId(42);

    load_user(user_id);
    // load_user(order_id); // falscher Typ
}
```

`UserId` und `OrderId` enthalten beide `u64`, sind aber unterschiedliche Typen. Genau das ist der Nutzen des Newtype-Patterns.

Unit-like Struct:

```rust
struct PlainText;

impl PlainText {
    fn render(input: &str) -> String {
        input.to_string()
    }
}

fn main() {
    let output = PlainText::render("Hallo Rust");
    println!("{output}");
}
```

Der Typ speichert nichts. Er dient als Name für Verhalten.

### 27.8.2 `impl`-Blöcke, Methoden und Empfänger

Rust unterscheidet nach dem ersten Parameter:

| Empfänger | Bedeutung | Typischer Einsatz |
|---|---|---|
| kein `self` | Assoziierte Funktion | Konstruktoren, Parser, Hilfsfunktionen. |
| `&self` | Lesender Borrow | Anzeigen, Berechnen, Abfragen. |
| `&mut self` | Verändernder Borrow | Zustand ändern, Felder ersetzen. |
| `self` | Ownership übernehmen | Konsumieren, Umbauen, Finalisieren. |

Beispiel:

```rust
struct Document {
    title: String,
    published: bool,
}

impl Document {
    fn draft(title: String) -> Self {
        Self {
            title,
            published: false,
        }
    }

    fn title(&self) -> &str {
        &self.title
    }

    fn rename(&mut self, title: String) {
        self.title = title;
    }

    fn publish(mut self) -> Self {
        self.published = true;
        self
    }
}

fn main() {
    let mut doc = Document::draft(String::from("Notizen"));
    doc.rename(String::from("Rust-Notizen"));
    println!("{}", doc.title());

    let doc = doc.publish();
    println!("Veröffentlicht: {}", doc.published);
}
```

Speicherwirkung:

- `draft` übernimmt den `String` und legt ihn im Feld `title` ab.
- `title(&self)` leiht nur und gibt `&str` zurück.
- `rename(&mut self)` ersetzt den alten `String`; der alte Heap-Speicher wird freigegeben.
- `publish(self)` übernimmt die komplette Instanz und gibt eine neue Instanz zurück.

### 27.8.3 Struct-Update-Syntax und Ownership

Mit der Struct-Update-Syntax übernehmen Sie Felder aus einer bestehenden Instanz:

```rust
#[derive(Debug)]
struct Settings {
    host: String,
    port: u16,
    debug: bool,
}

fn main() {
    let base = Settings {
        host: String::from("localhost"),
        port: 8080,
        debug: false,
    };

    let dev = Settings {
        debug: true,
        ..base
    };

    println!("{dev:?}");
    // println!("{base:?}"); // nicht erlaubt
}
```

Warum `base` danach nicht mehr vollständig nutzbar ist:

| Feld | Typ | Verhalten bei `..base` |
|---|---|---|
| `host` | `String` | Wird bewegt, weil `String` nicht `Copy` ist. |
| `port` | `u16` | Wird kopiert. |
| `debug` | `bool` | Wird im neuen Literal direkt gesetzt. |

Der relevante Speicherzustand:

```text
Vorher:
base.host -> Heap: "localhost"
base.port = 8080
base.debug = false

Nachher:
dev.host  -> Heap: "localhost"
dev.port  = 8080
dev.debug = true
base.host ist bewegt
```

> [!WARNING]
> Nach `..base` dürfen Sie `base` nur dann weiterverwenden, wenn keine nicht-kopierbaren Felder bewegt wurden oder wenn Sie die betreffenden Felder vorher klonen.

### 27.8.4 Ownership bei Feldern und partielle Moves

Wenn Sie ein nicht-`Copy`-Feld aus einem Struct herausbewegen, ist die Instanz nur noch eingeschränkt nutzbar:

```rust
struct Person {
    name: String,
    age: u8,
}

fn main() {
    let person = Person {
        name: String::from("Linus"),
        age: 38,
    };

    let name = person.name;

    println!("{name}");
    println!("{}", person.age);
    // println!("{}", person.name); // nicht erlaubt
}
```

`person.age` ist weiterhin lesbar, weil `age` nicht bewegt wurde. `person.name` ist nicht mehr gültig, weil der `String` in `name` verschoben wurde.

Sicherer ist oft ein Borrow:

```rust
struct Person {
    name: String,
    age: u8,
}

fn main() {
    let person = Person {
        name: String::from("Linus"),
        age: 38,
    };

    let name = &person.name;

    println!("{name}");
    println!("{}", person.age);
}
```

Hier bleibt `person` vollständig gültig, weil `name` nur eine Referenz ist.

### 27.8.5 Speicherlayout, Alignment und Padding

Ein Struct liegt konzeptionell als Gruppe seiner Felder im Speicher. Rust garantiert für normale Structs mit `repr(Rust)` aber keine stabile Feldreihenfolge für FFI oder Binärformate. Der Compiler darf das Layout optimieren.

Beispiel:

```rust
use std::mem::{align_of, size_of};

struct Mixed {
    a: u8,
    b: u32,
    c: u16,
}

fn main() {
    println!("size: {}", size_of::<Mixed>());
    println!("align: {}", align_of::<Mixed>());
}
```

Wichtige Begriffe:

| Begriff | Bedeutung |
|---|---|
| Größe | Anzahl der Bytes, die eine Instanz belegt. |
| Alignment | Adresse, an der ein Wert effizient und korrekt liegen muss. |
| Padding | Füllbytes, die der Compiler zwischen Feldern oder am Ende einfügt. |
| `repr(Rust)` | Standardlayout; nicht für externe Binärschnittstellen garantiert. |
| `repr(C)` | C-kompatibleres Layout für FFI und definierte Feldreihenfolge. |

Vereinfachtes Bild:

```text
Felder:
a: u8   -> braucht 1 Byte
b: u32  -> braucht 4 Bytes und meist 4-Byte-Alignment
c: u16  -> braucht 2 Bytes

Mögliches Layout:
[a][pad][pad][pad][b][b][b][b][c][c][pad][pad]
```

> [!IMPORTANT]
> Verlassen Sie sich bei normalem Rust-Code nicht auf Bytepositionen einzelner Felder. Wenn Sie ein stabiles Layout für C-Interop brauchen, verwenden Sie bewusst `#[repr(C)]` und dokumentieren Sie die Schnittstelle.

Ein Struct mit Heap-Feldern speichert nicht den kompletten Heap-Inhalt direkt:

```rust
struct Article {
    title: String,
    views: u64,
}
```

Speicherbild:

```text
Stack:
Article
  title: ptr,len,cap ----> Heap: "Rust Structs"
  views: u64
```

Beim Move eines `Article` werden die Stack-Felder verschoben. Die Heap-Bytes des `String` werden nicht kopiert.

### 27.8.6 Derive-Traits

Viele Standard-Traits kann Rust automatisch ableiten:

```rust
#[derive(Debug, Clone, PartialEq, Eq, Default)]
struct Tag {
    name: String,
    priority: u8,
}

fn main() {
    let tag = Tag {
        name: String::from("rust"),
        priority: 1,
    };

    let cloned = tag.clone();
    let empty = Tag::default();

    println!("{tag:?}");
    println!("gleich: {}", tag == cloned);
    println!("{empty:?}");
}
```

Häufige Derives:

| Derive | Nutzen | Voraussetzung |
|---|---|---|
| `Debug` | Ausgabe mit `{:?}` | Alle Felder implementieren `Debug`. |
| `Clone` | Explizite tiefe oder passende Kopie | Alle Felder implementieren `Clone`. |
| `Copy` | Implizite bitweise Kopie | Alle Felder implementieren `Copy`; kein `Drop`. |
| `PartialEq` | Vergleich mit `==` | Alle Felder implementieren `PartialEq`. |
| `Eq` | Vollständige Gleichheit | Zusätzlich zu `PartialEq`; nicht für `f32`/`f64`. |
| `Default` | Standardwert mit `::default()` | Alle Felder implementieren `Default`. |
| `Hash` | Nutzung in Hash-basierten Collections | Alle Felder implementieren `Hash`. |

> [!WARNING]
> Leiten Sie `Copy` nicht reflexartig ab. Für fachliche Typen mit Besitz, Identität oder späterem Ressourcenmanagement ist `Clone` oft die bewusstere Entscheidung.

### 27.8.7 Sichtbarkeit und Kapselung

Struct-Felder sind standardmäßig privat. Das ist eine gute Voreinstellung:

```rust
mod domain {
    #[derive(Debug)]
    pub struct Product {
        name: String,
        price_cents: u32,
    }

    impl Product {
        pub fn new(name: String, price_cents: u32) -> Self {
            Self { name, price_cents }
        }

        pub fn name(&self) -> &str {
            &self.name
        }

        pub fn price_cents(&self) -> u32 {
            self.price_cents
        }

        pub fn change_price(&mut self, price_cents: u32) {
            self.price_cents = price_cents;
        }
    }
}

fn main() {
    let mut product = domain::Product::new(String::from("Tastatur"), 7_990);
    product.change_price(6_990);

    println!("{}: {} Cent", product.name(), product.price_cents());
}
```

Die API kontrolliert:

- wie ein `Product` erzeugt wird;
- welche Felder gelesen werden dürfen;
- welche Änderungen erlaubt sind;
- welche Invarianten später ergänzt werden können.

> [!TIP]
> Machen Sie den Struct-Typ oft `pub`, aber halten Sie Felder zunächst privat. Öffentliche Felder sind schwer wieder zu schließen, weil anderer Code direkt davon abhängen kann.

### 27.8.8 Best Practices für Struct-Entwürfe

| Ziel | Empfehlung |
|---|---|
| Klarheit | Nutzen Sie Named-Field Structs für fachliche Daten. |
| Typsicherheit | Nutzen Sie Tuple Structs für IDs, Einheiten und Wrapper. |
| Zustandsloses Verhalten | Nutzen Sie Unit-like Structs sparsam für Marker oder Formatter. |
| Konstruktion | Bieten Sie `new` an, wenn Standardwerte oder Invarianten wichtig sind. |
| Lesen | Geben Sie bei `String`-Feldern häufig `&str` zurück. |
| Ändern | Verwenden Sie `&mut self` für klare Zustandsänderungen. |
| Konsumieren | Verwenden Sie `self`, wenn die alte Instanz danach nicht mehr gebraucht wird. |
| Kapselung | Halten Sie Felder privat, solange direkte Feldzugriffe nicht Teil der API sein müssen. |
| Derives | Leiten Sie nur Traits ab, deren Semantik fachlich stimmt. |
| Layout | Optimieren Sie Speicherlayout erst, wenn Messungen es rechtfertigen. |

Ein häufiger Anti-Pattern ist ein "Datenbeutel" ohne Bedeutung:

```rust
struct Data {
    a: String,
    b: i32,
    c: bool,
}
```

Besser ist ein Name, der Fachlichkeit trägt:

```rust
struct LoginAttempt {
    username: String,
    failed_count: u32,
    locked: bool,
}
```

## 27.9 Drei praktische Übungen

### Übung 1: Named-Field Struct festigen

Erstellen Sie ein Struct `Book` mit den Feldern:

- `title: String`
- `author: String`
- `pages: u32`

Anforderungen:

- Implementieren Sie `Book::new(title: String, author: String, pages: u32) -> Self`.
- Implementieren Sie `description(&self) -> String`.
- Geben Sie in `main` die Beschreibung aus.

Beispielausgabe:

```text
Rust Grundlagen von Ada, 320 Seiten
```

Lösungshinweis:

> [!TIP]
> `description` sollte `&self` nutzen, weil die Methode das Buch nur liest. Verwenden Sie `format!`, damit keine Felder verschoben werden.

### Übung 2: Tuple Struct für Einheiten

Erstellen Sie zwei Tuple Structs:

```rust
struct Kilometer(f64);
struct Miles(f64);
```

Anforderungen:

- Implementieren Sie `Miles::from_kilometer(km: Kilometer) -> Self`.
- Nutzen Sie den Faktor `0.621371`.
- Geben Sie das Ergebnis in `main` aus.

Beispiel:

```text
10 km sind 6.21371 Meilen
```

Lösungshinweis:

> [!TIP]
> Greifen Sie innerhalb des `impl`-Blocks mit `km.0` auf den inneren Wert zu. Das ist bei Tuple Structs normal, aber bei komplexeren Typen sollten benannte Felder bevorzugt werden.

### Übung 3: Kapselung und verändernde Methoden

Erstellen Sie einen öffentlich nutzbaren Struct `Counter`, dessen Feld privat bleibt:

```rust
pub struct Counter {
    value: u32,
}
```

Anforderungen:

- Implementieren Sie `Counter::new() -> Self`.
- Implementieren Sie `value(&self) -> u32`.
- Implementieren Sie `increment(&mut self)`.
- Implementieren Sie `reset(&mut self)`.
- Leiten Sie `Debug`, `Clone`, `Copy`, `PartialEq` und `Eq` ab.

Beispielablauf:

```text
Start: 0
Nach increment: 1
Nach reset: 0
```

Lösungshinweis:

> [!TIP]
> `Counter` kann `Copy` sein, weil `u32` `Copy` ist. Wenn Sie später ein `String`-Feld hinzufügen, ist `Copy` nicht mehr möglich.

## 27.10 Lernstrategie, Selbsteinschätzung & Merkzettel

### Spickzettel

```rust
// Named-Field Struct
struct User {
    name: String,
    active: bool,
}

// Tuple Struct / Newtype
struct UserId(u64);

// Unit-like Struct
struct JsonFormatter;

// Instanz
let user = User {
    name: String::from("Ada"),
    active: true,
};

// Field-Init-Shorthand
fn new_user(name: String) -> User {
    User { name, active: true }
}

// Struct-Update-Syntax
let changed = User {
    active: false,
    ..user
};

// impl-Block
impl User {
    fn new(name: String) -> Self {
        Self { name, active: true }
    }

    fn name(&self) -> &str {
        &self.name
    }

    fn deactivate(&mut self) {
        self.active = false;
    }

    fn into_name(self) -> String {
        self.name
    }
}
```

### Active Recall

Beantworten Sie diese Fragen ohne nachzuschlagen:

1. Warum ist `struct UserId(u64)` typsicherer als nur `u64`?
2. Wann wählen Sie `&self`, wann `&mut self` und wann `self`?
3. Warum kann `..base` eine bestehende Instanz teilweise bewegen?
4. Was ist Padding und warum kann es in Structs entstehen?
5. Warum sind private Felder oft besser als öffentliche Felder?

### Feynman-Methode

Erklären Sie Structs in drei einfachen Sätzen:

1. Ein Struct ist ein eigener Typ, der zusammengehörige Daten bündelt.
2. Methoden stehen in `impl`-Blöcken und entscheiden, ob sie lesen, verändern oder Besitz übernehmen.
3. Ownership, Sichtbarkeit und Traits bestimmen, wie sicher und bequem dieser Typ im restlichen Programm genutzt werden kann.

### Gezielte Fehlerprovokation

Ändern Sie den funktionierenden `User`-Code aus Abschnitt 27.6 bewusst:

- Entfernen Sie `mut` bei `let mut user`.
- Ersetzen Sie `&self` in `summary` durch `self`.
- Entfernen Sie `#[derive(Debug)]`, aber lassen Sie `println!("{user:?}")` stehen.
- Verwenden Sie `..user` und versuchen Sie danach, `user` vollständig auszugeben.

Lesen Sie die Fehlermeldungen genau. Der Compiler zeigt Ihnen, welche Ownership- oder Trait-Regel verletzt wurde.

### Selbsttest

Wechseln Sie erst zum nächsten Kapitel, wenn Sie:

- einen Named-Field Struct ohne Vorlage schreiben können;
- ein Tuple Struct als Newtype erklären können;
- eine Methode mit `&self`, eine mit `&mut self` und eine mit `self` implementieren können;
- die Struct-Update-Syntax inklusive Move-Folgen erklären können;
- mit `derive` mindestens `Debug`, `Clone`, `PartialEq` und `Default` sinnvoll einsetzen können;
- private Felder über öffentliche Methoden kapseln können.

## 27.11 Zusammenfassung

- Structs bündeln zusammengehörige Daten in einem neuen, benannten Typ.
- Named-Field Structs sind die Standardform für klare Domänenmodelle.
- Tuple Structs eignen sich besonders für Newtypes, IDs und Einheiten.
- Unit-like Structs speichern keine Daten und dienen als Marker oder Träger zustandslosen Verhaltens.
- `impl`-Blöcke binden Verhalten an Typen.
- Assoziierte Funktionen haben keinen `self`-Parameter; Methoden haben `self`, `&self` oder `&mut self`.
- `&self` liest, `&mut self` verändert, `self` übernimmt Ownership.
- Struct-Update-Syntax kann nicht-`Copy`-Felder bewegen.
- Felder mit `String`, `Vec<T>` oder ähnlichen Typen besitzen Heap-Speicher über Steuerdaten im Struct.
- Alignment und Padding beeinflussen die Größe eines Structs; verlassen Sie sich ohne `repr(C)` nicht auf exakte Feldpositionen.
- `derive` spart Boilerplate, muss aber semantisch zum Typ passen.
- Private Felder und öffentliche Methoden ermöglichen Kapselung und stabile APIs.
