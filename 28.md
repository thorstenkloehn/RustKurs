# Kapitel 28: Enums und Pattern Matching

> [!IMPORTANT]
> Enums sind in Rust kein Nebenthema. Sie sind ein zentrales Werkzeug, um Zustände, Alternativen und Fehlerfälle typsicher auszudrücken. Pattern Matching ist der Mechanismus, mit dem Sie diese Alternativen kontrolliert auswerten.

## 28.1 Lernziele & Lernplan

Nach diesem Kapitel können Sie:

- eigene Enums mit einfachen Varianten und Varianten mit Daten definieren;
- entscheiden, wann ein Enum besser passt als ein Struct mit Statusfeld;
- Methoden auf Enums mit `impl`-Blöcken schreiben;
- `Option<T>` als sichere Alternative zu `null` einsetzen;
- `match`-Ausdrücke vollständig und idiomatisch formulieren;
- Pattern-Bindings nutzen, um Daten aus Enum-Varianten zu entnehmen;
- `if let` und `let ... else` gezielt für einseitige Fälle verwenden;
- typische Best Practices für Enums, `Option<T>` und Pattern Matching anwenden.

Lernplan:

| Schritt | Thema | Ergebnis |
|---|---|---|
| 1 | Definition | Sie kennen Enums, Varianten und Pattern Matching als Fachbegriffe. |
| 2 | Motivation | Sie erkennen Zustände, die als Enum modelliert werden sollten. |

> [!TIP]
> Merksatz: Ein Struct sagt "dieses Ding hat diese Felder". Ein Enum sagt "dieses Ding ist genau eine dieser Möglichkeiten".

## 28.2 Die Definition

Ein **Enum** ist ein selbst definierter Typ, dessen Wert genau eine von mehreren benannten Varianten sein kann. Jede Variante kann keine Daten, Tupel-Daten oder benannte Felder tragen.

Ein **Pattern** ist ein Muster, mit dem ein Wert geprüft und gleichzeitig zerlegt werden kann. **Pattern Matching** bedeutet, dass Rust einen Wert gegen solche Muster vergleicht und den passenden Codezweig ausführt.

Grundsyntax:

```rust
enum Nachricht {
    Beenden,
    Text(String),
    Bewegen { x: i32, y: i32 },
}

fn main() {
    let nachricht = Nachricht::Text(String::from("Hallo"));

    match nachricht {
        Nachricht::Beenden => println!("Programm beenden"),
        Nachricht::Text(inhalt) => println!("Text: {inhalt}"),
        Nachricht::Bewegen { x, y } => println!("Position: {x}, {y}"),
    }
}
```

Zeile-für-Zeile:

| Zeile | Erklärung |
|---|---|
| `enum Nachricht` | Definiert einen neuen Typ mit mehreren möglichen Varianten. |
| `Beenden` | Eine Variante ohne zusätzliche Daten. |
| `Text(String)` | Eine Variante mit einem `String` als Nutzdaten. |
| `Bewegen { x, y }` | Eine Variante mit benannten Feldern ähnlich einem Struct. |
| `Nachricht::Text(...)` | Erzeugt einen Wert des Typs `Nachricht`. |
| `match nachricht` | Prüft, welche Variante tatsächlich vorliegt. |
| `Text(inhalt)` | Bindet den inneren `String` an den Namen `inhalt`. |

> [!NOTE]
> Die Varianten sind im Namensraum des Enums. Deshalb schreiben Sie `Nachricht::Text` und nicht nur `Text`, sofern die Variante nicht importiert wurde.

## 28.3 Das Problem & die Motivation

Viele Programme müssen fachliche Alternativen ausdrücken:

- eine Zahlung ist offen, bezahlt oder fehlgeschlagen;
- eine Netzwerkadresse ist IPv4 oder IPv6;
- ein Suchergebnis ist vorhanden oder nicht vorhanden;
- ein Kommando ist `Start`, `Stop`, `Move` oder `Write`;
- ein Parser liefert entweder einen gültigen Wert oder einen Fehler.

Ein naiver Ansatz verwendet häufig Strings:

```rust
fn main() {
    let status = String::from("bezahlt");

    if status == "bezahlt" {
        println!("Die Bestellung kann versendet werden.");
    } else if status == "offen" {
        println!("Warten auf Zahlung.");
    } else {
        println!("Unbekannter Status: {status}");
    }
}
```

EVA:

| Phase | Beschreibung |
|---|---|
| Eingabe | Ein `String`, der einen fachlichen Zustand darstellen soll. |
| Verarbeitung | Mehrere Textvergleiche entscheiden über den Ablauf. |
| Ausgabe | Eine passende Meldung wird ausgegeben. |

Das funktioniert technisch, ist aber schwach modelliert:

- Tippfehler wie `"bezhaltt"` erkennt der Compiler nicht.
- Neue Statuswerte werden nicht automatisch überall eingefordert.
- Die erlaubten Zustände sind nur Konvention, kein Typ.
- Der Code vermischt Datenformat und Fachlogik.

Ein Boolean ist ebenfalls oft zu schwach:

```rust
fn main() {
    let bezahlt = false;
    println!("Bezahlt: {bezahlt}");
}
```

`false` kann "offen", "fehlgeschlagen", "storniert" oder "noch nicht geprüft" bedeuten. Sobald mehr als zwei fachliche Zustände existieren, wird ein Boolean unklar.

> [!IMPORTANT]
> Wenn Sie eine feste, begrenzte Menge fachlicher Möglichkeiten haben, ist ein Enum meistens das passende Modell.

## 28.4 Der naive Versuch

Ein Anfänger möchte eine Bestellung modellieren. Die erste Version nutzt ein Statusfeld als `String` und einen optional gemeinten Tracking-Code als leeren Text:

```rust
fn versand_text(status: &str, tracking_code: &str) -> String {
    if status == "bezahlt" {
        if tracking_code == "" {
            String::from("Bezahlt, aber noch nicht versendet.")
        } else {
            format!("Versendet mit Tracking-Code {tracking_code}.")
        }
    } else if status == "offen" {
        String::from("Warten auf Zahlung.")
    } else if status == "fehlgeschlagen" {
        String::from("Zahlung fehlgeschlagen.")
    } else {
        String::from("Unbekannter Status.")
    }
}

fn main() {
    let status = String::from("bezhaltt");
    let tracking_code = String::from("");

    let text = versand_text(&status, &tracking_code);
    println!("{text}");
}
```

Zeile-für-Zeile:

| Zeile | Erklärung |
|---|---|
| `fn versand_text(status: &str, tracking_code: &str)` | Die Funktion bekommt zwei Textreferenzen. |
| `status == "bezahlt"` | Der fachliche Zustand wird über einen Stringvergleich geprüft. |
| `tracking_code == ""` | Ein leerer String wird als "nicht vorhanden" interpretiert. |
| `status = "bezhaltt"` | Der Tippfehler ist ein gültiger `String`, aber kein gültiger Fachstatus. |
| `println!("{text}")` | Das Programm läuft und gibt den Fallback aus. |

EVA:

| Phase | Beschreibung |
|---|---|
| Eingabe | Zwei Strings, deren Bedeutung durch Konvention entsteht. |
| Verarbeitung | Manuelle Vergleiche suchen bekannte Textwerte. |
| Ausgabe | Bei Tippfehlern entsteht nur zur Laufzeit ein unbekannter Status. |

Der Code kompiliert. Genau das ist das Problem: Der Compiler kann den fachlichen Fehler nicht sehen.

> [!WARNING]
> Ein Programm, das falsche Fachzustände akzeptiert, ist oft gefährlicher als ein Programm, das nicht kompiliert. Rust soll solche Zustände möglichst in den Typen sichtbar machen.

## 28.5 Die Anatomie des Fehlers

Der naive Code hat keinen Rust-Compilerfehler. Er hat einen Modellierungsfehler.

Speicherbild:

```text
Stack
status:
  ptr,len,cap ----> Heap: "bezhaltt"

tracking_code:
  ptr,len,cap ----> Heap: ""

Problem:
  Beide Werte sind gültige Strings.
  Der Compiler kennt aber nicht die erlaubten Fachwerte.
```

Der Compiler prüft:

- Ist `status` ein gültiger `String`? Ja.
- Ist `&status` als `&str` übergebbar? Ja.
- Ist `tracking_code` ein gültiger `String`? Ja.
- Ist der Text `"bezhaltt"` fachlich erlaubt? Das weiß der Compiler nicht.

Ein zweites Problem ist der leere Tracking-Code. Ein leerer String kann vieles bedeuten:

| Wert | Mögliche Bedeutung |
|---|---|
| `""` | Noch nicht versendet. |
| `""` | Tracking wurde vom Dienstleister nicht geliefert. |
| `""` | Eingabefehler. |
| `""` | Feld wurde versehentlich gelöscht. |

Rust bietet für solche Fälle `Option<T>`:

- `Some(wert)` bedeutet: Wert ist vorhanden.
- `None` bedeutet: Wert ist bewusst nicht vorhanden.

Ein bewusst nicht vorhandener Wert ist präziser als ein leerer Ersatzwert.

## 28.6 Die Lösung

Wir modellieren den Bestellstatus als Enum und den Tracking-Code als `Option<String>`:

```rust
#[derive(Debug)]
enum BestellStatus {
    Offen,
    Bezahlt,
    Versendet { tracking_code: String },
    Fehlgeschlagen(String),
}

impl BestellStatus {
    fn beschreibung(&self) -> String {
        match self {
            BestellStatus::Offen => String::from("Warten auf Zahlung."),
            BestellStatus::Bezahlt => String::from("Bezahlt, aber noch nicht versendet."),
            BestellStatus::Versendet { tracking_code } => {
                format!("Versendet mit Tracking-Code {tracking_code}.")
            }
            BestellStatus::Fehlgeschlagen(grund) => {
                format!("Zahlung fehlgeschlagen: {grund}.")
            }
        }
    }

    fn ist_abgeschlossen(&self) -> bool {
        matches!(self, BestellStatus::Versendet { .. })
    }
}

fn tracking_aus_status(status: &BestellStatus) -> Option<&str> {
    match status {
        BestellStatus::Versendet { tracking_code } => Some(tracking_code.as_str()),
        BestellStatus::Offen | BestellStatus::Bezahlt | BestellStatus::Fehlgeschlagen(_) => None,
    }
}

fn main() {
    let status = BestellStatus::Versendet {
        tracking_code: String::from("DHL-12345"),
    };

    println!("{:?}", status);
    println!("{}", status.beschreibung());
    println!("Abgeschlossen: {}", status.ist_abgeschlossen());

    match tracking_aus_status(&status) {
        Some(code) => println!("Tracking: {code}"),
        None => println!("Kein Tracking-Code vorhanden."),
    }
}
```

Zeile-für-Zeile:

| Zeile | Erklärung |
|---|---|
| `enum BestellStatus` | Der Status ist jetzt ein eigener Typ. |
| `Offen`, `Bezahlt` | Varianten ohne zusätzliche Daten. |
| `Versendet { tracking_code: String }` | Diese Variante trägt genau die Daten, die nur bei Versand sinnvoll sind. |
| `Fehlgeschlagen(String)` | Diese Variante trägt einen Fehlergrund. |
| `impl BestellStatus` | Methoden werden direkt an den Enum-Typ gebunden. |
| `fn beschreibung(&self)` | Die Methode liest den Status, ohne Ownership zu übernehmen. |
| `match self` | Alle Varianten werden vollständig behandelt. |
| `matches!` | Das Makro prüft kompakt, ob ein Pattern passt. |
| `Option<&str>` | Die Funktion gibt entweder eine geliehene Textreferenz oder `None` zurück. |

EVA:

| Phase | Beschreibung |
|---|---|
| Eingabe | Ein Wert des Typs `BestellStatus`. |
| Verarbeitung | `match` zerlegt die konkrete Variante und nutzt die passenden Daten. |
| Ausgabe | Text, Boolean oder `Option<&str>` als präzises Ergebnis. |

Warum akzeptiert der Compiler diese Lösung?

- Es gibt nur die Varianten, die im Enum definiert sind.
- Ein Tippfehler wie `BestellStatus::Bezhalt` kompiliert nicht.
- Der Tracking-Code kann nur bei `Versendet` existieren.
- `match` zwingt Sie, alle Varianten zu behandeln.
- `Option<&str>` macht Abwesenheit sichtbar.

> [!TIP]
> Binden Sie Daten möglichst an die Variante, zu der sie fachlich gehören. Ein Tracking-Code gehört nicht zu `Offen`, sondern zu `Versendet`.

## 28.7 Kleines Tutorial: Eine Bestelllogik bauen

In diesem Tutorial bauen Sie eine kleine Funktion, die aus einer Bestellung eine klare Aktion ableitet.

### Schritt 1: Die fachlichen Typen definieren

```rust
#[derive(Debug)]
enum Zahlung {
    Offen,
    Bezahlt { betrag_cent: u32 },
    Abgelehnt { grund: String },
}

#[derive(Debug)]
enum Aktion {
    ZahlungErinnern,
    VersandVorbereiten(u32),
    SupportInformieren(String),
}

fn main() {
    let zahlung = Zahlung::Bezahlt { betrag_cent: 4990 };
    println!("{zahlung:?}");
}
```

Erklärung:

| Code | Bedeutung |
|---|---|
| `Zahlung::Offen` | Es gibt noch keinen erfolgreichen Zahlungseingang. |
| `Zahlung::Bezahlt { betrag_cent }` | Die Zahlung ist erfolgreich und enthält den Betrag. |
| `Zahlung::Abgelehnt { grund }` | Die Zahlung ist gescheitert und enthält den Grund. |
| `Aktion` | Ein zweites Enum beschreibt, was das Programm als Nächstes tun soll. |

### Schritt 2: Mit `match` eine Entscheidung treffen

```rust
#[derive(Debug)]
enum Zahlung {
    Offen,
    Bezahlt { betrag_cent: u32 },
    Abgelehnt { grund: String },
}

#[derive(Debug)]
enum Aktion {
    ZahlungErinnern,
    VersandVorbereiten(u32),
    SupportInformieren(String),
}

fn naechste_aktion(zahlung: Zahlung) -> Aktion {
    match zahlung {
        Zahlung::Offen => Aktion::ZahlungErinnern,
        Zahlung::Bezahlt { betrag_cent } => Aktion::VersandVorbereiten(betrag_cent),
        Zahlung::Abgelehnt { grund } => Aktion::SupportInformieren(grund),
    }
}

fn main() {
    let zahlung = Zahlung::Bezahlt { betrag_cent: 4990 };
    let aktion = naechste_aktion(zahlung);

    println!("{aktion:?}");
}
```

EVA:

| Phase | Beschreibung |
|---|---|
| Eingabe | `naechste_aktion` übernimmt eine `Zahlung`. |
| Verarbeitung | `match` wählt den passenden Zweig und bindet Nutzdaten. |
| Ausgabe | Eine `Aktion`, die der Rest des Programms weiterverarbeiten kann. |

### Schritt 3: `Option<T>` für freiwillige Daten nutzen

```rust
#[derive(Debug)]
struct Bestellung {
    nummer: u32,
    gutschein_code: Option<String>,
}

fn rabatt_text(bestellung: &Bestellung) -> String {
    match &bestellung.gutschein_code {
        Some(code) => format!("Bestellung {} nutzt Gutschein {code}.", bestellung.nummer),
        None => format!("Bestellung {} hat keinen Gutschein.", bestellung.nummer),
    }
}

fn main() {
    let bestellung = Bestellung {
        nummer: 1001,
        gutschein_code: Some(String::from("RUST10")),
    };

    println!("{}", rabatt_text(&bestellung));
}
```

Warum `match &bestellung.gutschein_code`?

- Die Funktion bekommt nur `&Bestellung`.
- Der `String` im `Some` soll nicht aus der Bestellung bewegt werden.
- Durch das Matchen auf eine Referenz entsteht `code` als geliehener Wert.

### Schritt 4: `if let` für einen einzelnen interessanten Fall

```rust
fn main() {
    let gutschein_code = Some(String::from("RUST10"));

    if let Some(code) = gutschein_code {
        println!("Gutschein gefunden: {code}");
    }
}
```

`if let` ist passend, wenn Sie nur einen Fall behandeln und alle anderen Fälle bewusst ignorieren.

### Schritt 5: `let ... else` für frühes Aussteigen

```rust
fn erster_buchstabe(text: Option<&str>) -> Option<char> {
    let Some(text) = text else {
        return None;
    };

    text.chars().next()
}

fn main() {
    println!("{:?}", erster_buchstabe(Some("Rust")));
    println!("{:?}", erster_buchstabe(None));
}
```

`let ... else` hält den Hauptpfad linksbündig:

- Wenn `Some(text)` vorliegt, ist `text` danach im äußeren Scope verfügbar.
- Wenn `None` vorliegt, muss der `else`-Block den Kontrollfluss verlassen, hier mit `return`.

## 28.8 Mentale Modelle & Deep Dive

### Enums als Summentypen

Ein Struct kombiniert Felder. Ein Enum wählt zwischen Varianten.

```text
Struct:
  User = name UND email UND active

Enum:
  Zahlung = Offen ODER Bezahlt ODER Abgelehnt
```

In der Typentheorie nennt man Structs oft Produkttypen und Enums Summentypen. Für den Alltag reicht:

- Struct: mehrere Dinge gleichzeitig.
- Enum: genau eine Möglichkeit aus einer festen Liste.

### Varianten mit Daten

Enum-Varianten können unterschiedliche Datenformen tragen:

```rust
#[derive(Debug)]
enum Kommando {
    Beenden,
    Schreiben(String),
    Verschieben { x: i32, y: i32 },
    Farbe(u8, u8, u8),
}

fn main() {
    let befehle = [
        Kommando::Beenden,
        Kommando::Schreiben(String::from("Hallo")),
        Kommando::Verschieben { x: 10, y: -3 },
        Kommando::Farbe(255, 128, 0),
    ];

    for befehl in befehle {
        println!("{befehl:?}");
    }
}
```

| Variante | Datenform | Einsatz |
|---|---|---|
| `Beenden` | keine Daten | Reines Signal. |
| `Schreiben(String)` | Tupel-Variante | Ein einzelner Wert. |
| `Verschieben { x, y }` | benannte Felder | Mehrere Werte mit Bedeutung. |
| `Farbe(u8, u8, u8)` | mehrere Tupel-Werte | Kompakte technische Daten. |

### Exhaustive Matching

`match` muss erschöpfend sein. Das bedeutet: Jeder mögliche Wert muss behandelt werden.

Dieser Code kompiliert nicht:

```rust
enum Ampel {
    Rot,
    Gelb,
    Gruen,
}

fn aktion(ampel: Ampel) -> &'static str {
    match ampel {
        Ampel::Rot => "stehen bleiben",
        Ampel::Gruen => "fahren",
    }
}

fn main() {
    println!("{}", aktion(Ampel::Gelb));
}
```

Der Compiler meldet sinngemäß:

```text
error[E0004]: non-exhaustive patterns: `Ampel::Gelb` not covered
```

Korrekt:

```rust
enum Ampel {
    Rot,
    Gelb,
    Gruen,
}

fn aktion(ampel: Ampel) -> &'static str {
    match ampel {
        Ampel::Rot => "stehen bleiben",
        Ampel::Gelb => "bereit machen",
        Ampel::Gruen => "fahren",
    }
}

fn main() {
    println!("{}", aktion(Ampel::Gelb));
}
```

> [!IMPORTANT]
> Der Exhaustiveness-Check ist einer der größten Vorteile von Enums. Wenn Sie später eine neue Variante hinzufügen, zeigt der Compiler alle Stellen, die angepasst werden müssen.

### Wildcards und Sammelzweige

Der Unterstrich `_` passt auf jeden Wert und bindet ihn nicht:

```rust
fn main() {
    let zahl = 7;

    match zahl {
        1 => println!("eins"),
        2 => println!("zwei"),
        _ => println!("andere Zahl"),
    }
}
```

Das ist nützlich, kann aber wichtige Fälle verstecken. Bei fachlichen Enums ist es oft besser, Varianten explizit aufzulisten.

Mehrere Patterns können mit `|` kombiniert werden:

```rust
enum Status {
    Neu,
    InArbeit,
    Fertig,
    Archiviert,
}

fn ist_aktiv(status: Status) -> bool {
    match status {
        Status::Neu | Status::InArbeit => true,
        Status::Fertig | Status::Archiviert => false,
    }
}

fn main() {
    println!("{}", ist_aktiv(Status::InArbeit));
}
```

### Pattern-Bindings

Ein Pattern kann Daten prüfen und Namen binden:

```rust
enum DateiAktion {
    Lesen(String),
    Schreiben { pfad: String, bytes: usize },
}

fn beschreiben(aktion: DateiAktion) -> String {
    match aktion {
        DateiAktion::Lesen(pfad) => format!("Lese Datei {pfad}."),
        DateiAktion::Schreiben { pfad, bytes } => {
            format!("Schreibe {bytes} Bytes nach {pfad}.")
        }
    }
}

fn main() {
    let aktion = DateiAktion::Schreiben {
        pfad: String::from("log.txt"),
        bytes: 128,
    };

    println!("{}", beschreiben(aktion));
}
```

Speicher und Ownership:

- `aktion` besitzt die enthaltenen `String`-Werte.
- `beschreiben(aktion)` übernimmt Ownership.
- Der passende Match-Arm bewegt die enthaltenen Werte in lokale Bindungen.
- Danach kann `aktion` nicht mehr verwendet werden.

Wenn Sie nur lesen möchten, matchen Sie auf eine Referenz:

```rust
enum DateiAktion {
    Lesen(String),
    Schreiben { pfad: String, bytes: usize },
}

fn beschreiben(aktion: &DateiAktion) -> String {
    match aktion {
        DateiAktion::Lesen(pfad) => format!("Lese Datei {pfad}."),
        DateiAktion::Schreiben { pfad, bytes } => {
            format!("Schreibe {bytes} Bytes nach {pfad}.")
        }
    }
}

fn main() {
    let aktion = DateiAktion::Lesen(String::from("config.toml"));

    println!("{}", beschreiben(&aktion));
    println!("{}", beschreiben(&aktion));
}
```

### `Option<T>` statt `null`

Rust hat keinen allgemeinen `null`-Wert. Abwesenheit wird über `Option<T>` ausgedrückt:

```rust
enum Option<T> {
    None,
    Some(T),
}
```

In echtem Code schreiben Sie diese Definition nicht selbst. `Option<T>`, `Some` und `None` sind automatisch verfügbar.

```rust
fn finde_name(id: u32) -> Option<String> {
    if id == 1 {
        Some(String::from("Ada"))
    } else {
        None
    }
}

fn main() {
    match finde_name(1) {
        Some(name) => println!("Gefunden: {name}"),
        None => println!("Kein Name gefunden."),
    }
}
```

Dieser Code kompiliert bewusst nicht:

```rust
fn main() {
    let x: i32 = 5;
    let y: Option<i32> = Some(10);

    let summe = x + y;
    println!("{summe}");
}
```

Der Compiler meldet sinngemäß:

```text
error[E0277]: cannot add `Option<i32>` to `i32`
```

Das ist richtig. Bevor Sie mit dem inneren Wert rechnen, müssen Sie `Some(wert)` und `None` behandeln.

Korrekt:

```rust
fn addiere_optional(x: i32, y: Option<i32>) -> i32 {
    match y {
        Some(wert) => x + wert,
        None => x,
    }
}

fn main() {
    println!("{}", addiere_optional(5, Some(10)));
    println!("{}", addiere_optional(5, None));
}
```

### Nützliche `Option<T>`-Methoden

| Methode | Zweck | Beispiel |
|---|---|---|
| `is_some()` | Prüft auf `Some`. | `wert.is_some()` |
| `is_none()` | Prüft auf `None`. | `wert.is_none()` |
| `unwrap_or(default)` | Liefert Inhalt oder Default. | `zahl.unwrap_or(0)` |
| `map(f)` | Transformiert `Some`, lässt `None` unverändert. | `name.map(|n| n.len())` |
| `and_then(f)` | Verkettet Operationen, die selbst `Option` liefern. | `text.and_then(|t| t.chars().next())` |
| `as_ref()` | Macht aus `Option<T>` ein `Option<&T>`. | `name.as_ref()` |
| `take()` | Entnimmt den Wert und lässt `None` zurück. | `feld.take()` |

Beispiel mit `map` und `unwrap_or`:

```rust
fn main() {
    let name = Some(String::from("Rust"));

    let laenge = name.as_ref().map(|text| text.len()).unwrap_or(0);

    println!("Länge: {laenge}");
    println!("Original: {name:?}");
}
```

> [!WARNING]
> `unwrap()` ist für schnelle Experimente bequem, aber in Kurs-, Produktions- und Bibliothekscode oft die falsche Wahl. Nutzen Sie `match`, `if let`, `let ... else`, `unwrap_or` oder saubere Fehlerbehandlung.

### Speicherlayout und Performance

Ein Enum speichert:

- einen Diskriminanten, also die Information, welche Variante aktiv ist;
- genug Platz für die größte Variante;
- eventuell Padding wegen Alignment.

```rust
use std::mem::size_of;

enum Klein {
    A,
    B(u8),
    C(u64),
}

fn main() {
    println!("u8: {}", size_of::<u8>());
    println!("u64: {}", size_of::<u64>());
    println!("Klein: {}", size_of::<Klein>());
    println!("Option<&i32>: {}", size_of::<Option<&i32>>());
    println!("&i32: {}", size_of::<&i32>());
}
```

Rust kann bestimmte `Option<T>`-Typen optimieren. `Option<&T>` ist häufig so groß wie `&T`, weil der ungültige Null-Pointer intern als `None` genutzt werden kann. Sie verlassen sich im normalen Code nicht auf exakte Bytezahlen, aber Sie dürfen wissen: `Option<T>` ist oft eine Zero-Cost-Abstraktion.

### Thread-Safety

Enums erhalten Auto-Traits wie `Send` und `Sync`, wenn ihre enthaltenen Daten diese Traits erfüllen.

- `enum E { A(u32), B(String) }` ist grundsätzlich threadtauglich, weil `u32` und `String` entsprechend sicher sind.
- Enthält eine Variante etwa `Rc<T>`, ist der gesamte Enum nicht `Send`.
- Ein einziger nicht thread-sicherer Variantentyp reicht aus, um den gesamten Enum einzuschränken.

### Best Practices

| Situation | Empfehlung |
|---|---|
| Feste Alternativen | Verwenden Sie ein Enum. |
| Zustand mit zustandsspezifischen Daten | Speichern Sie Daten direkt in der passenden Variante. |
| Abwesenheit eines Werts | Verwenden Sie `Option<T>`. |
| Alle Fälle sind fachlich wichtig | Verwenden Sie `match` ohne `_`. |
| Nur ein Fall interessiert | Verwenden Sie `if let`. |
| Frühes Aussteigen bei falschem Pattern | Verwenden Sie `let ... else`. |
| Fehler mit Zusatzdaten | Nutzen Sie eigene Enums oder später `Result<T, E>`. |
| Schnelles Debugging | Leiten Sie `Debug` mit `#[derive(Debug)]` ab. |

## 28.9 Drei praktische Übungen

### Übung 1: Syntax festigen

Definieren Sie ein Enum `Rolle` mit den Varianten:

- `Gast`
- `Benutzer(String)`
- `Admin { name: String, level: u8 }`

Schreiben Sie eine Funktion:

```rust
fn begruessung(rolle: &Rolle) -> String
```

Erwartete Beispiele:

| Eingabe | Ausgabe |
|---|---|
| `Rolle::Gast` | `Willkommen, Gast.` |
| `Rolle::Benutzer(String::from("Ada"))` | `Willkommen, Ada.` |
| `Rolle::Admin { name: String::from("Linus"), level: 3 }` | `Admin Linus mit Level 3.` |

Lösungshinweis:

Verwenden Sie `match rolle`. Da Sie eine Referenz matchen, werden `String`-Werte nicht bewegt.

### Übung 2: Logik erweitern

Modellieren Sie einen Downloadstatus:

- `Wartet`
- `Laeuft { prozent: u8 }`
- `Fertig { pfad: String }`
- `Fehler(String)`

Schreiben Sie:

```rust
fn status_text(status: &DownloadStatus) -> String
fn ist_fertig(status: &DownloadStatus) -> bool
```

Anforderungen:

- `prozent` soll in der Ausgabe erscheinen.
- `Fertig` soll den Pfad ausgeben.
- `Fehler` soll den Fehlergrund ausgeben.
- `ist_fertig` soll `true` nur für `Fertig` liefern.

Lösungshinweis:

Für `ist_fertig` können Sie `matches!(status, DownloadStatus::Fertig { .. })` verwenden.

### Übung 3: Transferleistung

Schreiben Sie eine Funktion, die den ersten gültigen Rabatt aus einer Liste auswählt:

```rust
#[derive(Debug)]
enum Rabatt {
    Prozent(u8),
    Festbetrag(u32),
    Ungueltig(String),
}

fn erster_gueltiger(rabatte: &[Rabatt]) -> Option<&Rabatt>
```

Anforderungen:

- `Prozent(0)` und `Prozent(101)` sollen ungültig sein.
- `Festbetrag(0)` soll ungültig sein.
- `Ungueltig(_)` ist immer ungültig.
- Die Funktion soll eine Referenz auf den ersten gültigen Rabatt zurückgeben.
- Wenn keiner passt, soll `None` zurückgegeben werden.

Beispiel:

```rust
#[derive(Debug)]
enum Rabatt {
    Prozent(u8),
    Festbetrag(u32),
    Ungueltig(String),
}

fn erster_gueltiger(rabatte: &[Rabatt]) -> Option<&Rabatt> {
    for rabatt in rabatte {
        match rabatt {
            Rabatt::Prozent(wert) if (1..=100).contains(wert) => return Some(rabatt),
            Rabatt::Festbetrag(cent) if *cent > 0 => return Some(rabatt),
            Rabatt::Prozent(_) | Rabatt::Festbetrag(_) | Rabatt::Ungueltig(_) => {}
        }
    }

    None
}

fn main() {
    let rabatte = [
        Rabatt::Ungueltig(String::from("abgelaufen")),
        Rabatt::Prozent(0),
        Rabatt::Festbetrag(500),
    ];

    println!("{:?}", erster_gueltiger(&rabatte));
}
```

Lösungshinweis:

Nutzen Sie eine Schleife über `&[Rabatt]`. Das Rückgabe-`Option<&Rabatt>` vermeidet unnötige Kopien und hält die Ownership beim Slice.

## 28.10 Lernstrategie, Selbsteinschätzung & Merkzettel

### Merkzettel

| Aufgabe | Syntax |
|---|---|
| Enum definieren | `enum Status { Offen, Fertig }` |
| Variante erzeugen | `Status::Offen` |
| Variante mit Daten | `Status::Fehler(String::from("Timeout"))` |
| Benannte Variantendaten | `Status::Fertig { pfad: String::from("out.txt") }` |
| Methode auf Enum | `impl Status { fn text(&self) -> String { ... } }` |
| Vollständig matchen | `match wert { A => ..., B => ... }` |
| Daten binden | `Some(x) => println!("{x}")` |
| Fälle kombinieren | `A | B => ...` |
| Rest ignorieren | `_ => ...` |
| Nur einen Fall behandeln | `if let Some(x) = wert { ... }` |
| Frühes Aussteigen | `let Some(x) = wert else { return None; };` |
| Pattern prüfen | `matches!(status, Status::Fertig)` |

Kompakte Vorlage:

```rust
enum Ergebnis {
    Treffer(String),
    Leer,
}

impl Ergebnis {
    fn text(&self) -> String {
        match self {
            Ergebnis::Treffer(wert) => format!("Treffer: {wert}"),
            Ergebnis::Leer => String::from("Kein Treffer"),
        }
    }
}

fn main() {
    let ergebnis = Ergebnis::Treffer(String::from("Rust"));

    if let Ergebnis::Treffer(wert) = &ergebnis {
        println!("Kurzform: {wert}");
    }

    println!("{}", ergebnis.text());
}
```

### Feynman-Methode

Erklären Sie Enums in drei einfachen Sätzen:

1. Ein Enum beschreibt einen Typ, der genau eine von mehreren Varianten sein kann.
2. Jede Variante kann eigene Daten tragen, die nur für diesen Fall sinnvoll sind.
3. Mit `match`, `if let` und `let ... else` zerlegen Sie diese Varianten kontrolliert und typsicher.

### Gezielte Fehlerprovokation

Ändern Sie den funktionierenden Code aus Abschnitt 28.6 bewusst:

- Fügen Sie eine neue Variante `Storniert` hinzu, ohne den `match` in `beschreibung` zu erweitern.
- Schreiben Sie `BestellStatus::Bezhalt` statt `BestellStatus::Bezahlt`.
- Entfernen Sie den `None`-Arm beim Match auf `tracking_aus_status`.
- Versuchen Sie, `Option<i32>` direkt mit `i32` zu addieren.
- Ersetzen Sie `match &bestellung.gutschein_code` durch `match bestellung.gutschein_code` in einer Funktion, die nur `&Bestellung` bekommt.

Lesen Sie die Fehlermeldungen genau. Sie zeigen, ob ein Fall fehlt, eine Variante falsch geschrieben ist oder ein Wert bewegt werden würde.

### Selbsttest

Wechseln Sie erst zum nächsten Kapitel, wenn Sie:

- ein Enum mit mindestens drei Varianten selbst schreiben können;
- Varianten ohne Daten, mit Tupel-Daten und mit benannten Feldern unterscheiden können;
- `match` ohne fehlende Fälle formulieren können;
- `Option<T>` mit `Some` und `None` sicher auswerten können;
- erklären können, warum Rust keinen allgemeinen `null`-Wert braucht;
- `if let` und `let ... else` sinnvoll voneinander abgrenzen können;
- Pattern-Bindings lesen können, ohne Ownership-Fehler zu erzeugen.

## 28.11 Zusammenfassung

- Enums modellieren feste Alternativen als eigenen Typ.
- Ein Enum-Wert ist immer genau eine Variante.
- Varianten können keine Daten, Tupel-Daten oder benannte Felder enthalten.
- Methoden auf Enums werden wie bei Structs in `impl`-Blöcken definiert.
- `Option<T>` beschreibt bewusst vorhandene oder abwesende Werte.
- `Some(T)` enthält einen Wert, `None` enthält keinen Wert.
- `match` ist erschöpfend und zwingt Sie, alle Fälle zu behandeln.
- Pattern-Bindings entnehmen Daten direkt aus passenden Varianten.
- `if let` ist geeignet, wenn nur ein Pattern interessant ist.
- `let ... else` ist geeignet, wenn ein falsches Pattern früh aussteigen soll.
- `_` ist praktisch, kann aber bei fachlichen Enums wichtige Fälle verstecken.
- Enums, `Option<T>` und Pattern Matching machen ungültige Zustände schwerer darstellbar.
