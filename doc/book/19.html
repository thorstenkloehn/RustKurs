Rust-Videokurs für Anfänger

Kapitel 19: Referenzen und Borrowing (Ausleihen) im Detail

Das Ownership-System von Rust (siehe Kapitel 18) ist ein revolutionärer Ansatz zur Speicherverwaltung. Es garantiert absolute Speichersicherheit und verhindert Abstürze sowie Sicherheitslücken zur Kompilierzeit, ohne dass eine Laufzeitkomponente wie ein Garbage Collector benötigt wird. Doch so elegant das System ist, in der Praxis stößt man schnell auf Hürden, wenn man Variablen an Funktionen übergibt: Der Besitz (Ownership) wandert an die Funktion, und die ursprüngliche Variable ist danach nicht mehr nutzbar.

In diesem Kapitel betrachten wir die Lösung für dieses Problem: Referenzen (References) und das Prinzip des Ausleihens (Borrowing). Wir werden uns ansehen, wie Rust Daten sicher teilt, wie der Compiler (der sogenannte Borrow Checker) darüber wacht, und wie sich diese Mechanismen direkt auf der Ebene der Hardware (Stack und Heap) auswirken.

1. Einleitung: Was ist Ausleihen (Borrowing)?

Im echten Leben teilen wir ständig Besitztümer, ohne dass das Eigentum den Besitzer wechselt. Wenn du ein Buch besitzt und ein Freund möchte es lesen, schenkst du es ihm in der Regel nicht (das wäre eine Eigentumsübertragung oder ein “Move” in Rust). Stattdessen leihst du es ihm für eine gewisse Zeit aus.

Während dein Freund das Buch ausgeliehen hat, gelten bestimmte Regeln:

  1. Das Buch gehört weiterhin dir.
  2. Dein Freund darf das Buch lesen, aber er darf normalerweise keine Seiten herausreißen oder darin herumkribbeln (es ist eine unveränderliche Ausleihe).
  3. Wenn dein Freund fertig ist, gibt er dir das Buch zurück. Dein Besitzanspruch war nie unterbrochen, aber du konntest das Buch während der Leihfrist selbst nicht lesen.

Rust bildet genau diese Alltagserfahrung im Code ab.

Drei Analogien zur Veranschaulichung

Um die verschiedenen Arten des Ausleihens in Rust besser zu verstehen, betrachten wir drei praktische Analogien aus dem echten Leben:

Analogie A: Das Buch in der Bibliothek (Unveränderliches Ausleihen / Read-Only)

Stell dir ein seltenes Buch in einer Präsenzbibliothek vor.

  • Das Buch liegt fest auf einem Tisch im Lesesaal.
  • Die Besucher (Referenzen) dürfen an den Tisch kommen, das Buch aufschlagen und den Text lesen.
  • Es dürfen beliebig viele Besucher gleichzeitig in das Buch schauen und den Text lesen. Da niemand einen Stift hat und niemand Seiten herausreißen darf, gibt es keinen Konflikt. Alle sehen exakt denselben, unveränderlichen Text.
  • Dies entspricht in Rust der unveränderlichen Referenz (&T).

Analogie B: Der Steuerberater und die Steuererklärung (Veränderliches Ausleihen / Read-Write)

Stell dir vor, du hast ein Formular für deine Steuererklärung ausgedruckt.

  • Du gibst das Formular deinem Steuerberater, damit er Korrekturen einträgt und fehlende Zahlen ergänzt.
  • Während der Steuerberater das Formular bearbeitet, hat er das exklusive Recht, darauf zu schreiben.
  • Es darf kein anderer Steuerberater gleichzeitig auf demselben Blatt Papier schreiben, da sie sich sonst gegenseitig die Zahlen überschreiben würden.
  • Du darfst auch selbst nicht gleichzeitig darin lesen, während er schreibt, da du sonst veraltete oder halb ausgefüllte Daten sehen würdest.
  • Dies entspricht in Rust der veränderlichen Referenz (&mut T).

Analogie C: Die Bohrmaschine (Exklusiver Zugriff)

Du besitzt eine Bohrmaschine.

  • Dein Nachbar leiht sich die Bohrmaschine aus, um ein Loch in seine Wand zu bohren (veränderliche Nutzung).
  • Solange die Bohrmaschine bei deinem Nachbarn in der Wohnung ist, kannst du sie nicht benutzen, und du kannst sie auch keinem anderen Nachbarn ausleihen.
  • Erst wenn der Nachbar die Bohrmaschine zurückbringt, steht sie wieder zur freien Verfügung.

Warum das Ownership-System alleine nicht ausreicht

Wie wir in Kapitel 18 gelernt haben, führt Rust standardmäßig einen Move aus, wenn wir eine Variable, die ihre Daten auf dem Heap speichert (wie einen String), an eine andere Funktion übergeben. Das bedeutet: Das Eigentum wird vollständig übertragen.

Ohne die Möglichkeit, Daten auszuleihen, müssten wir jedes Mal, wenn wir eine Variable nur kurz untersuchen oder ausgeben wollen, diese Variable von der Funktion wieder zurückgeben lassen. Dies führt zu extrem unübersichtlichem Code, wie wir im Folgenden sehen werden.

2. Die Hardware- und Speicher-Ebene (RAM, Stack & Heap)

Bevor wir uns den Code ansehen, müssen wir verstehen, was im Arbeitsspeicher deines Computers passiert, wenn wir Referenzen nutzen. Rust ist eine Systemprogrammiersprache. Jede Zeile Code hat eine direkte Auswirkung auf den physischen Arbeitsspeicher.

Was ist eine Speicheradresse?

Der Arbeitsspeicher (RAM) kann als eine gigantische Reihe von durchnummerierten Schubladen vorgestellt werden. Jede Schublade fasst ein Byte an Daten und hat eine eindeutige Nummer: die Speicheradresse (meist im Hexadezimalformat dargestellt, z. B. 0x7ffd5f3a).

Wie sieht eine Referenz im Arbeitsspeicher aus?

Eine Referenz in Rust ist unter der Haube nichts anderes als ein Zeiger (Pointer). Ein Zeiger ist eine Variable, deren Wert eine Speicheradresse ist.

Wenn wir eine Variable let x = 5; deklarieren, reserviert das Betriebssystem einen Speicherplatz im Stack für die Zahl 5. Wenn wir nun eine Referenz let y = &x; erstellen, speichert y nicht die Zahl 5, sondern die Adresse der Schublade, in der x liegt.

Speicher-Visualisierung (Stack & Heap)

Stellen wir uns ein Programm vor, das einen String auf dem Heap anlegt und eine Referenz darauf erstellt:

#![allow(unused)]
fn main() {
let text = String::from("Rust");
let referenz = &text;
}

Im Arbeitsspeicher sieht das vereinfacht wie folgt aus:

1. Der Stack-Bereich

Der Stack ist schnell und speichert Variablen mit fester Größe.

  • Die Variable text belegt im Stack 24 Byte (auf 64-Bit-Systemen) und besteht aus:
    • Pointer (Zeiger): Zeigt auf die Adresse 0x1000 im Heap.
    • Kapazität (Capacity): 4 (Größe des reservierten Speichers).
    • Länge (Length): 4 (tatsächliche Länge des Texts “Rust”).
  • Die Variable referenz liegt ebenfalls im Stack und belegt 8 Byte (Größe einer Speicheradresse):
    • Wert: 0x7ffd5f3a (Dies ist die Speicheradresse der Variable text im Stack!).

2. Der Heap-Bereich

Der Heap speichert Daten mit dynamischer Größe.

  • An der Heap-Adresse 0x1000 liegen die eigentlichen Zeichendaten des Strings:
    • 0x1000: 'R'
    • 0x1001: 'u'
    • 0x1002: 's'
    • 0x1003: 't'

Der Unterschied: C/C++ Pointer vs. Rust Referenzen

In Sprachen wie C oder C++ können Zeiger (Pointer) auf beliebige Adressen zeigen, manipuliert werden (Pointer-Arithmetik) oder auf ungültigen Speicher verweisen (Null-Pointer oder Dangling Pointer). Dies führt häufig zu kritischen Sicherheitslücken.

In Rust sind Referenzen sichere Zeiger. Der Compiler garantiert:

  1. Eine Referenz zeigt niemals auf einen ungültigen Speicherbereich.
  2. Eine Referenz ist niemals null.
  3. Der Compiler prüft die Lebensdauer (Lifetime) der Referenz, um sicherzustellen, dass die Daten nicht gelöscht werden, solange die Referenz noch existiert.

3. Das Problem: Eigentumsübertragung (Move) und ihre Nachteile

Um zu verstehen, warum wir Referenzen brauchen, schreiben wir ein Programm ohne sie. Wir erstellen ein Rezept (einen String) und möchten es in einer Funktion anzeigen lassen und danach eine weitere Zutat hinzufügen.

Code-Beispiel 1: Umständlicher Datentransfer per Move

Hier ist der komplette, ausführbare Code, der zeigt, wie mühsam die Programmierung ohne Ausleihen is:

// Dieses Programm zeigt den umständlichen Weg OHNE Referenzen.
// Eigentum (Ownership) muss ständig hin- und hergegeben werden.

fn main() {
    // 1. Wir erstellen ein Rezept in main.
    // 'rezept' ist der Besitzer (Owner) des Strings auf dem Heap.
    let mut rezept = String::from("Teig");

    println!("1. In main: Rezept erstellt -> {:?}", rezept);

    // 2. Wir wollen das Rezept anzeigen.
    // Da wir keine Referenzen nutzen, müssen wir 'rezept' an die Funktion übergeben.
    // Dadurch findet ein MOVE statt! 'rezept' in main verliert den Besitz und wird ungültig.
    // Um das Rezept nicht zu verlieren, MUSS die Funktion es als Rückgabewert zurückgeben.
    rezept = rezept_anzeigen(rezept);

    // Nun besitzt 'rezept' in main die Daten wieder.
    println!("3. Zurück in main: Rezept wieder verfügbar -> {:?}", rezept);

    // 4. Jetzt wollen wir Mehl hinzufügen.
    // Wieder müssen wir das Eigentum übergeben und zurückerhalten.
    rezept = mehl_hinzufuegen(rezept);

    // Am Ende geben wir das fertige Rezept aus.
    println!("5. Finales Rezept in main: {:?}", rezept);
}

// Diese Funktion benötigt das volle Eigentum (Ownership) am String.
fn rezept_anzeigen(rezept_inhalt: String) -> String {
    println!("   [rezept_anzeigen] Inhalt: {}", rezept_inhalt);
    // Wir müssen das Eigentum zurückgeben, sonst stirbt der String am Ende der Funktion!
    rezept_inhalt
}

// Diese Funktion verändert den String und muss das Eigentum ebenfalls zurückgeben.
fn mehl_hinzufuegen(mut zutat: String) -> String {
    println!("   [mehl_hinzufuegen] Füge Mehl hinzu...");
    zutat.push_str(" + Mehl");
    // Rückgabe des geänderten Werts samt Ownership
    zutat
}

Schritt-für-Schritt-Ablaufverfolgung (Execution Trace)

Verfolgen wir den Weg des Eigentums im Detail:

  1. Zeile let mut rezept = String::from("Teig");
    • Ein String mit dem Inhalt "Teig" wird auf dem Heap angelegt.
    • Die Variable rezept in main ist der alleinige Eigentümer.
  2. Zeile rezept = rezept_anzeigen(rezept);
    • Das Argument rezept wird an rezept_anzeigen übergeben.
    • Move-Aktion: Das Eigentum wandert zur Argumentvariable rezept_inhalt in der Funktion rezept_anzeigen.
    • Die Variable rezept in main ist nun vorübergehend nicht initialisiert und ungültig. Würdest du versuchen, in der nächsten Zeile direkt darauf zuzugreifen, würde der Compiler mit einem Fehler abbrechen.
  3. Innerhalb von rezept_anzeigen:
    • Der Text wird per println! ausgegeben.
    • Am Ende gibt die Funktion rezept_inhalt zurück.
  4. Zurück in main (rezept = ...):
    • Der Rückgabewert der Funktion wird der Variable rezept zugewiesen.
    • rezept ist nun wieder der Eigentümer der Daten.
  5. Zeile rezept = mehl_hinzufuegen(rezept);
    • Das Eigentum wird erneut per Move an mehl_hinzufuegen abgegeben.
    • rezept in main wird wieder ungültig.
  6. Innerhalb von mehl_hinzufuegen:
    • Das Argument mut zutat übernimmt den Besitz. Durch das Schlüsselwort mut darf die Funktion den String verändern.
    • .push_str(" + Mehl") hängt den Text an.
    • Der modifizierte String wird zurückgegeben.
  7. Zurück in main:
    • rezept erhält das Eigentum zurück.

Warum das problematisch ist:

  1. Unnötiger Schreibaufwand: Wir müssen jede Funktion so deklarieren, dass sie die übergebenen Daten wieder zurückgibt (-> String).
  2. Komplexität bei mehreren Variablen: Wenn eine Funktion drei verschiedene Strings benötigt, müsste sie ein Tupel mit drei Strings zurückgeben (-> (String, String, String)), um den Besitz an alle drei Variablen zurückzugeben.
  3. Performance-Verlust: Obwohl Rust sehr effizient arbeitet, erfordert das ständige Verschieben von Ownership logischen Overhead im Programmablauf.

Wir brauchen also einen Weg, um einer Funktion Zugriff auf Daten zu geben, ohne ihr das Eigentum zu übertragen. Diesen Weg schauen wir uns im nächsten Abschnitt an.

4. Die Lösung: Borrowing (Ausleihen) mittels Referenzen (&)

Um die Probleme der Eigentumsübertragung zu lösen, bietet Rust uns die Möglichkeit, Referenzen zu erstellen. Wenn wir eine Referenz auf einen Wert übergeben, sprechen wir vom Ausleihen (Borrowing).

Eine Referenz verhält sich wie ein Zeiger: Sie zeigt auf den Speicherort des Originalwerts. Da sie aber kein Eigentümer ist, wird der Wert nicht gelöscht (deallokiert), wenn die Referenz ihren Gültigkeitsbereich (Scope) verlässt.

4.1 Unveränderliche Referenzen (&T)

Eine unveränderliche Referenz wird mit dem Symbol & erstellt. Sie erlaubt es uns, den Wert zu lesen, aber nicht zu verändern.

Code-Beispiel 2: Unveränderliches Ausleihen

// Dieses Programm zeigt, wie wir Daten unveränderlich ausleihen.

fn main() {
    let rezept = String::from("Teig");

    // Wir übergeben eine unveränderliche Referenz (&rezept) an die Funktion.
    // 'rezept' behält das Eigentum (Ownership) in main!
    rezept_anzeigen(&rezept);

    // Da main das Eigentum nie verloren hat, können wir 'rezept' hier problemlos nutzen.
    println!("In main: Rezept ist immer noch {:?}", rezept);
}

// Der Parameter-Typ ist '&String' (Referenz auf einen String), nicht 'String'.
fn rezept_anzeigen(rezept_inhalt: &String) {
    // Wir lesen den Inhalt über die Referenz.
    println!("   [rezept_anzeigen] Inhalt: {}", rezept_inhalt);
    // Am Ende der Funktion wird die Referenz gelöscht,
    // aber der String auf dem Heap bleibt am Leben!
}

Zeile-für-Zeile-Erklärung:

  1. let rezept = String::from("Teig");
    • Der String "Teig" wird auf dem Heap erstellt. rezept ist der Besitzer.
  2. rezept_anzeigen(&rezept);
    • Wir erstellen eine unveränderliche Referenz mit &rezept.
    • Diese Referenz (eine Speicheradresse) wird an die Funktion rezept_anzeigen übergeben.
  3. fn rezept_anzeigen(rezept_inhalt: &String)
    • Die Funktion nimmt den Typ &String entgegen. rezept_inhalt zeigt auf rezept im Stack von main.
  4. println!(" [rezept_anzeigen] Inhalt: {}", rezept_inhalt);
    • Rust liest den Inhalt der Heap-Adresse automatisch aus (automatisches Dereferenzieren).
  5. Am Ende der Funktion rezept_anzeigen:
    • Der Scope von rezept_anzeigen endet. Der Parameter rezept_inhalt (die Referenz) wird vom Stack gelöscht.
    • Da rezept_inhalt aber nicht der Besitzer der Daten war, bleibt der Speicher auf dem Heap unberührt.
  6. Zurück in main:
    • rezept ist weiterhin gültig und kann für den println!-Aufruf verwendet werden.

4.2 Veränderliche Referenzen (&mut T)

Wenn wir Daten nicht nur lesen, sondern auch verändern wollen, verwenden wir eine veränderliche Referenz (&mut T).

Damit wir eine veränderliche Referenz erstellen können, müssen zwei Voraussetzungen erfüllt sein:

  1. Die Originalvariable muss als veränderlich deklariert sein (let mut).
  2. Wir müssen die Referenz explizit mit &mut kennzeichnen.

Code-Beispiel 3: Veränderliches Ausleihen

// Dieses Programm zeigt, wie wir Daten veränderlich ausleihen und modifizieren.

fn main() {
    // 1. Die Variable muss 'mut' sein!
    let mut rezept = String::from("Teig");

    println!("Vor dem Hinzufügen: {}", rezept);

    // 2. Wir übergeben eine veränderliche Referenz mit '&mut'.
    zutat_hinzufuegen(&mut rezept);

    // 3. Der Originalwert wurde direkt im Heap verändert!
    println!("Nach dem Hinzufügen: {}", rezept);
}

// Der Parameter-Typ ist '&mut String' (veränderliche Referenz).
fn zutat_hinzufuegen(rezept_inhalt: &mut String) {
    // Da wir Schreibrechte haben, können wir den String modifizieren:
    rezept_inhalt.push_str(" + Mehl");
    
    // Keine Rückgabe nötig! Die Änderungen betreffen direkt das Original.
}

Zeile-für-Zeile-Erklärung:

  1. let mut rezept = String::from("Teig");
    • Wir erstellen einen veränderbaren String "Teig".
  2. zutat_hinzufuegen(&mut rezept);
    • Wir leihen rezept veränderlich aus. Dafür übergeben wir &mut rezept.
  3. fn zutat_hinzufuegen(rezept_inhalt: &mut String)
    • Die Funktion erwartet eine veränderliche Referenz &mut String.
  4. rezept_inhalt.push_str(" + Mehl");
    • Über die Speicheradresse greift die Methode .push_str direkt auf den Text im Heap zu und verändert ihn.
  5. Nach der Funktion:
    • Die veränderliche Referenz erlischt.
    • In main enthält rezept nun den modifizierten Wert "Teig + Mehl".

5. Der Borrow Checker – Rusts strenger Wächter

Die Möglichkeit, Referenzen zu erstellen, birgt eine große Gefahr, die in Sprachen wie C und C++ zu verheerenden Fehlern führt: Datenkonflikte (Data Races).

Ein Datenkonflikt tritt auf, wenn:

  1. Zwei oder mehr Zeiger gleichzeitig auf dieselbe Speicheradresse zugreifen.
  2. Mindestens einer dieser Zeiger versucht, die Daten zu verändern.
  3. Die Zugriffe nicht synchronisiert sind.

Die Bibliotheks-Metapher

Stell dir den Borrow Checker wie einen extrem strengen Bibliothekar vor.

  • Es dürfen beliebig viele Leute gleichzeitig in ein Buch schauen (unveränderliche Referenzen / Leser).
  • Sobald jedoch jemand beschließt, mit einem Tintenlöscher oder Stift Wörter im Buch zu ändern (veränderliche Referenz / Schreiber), darf niemand sonst das Buch gleichzeitig lesen oder darin schreiben. Der Bibliothekar sperrt das Buch komplett für alle anderen, bis der Schreiber fertig ist und das Buch zurückgibt.

Die zwei goldenen Regeln des Borrowings

Um Datenkonflikte zu verhindern, setzt der Rust-Compiler zwei unumstößliche Regeln zur Kompilierzeit durch:

  1. Die Lese-Regel: Du darfst beliebig viele unveränderliche Referenzen (&T) auf einen Wert zur gleichen Zeit haben.
  2. Die Schreiber-Regel: Du darfst nur eine einzige veränderliche Referenz (&mut T) auf einen Wert zur gleichen Zeit haben. Wenn du eine veränderliche Referenz hast, sind keine anderen Referenzen (weder lesend noch schreibend) erlaubt.

Important

Es gilt die Exklusiv-Regel: Entweder viele Leser ODER ein einziger Schreiber. Niemals beides gleichzeitig!

Die “Auto-Lackieren”-Analogie im Detail

Um zu verstehen, warum dieses Verbot absolut notwendig ist, schauen wir uns ein konkretes Alltagsszenario an:

Stell dir vor, du hast ein Auto.

  • Klaus leiht sich dein Auto aus. Er will damit zur Arbeit fahren. Da er das Auto nur fährt (unveränderliche Referenz), erwartet er, dass es rot bleibt.
  • Sabine leiht sich zeitgleich dein Auto aus, um es blau zu lackieren (veränderliche Referenz).
  • Wenn beide Aktionen gleichzeitig stattfinden, passiert Folgendes: Klaus fährt auf der Autobahn, während Sabine auf dem Autodach sitzt und das Auto blau pinselt. Klaus schaut in den Rückspiegel, sieht plötzlich eine andere Farbe und erschrickt. Zudem ist der Lack während der Fahrt nicht trocken, was zu einem unbrauchbaren Ergebnis führt.

Im Code würde dies bedeuten: Ein Teil deines Programms liest Daten und verarbeitet sie, während ein anderer Teil die Daten mittendrin verändert. Das Programm gerät in einen undefinierten Zustand und stürzt ab.

Code-Beispiel 4: Einen Datenkonflikt erzwingen (Fehlerhafter Code)

Schreiben wir Code, der diese Regeln verletzt, und sehen wir uns an, wie der Compiler reagiert:

// DIESER CODE LÄSST SICH NICHT KOMPILIEREN!
// Er demonstriert die Verletzung der Borrowing-Regeln.

fn main() {
    let mut auto = String::from("Rotes Auto");

    // 1. Klaus leiht das Auto unveränderlich aus (Leser)
    let blick_klaus = &auto;

    // 2. Sabine leiht das Auto zeitgleich veränderlich aus (Schreiber)
    // HIER meckert der Compiler noch nicht direkt, sondern erst, wenn wir beide gleichzeitig nutzen wollen!
    let lackierer_sabine = &mut auto; // ❌ Fehler deutet sich hier an!

    // 3. Klaus will sein Auto betrachten:
    println!("Klaus sieht: {}", blick_klaus);

    // 4. Sabine lackiert das Auto:
    lackierer_sabine.push_str(" -> Blau");
    println!("Sabine hat fertig lackiert: {}", lackierer_sabine);
}

Wenn du diesen Code mit cargo check kompilierst, erhältst du eine ausführliche Fehlermeldung:

error[E0502]: cannot borrow `auto` as mutable because it is also borrowed as immutable
  --> src/main.rs:12:28
   |
9  |     let blick_klaus = &auto;
   |                       ----- immutable borrow occurs here
12 |     let lackierer_sabine = &mut auto;
   |                            ^^^^^^^^^ mutable borrow occurs here
...
15 |     println!("Klaus sieht: {}", blick_klaus);
   |                                 ----------- immutable borrow later used here

Analyse der Fehlermeldung:

  1. immutable borrow occurs here: Zeile 9 erstellt eine Lese-Referenz.
  2. mutable borrow occurs here: Zeile 12 versucht, eine Schreib-Referenz auf dieselbe Variable zu erstellen. Dies ist verboten, da die Lese-Referenz (blick_klaus) später noch verwendet wird.
  3. immutable borrow later used here: In Zeile 15 wird blick_klaus ausgegeben. Dadurch überschneiden sich die Lebensdauern der Lese- und Schreib-Referenzen. Der Compiler greift schützend ein und verweigert den Bau.

6. Lebensdauern (Lifetimes) verstehen – Die moderne Sichtweise

Früher (in den ersten Rust-Versionen vor 2018) mass der Compiler die Gültigkeit von Referenzen stur an den geschweiften Klammern {}. Eine Referenz galt als aktiv bis zum Ende des Blocks, in dem sie deklariert wurde. Das führte oft zu Frustration, da vollkommen sicherer Code blockiert wurde.

Heute verwendet Rust ein intelligentes System namens Non-Lexical Lifetimes (NLL). Der Compiler analysiert den Code Zeile für Zeile und ermittelt den genauen Punkt, an dem eine Referenz das letzte Mal tatsächlich im Code benutzt wird. Ab diesem Moment gilt die Referenz als erloschen und blockiert die Variable nicht mehr.

6.1 🟢 Gültiger Code: Nacheinander ausleihen (Keine Koexistenz)

Im folgenden Beispiel werden Lese- und Schreibzugriffe nacheinander durchgeführt. Da die Lebenszeit des Schreibers endet, bevor der Leser erzeugt wird, ist dieser Code absolut gültig:

// Dieses Programm zeigt, dass nacheinander stattfindende Ausleihen erlaubt sind.

fn main() {
    let mut auto = String::from("Rotes Auto");

    // 1. Sabine leiht das Auto veränderlich aus (Schreiber)
    let lackierer_sabine = &mut auto;
    lackierer_sabine.push_str(" (jetzt Blau)"); // <- LETZTE Nutzung des Lackierers!
    
    // Ab hier ist 'lackierer_sabine' für den Compiler "tot".

    // 2. Klaus leiht das Auto unveränderlich aus (Leser)
    // Das ist erlaubt, da kein anderer Schreiber mehr aktiv ist!
    let blick_klaus = &auto; 
    
    println!("Klaus sieht: {}", blick_klaus); // Nutzung von blick_klaus
}

6.2 🔴 Ungültiger Code: Gleichzeitiges Ausleihen (Koexistenz = Fehler)

Wenn wir die Verwendung von lackierer_sabine nach unten verschieben, überschneiden sich die Lebensdauern der Referenzen. Klaus möchte lesen, während Sabine noch Zugriff auf das Auto hat. Das blockiert der Compiler:

// DIESER CODE LÄSST SICH NICHT KOMPILIEREN!

fn main() {
    let mut auto = String::from("Rotes Auto");

    // 1. Sabine leiht das Auto veränderlich aus.
    let lackierer_sabine = &mut auto; 

    // 2. Klaus leiht das Auto zeitgleich unveränderlich aus.
    let blick_klaus = &auto; // ❌ FEHLER: auto ist bereits veränderlich ausgeliehen!

    // 3. Hier nutzen wir den Lackierer (Lebensdauer geht bis hierhin):
    lackierer_sabine.push_str(" (jetzt Blau)");

    // 4. Und hier nutzen wir den Leser (Lebensdauern überschneiden sich):
    println!("Klaus sieht: {}", blick_klaus);
}

Zusammenfassung:

Eine Referenz blockiert den Originalwert immer von ihrer Deklaration bis zu ihrer allerletzten Verwendung im Code. Danach ist sie frei.

7. Copy vs. Move bei Referenzen

In Kapitel 6 haben wir gelernt, dass einfache Datentypen (wie Zahlen und Booleans) kopiert werden (Copy), während komplexe Datentypen auf dem Heap (wie Strings) verschoben werden (Move).

Spannenderweise gilt diese Unterscheidung auch für Referenzen! Es macht einen großen Unterschied, ob wir eine unveränderliche oder eine veränderliche Referenz zuweisen:

7.1 Unveränderliche Referenzen (&T) implementieren Copy

Da Lese-Referenzen nur Daten betrachten und niemals modifizieren, können sie beliebig oft kopiert werden. Wenn wir eine Lese-Referenz einer anderen Variablen zuweisen, entsteht ein Duplikat der Adresse. Beide Zeiger bleiben voll gültig.

// Dieses Programm zeigt, dass unveränderliche Referenzen kopierbar sind.

fn main() {
    let kaffee = String::from("Mokka");
    
    let leser1 = &kaffee; // 'leser1' zeigt auf kaffee
    let leser2 = leser1;  // KOPIE! Die Speicheradresse wird dupliziert.
    
    // Beide Lese-Referenzen sind gleichzeitig nutzbar:
    println!("leser1: {}, leser2: {}", leser1, leser2); 
}

7.2 Veränderliche Referenzen (&mut T) implementieren Copy NICHT (sie verwenden Move)

Wenn veränderliche Referenzen kopierbar wären, hätten wir im obigen Beispiel plötzlich zwei aktive Schreiber (schreiber1 und schreiber2). Das würde die goldene Regel des Borrowings verletzen.

Daher verwendet Rust bei veränderlichen Referenzen die Ownership-Verschiebung (Move). Wenn du eine veränderliche Referenz einer neuen Variable zuweist, verliert die alte Variable sofort ihre Gültigkeit!

// Dieses Programm demonstriert den Move bei veränderlichen Referenzen.

fn main() {
    let mut kaffee = String::from("Mokka");
    
    let schreiber1 = &mut kaffee; // 'schreiber1' hat das exklusive Schreibrecht.
    let schreiber2 = schreiber1;  // MOVE! Das Schreibrecht wandert komplett zu schreiber2.

    // Ab hier ist 'schreiber1' ungültig!
    
    // println!("{}", schreiber1); // 🔴 COMPILER-FEHLER: schreiber1 darf nicht mehr genutzt werden!
    println!("schreiber2 ändert den Kaffee: {}", schreiber2); // 🟢 Erlaubt.
}

Die Stift-Metapher zur Wiederholung

  • Lesen: Du hast ein Dokument. 100 Leute dürfen gleichzeitig ein Foto davon machen (Kopie der Lese-Referenz).
  • Schreiben: Es gibt nur einen einzigen Stift in der Abteilung. Wenn du den Stift auf den Tisch legst und dein Kollege ihn nimmt, hat er jetzt das exklusive Schreibrecht. Du selbst kannst nicht mehr schreiben, bis er dir den Stift wieder zurückgibt (Move der veränderlichen Referenz).

8. Was ist eine Dangling Reference (Totzeiger)?

Eine Dangling Reference (auf Deutsch oft “hängender Zeiger” oder “Totzeiger” genannt) entsteht, wenn ein Zeiger auf eine Speicheradresse verweist, deren Inhalt bereits gelöscht oder freigegeben wurde.

Die Analogie

Stell dir vor, du schreibst einem Freund deine Hausadresse auf einen Zettel. Ein paar Wochen später ziehst du um und das Haus wird vollständig abgerissen. Wenn dein Freund dich an der alten Adresse besuchen will, steht er vor einer leeren Baugrube. Die Adresse ist “dangling” – sie zeigt auf ein Nichts.

Die Gefahr in C/C++

In Sprachen wie C oder C++ ist es ein Leichtes, unbewusst eine Dangling Reference zu erzeugen. Wenn du eine Funktion verlässt, in der ein lokales Objekt auf dem Stack angelegt wurde, und eine Referenz darauf zurückgibst, stürzt dein Programm später ab oder wird gehackt, weil es versucht, auf nicht mehr existierenden Speicher zuzugreifen.

Rusts Rettung

In Rust verhindert der Compiler (Borrow Checker) solche Fehler bereits beim Kompilieren. Ein Programm mit einer Dangling Reference wird niemals fertig gebaut.

Code-Beispiel 9: Der klassische Fehler (Nicht kompilierbar)

Versuchen wir, eine Referenz auf ein Objekt zurückzugeben, das in einer Funktion erstellt wurde:

// DIESER CODE LÄSST SICH NICHT KOMPILIEREN!

fn main() {
    let adresse = erstelle_stadt(); // ❌ Sollte auf gelöschten Speicher zeigen!
}

fn erstelle_stadt() -> &String { // 🔴 FEHLER: Gibt eine Referenz auf einen String zurück
    let stadt = String::from("New York"); // 'stadt' wird in dieser Funktion erstellt (Stack & Heap)
    &stadt // ❌ Wir versuchen, die Adresse der lokalen Variable zurückzugeben
} // ⚠️ HIER STIRBT 'stadt'! Der Scope der Funktion endet, der Heap-Speicher wird gelöscht!

Wenn du versuchst, diesen Code zu kompilieren, wird der Rust-Compiler sich weigern:

error[E0515]: cannot return reference to local variable `stadt`
  --> src/main.rs:9:5
   |
9  |     &stadt
   |     ^^^^^^ returns a reference to data owned by the current function

Erklärung:

Die Funktion erstelle_stadt besitzt den String stadt. Sobald die geschlossene geschweifte Klammer } erreicht wird, endet der Gültigkeitsbereich von stadt. Rust gibt den Speicher von "New York" auf dem Heap sofort frei (Deallokation).

Wenn wir nun &stadt (die Adresse des gelöschten Speichers) an main zurückgeben würden, würde adresse in main auf ein leeres Nichts verweisen. Rust verhindert dies mit dem Fehler returns a reference to data owned by the current function.

Die Lösung: Daten übergeben (Move), nicht die Adresse

Um das Problem zu lösen, geben wir nicht die Speicheradresse zurück, sondern verschieben das gesamte Eigentum (Ownership) des Werts per Move an die aufrufende Funktion main:

Code-Beispiel 10: Die korrekte Lösung

// Dieses Programm zeigt, wie man Daten korrekt aus einer Funktion zurückgibt.

fn main() {
    // 'stadt' übernimmt das volle Eigentum der zurückgegebenen Daten in main.
    let stadt = erstelle_stadt(); 
    println!("Stadt lebt in main weiter: {}", stadt); // 🟢 Funktioniert!
}

// Der Rückgabetyp ist 'String' (nicht '&String').
fn erstelle_stadt() -> String {
    let stadt = String::from("New York");
    stadt // Wir geben den Wert selbst zurück. Ownership wandert per Move nach main!
} // 'stadt' stirbt hier nicht, da das Eigentum bereits übertragen wurde!

Die Lebenszeit-Goldregel des Borrowings

Important

Eine Referenz darf niemals länger leben als der Wert, auf den sie zeigt!

9. Besitz-Hierarchie und Referenzen in Sammlungen (Arrays & Tupel)

In Rust gilt ein wichtiges Prinzip: Eine Sammlung (wie ein Array oder ein Tupel) ist der alleinige Besitzer (Owner) aller Elemente, die in ihr gespeichert sind. Die Variable, die die Sammlung hält, besitzt somit die gesamte Hierarchie.

Das führt zu einer interessanten Frage: Was passiert, wenn wir auf ein einzelnes Element über den Index (z. B. sprachen[0]) zugreifen wollen? Das Verhalten hängt grundlegend vom Datentyp der Elemente ab.

9.1 Szenario A: Elemente mit der Copy-Eigenschaft (z. B. einfache Datentypen)

Wenn das Array einfache Datentypen wie Zahlen (i32, f64) oder Booleans (bool) enthält, ist der Zugriff unkompliziert. Da diese Typen das Copy-Trait besitzen, kopiert Rust den Wert beim Zugriff automatisch. Das Array bleibt intakt und unverändert.

Code-Beispiel 11: Indexzugriff bei einfachen Typen

fn main() {
    // Das Array besitzt die drei Booleans:
    let anmeldungen = [true, false, true];

    // Rust kopiert den Wert an Index 0 in die Variable 'erste':
    let erste = anmeldungen[0]; // Automatische KOPIE!

    // Beide Variablen sind vollkommen unabhängig nutzbar:
    println!("Kopie: {}, Original-Array: {:?}", erste, anmeldungen);
}

9.2 Szenario B: Elemente ohne Copy (z. B. Heap-Daten wie String)

Ein String liegt auf dem Heap und besitzt die Copy-Eigenschaft nicht. Wenn wir versuchen, mit let erste = sprachen[0]; direkt auf einen String im Array zuzugreifen, versucht Rust, einen Move (Besitzübertragung) durchzuführen.

Das würde bedeuten, dass das Element an Index 0 aus dem Array “herausgerissen” wird. Das Array wäre danach an dieser Stelle ungültig bzw. unvollständig. Rust verbietet dies strikt, um undefiniertes Verhalten zu vermeiden.

Code-Beispiel 12: Der Fehler beim direkten Zugriff auf Heap-Daten

// DIESER CODE LÄSST SICH NICHT KOMPILIEREN!

fn main() {
    let sprachen = [String::from("Rust"), String::from("JS")];

    // Rust versucht hier, den String aus dem Array herauszubewegen (Move):
    let erste = sprachen[0]; // ❌ COMPILER-FEHLER!
    
    println!("{}", erste);
}

Wenn du diesen Code prüfst, erhältst du den Fehler: cannot move out of type [String; 2], a non-copy array.

Die zwei Lösungen für dieses Problem

Um auf Heap-Daten in Arrays zuzugreifen, gibt es zwei Wege:

Lösung A: Klonen (.clone()) – teuer und speicherintensiv

Wir zwingen Rust dazu, eine exakte Kopie des gesamten Strings auf dem Heap zu erstellen. Das Array bleibt unberührt, aber wir verdoppeln den Speicherverbrauch für diesen String.

fn main() {
    let sprachen = [String::from("Rust"), String::from("JS")];

    // Wir erstellen eine tiefe Kopie auf dem Heap:
    let erste = sprachen[0].clone(); // 🟢 Erlaubt, aber verbraucht extra Speicher.

    println!("Klon: {}, Original: {:?}", erste, sprachen);
}

Lösung B: Ausleihen (&) – hocheffizient (Best Practice)

Statt den String zu kopieren oder zu verschieben, holen wir uns einfach nur eine unveränderliche Referenz (&) auf den String im Array. Der Besitz verbleibt vollständig beim Array.

fn main() {
    let sprachen = [String::from("Rust"), String::from("JS")];

    // Wir leihen uns nur die Leseadresse des Elements aus:
    let erste = &sprachen[0]; // 🟢 Best Practice: Nur die Adresse geliehen!

    println!("Ausgeliehen: {}, Original: {:?}", erste, sprachen);
}

Das gleiche Prinzip gilt für Tupel

Tupel verhalten sich beim Zugriff über die Punkt-Syntax (tupel.0) exakt genauso:

fn main() {
    let sprachen_tupel = (String::from("Rust"), String::from("JS"));
    
    // let erste = sprachen_tupel.0; // 🔴 FEHLER: Move aus dem Tupel verboten!
    let erste = &sprachen_tupel.0;   // 🟢 Erlaubt: Nur die Adresse geliehen.
    
    println!("Erste Sprache im Tupel: {}", erste);
}

10. Fortgeschrittene Konzepte für Anfänger

10.1 Dereferenzierung (*)

Wenn wir eine Referenz vor uns haben (z. B. &i32), zeigt diese auf einen Wert im Speicher. Wenn wir den eigentlichen Wert dahinter lesen oder überschreiben möchten, müssen wir die Referenz “verfolgen”. Diesen Vorgang nennt man Dereferenzieren.

In Rust wird dies mit dem Stern-Operator (*) durchgeführt:

fn main() {
    let mut zahl = 10;
    let referenz = &mut zahl;

    // Wir wollen den Wert hinter der Referenz um 5 erhöhen.
    // Mit *referenz greifen wir direkt auf die 10 im Speicher zu:
    *referenz += 5;

    println!("Zahl: {}", zahl); // Gibt 15 aus!
}

Automatisches Dereferenzieren in Rust

Die gute Nachricht für Anfänger: In 95% der Fälle musst du den *-Operator nicht manuell schreiben. Rust dereferenziert Referenzen automatisch bei:

  • Methodenaufrufen (z. B. text.push_str(...))
  • Makros (z. B. println!("{}", referenz))
  • Zugriffen auf Struct-Felder (z. B. punkt.x)

10.2 Referenzen auf Referenzen (&&T)

Es ist in Rust möglich, Referenzen auf Referenzen zu erstellen (z. B. &&String). Das ist so, als ob du eine Adresse auf einen Zettel schreibst, und dann die Adresse des Zettels auf einen zweiten Zettel schreibst.

Für Anfänger ist das meist verwirrend, aber dank Rusts automatischer Dereferenzierung kannst du ein &&String oft genauso benutzen wie ein einfaches &String.

10.3 Der self-Empfänger in Methoden (&self vs. &mut self vs. self)

Wenn du Methoden für ein Struct definierst (siehe Kapitel 21), musst du festlegen, wie die Methode auf das Struct zugreift. Auch hier gelten die Borrowing-Regeln:

  1. fn zeige_daten(&self): Leiht das Struct unveränderlich aus (nur lesen). Dies ist der häufigste Fall.
  2. fn aendere_daten(&mut self): Leiht das Struct veränderlich aus (lesen und schreiben).
  3. fn loesche_oder_verbrauche(self): Übernimmt das volle Eigentum (Ownership) am Struct. Danach ist das Struct in main gelöscht.

11. Die 10 häufigsten Compiler-Fehler zu Borrowing (Teil 1)

Um den Umgang mit dem Borrow Checker zu meistern, muss man lernen, seine Fehlermeldungen zu deuten. Schauen wir uns die ersten 5 der häufigsten Fehler an:

❌ Fehler 1: Veränderliches Ausleihen einer unveränderlichen Variable

Fehlerhafter Code:

fn main() {
    let name = String::from("Rust");
    let aenderung = &mut name; // ❌ Fehler!
    aenderung.push_str(" Kurs");
}

Rust-Compiler-Meldung:

error[E0596]: cannot borrow `name` as mutable, as it is not declared as mutable
  --> src/main.rs:3:21
   |
2  |     let name = String::from("Rust");
   |         ---- help: consider making this binding mutable: `mut name`
3  |     let aenderung = &mut name;
   |                     ^^^^^^^^^ cannot borrow as mutable

Erklärung:

Du kannst keine Schreib-Referenz (&mut) auf eine Variable erstellen, die selbst unveränderlich (let) deklariert wurde. Man kann nichts veränderlich ausleihen, was man selbst nicht verändern darf.

Korrigierter Code:

fn main() {
    // Wir fügen 'mut' hinzu:
    let mut name = String::from("Rust");
    let aenderung = &mut name; // 🟢 Jetzt erlaubt!
    aenderung.push_str(" Kurs");
}

❌ Fehler 2: Mehrere veränderliche Referenzen gleichzeitig (Koexistenz)

Fehlerhafter Code:

fn main() {
    let mut punkte = 100;
    
    let ref1 = &mut punkte;
    let ref2 = &mut punkte; // ❌ Fehler!
    
    *ref1 += 10;
    *ref2 += 20;
}

Rust-Compiler-Meldung:

error[E0499]: cannot borrow `punkte` as mutable more than once at a time
  --> src/main.rs:5:16
   |
4  |     let ref1 = &mut punkte;
   |                ----------- first mutable borrow occurs here
5  |     let ref2 = &mut punkte;
   |                ^^^^^^^^^^^ second mutable borrow occurs here
...
7  |     *ref1 += 10;
   |     ----------- first borrow later used here

Erklärung:

Zwei veränderliche Referenzen (ref1 und ref2) dürfen nicht gleichzeitig existieren. Da ref1 in Zeile 7 noch benutzt wird, überschneidet sich ihre Lebensdauer mit ref2 in Zeile 5.

Korrigierter Code (Nutzung trennen):

fn main() {
    let mut punkte = 100;
    
    // Die Lebensdauer von ref1 endet in Zeile 6 nach der Benutzung:
    let ref1 = &mut punkte;
    *ref1 += 10; 
    
    // Erst danach erstellen wir ref2. Keine Überschneidung!
    let ref2 = &mut punkte;
    *ref2 += 20;
}

❌ Fehler 3: Gleichzeitiges Lese- und Schreibrecht

Fehlerhafter Code:

fn main() {
    let mut score = 50;
    
    let leser = &score;
    let schreiber = &mut score; // ❌ Fehler!
    
    println!("Score: {}, Neuer Score: {}", leser, schreiber);
}

Rust-Compiler-Meldung:

error[E0502]: cannot borrow `score` as mutable because it is also borrowed as immutable
  --> src/main.rs:5:21
   |
4  |     let leser = &score;
   |                 ------ immutable borrow occurs here
5  |     let schreiber = &mut score;
   |                     ^^^^^^^^^^ mutable borrow occurs here
6  |     
7  |     println!("Score: {}, Neuer Score: {}", leser, schreiber);
   |                                            ----- immutable borrow later used here

Erklärung:

Solange eine Lese-Referenz (leser) aktiv ist, darf kein Schreibrecht (schreiber) vergeben werden. Klaus darf das Auto nicht lesen, während Sabine es lackiert.

Korrigierter Code:

fn main() {
    let mut score = 50;
    
    let leser = &score;
    println!("Score: {}", leser); // Letzte Nutzung des Lesers. Lebensdauer endet hier!
    
    let schreiber = &mut score; // 🟢 Erlaubt, da der Leser inaktiv ist.
    *schreiber += 10;
}

❌ Fehler 4: Versuch, ein Element aus einem Array herauszubewegen

Fehlerhafter Code:

fn main() {
    let namen = [String::from("Anna"), String::from("Bob")];
    let erste = namen[0]; // ❌ Fehler!
    println!("{}", erste);
}

Rust-Compiler-Meldung:

error[E0507]: cannot move out of type `[String; 2]`, a non-copy array
  --> src/main.rs:3:17
   |
3  |     let erste = namen[0];
   |                 ^^^^^^^^
   |                 |
   |                 move occurs because `namen[_]` has type `String`, which does not implement the `Copy` trait

Erklärung:

Ein String im Array besitzt keine Copy-Eigenschaft. Du darfst ihn nicht per Zuweisung herausbewegen, da das Array sonst beschädigt würde.

Korrigierter Code:

fn main() {
    let namen = [String::from("Anna"), String::from("Bob")];
    // Wir leihen den String nur aus (&):
    let erste = &namen[0]; // 🟢 Best Practice!
    println!("{}", erste);
}

❌ Fehler 5: Zurückgeben einer Referenz auf lokalen Speicher

Fehlerhafter Code:

fn main() {
    let gruss = erstelle_gruss();
}

fn erstelle_gruss() -> &String { // ❌ Fehler!
    let text = String::from("Hallo");
    &text
}

Rust-Compiler-Meldung:

error[E0515]: cannot return reference to local variable `text`
  --> src/main.rs:7:5
   |
7  |     &text
   |     ^^^^^ returns a reference to data owned by the current function

Erklärung:

Der String text wird am Ende der Funktion erstelle_gruss gelöscht. Eine zurückgegebene Referenz &text würde ins Nichts (Dangling Reference) zeigen.

Korrigierter Code:

fn main() {
    let gruss = erstelle_gruss(); // 🟢 Übernimmt das Eigentum!
    println!("{}", gruss);
}

fn erstelle_gruss() -> String { // Rückgabe des Werts
    String::from("Hallo")
}

❌ Fehler 6: Verwenden einer Variable nach einem Move (Eigentums-Konflikt)

Fehlerhafter Code:

fn main() {
    let text = String::from("Rust");
    ausgabe(text); // Ownership wandert an 'ausgabe'
    println!("In main: {}", text); // ❌ Fehler! text ist nicht mehr gültig.
}

fn ausgabe(s: String) {
    println!("{}", s);
}

Rust-Compiler-Meldung:

error[E0382]: borrow of moved value: `text`
  --> src/main.rs:4:29
   |
2  |     let text = String::from("Rust");
   |         ---- move occurs because `text` has type `String`, which does not implement the `Copy` trait
3  |     ausgabe(text);
   |             ---- value moved here
4  |     println!("In main: {}", text);
   |                             ^^^^ value borrowed here after move

Erklärung:

Die Funktion ausgabe übernimmt das Eigentum an text. Nach dem Aufruf ist die Variable text in main gelöscht und darf nicht mehr verwendet werden.

Korrigierter Code (Ausleihen statt Verschieben):

fn main() {
    let text = String::from("Rust");
    ausgabe(&text); // 🟢 Wir leihen den String nur aus!
    println!("In main: {}", text); // 🟢 Erlaubt, da main der Besitzer bleibt.
}

fn ausgabe(s: &String) { // Typ zu &String geändert
    println!("{}", s);
}

❌ Fehler 7: Element in einer Sammlung verändern, während eine Referenz darauf zeigt

Fehlerhafter Code:

fn main() {
    let mut zahlen = vec![1, 2, 3];
    let erste = &zahlen[0]; // Leser zeigt auf Index 0
    zahlen.push(4); // ❌ Fehler: Vektor wird verändert!
    println!("Erste Zahl: {}", erste);
}

Rust-Compiler-Meldung:

error[E0502]: cannot borrow `zahlen` as mutable because it is also borrowed as immutable
  --> src/main.rs:4:5
   |
3  |     let erste = &zahlen[0];
   |                  ------ immutable borrow occurs here
4  |     zahlen.push(4);
   |     ^^^^^^^^^^^^^^ mutable borrow occurs here
5  |     println!("Erste Zahl: {}", erste);
   |                                ----- immutable borrow later used here

Erklärung:

Wenn du einen Vektor oder ein Array modifizierst (z. B. durch .push()), könnte der Vektor im Arbeitsspeicher an einen anderen Ort verschoben werden, um Platz für das neue Element zu schaffen. Wenn dies geschieht, zeigt die Referenz erste plötzlich auf eine veraltete Speicheradresse (Dangling Reference). Rust verhindert dies.

Korrigierter Code:

fn main() {
    let mut zahlen = vec![1, 2, 3];
    let erste = &zahlen[0]; 
    println!("Erste Zahl: {}", erste); // Letzte Nutzung von 'erste'!
    
    zahlen.push(4); // 🟢 Erlaubt, da 'erste' danach nicht mehr benutzt wird.
}

❌ Fehler 8: Referenz überlebt die Lebensdauer der Daten (Scope-Fehler)

Fehlerhafter Code:

fn main() {
    let r;
    {
        let x = 5;
        r = &x; // ❌ Fehler!
    } // x wird hier gelöscht!
    println!("r: {}", r);
}

Rust-Compiler-Meldung:

error[E0597]: `x` does not live long enough
  --> src/main.rs:5:13
   |
4  |         let x = 5;
   |             - binding `x` declared here
5  |         r = &x;
   |             ^^ borrowed value does not live long enough
6  |     }
   |     - `x` dropped here while still borrowed
7  |     println!("r: {}", r);
   |                       - borrow later used here

Erklärung:

Die Variable x existiert nur innerhalb des inneren Blocks. Am Ende des Blocks (Zeile 6) wird sie gelöscht. Die Referenz r soll jedoch in Zeile 7 ausgegeben werden, wodurch sie auf gelöschte Daten zeigen würde.

Korrigierter Code:

fn main() {
    let r;
    let x = 5; // x im selben Scope wie r deklarieren!

📝 Aufgabe 4: Das fehlerhafte Bankkonto reparieren

Aufgabenstellung:

    let sparkonto = &kontostand;
    let abhebung = &mut kontostand;

    *abhebung -= 200.0;

    println!("Kontostand nach Abhebung: {}", abhebung);
}

Musterlösung und Erklärung:

fn main() {
    let mut kontostand = 1000.0;

    // Wir dürfen Lese- und Schreibzugriff nicht mischen!
    // Die Lösung besteht darin, die Lebenszeiten zeitlich zu trennen.
    
    // 1. Abhebung durchführen (veränderlich):
    let abhebung = &mut kontostand;
    *abhebung -= 200.0;
    // Ab hier wird 'abhebung' nicht mehr verwendet. Lebensdauer endet!

    println!("Kontostand nach Abhebung: {}", kontostand);

Erklärung: Im fehlerhaften Code überschnitten sich die Lebensdauer von sparkonto (Lese-Referenz) und abhebung (Schreib-Referenz), da beide Variablen am Ende der main-Funktion im println!-Makro genutzt wurden. 13. Zusammenfassung & Spickzettel

  • Referenzierung (&): Erstellt einen Zeiger auf eine Variable, ohne deren Eigentum (Ownership) zu beanspruchen.
  • Borrowing (Ausleihen): Das Konzept, Referenzen an Funktionen zu übergeben, damit diese mit den Daten arbeiten können, ohne sie zu löschen.
  • Unveränderliche Referenz (&T): Ermöglicht exklusiven Lesezugriff. Es darf beliebig viele Lese-Referenzen gleichzeitig geben.
  • Veränderliche Referenz (&mut T): Ermöglicht Lese- und Schreibzugriff. Es darf nur ein einziger Schreiber zur selben Zeit existieren und keine Lese-Referenzen parallel aktiv sein.
  • Borrow Checker: Der Teil des Compilers, der die Einhaltung der Borrowing-Regeln statisch prüft. Er garantiert absolute Speichersicherheit zur Kompilierzeit.
  • Lifetimes (Lebenszeiten): Rust misst die Gültigkeit von Referenzen zeilenbasiert (Non-Lexical Lifetimes). Eine Referenz blockiert den Speicher nur so lange, bis sie das letzte Mal im Code aufgerufen wird.
  • Dangling Reference: Ein gefährlicher Verweis auf bereits gelöschten Speicher. Rust verbietet dies vollständig. Wenn du Daten in einer Funktion erzeugst, musst du den Wert selbst (T) zurückgeben, niemals eine Referenz (&T).

📝 Aufgabe 5: Der Studenten-Noten-Manager

Problembeschreibung:

Ein Noten-Manager soll Studenten verwalten. Jeder Student wird durch ein Struct namens Student dargestellt, das den Namen (String) und eine Liste von Noten (Vec<u32>) enthält. Du sollst:

  2. Eine Methode note_hinzufuegen implementieren, die eine neue Note zur Liste hinzufügt. Da diese Methode das Struct verändert, soll sie das Struct veränderlich ausleihen (&mut self).
  3. In main einen Studenten anlegen, Noten hinzufügen, den Durchschnitt berechnen und am Ende den Namen des Studenten ausgeben.

Der folgende Code enthält typische Anfängerfehler bezüglich der Referenzierung von self in Struct-Methoden. Finde und behebe die Fehler.

Fehlerhafter Code:

struct Student {
    name: String,
    noten: Vec<u32>,
}

impl Student {
    // FEHLER: Übernimmt das volle Eigentum an self!
    fn durchschnitt_berechnen(self) -> f64 {
        if self.noten.is_empty() {
            return 0.0;
        }
        let summe: u32 = self.noten.iter().sum();
        summe as f64 / self.noten.len() as f64
    }

    // FEHLER: Übernimmt das volle Eigentum an self und ist nicht mut!
    fn note_hinzufuegen(self, note: u32) {
        self.noten.push(note);
    }
}

fn main() {
    let s = Student {
        name: String::from("Max Mustermann"),
        noten: vec![2, 3, 1],
    };

    s.note_hinzufuegen(2); // ❌ Fehler!
    
    let schnitt = s.durchschnitt_berechnen(); // ❌ Fehler!
    println!("Student {} hat Schnitt: {}", s.name, schnitt); // ❌ Fehler!
}

Didaktische Tipps:

  • Untersuche die Methodensignatur von durchschnitt_berechnen. Wenn du self ohne & verwendest, findet ein Move statt. Nach dem Aufruf der Methode ist das gesamte Student-Struct gelöscht.
  • Für note_hinzufuegen benötigst du Schreibrechte auf das Struct. Verwende &mut self statt self.
  • Achte darauf, dass die Variable s in main veränderbar sein muss (let mut s), wenn du Methoden aufrufst, die &mut self erwarten.

Musterlösung:

struct Student {
    name: String,
    noten: Vec<u32>,
}

impl Student {
    // 1. Wir leihen self unveränderlich aus (&self):
    fn durchschnitt_berechnen(&self) -> f64 {
        if self.noten.is_empty() {
            return 0.0;
        }
        // Wir summieren die Elemente über eine Lese-Referenz
        let summe: u32 = self.noten.iter().sum();
        summe as f64 / self.noten.len() as f64
    }

    // 2. Wir leihen self veränderlich aus (&mut self):
    fn note_hinzufuegen(&mut self, note: u32) {
        self.noten.push(note);
    }
}

fn main() {
    // 3. 's' muss mut sein, um veränderliche Methoden aufzurufen!
    let mut s = Student {
        name: String::from("Max Mustermann"),
        noten: vec![2, 3, 1],
    };

    // Rust übergibt hier automatisch '&mut s' unter der Haube:
    s.note_hinzufuegen(2);
    
    // Rust übergibt hier automatisch '&s' unter der Haube:
    let schnitt = s.durchschnitt_berechnen(); 
    
    // 's' ist weiterhin voll gültig und besitzt seinen Namen:
    println!("Student {} hat Schnitt: {:.2}", s.name, schnitt);
}

Detaillierte Code-Analyse:

  • &self in durchschnitt_berechnen: Durch das Voranstellen des kaufmännischen Unds (&) vor self weiß Rust, dass diese Methode das Objekt nur betrachten möchte. Es findet kein Move statt. Die Aufrufer in main behalten das Eigentum.
  • &mut self in note_hinzufuegen: Um Einträge in den Vektor self.noten einzufügen, benötigen wir Schreibrechte auf das Struct. Deshalb ist &mut self zwingend notwendig.
  • let mut s in main: Da note_hinzufuegen eine veränderliche Referenz benötigt, muss die Variable s selbst als veränderbar (mut) markiert sein. Andernfalls verbietet der Compiler das veränderliche Ausleihen.

Der folgende Code ist fehlerhaft, da er Slices falsch deklariert.

Fehlerhafter Code:

Didaktische Tipps:

  • Ein Slice-Typ wird als &[T] geschrieben (z. B. &[f64]). Vermeide es, Vec<T> zu verwenden, wenn die Funktion die Daten nur lesen soll – ein Slice ist viel flexibler!
  • Um einen Vektor vollständig als Slice zu übergeben, schreibt man ein einfaches & davor: &messwerte oder &messwerte[..].

    analysiere_daten(&messwerte[0..3]);

// Die Funktion erwartet einen generischen Slice '&[f64]':
fn analysiere_daten(daten: &[f64]) {

        println!("Keine Daten vorhanden.");
        return;

    let schnitt = summe / daten.len() as f64;

}

Detaillierte Code-Analyse:

  • Flexibilität von &[f64]: Eine Funktion, die einen Slice &[T] erwartet, kann sowohl mit Vektoren (Vec<T>) als auch mit normalen Arrays ([T; N]) aufgerufen werden. Das macht sie im Vergleich zu &Vec<T> deutlich vielseitiger.

        self.artikel.push(name);
        self.gesamtpreis += preis;
    }

    // FEHLER: Falsche Referenzierung von self!
    fn warenkorb_leeren(self) {
        self.artikel.clear();
        self.gesamtpreis = 0.0;
    }
}

fn main() {
    let mein_korb = Warenkorb {
        artikel: Vec::new(),
        gesamtpreis: 0.0,
    };

    mein_korb.artikel_hinzufuegen(String::from("Laptop"), 999.99); // ❌ Fehler!
    mein_korb.warenkorb_leeren(); // ❌ Fehler!
}

Didaktische Tipps:

  • Da beide Methoden den Zustand des Structs verändern, müssen sie &mut self als ersten Parameter deklarieren.
  • Die Variable mein_korb in main muss mit let mut deklariert werden, andernfalls sind keine Zustandsänderungen erlaubt.

Musterlösung:

struct Warenkorb {
    artikel: Vec<String>,
    gesamtpreis: f64,
}

impl Warenkorb {
    // 1. Wir deklarieren &mut self, da wir den Zustand ändern:
    fn artikel_hinzufuegen(&mut self, name: String, preis: f64) {
        self.artikel.push(name);
        self.gesamtpreis += preis;
        println!("Artikel '{}' ({:.2}€) hinzugefügt.", name, preis);
    }

    // 2. Auch hier ist &mut self nötig:
    fn warenkorb_leeren(&mut self) {
        self.artikel.clear();
        self.gesamtpreis = 0.0;
        println!("Der Warenkorb wurde geleert.");
    }
}

fn main() {
    // 3. 'mein_korb' muss veränderbar sein!
    let mut mein_korb = Warenkorb {
        artikel: Vec::new(),
        gesamtpreis: 0.0,
    };

    mein_korb.artikel_hinzufuegen(String::from("Laptop"), 999.99);
    mein_korb.artikel_hinzufuegen(String::from("Maus"), 49.99);
    
    println!("Zwischenstand: {} Artikel, Gesamtpreis: {:.2}€", mein_korb.artikel.len(), mein_korb.gesamtpreis);

    mein_korb.warenkorb_leeren();
}

Detaillierte Code-Analyse:

  • Partielle Ausleihe (Partial Borrowing): Wenn wir eine Methode aufrufen, die &mut self entgegennimmt, leiht Rust das gesamte Struct veränderlich aus. Während des Methodenaufrufs dürfen wir in main keine Referenzen auf einzelne Felder (z. B. let preis = &mein_korb.gesamtpreis;) parallel aktiv halten.
  • Speicher-Freigabe bei .clear(): Die Methode self.artikel.clear() entfernt alle Strings aus dem Vektor. Rust löscht dabei augenblicklich die Heap-Speicherbereiche dieser Strings aus dem RAM, da der Vektor ihr Besitzer war.

📝 Aufgabe 9: Das Navigationssystem

Problembeschreibung:

Ein Navigationssystem berechnet Entfernungen zwischen Wegpunkten. Die Wegpunkte sind in einem Vektor von Strings gespeichert. Du sollst:

  1. Eine Funktion route_anzeigen schreiben, die den Vektor von Wegpunkten unveränderlich ausleiht und die Wegpunkte nacheinander in einer Schleife ausgibt.
  2. In main einen Vektor mit Städten erstellen.
  3. Die Funktion aufrufen und danach den Vektor in main sortieren und erneut anzeigen.

Der folgende Code scheitert, da der Vektor in der Schleife irrtümlich verschoben (moved) wird.

Fehlerhafter Code:

fn main() {
    let mut route = vec![
        String::from("Berlin"),
        String::from("Hannover"),
        String::from("Dortmund"),
    ];

    route_anzeigen(route); // ❌ Vektor wird hier verschoben!

    // FEHLER: Kann den Vektor hier nicht mehr sortieren!
    route.sort(); // ❌ Fehler!
}

fn route_anzeigen(wegpunkte: Vec<String>) {
    // Die Schleife übernimmt das Eigentum an den Strings im Vektor!
    for stadt in wegpunkte { // ❌ Fehler!
        println!("Wegpunkt: {}", stadt);
    }
}

Didaktische Tipps:

  • Wenn du for stadt in wegpunkte schreibst, führt Rust einen Move durch und zieht die Strings aus dem Vektor heraus. Der Vektor ist danach leer und zerstört.
  • Um über eine Sammlung zu iterieren, ohne die Elemente zu zerstören, verwende eine Lese-Referenz in der Schleife: for stadt in &wegpunkte oder for stadt in wegpunkte.iter().
  • Die Funktion route_anzeigen sollte eine Referenz auf den Vektor (&Vec<String>) oder besser einen Slice (&[String]) erwarten.

Musterlösung:

fn main() {
    let mut route = vec![
        String::from("Berlin"),
        String::from("Hannover"),
        String::from("Dortmund"),
    ];

    // Wir übergeben eine Lese-Referenz auf den Vektor:
    route_anzeigen(&route);

    // Da route nicht verschoben wurde, können wir sie modifizieren:
    println!("Sortiere Route alphabetisch...");
    route.sort();

    // Erneuter Aufruf mit der sortierten Route:
    route_anzeigen(&route);
}

// Wir verwenden einen Slice von Strings als Parameter:
fn route_anzeigen(wegpunkte: &[String]) {
    // Wir iterieren über Lese-Referenzen (&stadt):
    for stadt in wegpunkte {
        println!("   Wegpunkt: {}", stadt);
    }
    // Alternativ: for stadt in wegpunkte.iter() { ... }
}

Detaillierte Code-Analyse:

  • Iteration über &route: Das Zeichen & vor wegpunkte in der for-Schleife sorgt dafür, dass die Variable stadt vom Typ &String ist. Wir leihen uns jeden String im Vektor also nur nacheinander aus. Nach dem Ende der Schleife ist der Vektor weiterhin voll funktionsfähig.
  • .sort() in main: Da route_anzeigen die Daten nur ausgeliehen hat, sind alle Referenzen nach dem Funktionsaufruf erloschen. Somit kann main die Methode .sort() aufrufen, welche intern eine veränderliche Referenz benötigt, um die Positionen der Strings im Speicher zu vertauschen.

📝 Aufgabe 10: Die Chat-Nachrichten-Verarbeitung

Problembeschreibung:

Ein Chat-Filter soll unzulässige Wörter in einer Nachricht durch Sternchen ersetzen. Die Nachricht wird als String übergeben. Du sollst:

  1. Eine Funktion zensieren schreiben, die eine veränderliche Referenz auf die Nachricht (&mut String) und eine Liste von verbotenen Wörtern (als Slice von Strings &[String]) entgegennimmt.
  2. Jedes Vorkommen eines verbotenen Worts in der Nachricht soll durch *** ersetzt werden. Nutze dazu die String-Methode .replace().
  3. In main soll eine Nachricht definiert und veränderlich an die Funktion übergeben werden.

Finde und korrigiere den Fehler im folgenden Code.

Fehlerhafter Code:

fn main() {
    let nachricht = String::from("Rust ist blöd und nervig!");
    let zensiert_liste = vec![String::from("blöd"), String::from("nervig")];

    // FEHLER: Nachricht ist nicht mut und wir übergeben keine Referenz!
    zensieren(nachricht, zensiert_liste); // ❌ Fehler!

    println!("Nachricht: {}", nachricht);
}

fn zensieren(mut text: String, verboten: Vec<String>) {
    // FEHLER: Wir verändern nur die lokale Kopie und nicht das Original!
    for wort in verboten {
        text = text.replace(&wort, "***");
    }
}

Didaktische Tipps:

  • Um einen String im Speicher zu überschreiben, musst du eine veränderliche Referenz &mut String übergeben.
  • Wenn du .replace() aufrufst, gibt diese Methode einen neuen String zurück. Du musst den Wert der Referenz mit dem Dereferenzierungs-Operator * überschreiben: *text = text.replace(...).
  • Die verbotenen Wörter können als Slice &[String] übergeben werden.

Musterlösung:

fn main() {
    // 1. Die Nachricht muss veränderbar (mut) sein:
    let mut nachricht = String::from("Rust ist blöd und nervig!");
    let zensiert_liste = vec![String::from("blöd"), String::from("nervig")];

    // 2. Wir übergeben die veränderliche Referenz und einen Slice:
    zensieren(&mut nachricht, &zensiert_liste);

    println!("Zensierte Nachricht: {}", nachricht);
}

fn zensieren(text: &mut String, verboten: &[String]) {
    // 3. Wir iterieren über die verbotenen Wörter:
    for wort in verboten {
        // Wir dereferenzieren 'text', um das Original im Heap zu überschreiben:
        *text = text.replace(wort, "***");
    }
}

Detaillierte Code-Analyse:

  • Der *text-Zugriff: Da text vom Typ &mut String ist, ist text selbst nur eine Adresse auf dem Stack. Durch das Voranstellen des Sterns (*text) greifen wir direkt auf das Original-String-Objekt zu und ersetzen dessen gesamten Inhalt durch das Ergebnis von .replace().
  • Einfluss auf den Heap: Jedes Mal, wenn text.replace aufgerufen wird, reserviert Rust neuen Speicher für den zensierten Text, schreibt diesen und gibt den alten Speicherbereich des vorherigen Texts frei. Der Borrow Checker stellt sicher, dass während dieses Vorgangs niemand sonst auf den String zugreifen kann.

📝 Aufgabe 11: Der Task-Scheduler

Problembeschreibung:

Ein Task-Scheduler soll Aufgaben verwalten. Jede Aufgabe (Aufgabe) hat einen Titel (String) und einen Status (erledigt: bool). Du sollst:

  1. Eine Methode abschliessen für Aufgabe schreiben, die den Status auf true setzt.
  2. Eine Funktion alle_aufgaben_zeigen schreiben, die eine Liste von Aufgaben (&Vec<Aufgabe>) unveränderlich ausleiht und diese formatiert ausgibt.
  3. In main sollen Aufgaben erstellt, eine davon als erledigt markiert und die Liste ausgegeben werden.

Der folgende Code scheitert am veränderlichen und unveränderlichen Ausleihen in Kombination mit Vektoren.

Fehlerhafter Code:

struct Aufgabe {
    titel: String,
    erledigt: bool,
}

impl Aufgabe {
    fn abschliessen(&mut self) {
        self.erledigt = true;
    }
}

fn main() {
    let mut liste = vec![
        Aufgabe { titel: String::from("Rust lernen"), erledigt: false },
        Aufgabe { titel: String::from("Einkaufen"), erledigt: false },
    ];

    // Wir erstellen eine Lese-Referenz auf die Liste
    let leser = &liste;

    // FEHLER: Wir versuchen, ein Element veränderlich auszuliehen,
    // während die Liste bereits unveränderlich ausgeliehen ist!
    let task = &mut liste[0]; // ❌ Fehler!
    task.abschliessen();

    alle_aufgaben_zeigen(leser);
}

fn alle_aufgaben_zeigen(aufgaben: &Vec<Aufgabe>) {
    for a in aufgaben {
        let status = if a.erledigt { "erledigt" } else { "offen" };
        println!("Aufgabe: {} ({})", a.titel, status);
    }
}

Didaktische Tipps:

  • Das Problem liegt in der Überschneidung der Lebensdauern. leser leiht die Liste unveränderlich aus, und danach wird task veränderlich ausgeliehen. Beide werden am Ende in alle_aufgaben_zeigen zusammengeführt.
  • Entferne den vorzeitigen leser = &liste und übergib die Liste direkt beim Funktionsaufruf mit &liste. Dadurch enden die veränderlichen Ausleihen von task, bevor die unveränderliche Ausleihe für die Anzeige beginnt.

Musterlösung:

struct Aufgabe {
    titel: String,
    erledigt: bool,
}

impl Aufgabe {
    fn abschliessen(&mut self) {
        self.erledigt = true;
    }
}

fn main() {
    let mut liste = vec![
        Aufgabe { titel: String::from("Rust lernen"), erledigt: false },
        Aufgabe { titel: String::from("Einkaufen"), erledigt: false },
    ];

    // 1. Wir führen die Änderung durch. Die Lebensdauer dieser Referenz
    // beschränkt sich auf diese beiden Zeilen:
    let task = &mut liste[0]; 
    task.abschliessen();

    // 2. Jetzt ist der Schreiber inaktiv. Wir können die Liste problemlos
    // für die Anzeige unveränderlich ausleihen:
    alle_aufgaben_zeigen(&liste);
}

fn alle_aufgaben_zeigen(aufgaben: &[Aufgabe]) { // Slice als Best Practice verwendet
    for a in aufgaben {
        let status = if a.erledigt { "[X]" } else { "[ ]" };
        println!("{} {}", status, a.titel);
    }
}

Detaillierte Code-Analyse:

  • Lebensdauer-Trennung: Der Borrow Checker erkennt, dass task (die veränderliche Referenz auf das erste Element des Vektors) nach Zeile 17 nie wieder angefasst wird. Seine Lebensdauer endet genau dort. Deshalb ist es ab Zeile 20 wieder erlaubt, die gesamte Liste unveränderlich auszuleihen und an alle_aufgaben_zeigen zu übergeben.
  • Slice-Parameter &[Aufgabe]: Wir haben den Parametertyp von &Vec<Aufgabe> auf &[Aufgabe] geändert. Das ist idiomatisch und flexibler, da wir nun auch Teilstücke der Aufgabenliste übergeben könnten (z. B. &liste[0..1]).

📝 Aufgabe 12: Die Autovermietung

Problembeschreibung:

Eine Autovermietung verwaltet Autos in einer Liste. Jedes Auto hat einen Namen (String) und einen Status, ob es vermietet ist (vermietet: bool). Du sollst:

  1. Eine Funktion auto_vermieten schreiben, die ein Auto veränderlich ausleiht und seinen Status auf true setzt. Falls es bereits vermietet ist, soll eine Fehlermeldung ausgegeben werden.
  2. In main soll eine Liste mit Autos angelegt werden. Ein Auto soll vermietet werden, während ein anderes Auto unveränderlich ausgeliehen wird, um dessen Zustand zu prüfen.

Finde den Fehler im folgenden Code.

Fehlerhafter Code:

struct Auto {
    modell: String,
    vermietet: bool,
}

fn main() {
    let mut fuhrpark = vec![
        Auto { modell: String::from("Golf"), vermietet: false },
        Auto { modell: String::from("Tesla"), vermietet: false },
    ];

    // Wir wollen das erste Auto prüfen
    let check_golf = &fuhrpark[0];

    // FEHLER: Wir versuchen, den Fuhrpark zu verändern (Tesla vermieten),
    // während check_golf noch eine Referenz auf ein Element im Fuhrpark hält!
    auto_vermieten(&mut fuhrpark[1]); // ❌ Fehler!

    println!("Modell: {}, Status: {}", check_golf.modell, check_golf.vermietet);
}

fn auto_vermieten(auto: &mut Auto) {
    if !auto.vermietet {
        auto.vermietet = true;
        println!("Auto {} erfolgreich vermietet.", auto.modell);
    } else {
        println!("Auto {} ist bereits vermietet!", auto.modell);
    }
}

Didaktische Tipps:

  • In Rust blockiert eine Referenz auf ein Element eines Vektors (wie &fuhrpark[0]) den gesamten Vektor. Der Compiler kann nicht garantieren, dass das Hinzufügen oder Ändern eines anderen Elements in dem Vektor nicht den gesamten Speicher des Vektors neu organisiert.
  • Gib die Informationen von check_golf aus, bevor du auto_vermieten aufrufst, um die Lebenszeit der Lese-Referenz abzuschließen.

Musterlösung:

struct Auto {
    modell: String,
    vermietet: bool,
}

fn main() {
    let mut fuhrpark = vec![
        Auto { modell: String::from("Golf"), vermietet: false },
        Auto { modell: String::from("Tesla"), vermietet: false },
    ];

    // 1. Wir lesen den Status des Golfs und geben ihn sofort aus:
    let check_golf = &fuhrpark[0];
    println!("Modell: {}, Status: {}", check_golf.modell, check_golf.vermietet);
    // Ab hier wird 'check_golf' nicht mehr genutzt. Lebensdauer endet!

    // 2. Jetzt ist der Fuhrpark wieder frei von Lese-Referenzen.
    // Wir können den Tesla veränderlich ausleihen:
    auto_vermieten(&mut fuhrpark[1]);
}

fn auto_vermieten(auto: &mut Auto) {
    if !auto.vermietet {
        auto.vermietet = true;
        println!("Auto {} erfolgreich vermietet.", auto.modell);
    } else {
        println!("Auto {} ist bereits vermietet!", auto.modell);
    }
}

Detaillierte Code-Analyse:

  • Vektor-Stabilität: Warum blockiert check_golf den gesamten Vektor fuhrpark? Vektoren liegen im Heap. Wenn wir ein Element verändern oder hinzufügen, muss der Vektor eventuell vergrößert werden. Dabei kopiert Rust alle Elemente an eine neue, größere Stelle im Heap. Die Referenz check_golf würde dann auf die alte, gelöschte Stelle im Heap zeigen. Um diese Katastrophe zu verhindern, blockiert jede Referenz auf ein Element des Vektors den gesamten Vektor gegen Schreibzugriffe.

📝 Aufgabe 13: Der Datei-Parser

Problembeschreibung:

Ein Parser liest Konfigurationsdateien zeilenweise ein. Eine Zeile sieht beispielsweise so aus: port=8080. Du sollst:

  1. Eine Funktion wert_extrahieren schreiben, die eine Zeile als &String und einen Schlüssel (Key) als &str entgegennimmt.
  2. Wenn die Zeile mit dem Schlüssel beginnt, soll der Wert dahinter als String-Slice (&str) zurückgegeben werden. Beginnt sie nicht damit, soll None zurückgegeben werden (Rückgabetyp: Option<&str>).
  3. In main soll eine Zeile analysiert und das Ergebnis ausgegeben werden.

Finde den Lifetime-Fehler im folgenden fehlerhaften Code.

Fehlerhafter Code:

fn main() {
    let ergebnis;
    {
        let zeile = String::from("port=8080");
        ergebnis = wert_extrahieren(&zeile, "port"); // ❌ Fehler!
    } // 'zeile' stirbt hier!

    if let Some(wert) = ergebnis {
        println!("Gefundener Wert: {}", wert);
    }
}

fn wert_extrahieren(zeile: &String, schluessel: &str) -> Option<&str> {
    if zeile.starts_with(schluessel) {
        // Wir teilen den String am '=' und nehmen den zweiten Teil
        let teile: Vec<&str> = zeile.split('=').collect();
        if teile.len() > 1 {
            return Some(teile[1]); // Gibt eine Referenz zurück, die auf 'zeile' zeigt!
        }
    }
    None
}

Didaktische Tipps:

  • Der zurückgegebene Slice &str zeigt direkt in den Speicher der Variable zeile.
  • Wenn zeile am Ende des inneren Blocks stirbt, wird der Speicher gelöscht. Der zurückgegebene Slice ergebnis wäre eine Dangling Reference.
  • Deklariere zeile im äußeren Scope, sodass sie mindestens so lange lebt wie ergebnis.

Musterlösung:

fn main() {
    // 1. Wir deklarieren 'zeile' im äußeren Scope, damit sie lang genug lebt:
    let zeile = String::from("port=8080");
    let ergebnis;

    {
        // Wir extrahieren den Wert:
        ergebnis = wert_extrahieren(&zeile, "port");
    } 

    if let Some(wert) = ergebnis {
        println!("Gefundener Wert: {}", wert);
    }
}

// Die Funktion gibt einen Slice zurück, dessen Lebensdauer an 'zeile' gebunden ist:
fn wert_extrahieren<'a>(zeile: &'a String, schluessel: &str) -> Option<&'a str> {
    if zeile.starts_with(schluessel) {
        let teile: Vec<&str> = zeile.split('=').collect();
        if teile.len() > 1 {
            return Some(teile[1]);
        }
    }
    None
}

Detaillierte Code-Analyse:

  • Lifetime Elision & Annottionen (<'a>): In der Funktion wert_extrahieren haben wir eine explizite Lifetime-Annotation 'a hinzugefügt. Sie signalisiert dem Compiler: “Der zurückgegebene Slice &str lebt exakt so lange wie der übergebene String zeile”. Da zeile in main bis zum Ende lebt, weiß der Compiler, dass der Zugriff auf ergebnis absolut sicher ist.

📝 Aufgabe 14: Die Playlist-Verwaltung

Problembeschreibung:

Eine Musik-Playlist verwaltet Songs. Jeder Song hat einen Titel (String). Die Playlist besitzt eine Liste von Songs (Vec<Song>). Du sollst:

  1. Eine Methode song_hinzufuegen erstellen, die das Eigentum an einem Song übernimmt und ihn zur Playlist hinzufügt.
  2. Eine Funktion aktuelle_songs_ausgeben erstellen, die die Playlist unveränderlich ausleiht und alle Titel ausgibt.
  3. In main soll eine Playlist erstellt und Songs hinzugefügt werden.

Der folgende Code enthält Fehler bei der Übergabe von Songs.

Fehlerhafter Code:

struct Song {
    titel: String,
}

struct Playlist {
    songs: Vec<Song>,
}

impl Playlist {
    // FEHLER: Falsche Parametertypen für das Hinzufügen!
    fn song_hinzufuegen(&mut self, song: &Song) {
        // FEHLER: Kann einen ausgeliehenen Song nicht in den Vektor verschieben!
        self.songs.push(song); // ❌ Fehler!
    }
}

fn main() {
    let mut liste = Playlist { songs: Vec::new() };
    let mein_song = Song { titel: String::from("Yesterday") };

    liste.song_hinzufuegen(&mein_song);
    
    // Wir wollen den Song in main weiter benutzen:
    println!("Mein Lieblingssong: {}", mein_song.titel);
}

Didaktische Tipps:

  • Wenn der Vektor self.songs den Song besitzen soll, muss die Funktion das Eigentum (Song) übernehmen, nicht eine Referenz (&Song).
  • Wenn die Funktion das Eigentum übernimmt (fn song_hinzufuegen(&mut self, song: Song)), findet in main ein Move statt. Danach darf mein_song in main nicht mehr verwendet werden.
  • Falls du den Song in main danach noch brauchst, musst du ihn entweder klonen (mein_song.clone()) oder die Programmstruktur anpassen.

Musterlösung:

#[derive(Clone)] // Wir erlauben das Klonen des Songs
struct Song {
    titel: String,
}

struct Playlist {
    songs: Vec<Song>,
}

impl Playlist {
    // Die Methode übernimmt das volle Eigentum (Ownership) am Song:
    fn song_hinzufuegen(&mut self, song: Song) {
        self.songs.push(song);
    }
}

fn main() {
    let mut liste = Playlist { songs: Vec::new() };
    let mein_song = Song { titel: String::from("Yesterday") };

    // Wir übergeben eine Kopie des Songs (Klon), damit das Original in main überlebt:
    liste.song_hinzufuegen(mein_song.clone());
    
    // Das Original lebt in main weiter:
    println!("Mein Lieblingssong in main: {}", mein_song.titel);
    
    // Wir geben die Playlist aus:
    aktuelle_songs_ausgeben(&liste);
}

fn aktuelle_songs_ausgeben(playlist: &Playlist) {
    for song in &playlist.songs {
        println!("   Wiedergabe: {}", song.titel);
    }
}

Detaillierte Code-Analyse:

  • #[derive(Clone)]: Durch dieses Makro generiert Rust automatisch Code, mit dem wir .clone() auf einem Song aufrufen können. Dies erstellt eine tiefe Kopie des Strings auf dem Heap.
  • Wahl zwischen Move und Clone: Wenn wir mein_song nach dem Hinzufügen zur Playlist nicht mehr in main gebraucht hätten, wäre ein einfacher Transfer ohne .clone() die effizientere Wahl gewesen. Da wir das Objekt aber in beiden Scopes (in der Playlist und in main) benötigen, ist das Klonen hier der korrekte Weg.

16. Die 10 häufigsten Compiler-Fehler zu Borrowing (Teil 2)

Fahren wir mit den verbleibenden 5 häufigen Compiler-Fehlern fort:

❌ Fehler 11: Veränderlicher Zugriff auf ein Element eines Vektors, während der Vektor unveränderlich ausgeliehen ist

Fehlerhafter Code:

fn main() {
    let mut list = vec![1, 2, 3];
    for x in &list { // Unveränderliche Ausleihe beginnt hier
        list.push(*x); // ❌ FEHLER: Schreibzugriff verboten!
    }
}

Rust-Compiler-Meldung:

error[E0502]: cannot borrow `list` as mutable because it is also borrowed as immutable
  --> src/main.rs:4:9
   |
3  |     for x in &list {
   |              -----
   |              |
   |              immutable borrow occurs here
   |              immutable borrow later used here
4  |         list.push(*x);
   |         ^^^^^^^^^^^^^ mutable borrow occurs here

Erklärung:

Während du in einer Schleife über einen Vektor iterierst (unveränderlich liest), darfst du den Vektor nicht verändern (z. B. Elemente hinzufügen). Dies würde die internen Zeiger der Schleife ungültig machen.

Korrigierter Code (Daten vorher kopieren):

fn main() {
    let mut list = vec![1, 2, 3];
    // Wir klonen die Liste, um über die Kopie zu iterieren:
    let temp_list = list.clone();
    for x in &temp_list {
        list.push(*x); // 🟢 Erlaubt!
    }
}

Fehlerhafter Code:

    x: i32,
    y: i32,
}

    p.x = 10; // ❌ FEHLER!

}

Rust-Compiler-Meldung:

error[E0506]: cannot assign to `p.x` because it is borrowed
  --> src/main.rs:9:5
   |
8  |     let ref_p = &p;
   |                 -- borrow of `p` occurs here

   |     ^^^^^^^^ assignment to borrowed `p.x` occurs here

   |                               ------- borrow later used here

Erklärung:

Da ref_p das gesamte Struct p unveränderlich ausleiht, sind während der Lebensdauer dieser Referenz keine Schreiboperationen auf Feldern des Structs erlaubt.

}

❌ Fehler 18: Struct-Methodenaufruf mit sich überschneidenden veränderlichen Ausleihen

Fehlerhafter Code:

struct Rechner {
    wert: i32,
}

impl Rechner {
    fn addieren(&mut self, anderer: &Rechner) {
        self.wert += anderer.wert;
    }
}

fn main() {
    let mut r = Rechner { wert: 10 };
    r.addieren(&r); // ❌ FEHLER!
}

Rust-Compiler-Meldung:

error[E0502]: cannot borrow `r` as immutable because it is also borrowed as mutable
  --> src/main.rs:13:16
   |
13 |     r.addieren(&r);
   |     -          ^^ immutable borrow occurs here
   |     |
   |     mutable borrow occurs here (via `r.addieren`)

Erklärung:

Der Aufruf r.addieren(&r) versucht, r gleichzeitig veränderlich (als &mut self für den Methodenaufruf) und unveränderlich (als Argument anderer: &Rechner) auszuleihen. Dies ist eine direkte Verletzung der Borrowing-Regeln.

Korrigierter Code:

fn main() {
    let mut r = Rechner { wert: 10 };
    // Wir speichern den Wert vorher in einer temporären Variable:
    let temp_wert = r.wert;
    
    // Nun leihen wir r nur einmal veränderlich aus:
    r.wert += temp_wert; // 🟢 Erlaubt!
}

❌ Fehler 19: Referenz auf einen temporären Wert erstellen (Temporary Value Dropped)

Fehlerhafter Code:

fn main() {
    // String::from erzeugt einen temporären Wert. 
    // Wir versuchen, eine Referenz darauf zu speichern, ohne den Besitzer zu sichern.
    let ref_text = &String::from("Temporär"); // ❌ FEHLER!
    println!("{}", ref_text);
}

Rust-Compiler-Meldung:

error[E0716]: temporary value dropped while still borrowed
  --> src/main.rs:4:21
   |
4  |     let ref_text = &String::from("Temporär");
   |                     ^^^^^^^^^^^^^^^^^^^^^^^^ - temporary value is freed at the end of this statement
   |                     |
   |                     creates a temporary value which is freed while still in use
5  |     println!("{}", ref_text);
   |                    -------- borrow later used here

Erklärung:

Der Aufruf String::from("Temporär") erstellt ein temporäres String-Objekt auf dem Heap. Da dieses Objekt keiner Variable zugewiesen wird, besitzt niemand den String. Er wird am Ende der Zeile 4 sofort gelöscht. Die Referenz ref_text würde somit in Zeile 5 ins Leere zeigen.

Korrigierter Code:

fn main() {
    // Wir deklarieren zuerst die Variable, die den String besitzt:
    let text = String::from("Temporär");
    let ref_text = &text; // 🟢 Gültig, da 'text' den String am Leben hält!
    println!("{}", ref_text);
}

❌ Fehler 20: Laufzeit-Borrow-Fehler bei RefCell (Interior Mutability)

Fehlerhafter Code:

use std::cell::RefCell;

fn main() {
    // RefCell verschiebt die Borrowing-Prüfung von der Kompilierzeit zur Laufzeit.
    let daten = RefCell::new(String::from("Daten"));

    let leser = daten.borrow(); // Unveränderlich ausleihen
    let mut schreiber = daten.borrow_mut(); // ❌ Fehler tritt zur LAUFZEIT auf!

    println!("{}, {}", leser, schreiber);
}

Rust-Laufzeit-Fehlermeldung (Panic):

thread 'main' panicked at src/main.rs:8:31:
already borrowed: BorrowMutError
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace

Erklärung:

RefCell erlaubt es uns, die Borrowing-Regeln zur Kompilierzeit zu umgehen. Doch die Regeln gelten weiterhin! Wenn du zur Laufzeit gleichzeitig versuchst, .borrow() (Lesen) und .borrow_mut() (Schreiben) aufzurufen, stürzt das Programm mit einem kontrollierten Abbruch (Panic) ab.

Korrigierter Code:

use std::cell::RefCell;

fn main() {
    let daten = RefCell::new(String::from("Daten"));

    {
        let leser = daten.borrow();
        println!("Leser: {}", leser);
    } // Lese-Referenz 'leser' erlischt am Blockende!

    // Nun ist das veränderliche Ausleihen erlaubt:
    let mut schreiber = daten.borrow_mut();
    schreiber.push_str(" geändert");
    println!("Schreiber: {}", schreiber);
}

18. Der Refactoring-Leitfaden: Von Clone zu Borrow

Anfänger neigen oft dazu, den Borrow Checker zu umgehen, indem sie überall .clone() aufrufen oder Daten unstrukturiert kopieren. Das führt zu unperformantem und unprofessionellem Code.

In diesem Abschnitt zeigen wir dir 5 typische Anti-Patterns (schlechte Entwürfe) und wie man sie in elegantes Borrowing umschreibt.

🛠️ Refactoring 1: Die Klon-Orgie (Unnötiges Kopieren)

Schlechtes Anti-Pattern:

Überall dort, wo eine Funktion Daten lesen möchte, wird .clone() aufgerufen, um dem Compiler aus dem Weg zu gehen.

struct Benutzer {
    username: String,
    email: String,
}

fn main() {
    let user = Benutzer {
        username: String::from("rust_dev"),
        email: String::from("dev@rust.org"),
    };

    // Wir klonen das gesamte Objekt nur, um Daten anzuzeigen!
    profil_anzeigen(user.clone()); 
    newsletter_senden(user.clone());

    println!("User {} ist weiterhin aktiv.", user.username);
}

fn profil_anzeigen(u: Benutzer) {
    println!("Profil: {} ({})", u.username, u.email);
}

fn newsletter_senden(u: Benutzer) {
    println!("Sende Newsletter an: {}", u.email);
}

Problem: Der Heap-Speicher für die Strings wird bei jedem Aufruf dupliziert. Das bremst das Programm unnötig aus.

Gutes Refactoring (mit Referenzen):

struct Benutzer {
    username: String,
    email: String,
}

fn main() {
    let user = Benutzer {
        username: String::from("rust_dev"),
        email: String::from("dev@rust.org"),
    };

    // Wir übergeben nur Lese-Referenzen (&):
    profil_anzeigen(&user); 
    newsletter_senden(&user);

    println!("User {} ist weiterhin aktiv.", user.username);
}

// Funktionen nehmen Lese-Referenzen entgegen:
fn profil_anzeigen(u: &Benutzer) {
    println!("Profil: {} ({})", u.username, u.email);
}

fn newsletter_senden(u: &Benutzer) {
    println!("Sende Newsletter an: {}", u.email);
}

Vorteil: Keine Heap-Allokationen, kein Klonen nötig. Das Programm läuft blitzschnell und speicherschonend.

🛠️ Refactoring 2: Die Tupel-Rückgabe-Hölle (Ownership-Schubsen)

Schlechtes Anti-Pattern:

Weil wir den Besitz nicht verlieren wollen, lassen wir jede Funktion die übergebenen Werte mühsam in einem Tupel zurückgeben.

fn main() {
    let mut text = String::from("Hallo");
    
    // Eigentum wandert hin und her
    let (neuer_text, laenge) = analysieren(text);
    text = neuer_text;
    
    println!("Text: {}, Länge: {}", text, laenge);
}

fn analysieren(s: String) -> (String, usize) {
    let l = s.len();
    (s, l) // Mühsame Rückgabe der Daten samt Länge
}

Gutes Refactoring (mit Referenzen):

fn main() {
    let text = String::from("Hallo");
    
    // Wir leihen den Text nur aus. Kein Ownership-Transfer!
    let laenge = analysieren(&text);
    
    println!("Text: {}, Länge: {}", text, laenge);
}

fn analysieren(s: &String) -> usize {
    s.len() // Nur die Länge zurückgeben
}

🛠️ Refactoring 3: Der Vektor-Neubau (Daten kopieren statt Slices nutzen)

Schlechtes Anti-Pattern:

Wenn wir nur einen Teil einer Liste verarbeiten wollen, kopieren wir diesen Teil in einen neuen Vektor.

fn main() {
    let daten = vec![1, 2, 3, 4, 5];
    
    // Wir wollen nur die ersten 3 Elemente verarbeiten.
    // Dazu erstellen wir einen komplett neuen Vektor!
    let mut teil_daten = Vec::new();
    for i in 0..3 {
        teil_daten.push(daten[i]);
    }
    
    summe_berechnen(teil_daten);
}

fn summe_berechnen(liste: Vec<i32>) {
    let summe: i32 = liste.iter().sum();
    println!("Summe: {}", summe);
}

Gutes Refactoring (mit Slices):

fn main() {
    let daten = vec![1, 2, 3, 4, 5];
    
    // Wir übergeben einfach einen Slice (&[T]) des Vektors.
    // Keine Kopien im Speicher!
    summe_berechnen(&daten[0..3]);
}

fn summe_berechnen(liste: &[i32]) { // Parameter zu Slice geändert
    let summe: i32 = liste.iter().sum();
    println!("Summe: {}", summe);
}

🛠️ Refactoring 4: Klonen von Structs in Schleifen

Schlechtes Anti-Pattern:

Wir kopieren Objekte innerhalb einer Schleife, um Besitzkonflikte mit dem Schleifenkörper zu vermeiden.

struct Config {
    ip: String,
}

fn main() {
    let config = Config { ip: String::from("127.0.0.1") };
    
    for i in 0..5 {
        // Wir klonen das Struct bei jedem Schleifendurchlauf!
        verbindung_aufbauen(config.clone(), i);
    }
}

fn verbindung_aufbauen(c: Config, index: i32) {
    println!("Verbinde mit {} (Versuch {})...", c.ip, index);
}

Gutes Refactoring (mit Referenzen):

struct Config {
    ip: String,
}

fn main() {
    let config = Config { ip: String::from("127.0.0.1") };
    
    for i in 0..5 {
        // Wir übergeben nur eine Referenz auf die Config:
        verbindung_aufbauen(&config, i);
    }
}

fn verbindung_aufbauen(c: &Config, index: i32) {
    println!("Verbinde mit {} (Versuch {})...", c.ip, index);
}

🛠️ Refactoring 5: Zeichenketten-Klonen beim Splitten

Schlechtes Anti-Pattern:

Wenn wir aus einem Text Teilstrings gewinnen wollen, wandeln wir jeden Slice mühsam mit .to_string() in ein neues Heap-Objekt um.

fn main() {
    let text = String::from("Rust,Java,Python");
    let mut sprachen = Vec::new();

    for sprache in text.split(',') {
        // Unnötige Konvertierung in einen neuen String auf dem Heap:
        sprachen.push(sprache.to_string());
    }

    println!("Sprachen: {:?}", sprachen);
}

Gutes Refactoring (mit Slices):

fn main() {
    let text = String::from("Rust,Java,Python");
    let mut sprachen: Vec<&str> = Vec::new(); // Vektor speichert Slices!

    for sprache in text.split(',') {
        // Wir speichern nur die Referenzen auf die Textbereiche:
        sprachen.push(sprache); // 🟢 Hocheffizient!
    }

    println!("Sprachen: {:?}", sprachen);
}

19. Ausführlicher Spickzettel & Cheat Sheet

Nutze diese Zusammenfassung als schnelles Nachschlagewerk im Programmieralltag:

1. Grundregeln auf einen Blick

  • &x $ ightarrow$ Unveränderliche Ausleihe (Lesen). Beliebig viele zur gleichen Zeit erlaubt.
  • &mut x $ ightarrow$ Veränderliche Ausleihe (Schreiben). Maximal eine zur gleichen Zeit erlaubt, und keine Leser parallel.
  • Dereferenzierung (*r) $ ightarrow$ Folgt dem Zeiger und greift auf den eigentlichen Wert im Speicher zu.
  • Slices (&[T]) $ ightarrow$ Eine unveränderliche Referenz auf ein zusammenhängendes Teilstück einer Sammlung.

2. Typische Borrow-Checker-Fehlermeldungen deuten

  • cannot borrow as mutable, as it is not declared as mutable $ ightarrow$ Lösung: Füge ein mut bei der Deklaration der Originalvariable hinzu.
  • cannot borrow x as mutable more than once at a time $ ightarrow$ Lösung: Verringere die Lebenszeit der ersten veränderlichen Referenz oder trenne die Aufrufe zeitlich.
  • cannot borrow x as mutable because it is also borrowed as immutable $ ightarrow$ Lösung: Stelle sicher, dass alle Lese-Referenzen beendet sind, bevor du die veränderliche Referenz erstellst.
  • cannot return reference to local variable $ ightarrow$ Lösung: Gib den Wert direkt zurück (T statt &T) oder sorge dafür, dass der Besitzer außerhalb der Funktion deklariert wurde.
  • cannot move out of index $ ightarrow$ Lösung: Greife auf das Element im Array mit einem kaufmännischen Und (&) zu, statt es direkt zuzuweisen.

3. Merkhilfen zur Hardware

  • Eine Referenz belegt auf einem 64-Bit-System immer exakt 8 Byte im Stack, da sie lediglich eine Speicheradresse speichert.
  • Durch die Übergabe von Referenzen an Funktionen wird verhindert, dass große Heap-Datenmengen dupliziert werden müssen. Dies macht Rust-Programme standardmäßig extrem performant.

20. Häufig gestellte Fragen (FAQ) von Rust-Anfängern

Der Einstieg in das Referenz- und Borrowing-System von Rust ist eine der größten mentalen Umstellungen in der modernen Programmierung. Hier sind die Antworten auf die fünf am häufigsten gestellten Fragen von Einsteigern:

❓ Frage 1: Was ist der Unterschied zwischen &String und &str? Wann sollte ich was verwenden?

Detaillierte Antwort:

  • &String ist eine Referenz auf ein String-Objekt, das auf dem Stack liegt und auf Heap-Daten zeigt. Es ist ein veränderbarer, dynamischer Texttyp.
  • &str (String-Slice) ist eine Referenz auf ein Teilstück einer Zeichenkette. Es speichert lediglich einen Zeiger auf den Anfang des Texts und eine Länge. &str kann auf Heap-Daten zeigen, aber auch auf statische Textliterale (z. B. "Hallo"), die direkt im Binärcode der Anwendung eingebrannt sind.

Faustregel für die Praxis:

Verwende in Funktionsparametern immer &str statt &String.

  • Grund: Ein &str ist viel flexibler. Wenn eine Funktion &str erwartet, kannst du ihr ein normales String-Literal ("Hallo"), einen Ausschnitt eines Strings (&mein_string[0..3]) oder auch ein vollständiges &String übergeben (da Rust ein &String bei Bedarf automatisch in ein &str umwandelt). Erwartet die Funktion hingegen ein &String, kannst du ihr auch nur exakt diesen Typ übergeben.

Schlechte Praxis:

#![allow(unused)]
fn main() {
fn gruss_ausgeben(name: &String) {
    println!("Hallo, {}!", name);
}
}

Gute Praxis:

#![allow(unused)]
fn main() {
fn gruss_ausgeben(name: &str) { // Viel flexibler!
    println!("Hallo, {}!", name);
}
}

❓ Frage 2: Kann ich den Borrow Checker umgehen, wenn er mich zu sehr nervt?

Detaillierte Antwort:

Ja, es gibt Wege, den Borrow Checker zu umgehen, aber sie sind für produktiven Code in den meisten Fällen eine schlechte Idee:

  1. Verwendung von .clone(): Wenn du Objekte kopierst, statt sie auszuleihen, hat jede Variable ihre eigenen Daten. Der Borrow Checker meckert nicht mehr. Allerdings verdoppelt oder vervielfacht dies den Speicherverbrauch und die Rechenzeit.
  2. Interior Mutability mit RefCell oder Mutex: Diese Typen verlagern die Prüfung der Borrowing-Regeln von der Kompilierzeit zur Laufzeit. Das Programm kompiliert zwar, stürzt dann aber zur Laufzeit ab (Panics), falls du die Regeln verletzt.
  3. Der unsafe-Block: In einem unsafe-Block kannst du rohe Pointer (*const T und *mut T) wie in C/C++ deklarieren. Der Compiler prüft hier nichts mehr.

Warning

Benutze unsafe niemals, nur um den Compiler zu beruhigen! Wenn du Fehler in einem unsafe-Block machst, riskierst du Memory Leaks, Speicherüberschreibungen und schwer auffindbare Sicherheitslücken. Nutze stattdessen das Typsystem und lerne, mit dem Borrow Checker zusammenzuarbeiten.

❓ Frage 3: Warum kann ich keine Referenz auf ein neu erzeugtes Element in einer Funktion zurückgeben?

Detaillierte Antwort:

Weil der Speicherbereich des Elements gelöscht wird, sobald die Funktion zu Ende ist.

Stell dir vor, eine Funktion baut einen Tisch (Objekt auf dem Heap) und gibt dir einen Zettel mit der Adresse des Tischs (Referenz). Sobald die Arbeiter die Werkstatt verlassen (die Funktion endet), reißen sie den Tisch jedoch sofort wieder ab. Der Zettel mit der Adresse ist nutzlos.

Wenn du Daten in einer Funktion erzeugst und sie in main weiterverwenden willst, musst du den Tisch selbst (das Objekt, also String, Vec oder das Struct) zurückgeben. Rust verschiebt den Speicherbesitz hocheffizient (Move), ohne die Daten im RAM physisch kopieren zu müssen.

❓ Frage 4: Was bedeutet “Lifetime Elision” (Lebenszeit-Auslassung) genau?

Detaillierte Antwort:

In den ersten Versionen von Rust musste man bei fast jeder Funktion, die Referenzen entgegennahm oder zurückgab, explizit angeben, wie lange die Referenzen leben (z. B. fn test<'a>(x: &'a i32)).

Da das Schreiben dieser Annotationen sehr mühsam war, hat das Rust-Team Muster analysiert und die Lifetime Elision Rules in den Compiler eingebaut. Der Compiler wendet heute drei feste Regeln an, um die Lebenszeiten automatisch zu erraten:

  1. Jeder Parameter, der eine Referenz ist, erhält eine eigene Lebenszeit.
  2. Wenn es genau einen Eingabe-Referenz-Parameter gibt, wird dessen Lebenszeit automatisch auf alle Ausgabe-Referenzen übertragen.
  3. Wenn es sich um eine Methode handelt (die &self oder &mut self empfängt), wird die Lebenszeit von self auf alle Ausgabewerte übertragen.

Nur wenn diese Regeln nicht ausreichen (z. B. wenn eine Funktion zwei verschiedene Referenzen entgegennimmt und eine davon zurückgibt), musst du dem Compiler mit Lifetime-Annotationen (<'a>) helfen.

❓ Frage 5: Kann ein Struct selbst eine Referenz als Feld besitzen?

Detaillierte Antwort:

Ja, ein Struct kann Referenzen auf Daten speichern, die einem anderen Teil des Programms gehören. In diesem Fall musst du dem Compiler jedoch mitteilen, dass das Struct nicht länger leben darf als die Daten, auf die es zeigt. Dazu nutzt man Lifetime-Annotationen am Struct:

// Das Struct 'Leser' hält eine Referenz auf einen String.
// Das '<'a>' deklariert die Lebenszeit, die an das Feld 'text' gebunden ist.
struct Leser<'a> {
    text: &'a String,
}

fn main() {
    let original = String::from("Original-Daten");
    
    let mein_leser = Leser {
        text: &original, // Wir leihen die Daten aus
    };

    println!("Leser liest: {}", mein_leser.text);
}

Wenn original vor mein_leser gelöscht werden würde, würde der Compiler dies sofort als Fehler melden, da das Struct sonst eine Dangling Reference enthalten würde.

21. Fazit und Ausblick

Herzlichen Glückwunsch! Du hast eines der anspruchsvollsten und zugleich mächtigsten Konzepte von Rust gemeistert. Das Zusammenspiel aus Ownership, Referenzen und dem Borrow Checker ist das Fundament, auf dem die gesamte Sicherheit und Performance von Rust ruht.

Was du in diesem Kapitel gelernt hast:

  1. Ausleihen (Borrowing) spart Zeit und Speicher, indem wir Adressen statt Werten übergeben.
  2. Die goldenen Regeln: Beliebig viele Leser (&) ODER genau ein Schreiber (&mut), niemals beides gleichzeitig.
  3. Datenkonflikte (Data Races) werden durch diese Regeln zur Kompilierzeit unmöglich gemacht.
  4. Lebensdauern (Lifetimes) bestimmen zeilenbasiert, wie lange eine Ausleihe im Speicher aktiv bleibt.
  5. Dangling References werden durch den Compiler unmöglich gemacht.
