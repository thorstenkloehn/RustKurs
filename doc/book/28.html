Kapitel 28: Enums und Pattern Matching

Enums (Aufzählungstypen) und Pattern Matching (Musterabgleich) bilden ein zentrales Fundament der Typsicherheit und Kontrollflusssteuerung in Rust. Während Structs mehrere Werte zu einer logischen Einheit kombinieren (Produkttypen), erlauben es Enums, exklusive Alternativen typsicher auszudrücken (Summentypen). Zusammen mit dem mächtigen Pattern Matching stellt Rust sicher, dass alle fachlichen Fälle lückenlos behandelt werden und ungültige Zustände zur Kompilierzeit unmöglich darstellbar sind.

Dieses Kapitel bietet eine allumfassende, lückenlose Referenz über alle Facetten von Rust-Enums – von den syntaktischen Grundlagen für Anfänger über fortgeschrittene Speicherverwaltungs- und Nischenoptimierungstechniken bis hin zu systemnahen Details wie Thread-Sicherheit, CPU-Performance und einer exhaustiven API-Referenz des wichtigsten Enums der Standardbibliothek: Option<T>.

Die didaktischen und strukturellen Vorgaben für dieses Kapitel wurden gemäß den Richtlinien in markdown.md und AGENTS.md umgesetzt.

2. Die Definition

Ein Enum (kurz für Enumeration) ist ein selbst definierter Datentyp, der eine feste Menge exklusiver Zustände oder Alternativen – die sogenannten Varianten – beschreibt. Ein konkreter Wert des Enums repräsentiert zu jedem Zeitpunkt exakt eine dieser Varianten. Varianten können optional eigene Daten tragen (Tupel-Daten oder benannte Felder).

Ein Pattern (Muster) ist eine syntaktische Struktur, die mit der Form eines Werts verglichen wird. Pattern Matching ist der Mechanismus, mit dem Rust prüft, ob ein Wert einem bestimmten Pattern entspricht, und im Erfolgsfall die darin enthaltenen Daten extrahiert (bindet) und einen dedizierten Codezweig ausführt.

Alltagsnahe Analogien

[!NOTE] Die Ampel-Metapher (Einfaches Enum): Eine Straßenampel ist ein perfektes Enum. Sie kann rot, gelb oder grün leuchten. Sie kann niemals rot und grün gleichzeitig sein, und es gibt keinen Zustand dazwischen. Jede Farbe signalisiert dem Fahrer eine klare, exklusive Verhaltensregel. Im Code entspricht dies einem Enum ohne zusätzliche Nutzdaten.

[!TIP] Die Postfach-Metapher (Option-Enum): Stellen Sie sich ein physisches Postfach vor. Wenn Sie hineinsehen, gibt es genau zwei exklusive Möglichkeiten: Entweder das Fach ist vollkommen leer (None) oder es befindet sich ein konkreter Brief darin (Some(Brief)). Sie können den Brief erst lesen (auspacken), wenn Sie das Postfach geöffnet und den Brief entnommen haben. Das ist das Prinzip von Option<T> in Rust.

[!IMPORTANT] Die Paketdienst-Metapher (Enum mit Daten): Ein Zustelldienst transportiert Sendungen. Eine Sendung kann ein Brief sein (benötigt nur ein Adressfeld), ein Paket (benötigt Gewicht und Abmessungen) oder eine Palette (benötigt Stellplatz-Koordinaten). Obwohl alle diese Objekte „Sendungen“ sind, tragen sie völlig unterschiedliche Datenstrukturen. Ein Enum gruppiert diese Möglichkeiten unter einem gemeinsamen Typnamen.

3. Das Problem & Die Motivation

In vielen Programmiersprachen werden fachliche Alternativen oder Zustände unzureichend modelliert. Betrachten wir ein typisches Bestellsystem, das vier Zustände abbilden muss:

  • Eine Bestellung ist offen (wartet auf Zahlung).
  • Eine Bestellung ist bezahlt (wartet auf Versand).
  • Eine Bestellung ist versendet (besitzt einen Tracking-Code).
  • Eine Bestellung ist fehlgeschlagen (besitzt einen Fehlergrund).

Ein naiver Entwurf nutzt lose Variablen oder String-Zustandsfelder:

// Modellierung über ein Struct mit statusfeld
struct Bestellung {
    id: u32,
    status: String,        // Erlaubt beliebige Texte: "bezahlt", "offen", "fehlgeschlagen"
    tracking_code: String, // Nur sinnvoll, wenn status == "versendet"
    fehler_grund: String,  // Nur sinnvoll, wenn status == "fehlgeschlagen"
}

Dieser Ansatz weist fundamentale Schwachstellen auf:

  1. Fehlende Typsicherheit: Der Compiler akzeptiert jeden beliebigen Text für das Feld status. Tippfehler wie "bezhaltt" werden nicht erkannt.
  2. Ungültige Kombinationen (Invalide Zustände): Es ist möglich, ein Objekt zu erzeugen, dessen status auf "offen" gesetzt ist, das aber gleichzeitig einen tracking_code besitzt. Die logische Integrität der Daten hängt rein von der Disziplin des Programmierers ab.
  3. Mangelnde Wartbarkeit: Wird ein neuer Status eingeführt (z. B. "storniert"), muss jede if-else-Kette im gesamten Programm manuell gesucht und erweitert werden. Der Compiler bietet keine Hilfestellung.
  4. Fehlende Semantik bei Null-Werten: Um abwesende Werte (wie den Tracking-Code im Zustand "offen") darzustellen, müssen leere Ersatzwerte ("") oder riskante Null-Zeiger verwendet werden, was zu Laufzeitfehlern führen kann.

Rust löst dieses Problem durch Enums. Sie erlauben es, Daten so zu modellieren, dass ungültige Zustände syntaktisch gar nicht erst repräsentiert werden können ("Make invalid states unrepresentable").

4. Drei naive Versuche

Wir betrachten drei typische Fehlermuster, die bei der Arbeit mit Statusfeldern, optionalen Daten und Pattern Matching in Rust entstehen.

Versuch 1: Statusmodellierung über lose Strings

Ein Entwickler versucht, die Versandlogik über String-Vergleiche und leere String-Platzhalter abzubilden.

// Filename: src/main.rs
// Dieser Code kompiliert, hat aber schwerwiegende logische Modellierungsfehler!
fn versand_text(status: &str, tracking_code: &str) -> String {
    if status == "bezahlt" {
        if tracking_code == "" {
            String::from("Bezahlt, wartet auf Versand.")
        } else {
            format!("Versendet. Tracking: {tracking_code}")
        }
    } else if status == "offen" {
        String::from("Warten auf Zahlung.")
    } else {
        String::from("Unbekannter Status.")
    }
}

fn main() {
    // Ein kleiner Tippfehler im Status macht die Logik unbrauchbar
    let status = String::from("bezhaltt");
    let tracking = String::from("");
    let text = versand_text(&status, &tracking);
    println!("{text}"); // Gibt "Unbekannter Status." aus
}

Versuch 2: Unsicheres Auspacken von Optionen mittels unwrap

Der Entwickler hat gelernt, dass Option<T> für optionale Daten verwendet werden soll. Er greift jedoch unvorsichtig auf den Inhalt zu.

// Filename: src/main.rs
// Dieser Code kompiliert, stürzt jedoch zur Laufzeit ab (Panic)!
fn print_tracking_code(code: Option<String>) {
    // Unvorsichtiges Auspacken ohne vorherige Prüfung
    let text = code.unwrap(); 
    println!("Tracking-Code: {text}");
}

fn main() {
    let tracking: Option<String> = None; // Kein Tracking-Code vorhanden
    print_tracking_code(tracking);
}

Versuch 3: Unvollständiges Pattern Matching bei Enums

Ein Programmierer definiert ein Enum für das Ampelsystem, vergisst jedoch beim Auswerten eine Variante im match-Block.

// Filename: src/main.rs
// Dieser Code kompiliert NICHT!
enum Ampel {
    Rot,
    Gelb,
    Gruen,
}

fn signal_aktion(farbe: Ampel) -> &'static str {
    match farbe {
        Ampel::Rot => "Stopp",
        Ampel::Gruen => "Fahren",
        // Die Variante "Gelb" wurde vergessen!
    }
}

fn main() {
    let s = signal_aktion(Ampel::Gelb);
    println!("{s}");
}

5. Die Anatomie der Fehler

1. Analyse von Versuch 1 (Logischer Modellierungsfehler)

Der Code kompiliert problemlos, da alle Typen formal korrekt sind. Das Problem liegt im physischen Speicher und der mangelnden Validierung:

Stack (main):
  status:        [ ptr ] -----------> Heap: "bezhaltt" (Tippfehler!)
  tracking:      [ ptr ] -----------> Heap: ""         (Konvention für "kein Code")

Problem:
  Der Compiler sieht nur zwei gültige Strings.
  Er kann die fachliche Regel "Status darf nur aus ('offen', 'bezahlt', 'versendet') bestehen"
  nicht erzwingen. Der Fehler wird erst zur Laufzeit durch Fehlverhalten sichtbar.

2. Analyse von Versuch 2 (Laufzeit-Panic bei unwrap)

Der Code baut fehlerfrei, stürzt aber bei der Ausführung mit einer CPU-Fehlermeldung ab:

thread 'main' panicked at 'called Option::unwrap() on a None value', src/main.rs:4:16
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
  • Erklärung: Die Methode unwrap() ist eine zusichernde Methode. Sie sagt dem Compiler: „Ich garantiere, dass hier ein Some-Wert vorliegt. Falls nicht, bringe das Programm kontrolliert zum Absturz.“ Da tracking jedoch None war, bricht das Programm ab. Rust erzwingt Typsicherheit zur Compilezeit, aber unwrap() umgeht diese Sicherheitsbarriere manuell und verlagert das Risiko auf die Laufzeit.

3. Analyse von Versuch 3 (Compilerfehler bei Exhaustiveness)

Der Compiler bricht den Build-Prozess mit einer klaren Fehlermeldung ab:

error[E0004]: non-exhaustive patterns: `Ampel::Gelb` not covered
 --> src/main.rs:9:11
  |
1 | / enum Ampel {
2 | |     Rot,
3 | |     Gelb,
  | |     ---- `Ampel::Gelb` not covered
4 | |     Gruen,
5 | | }
  | \- `Ampel` defined here
...
9 |       match farbe {
  |             ^^^^^ pattern `Ampel::Gelb` not covered
  |
  = note: the matched value is of type `Ampel`
help: ensure that all possible cases are being handled by adding a match arm with a wildcard pattern or an explicit pattern as shown
  |
11~         Ampel::Gruen => "Fahren",
12+         Ampel::Gelb => todo!(),
  |
  • Erklärung: Rust verlangt, dass ein match-Ausdruck erschöpfend (exhaustive) ist. Das bedeutet: Jeder theoretisch mögliche Wert des Typs muss abgedeckt werden. Da die Variante Ampel::Gelb im Match-Block fehlt, verweigert der Compiler das Übersetzen. Dies garantiert, dass Sie niemals vergessen können, eine neu hinzugefügte Variante auszuwerten.

6. Die Lösung

Wir präsentieren die korrekten, sicheren Lösungsansätze unter Verwendung von Enums, Pattern Matching und der typsicheren Option<T>-Auswertung.

Didaktischer Pseudocode

1. MODELLIERUNG:
   Definiere BestellStatus als Enum:
     - Offen
     - Bezahlt
     - Versendet (mit enthaltenem Tracking-String)
     - Fehlgeschlagen (mit enthaltenem Fehler-String)

2. BEWERTUNG DER VERSAND-AKTION:
   Prüfe den BestellStatus:
     - Wenn Offen: Gib "Warten auf Zahlung." zurück.
     - Wenn Bezahlt: Gib "Bezahlt, wartet auf Versand." zurück.
     - Wenn Versendet mit Code: Gib "Versendet mit Code X" zurück.
     - Wenn Fehlgeschlagen mit Grund: Gib "Fehlgeschlagen wegen Y" zurück.
   (Der Compiler garantiert, dass alle diese Fälle behandelt werden müssen.)

Rust-Implementierung

// Wir erlauben Debug-Ausgaben für unser Enum
#[derive(Debug)]
enum BestellStatus {
    Offen,
    Bezahlt,
    Versendet { tracking_code: String },
    Fehlgeschlagen(String),
}

impl BestellStatus {
    // Methode zur Ermittlung des Statustextes
    fn beschreibung(&self) -> String {
        // Wir matchen auf die Referenz &self, um keine Daten zu verschieben (kein Move)
        match self {
            BestellStatus::Offen => String::from("Warten auf Zahlung."),
            BestellStatus::Bezahlt => String::from("Bezahlt, aber noch nicht versendet."),
            BestellStatus::Versendet { tracking_code } => {
                format!("Versendet mit Tracking-Code {tracking_code}.")
            }
            BestellStatus::Fehlgeschlagen(grund) => {
                format!("Zahlung fehlgeschlagen: {grund}.")
            }
        }
    }

    // Methode zur Abfrage des Abschluss-Zustands
    fn ist_abgeschlossen(&self) -> bool {
        matches!(self, BestellStatus::Versendet { .. })
    }
}

// Funktion zur sicheren Extraktion des Tracking-Codes
fn tracking_aus_status(status: &BestellStatus) -> Option<&str> {
    match status {
        BestellStatus::Versendet { tracking_code } => Some(tracking_code.as_str()),
        _ => None, // Sammelzweig für alle anderen Varianten
    }
}

fn main() {
    // 1. Initialisierung einer gültigen Instanz
    let status_offen = BestellStatus::Offen;
    let status_versendet = BestellStatus::Versendet {
        tracking_code: String::from("DHL-987654"),
    };

    // 2. Abfragen der Beschreibungen
    println!("Status 1: {}", status_offen.beschreibung());
    println!("Status 2: {}", status_versendet.beschreibung());

    // 3. Sicheres Prüfen des Tracking-Codes ohne unwrap()
    match tracking_aus_status(&status_versendet) {
        Some(code) => println!("Gefundener Tracking-Code: {code}"),
        None => println!("Kein Tracking-Code für diese Bestellung verfügbar."),
    }

    println!("Bestellung abgeschlossen? {}", status_versendet.ist_abgeschlossen());
}

Zeile-für-Zeile-Erklärung des Speicherverhaltens (EVA)

  • Eingabe (Input):
    • In main wird die Variable status_versendet angelegt. Ihr wird die Variante BestellStatus::Versendet zugewiesen.
    • Das Feld tracking_code besitzt den Heap-String "DHL-987654" (24 Bytes Stack-Verweis auf den Heap).
    • Der Typ BestellStatus benötigt auf dem Stack genug Platz für das Diskriminanten-Byte (zur Unterscheidung der Varianten) und die größte Variante (hier Versendet mit 24 Bytes String-Daten + Alignment).
  • Verarbeitung (Processing):
    • Beim Aufruf von status_versendet.beschreibung() wird eine unveränderliche Referenz &self übergeben.
    • Der match self-Block vergleicht die Variante. Da es sich um eine Referenz handelt, wird der innere String tracking_code im Arm BestellStatus::Versendet { tracking_code } automatisch als Referenz &String gebunden. Es findet kein Ownership-Transfer (Move) statt, weshalb status_versendet in main weiterhin gültig bleibt.
    • tracking_aus_status liefert Option<&str>. Das bedeutet: Wenn die Variante Versendet vorliegt, wird eine geliehene Textreferenz auf die Heap-Daten des Strings zurückgegeben, verpackt in Some. Andernfalls wird None zurückgegeben.
  • Ausgabe (Output):
    • Die Textausgaben werden über println! ausgegeben. Das System verarbeitet die Daten absolut typsicher. Tippfehler sind ausgeschlossen, da der Compiler nur die definierten Enum-Varianten akzeptiert.

7. Kleines Tutorial: Eine Bestelllogik bauen

In diesem Tutorial implementieren wir eine zustandsgesteuerte Bestellabwicklung. Wir verbinden dabei Enums für Zahlungen und Aktionen mit Scopes, Optionals, if let und let ... else.

Schritt 1: Fachliche Typen und Zustände definieren

Wir legen fest, welche Zahlungszustände eintreten können und welche Folgeaktionen unser System daraufhin ausführen muss.

#[derive(Debug)]
enum Zahlung {
    Offen,
    Bezahlt { betrag_cent: u32 },
    Abgelehnt { grund: String },
}

#[derive(Debug, PartialEq)]
enum FolgeAktion {
    ZahlungsErinnerungSenden,
    VersandVorbereiten { betrag_cent: u32 },
    SupportAlarmieren(String),
}

Schritt 2: Entscheidungslogik mit match

Wir schreiben eine reine Funktion, die eine Zahlung entgegennimmt (Ownership übernimmt) und die logisch folgende FolgeAktion ermittelt.

fn verarbeite_zahlung(zahlung: Zahlung) -> FolgeAktion {
    match zahlung {
        Zahlung::Offen => FolgeAktion::ZahlungsErinnerungSenden,
        Zahlung::Bezahlt { betrag_cent } => FolgeAktion::VersandVorbereiten { betrag_cent },
        Zahlung::Abgelehnt { grund } => FolgeAktion::SupportAlarmieren(grund),
    }
}

Schritt 3: Gekapselte Bestellung mit optionalem Gutschein

Wir definieren ein Bestell-Struct, das eine Bestellnummer und einen optionalen Gutscheincode aufweist.

struct Bestellung {
    id: u32,
    gutschein: Option<String>,
}

fn rabatt_information(bestellung: &Bestellung) -> String {
    // Da wir das Gutschein-Feld nur referenzieren, matchen wir auf &bestellung.gutschein.
    // Das verhindert ein unerlaubtes Verschieben (Move) aus dem Struct heraus.
    match &bestellung.gutschein {
        Some(code) => format!("Bestellung {} nutzt Rabattcode: {code}", bestellung.id),
        None => format!("Bestellung {} nutzt keinen Rabattcode.", bestellung.id),
    }
}

Schritt 4: Selektives Pattern Matching mit if let

Manchmal interessiert uns nur eine einzige Variante eines Enums, während alle anderen ignoriert werden können. Hierfür nutzen wir die kompakte if let-Syntax.

fn bewerbe_gutschein(bestellung: &Bestellung) {
    // Wir reagieren nur, wenn tatsächlich ein Gutschein existiert
    if let Some(code) = &bestellung.gutschein {
        println!("Sende personalisierte Werbung für Code: {code}");
    }
}

Schritt 5: Frühes Aussteigen mit let ... else

Wenn wir eine Funktion früh beenden wollen, falls eine Bedingung (ein Pattern) nicht erfüllt ist, ist let ... else die am besten lesbare Wahl. Sie hält den Hauptpfad der Funktion linksbündig (Flache Hierarchie).

fn extrahiere_aktiven_gutschein(bestellung: &Bestellung) -> Option<String> {
    // Wenn das Pattern Some(code) nicht passt, MUSS der else-Block den Kontrollfluss verlassen!
    let Some(code) = &bestellung.gutschein else {
        println!("Kein Gutschein vorhanden. Breche Suche ab.");
        return None;
    };

    // Hier ist 'code' im gesamten äußeren Funktionsscope verfügbar!
    Some(code.to_uppercase())
}

Schritt 6: Integration in die main

Wir fügen alle Bausteine zusammen und testen die Logik.

fn main() {
    // 1. Zahlungen verarbeiten
    let z1 = Zahlung::Bezahlt { betrag_cent: 4990 };
    let action = verarbeite_zahlung(z1);
    println!("Folgeaktion: {:?}", action);

    // 2. Bestellung mit Gutschein testen
    let b1 = Bestellung {
        id: 1001,
        gutschein: Some(String::from("rust2026")),
    };

    println!("{}", rabatt_information(&b1));
    bewerbe_gutschein(&b1);

    if let Some(upper_code) = extrahiere_aktiven_gutschein(&b1) {
        println!("Verarbeiteter Code: {upper_code}");
    }
}

8. Mentale Modelle & Deep Dive

8.1 Enums als Summentypen

In der Informatik und Typentheorie unterscheidet man Datenstrukturen nach der Anzahl ihrer Kombinationsmöglichkeiten (Kardinalität):

Produkttypen (Structs und Tupel)

Kombinieren Typen mit einem logischen UND. Beispiel: struct Point { x: u8, y: u8 } Anzahl der möglichen Werte: $256 \times 256 = 65.536$ (Produkt der Mengen).

Summentypen (Enums)

Kombinieren Typen mit einem logischen ODER. Beispiel: enum Wahl { Ja(u8), Nein } Anzahl der möglichen Werte: $256 + 1 = 257$ (Summe der Mengen).

Struct (Produkt): name UND email UND status
   +---------------------------------------+
   |   name    |    email    |   status    |  (Alle existieren gleichzeitig)
   +---------------------------------------+

Enum (Summe): Offen ODER Bezahlt ODER Versendet
   +---------------------------------------+
   | Variante: Offen                       |  (Es existiert stets nur)
   | ODER:     Bezahlt                     |  (eine der Varianten im)
   | ODER:     Versendet { tracking_code } |  (Speicherbereich)
   +---------------------------------------+

8.2 Speicherlayout & Performance

Ein Enum-Wert muss alle seine Varianten im selben Speicherbereich abbilden können. Daher bestimmt die größte Variante die Gesamtgröße des Enums.

Das physische Layout im Detail:

  1. Der Diskriminant (Tag): Ein internes Byte (in der Regel 1 Byte, bei Bedarf an Alignment angepasst), das eine Zahl speichert. Diese Zahl identifiziert, welche Variante aktuell aktiv ist (z. B. 0 für Offen, 1 für Bezahlt).
  2. Die Nutzdaten (Payload): Speicherplatz für die Daten der größten Variante.
  3. Padding: Füllbytes, die eingefügt werden, um das Alignment der Nutzdaten einzuhalten.
use std::mem::size_of;

enum SpeicherTest {
    A,                  // 0 Bytes Nutzdaten
    B(u8),              // 1 Byte Nutzdaten
    C(u64),             // 8 Bytes Nutzdaten
}

fn main() {
    println!("u8: {} Byte", size_of::<u8>());          // 1 Byte
    println!("u64: {} Byte", size_of::<u64>());        // 8 Bytes
    println!("Test: {} Byte", size_of::<SpeicherTest>()); // 16 Bytes (1 Byte Tag + 7 Bytes Padding + 8 Bytes Nutzdaten)
}

Die Nischen-Optimierung (Null Pointer Optimization)

Rust nutzt ungenutzte Bitmuster (Nischen) von Datentypen, um Speicherplatz einzusparen. Eine Referenz &T oder ein intelligenter Zeiger wie Box<T> darf niemals die Speicheradresse 0 (null) annehmen. Rust nutzt diese ungültige Adresse 0 intern, um die Variante None eines Option<&T> darzustellen.

fn main() {
    // Keine zusätzliche Tag-Größe! Option<&i32> ist exakt so groß wie ein nackter Zeiger &i32.
    println!("Größe &i32: {} Bytes", size_of::<&i32>());                 // 8 Bytes
    println!("Größe Option<&i32>: {} Bytes", size_of::<Option<&i32>>()); // 8 Bytes (Zero-Cost!)
}

8.3 Pattern Matching & Exhaustiveness

Pattern Matching ist in Rust kein einfaches switch-case wie in C oder Java. Es ist ein mächtiges Werkzeug zur Typprüfung und Datenextraktion.

1. Exhaustive (Erschöpfende) Prüfung

Der Compiler prüft jeden Pfad. Wenn Sie eine Variante vergessen, verweigert das System den Build.

2. Der Sammelarm (Wildcard _)

Der Unterstrich _ fängt jeden Wert ab, der von den vorherigen Armen nicht getroffen wurde. Er ignoriert die Daten.

[!WARNING] Vorsicht vor Wildcards bei Domänen-Enums! Wenn Sie ein Enum für geschäftsrelevante Zustände (wie BestellStatus) nutzen, sollten Sie auf den Sammelarm _ verzichten. Verwenden Sie stattdessen explizite Varianten-Auflistungen. Fügen Sie später eine neue Variante hinzu, zwingt der Compiler Sie an jeder Stelle im Code zur Anpassung. Mit einem Wildcard _ würde der Compiler stumm durchlaufen, was zu unentdeckten Logikfehlern führen kann.

3. Der | (Oder)-Operator

Sie können mehrere Muster in einem einzigen Match-Arm zusammenfassen:

match status {
    BestellStatus::Offen | BestellStatus::Bezahlt => println!("Nicht versandbereit"),
    _ => println!("Versandbereit oder Fehler"),
}

4. Bindings: ref und ref mut im Pattern

Wenn Sie ein Struct oder Enum destrukturieren und nur Referenzen auf die inneren Felder erhalten möchten, nutzen Sie das standardmäßige Referenz-Matching des Compilers.

let opt_name = Some(String::from("Alice"));
match &opt_name {
    Some(name) => println!("Name ist: {name}"), // 'name' wird automatisch als &String gebunden
    None => {}
}
// opt_name ist hier weiterhin gültig, da wir nur referenziert (geliehen) haben!

8.4 Option<T> als sicherer Null-Ersatz

In vielen Sprachen existiert das Konzept von null oder nil (z. B. Java, C++, Python). Tony Hoare, der Erfinder der Null-Referenz, nannte dies seinen „Billion Dollar Mistake“.

Das Problem von null:

  • Jede Variable, die auf ein Objekt verweist, kann theoretisch auch auf null zeigen.
  • Der Compiler kann nicht prüfen, ob eine Referenz gültig ist.
  • Programmierer vergessen häufig, auf null zu prüfen, was zu plötzlichen Laufzeitabstürzen (NullPointerException) führt.

Die Rust-Lösung:

Es gibt in sicherem Rust keine Null-Zeiger. Ein Wert ist immer gültig. Wenn ein Wert fehlen kann, müssen Sie dies explizit im Typ sichtbar machen. Das geschieht über das Standard-Enum:

enum Option<T> {
    None,
    Some(T),
}

Sie können mit einem Option<i32> nicht direkt rechnen. Der Compiler zwingt Sie, die Kapsel über Pattern Matching oder Standardmethoden zu öffnen, bevor Sie an den inneren Wert gelangen.

8.5 Thread-Safety & Concurrency

Enums besitzen in Rust keine feste Thread-Sicherheit an sich. Ihre Thread-Tauglichkeit wird über die sogenannten Auto-Traits Send und Sync dynamisch abgeleitet.

  • Regel: Ein Enum ist Send bzw. Sync, wenn alle in den Varianten enthaltenen Datentypen selbst Send bzw. Sync implementieren.
Beispiel 1:
  enum Safe { A(u32), B(String) }
  -> u32 und String sind Send/Sync.
  -> Safe ist Send/Sync und kann gefahrlos zwischen Threads geteilt werden.

Beispiel 2:
  enum Unsafe { A(Rc<u32>), B(String) }
  -> Rc<T> ist explizit NICHT Send/Sync (nicht-atomarer Referenzzähler).
  -> Unsafe verliert automatisch die Send/Sync-Eigenschaften.

8.7 Exhaustive API-Reference für Option<T>

Option<T> ist der meistgenutzte Typ in Rust. Nachfolgend finden Sie eine lückenlose Referenz aller wichtigen Methoden der Standardbibliothek für diesen Typ.

1. is_some

  • Signatur: pub const fn is_some(&self) -> bool
  • Parameter: &self (unveränderliche Ausleihe)
  • Rückgabetyp: bool (liefert true, wenn die Option Some ist)
  • Panics / Sicherheit: Keine Risiken.
  • Code-Beispiel: 
    let x: Option<i32> = Some(2);
assert_eq!(x.is_some(), true);

2. is_none

  • Signatur: pub const fn is_none(&self) -> bool
  • Parameter: &self (unveränderliche Ausleihe)
  • Rückgabetyp: bool (liefert true, wenn die Option None ist)
  • Panics / Sicherheit: Keine Risiken.
  • Code-Beispiel: 
    let x: Option<i32> = None;
assert_eq!(x.is_none(), true);

3. as_ref

  • Signatur: pub const fn as_ref(&self) -> Option<&T>
  • Parameter: &self (unveränderliche Ausleihe)
  • Rückgabetyp: Option<&T> (wandelt Option des Werts in Option der Referenz um)
  • Panics / Sicherheit: Keine Risiken. Verhindert das Bewegen (Move) von Werten.
  • Code-Beispiel: 
    let text = Some(String::from("Hallo"));
let text_ref: Option<&String> = text.as_ref();
assert!(text_ref.is_some());

4. as_mut

  • Signatur: pub fn as_mut(&mut self) -> Option<&mut T>
  • Parameter: &mut self (veränderliche Ausleihe)
  • Rückgabetyp: Option<&mut T> (erzeugt eine veränderliche Referenz auf den inneren Wert)
  • Panics / Sicherheit: Keine Risiken.
  • Code-Beispiel: 
    let mut x = Some(2);
if let Some(val) = x.as_mut() {
    *val += 1;
}
assert_eq!(x, Some(3));

5. expect

  • Signatur: pub fn expect(self, msg: &str) -> T
  • Parameter: self (übernimmt Ownership), msg (Fehlermeldung)
  • Rückgabetyp: T (der innere Wert)
  • Panics / Sicherheit: Stürzt ab (Panic) mit der Nachricht msg, wenn der Wert None ist. Nur im Testcode oder bei logisch garantierten Zuständen nutzen!
  • Code-Beispiel: 
    let x = Some("Wert");
assert_eq!(x.expect("Sollte da sein"), "Wert");

6. unwrap

  • Signatur: pub fn unwrap(self) -> T
  • Parameter: self (übernimmt Ownership)
  • Rückgabetyp: T (der innere Wert)
  • Panics / Sicherheit: Stürzt ab (Panic), wenn der Wert None ist. In Produktionscode vermeiden!
  • Code-Beispiel: 
    let x = Some("Wert");
assert_eq!(x.unwrap(), "Wert");

7. unwrap_or

  • Signatur: pub fn unwrap_or(self, default: T) -> T
  • Parameter: self (übernimmt Ownership), default (Ausweichwert)
  • Rückgabetyp: T (der innere Wert oder der Standardwert)
  • Panics / Sicherheit: Keine Risiken. Der Standardwert wird sofort evaluiert (unabhängig davon, ob er benötigt wird).
  • Code-Beispiel: 
    let x: Option<i32> = None;
assert_eq!(x.unwrap_or(42), 42);

8. unwrap_or_else

  • Signatur: pub fn unwrap_or_else<F: FnOnce() -> T>(self, f: F) -> T
  • Parameter: self (übernimmt Ownership), f (eine anonyme Funktion / Closure)
  • Rückgabetyp: T (der innere Wert oder das Ergebnis der Funktion f)
  • Panics / Sicherheit: Keine Risiken. Die Funktion wird nur ausgeführt (lazy evaluation), wenn die Option tatsächlich None ist.
  • Code-Beispiel: 
    let x: Option<i32> = None;
assert_eq!(x.unwrap_or_else(|| 20 + 22), 42);

9. unwrap_or_default

  • Signatur: pub fn unwrap_or_default(self) -> T where T: Default
  • Parameter: self (übernimmt Ownership)
  • Rückgabetyp: T (der innere Wert oder der Default-Wert des Typs T)
  • Panics / Sicherheit: Keine Risiken. Setzt voraus, dass der Typ T das Default-Trait implementiert.
  • Code-Beispiel: 
    let x: Option<i32> = None;
assert_eq!(x.unwrap_or_default(), 0); // 0 ist der Standard für i32

10. map

  • Signatur: pub fn map<U, F: FnOnce(T) -> U>(self, f: F) -> Option<U>
  • Parameter: self (übernimmt Ownership), f (Umwandlungs-Funktion)
  • Rückgabetyp: Option<U> (wird auf den inneren Wert angewendet, None bleibt None)
  • Panics / Sicherheit: Keine Risiken.
  • Code-Beispiel: 
    let x = Some("Text");
let laenge = x.map(|s| s.len());
assert_eq!(laenge, Some(4));

11. map_or

  • Signatur: pub fn map_or<U, F: FnOnce(T) -> U>(self, default: U, f: F) -> U
  • Parameter: self (übernimmt Ownership), default (Standardwert), f (Umwandlungs-Funktion)
  • Rückgabetyp: U (das Ergebnis von f oder der Standardwert)
  • Panics / Sicherheit: Keine Risiken.
  • Code-Beispiel: 
    let x = Some("Text");
assert_eq!(x.map_or(0, |s| s.len()), 4);

12. map_or_else

  • Signatur: pub fn map_or_else<U, D: FnOnce() -> U, F: FnOnce(T) -> U>(self, default: D, f: F) -> U
  • Parameter: self (übernimmt Ownership), default (standardwert-erzeugende Closure), f (Umwandlungs-Funktion)
  • Rückgabetyp: U
  • Panics / Sicherheit: Keine Risiken.
  • Code-Beispiel: 
    let x: Option<&str> = None;
assert_eq!(x.map_or_else(|| 0, |s| s.len()), 0);

13. ok_or

  • Signatur: pub fn ok_or<E>(self, err: E) -> Result<T, E>
  • Parameter: self (übernimmt Ownership), err (Fehlerwert)
  • Rückgabetyp: Result<T, E> (wandelt Some(v) in Ok(v) und None in Err(err) um)
  • Panics / Sicherheit: Keine Risiken.
  • Code-Beispiel: 
    let x = Some("Erfolg");
let res: Result<&str, &str> = x.ok_or("Fehler");
assert_eq!(res, Ok("Erfolg"));

14. and_then

  • Signatur: pub fn and_then<U, F: FnOnce(T) -> Option<U>>(self, f: F) -> Option<U>
  • Parameter: self (übernimmt Ownership), f (Funktion, die selbst ein Option liefert)
  • Rückgabetyp: Option<U> (Verhindert verschachtelte Option<Option<U>>-Strukturen beim Chaining)
  • Panics / Sicherheit: Keine Risiken.
  • Code-Beispiel: 
    let x = Some("42");
let zahl = x.and_then(|s| s.parse::<i32>().ok());
assert_eq!(zahl, Some(42));

15. filter

  • Signatur: pub fn filter<P: FnOnce(&T) -> bool>(self, predicate: P) -> Option<T>
  • Parameter: self (übernimmt Ownership), predicate (Prüf-Funktion)
  • Rückgabetyp: Option<T> (behält den Wert nur, wenn die Prüfung true liefert, sonst None)
  • Panics / Sicherheit: Keine Risiken.
  • Code-Beispiel: 
    let x = Some(10);
let gefiltert = x.filter(|n| n % 2 == 0);
assert_eq!(gefiltert, Some(10));

16. or

  • Signatur: pub fn or(self, optb: Option<T>) -> Option<T>
  • Parameter: self (übernimmt Ownership), optb (Alternativ-Option)
  • Rückgabetyp: Option<T> (gibt self zurück, falls Some, andernfalls optb)
  • Panics / Sicherheit: Keine Risiken.
  • Code-Beispiel: 
    let x = None;
let y = Some(5);
assert_eq!(x.or(y), Some(5));

17. or_else

  • Signatur: pub fn or_else<F: FnOnce() -> Option<T>>(self, f: F) -> Option<T>
  • Parameter: self (übernimmt Ownership), f (funktionale Alternative)
  • Rückgabetyp: Option<T>
  • Panics / Sicherheit: Keine Risiken.
  • Code-Beispiel: 
    let x = None;
assert_eq!(x.or_else(|| Some(10)), Some(10));

18. take

  • Signatur: pub fn take(&mut self) -> Option<T>
  • Parameter: &mut self (veränderliche Ausleihe)
  • Rückgabetyp: Option<T> (entnimmt den Wert aus dem Original-Speicherplatz und hinterlässt dort None)
  • Panics / Sicherheit: Keine Risiken. Extrem wichtig bei der Arbeit mit veränderlichen Referenzen, um Daten ohne Verletzung der Aliasing-Regeln zu verschieben.
  • Code-Beispiel: 
    let mut x = Some(123);
let y = x.take();
assert_eq!(x, None);
assert_eq!(y, Some(123));

19. replace

  • Signatur: pub fn replace(&mut self, value: T) -> Option<T>
  • Parameter: &mut self (veränderliche Ausleihe), value (neuer Wert)
  • Rückgabetyp: Option<T> (ersetzt den aktuellen Wert durch value und gibt die alte Option zurück)
  • Panics / Sicherheit: Keine Risiken.
  • Code-Beispiel: 
    let mut x = Some(2);
let alt = x.replace(5);
assert_eq!(x, Some(5));
assert_eq!(alt, Some(2));

20. zip

  • Signatur: pub fn zip<U>(self, other: Option<U>) -> Option<(T, U)>
  • Parameter: self (übernimmt Ownership), other (zweite Option)
  • Rückgabetyp: Option<(T, U)> (kombiniert zwei Optionen zu einer Option, die ein Tupel enthält)
  • Panics / Sicherheit: Keine Risiken.
  • Code-Beispiel: 
    let x = Some(1);
let y = Some("eins");
assert_eq!(x.zip(y), Some((1, "eins")));

21. flatten

  • Signatur: pub fn flatten(self) -> Option<U> where T = Option<U>
  • Parameter: self (übernimmt Ownership)
  • Rückgabetyp: Option<U> (entfernt eine Verschachtelungsebene)
  • Panics / Sicherheit: Keine Risiken.
  • Code-Beispiel: 
    let x = Some(Some(6));
assert_eq!(x.flatten(), Some(6));

    • Gast

Rabatt::Prozent(wert) if *wert >= 1 && *wert <= 100 => Some(rabatt)), um die numerischen Werte direkt im Match-Arm abzuprüfen. Achten Sie auf die Dereferenzierung bei Guards, da Sie über Referenzen iterieren.

11. Zusammenfassung

  • Enums (Summentypen) beschreiben eine exklusive Auswahl aus einer festen Menge von Varianten. Sie sind das primäre Werkzeug zur Zustands- und Alternativen-Modellierung.
  • Datentragende Varianten erlauben es, Nutzdaten direkt an den Zustand zu binden, zu dem sie fachlich gehören (z. B. ein Tracking-Code nur bei Versendet).
  • Pattern Matching (match) erzwingt die vollständige und lückenlose Auswertung aller Fälle zur Compilezeit. Es minimiert Logikfehler bei der Code-Wartung.
  • Option ersetzt die unsichere Null-Referenz. Rust-Code kann optionale Werte nicht versehentlich nutzen, ohne sie vorher explizit entpackt zu haben.
  • Kompakte Syntax-Alternativen: if let filtert gezielt auf einen interessanten Fall. let ... else filtert das falsche Pattern frühzeitig aus und hält den Code flach.
  • Zero-Cost-Abstraktion: Dank der Nischen-Optimierung belegen Typen wie Option<&T> exakt denselben Speicherplatz wie ein einfacher Zeiger (8 Bytes auf 64-Bit Systemen).
