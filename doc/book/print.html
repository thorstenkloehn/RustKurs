Kapitel 2: Installation & Systemkonfiguration

Um mit der Programmierung in Rust unter Ubuntu Linux zu beginnen, müssen wir unser System vorbereiten und die notwendigen Entwicklungswerkzeuge installieren. Dieses Kapitel führt dich Schritt für Schritt durch die Installation aller Voraussetzungen, der Entwicklungsumgebung (IDE) und von Rust selbst.

1. Voraussetzungen: build-essential

Bevor wir Rust installieren können, benötigt unser System grundlegende Werkzeuge zum Übersetzen und Linken von Software. Rust-Programme greifen beim Kompilieren auf Systembibliotheken und den System-Linker zu.

Was ist build-essential?

Das Paket build-essential ist ein Meta-Paket in Ubuntu, das eine Sammlung der wichtigsten Werkzeuge für die C/C++-Entwicklung enthält. Dazu gehören:

  • gcc / g++: Die GNU Compiler Collection zum Übersetzen von C- und C++-Code.
  • make: Ein Werkzeug zur Automatisierung von Kompilierungsvorgängen.
  • libc-dev: Die Standard-C-Bibliotheken, die für Systemaufrufe benötigt werden.
  • dpkg-dev: Werkzeuge zur Paketierung.

Rust benötigt den in diesem Paket enthaltenen C-Linker, um den generierten Maschinencode zu lauffähigen Binärdateien zusammenzufügen.

Installation

Öffne dein Terminal und führe die folgenden Befehle aus:

# Paketquellen aktualisieren
sudo apt update

# build-essential installieren
sudo apt install -y build-essential

2. Editor & IDE: Visual Studio Code

Als Entwicklungsumgebung verwenden wir Visual Studio Code (VS Code). Es ist ein moderner, performanter und erweiterbarer Editor von Microsoft, der sich in der Entwickler-Community großer Beliebtheit erfreut.

VS Code auf Ubuntu installieren

Unter Ubuntu lässt sich VS Code am einfachsten und sichersten als klassisches Snap-Paket über das Terminal installieren:

sudo snap install --classic code

Die Erweiterung rust-analyzer

VS Code selbst besitzt standardmäßig keine tiefe Integration für Rust. Um komfortabel arbeiten zu können, installieren wir das offizielle Rust-Plugin: rust-analyzer.

  1. Öffne VS Code.
  2. Drücke Strg + Umschalt + X, um die Extensions-Ansicht zu öffnen.
  3. Suche nach rust-analyzer (von der Rust Programming Language Organisation).
  4. Klicke auf Install.

Was bietet rust-analyzer?

  • Intelligente Codevervollständigung: Vorschläge beim Tippen.
  • Syntaxhervorhebung & Formatierung: Automatisches Formatieren nach dem Rust-Standard rustfmt.
  • Echtzeit-Diagnose: Fehler und Warnungen werden direkt beim Schreiben im Code rot unterstrichen, bevor du überhaupt kompilierst.
  • Typen-Inferenz: Anzeige von automatisch erkannten Datentypen direkt im Editor.

3. Rust-Installation via rustup

Der offizielle, empfohlene und flexibelste Weg, Rust auf Unix-ähnlichen Systemen wie Linux zu installieren, ist rustup.

Was ist rustup?

rustup is der Versionsmanager für Rust. Ähnlich wie nvm für Node.js verwaltet es verschiedene Rust-Versionen (z. B. Stable, Beta, Nightly) und sorgt dafür, dass Tools wie der Compiler (rustc) und der Paketmanager (Cargo) immer auf dem neuesten Stand sind.

Installation

Kopiere das offizielle Installationsskript in dein Terminal und führe es aus:

curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh

Während des Installationsprozesses wird im Terminal ein Auswahlmenü angezeigt:

1) Proceed with installation (default)
2) Customize installation
3) Cancel installation

Drücke einfach 1 und dann Enter, um die Standardinstallation fortzusetzen.

Systempfad aktualisieren

Nachdem die Installation abgeschlossen ist, müssen die Rust-Tools zu den Umgebungsvariablen deines Terminals hinzugefügt werden. Führe dazu entweder den folgenden Befehl aus oder starte dein Terminal einfach neu:

source "$HOME/.cargo/env"

Überprüfung der Installation

Um zu verifizieren, dass Rust erfolgreich installiert wurde und einsatzbereit ist, kannst du die Version des Compilers abfragen:

rustc --version

Die Ausgabe sollte der folgenden ähneln (Version und Datum können abweichen): rustc 1.80.0 (sha 2026-06-06)

Das Prinzip in Kürze

Wenn du Argumente an println! übergibst, zählt Rust im Hintergrund ab 0:

Rust println!("Ich mag {0} und {1}. Ja, wirklich {0}!", äpfel, orangen); // ^ ^ ^ ^ ^ // | | | | | // Position 0 Position 1 Position 0 | | // Argument 0 | // Argument 1

Das Problem: Ungenutzte Variablen

Wenn du eine Variable erstellst, sie aber nirgends im Code benutzt (kein println!, keine Berechnung), meckert der Rust-Compiler mit einer Warnung (warning: unused variable). Das Programm läuft zwar, aber Rust mag keinen unaufgeräumten Code.

Die Lösung: Der Unterstrich (_)

Wenn eine Variable absichtlich (oder vorübergehend beim Testen) ungenutzt bleiben soll, setzt du einfach einen Unterstrich vor den Namen.

Standard: Unveränderlich (Immutable)

In Rust ist jede normale Variable wie in Stein gemeißelt. Einmal zugewiesen, darfst du den Wert nicht mehr ändern.

Der Trick: Das Schlüsselwort mut (Mutable)

Wenn sich ein Wert im Laufe des Programms ändern muss, musst du Rust explizit um Erlaubnis bitten. Das machst du mit mut (kurz für mutable = veränderlich).

Mini-Merkmerkmale:

  • Ohne mut = Konstant/Gesperrt
  • Mit mut = Veränderbar

Mini-Merkmerkmale:

  • rustc = Die Abkürzung für den Rust-Compiler.
  • --explain = Der Befehl, der dir den Fehler haarklein erklärt.
  • Keine Panik bei Fehlern: Code eingeben, Erklärung lesen, Fix anwenden. Du musst den Editor dafür nicht mal verlassen!

Variablen-Shadowing (Beschattung)

Normalerweise darf eine Variable ihren Datentyp niemals ändern. Mit let (Shadowing) darfst du es, weil die alte Variable quasi gelöscht (überschattet) und eine komplett neue gebaut wird.

Shadowing = Altes Buch wegschmeißen, neues Buch mit demselben Titel, aber völlig anderem Inhalt ins Regal stellen.

Die 3 goldenen Scope-Regeln

  • Von außen nach innen (Ja): Ein innerer Block kann alles sehen und nutzen, was im äußeren Block darüber deklariert wurde.
  • Von innen nach außen (Nein): Ein äußerer Block kann nicht sehen, was in einem inneren Block eingesperrt ist.
  • Das Lebensende (Drop): Sobald der Code die schließende Klammer } eines Blocks erreicht, „stirbt“ die Variable (sie geht out of scope) und Rust löscht sie sofort aus dem Arbeitsspeicher.

Namens-Doppelgänger (Kein Shadowing!)

Wenn du im inneren Block eine Variable mit demselben Namen wie außen erstellst, überdeckt sie die äußere Variable – aber nur solange der innere Block läuft!

Mini-Merkmerkmal

Scope ist wie ein Haus mit Einwegspiegeln: Wer im Haus (innerer Block) steht, kann durch die Fenster nach draußen (äußerer Block) sehen. Wer draußen steht, kann aber nicht reinschauen. Und zieht man das Haus ab (}), ist alles darin weg.

Konstanten (const) in Rust

Eine Konstante ist ein Name für einen Wert, der sich niemals ändern kann. Sie ist noch strenger als eine normale, unveränderliche Variable.

  • Variable (let): Ein beschreibbares Whiteboard im Zimmer.
  • Konstante (const): Ein Schild aus Stein, das draußen an der Hauswand für alle sichtbar eingemeißelt ist.

Skalare Typen

Ein skalarer Typ repräsentiert einen einzigen Wert. Die wichtigsten numerischen Typen sind:

Ganzzahlen (Integers): Zahlen ohne Komma.

Ganzzahlen (Integers): Zahlen ohne Komma.
  • Mit Vorzeichen (i für signed): Können positiv und negativ sein (z. B. -5, 12). Standard ist i32.
  • Ohne Vorzeichen (u für unsigned): Können nur 0 oder positiv sein (z. B. 5). Weil sie kein Minuszeichen speichern müssen, passen größere positive Zahlen hinein.

Fließkommazahlen (Floats): Zahlen mit Nachkommastellen (Dezimalzahlen). Standard ist

  • f64

Was bedeuten die Zahlen (z. B. 8, 32, 64)?

Wichtig für Anfänger: Verschwende am Anfang keine Zeit mit "Mikro-Optimierung" des Speichers. Nutze einfach die * * * * Rust-Standards (i32 und f64). Heutige Computer haben mehr als genug Speicher.

  • Statische Typisierung: Rust muss jeden Datentyp vor dem Start des Programms kennen.

  • Typinferenz: Rust erkennt den Typ oft automatisch anhand des zugewiesenen Wertes.

  • Zusammengesetzte Typen (Vorschau): Können im Gegensatz zu skalaren Typen mehrere Werte wie ein "Behälter" aufnehmen.

Speicher-Eselsbrücke

  • i = Integer (Ganzzahl mit Vorzeichen, kann ins Ins Negative gehen).

  • u = Unsigned (Vorzeichenlos, Unmöglich negativ).

  • Standard-Regel: Wenn du eine normale Zahl brauchst, nimm einfach i32. Wenn du eine Kommazahl brauchst, nimm f64.

Das Wichtigste in Kürze

  • Explizite Typisierung: Standardmäßig macht Rust aus ganzen Zahlen ein i32. Willst du das ändern, hängst du einen Doppelpunkt und den Typ an den Variablennamen (z. B. let x: i8 = -100;).
  • Wertebereich beachten: Jeder Typ hat Grenzen. Passt eine Zahl nicht in den Speicherplatz (z. B. 400 in ein u8), streikt der Compiler und das Programm startet erst gar nicht.
  • Alternative Schreibweise (Suffix): Du kannst den Typ auch direkt ohne Leerzeichen an die Zahl klatschen (z. B. let x = 20i8;). Das bewirkt genau dasselbe, wird aber seltener genutzt.

Merkzettel: Rust Integer (Ganzzahlen) im Überblick

  • i (signed / mit Vorzeichen): Kann negative und positive Zahlen speichern.
  • u (unsigned / ohne Vorzeichen): Kann nur positive Zahlen und 0 speichern. Vorteil: Da kein Minuszeichen gespeichert werden muss, verdoppelt sich die Reichweite im positiven Bereich.

Das Wichtigste in Kürze

  • Große Zahlen im Code (wie 6000000) sind schwer zu lesen. Rust erlaubt es dir, Unterstriche (_) als visuelle Trennzeichen in Zahlen einzufügen (wie das Tausendertrennzeichen in der Mathematik).

  • Dem Compiler ist es egal: Rust ignoriert die Unterstriche beim Kompilieren komplett.

  • Flexibel: Du kannst so viele Unterstriche setzen, wo du willst.

  • Best Practice: Sinnvoll ist es, Zahlen in 3er-Blöcke aufzuteilen (z. B. 6_000_000).

  • Eselsbrücke: Ersetze das mathematische Tausender-Komma (oder den Punkt) im Code einfach durch einen Unterstrich _. Das erhöht die Lesbarkeit sofort und verhindert Tippfehler bei vielen Nullen!

Das Wichtigste in Kürze

Während Typen wie i32 oder u8 auf jedem Computer immer exakt gleich groß sind, passen sich isize und usize automatisch an den Computer an, auf dem das Programm gerade läuft.

  • Die Anpassung: Auf einem 64-Bit-Computer werden sie zu 64-Bit-Typen (i64 / u64). Auf einem 32-Bit-Computer werden sie zu 32-Bit-Typen (i32 / u32).
  • Der Zweck: Sie dienen als "Spitznamen" (Aliase) für den nativen Typ des Systems. Das macht den Code extrem flexibel und spart automatisch Speicher auf älteren Systemen, während es auf modernen Computern die maximale Leistung herausholt. Wofür braucht man das? In der Praxis nutzt man usize vor allem, wenn man Dinge zählt, die mit der Speichergröße des Computers zu tun haben – zum Beispiel, um die Länge von Listen (Arrays/Vektoren) zu bestimmen oder Elemente darin über einen Index anzusprechen.

Was ist ein String-Literal?

Ein Text in doppelten Anführungszeichen (z. B. "Hello World") ist in Rust technisch gesehen ein String-Literal. Der Compiler kennt diesen Text schon beim Verharmlosen (Kompilieren), weil er fest im Quellcode geschrieben steht. Dynamische Texte (z. B. Benutzereingaben) funktionieren später anders.

Maskierung (Escaping) & Sonderzeichen

Manche Zeichen haben in Rust eine Sonderfunktion. Sie beginnen immer mit einem Backslash (). Möchtest du diese Zeichen wörtlich als Text drucken, musst du sie mit einem zusätzlichen Backslash "maskieren" (escapen).

  • \n erzeugt eine neue Zeile.

  • \t erzeugt einen Tabulator-Abstand.

  • " druckt ein echtes Anführungszeichen, ohne dass Rust denkt, der String ist vorbei.

  • \ druckt einen einzelnen, echten Backslash (wichtig z. B. bei Windows-Dateipfaden).

Die Rettung: Raw Strings Wenn du viele Backslashes oder Pfade hast, wird der Code durch das ständige Maskieren (\) unleserlich. Die Lösung ist ein Raw String (Roh-Zeichenkette). Setze einfach ein r vor die Anführungszeichen. Rust ignoriert dann alle Sonderfunktionen und druckt alles exakt so, wie es da steht.

  1. Was ist eine Methode? Eine Methode ist im Grunde eine Funktion, die fest an einen bestimmten Wert oder Datentyp gebunden ist. Sie ist wie ein Befehl, den man direkt auf eine Variable anwendet.

  • Funktion / Makro: Steht für sich alleine (z. B. println!(...)).

  • Methode: Klebt immer mit einem Punkt an einer Variablen (z. B. text.trim()).

  • Eingabe (Argument): Was in die Klammern reinwandert.

  • Ausgabe (Rückgabewert): Das Ergebnis, das am Ende rauskommt.

Ein Float (Fließkommazahl) stellt eine Dezimalzahl mit Nachkommastellen dar. In Rust sind Floats immer vorzeichenbehaftet (sie können also positive und negative Werte haben). Es gibt keine "unsigned" (rein positiven) Floats.

fn main() { let pi: f64 = 3.14159;

// 1. .floor() -> Abrunden (zum "Boden")
println!("{}", pi.floor()); // Ausgabe: 3.0

// 2. .ceil() -> Aufrunden (zur "Decke" / Ceiling)
println!("{}", pi.ceil());  // Ausgabe: 4.0

// 3. .round() -> Kaufmännisch runden (zur nächsten ganzen Zahl)
println!("{}", pi.round()); // Ausgabe: 3.0 (da .14 näher an 3 ist)

let kaffee_preis: f64 = 3.75;
println!("{}", kaffee_preis.round()); // Ausgabe: 4.0 (da .75 näher an 4 ist)

}

Das Zaubermittel dafür heißt Formatbezeichner (Format Speci) Die Syntax: Innerhalb der geschweiften Klammern fügst du einen Doppelpunkt :, einen Punkt . und die gewünschte Anzahl an Stellen ein (z.   • Zwei Wege: Das funktioniert sowohl, wenn die Variable direkt in den Klammern steht ({pi:.2}), als auch, wenn sie als Argument hinten dranhängt ({:.2}, pi).

// ---- Variante 1: Variable direkt in der Klammer (Kompakt) ----

Datentypen: Skalare vs. zusammengesetzte Datentypen

Wir haben bereits skalare Datentypen besprochen. Jetzt besprechen wir zusammengesetzte (oder strukturierte) Datentypen. In Rust gibt es zwei zusammengesetzte Datentypen: Arrays und Tupel. (Dynamische Datentypen werden später besprochen.)

Was ist ein Array?

Ein Array kannst du dir wie eine Schachtel mit festen Fächern vorstellen. Es hat drei wichtige Eigenschaften:

  • Homogen: Alle Elemente müssen vom selben Datentyp sein (z. B. nur ganze Zahlen).
  • Feste Größe: Die Anzahl der Fächer steht von Anfang an fest. Ein Array kann im Nachhinein weder wachsen noch schrumpfen.
  • Geordnet: Die Elemente liegen in einer festen Reihenfolge vor (von links nach rechts).

Syntax in Rust

So schreibt man ein Array in Rust:

// Rust erkennt den Typ (6 Ganzzahlen) automatisch:
let numbers = [4, 8, 15, 16, 23, 42];

// Explizite Typschreibweise: [Typ; Anzahl]
let numbers: [i32; 6] = [4, 8, 15, 16, 23, 42];

Wichtig: Wenn du den Typ [i32; 6] (6 Elemente) angibst, musst du auch exakt 6 Elemente in die eckigen Klammern schreiben. Sonst streikt der Compiler!

Nützliche Funktionen und Sonderfälle

  • Länge abfragen: Mit .len() findest du heraus, wie viele Elemente im Array sind.
let length = numbers.len(); // Ergibt 6
  • Leere Arrays: Ein komplett leeres Array [] erlaubt Rust nur, wenn du den Typ und die Länge 0 ausdrücklich dazuschreibst, da der Compiler sonst nicht weiß, was später hineinsoll:
let empty_array: [f64; 0] = []; // Gültig

Array-Elemente aufrufen und ändern

Das Zählen beginnt bei 0 (Index)

Menschen zählen ab 1, Programmiersprachen ab 0. Die Position eines Elements nennt man Index.

  • Erstes Element = Index 0
  • Zweites Element = Index 1
  • Der letzte Index ist immer: Länge minus 1

Werte ändern (Überschreiben)

Ein normales Array hat eine feste Größe (du kannst keine neuen Elemente hinzufügen oder löschen). Wenn du das Array mit mut veränderbar machst, kannst du aber bestehende Werte überschreiben:

let mut seasons = ["Frühling", "Sommer", "Fall", "Winter"];
seasons[2] = "Herbst"; // Ersetzt "Fall" durch "Herbst"

Das Wichtigste auf einen Blick

  • Index startet bei 0: array[0] ist das erste Element.
  • Feste Größe: Elemente können weder gelöscht noch hinzugefügt werden.
  • Verändern: Nur erlaubt, wenn das Array mit let mut deklariert wurde.
  • Vorschau: Wenn du ein Array brauchst, das wachsen oder schrumpfen kann, nutzt man in Rust später einen sogenannten Vektor (Vec<T>).

Das Tupel: Der flexible Mix-Container

Ein Tupel ist (genau wie ein Array) ein zusammengesetzter Datentyp, der mehrere Werte in einer festen Reihenfolge speichert.

Der riesige Unterschied zum Array: Ein Tupel darf verschiedene Datentypen mischen! Du kannst darin gleichzeitig Text, ganze Zahlen und Wahrheitswerte speichern. Es eignet sich perfekt, um zusammengehörige Daten (wie die Informationen zu einer Person) zu bündeln.

1. Ein Tupel erstellen

Ein Tupel wird mit normalen, runden Klammern () geschrieben:

// Ein Tupel mit: Text (Name), Zahl (Alter), Text (Abteilung)
let employee = ("Molly", 32, "Marketing");

2. Zugriff auf die Werte (Die Punkt-Notation)

Genau wie beim Array startet der Index bei 0. Um an die Werte zu kommen, nutzt man beim Tupel jedoch einen Punkt . statt eckiger Klammern:

let name = employee.0;       // "Molly"
let age = employee.1;        // 32
let department = employee.2; // "Marketing"

3. Der Profi-Trick: Destrukturieren (Musterabgleich)

Weil das manuelle Auslesen über .0, .1 mühsam ist, gibt es in Rust eine geniale Abkürzung. Du kannst das Tupel in einer einzigen Zeile komplett in einzelne Variablen zerlegen:

// Rust entpackt das Tupel automatisch von links nach rechts!
let (name, age, department) = employee;

// Jetzt kannst du die Variablen direkt nutzen:
println!("Name: {}, Alter: {}", name, age);

Spickzettel: Tupel in Rust

💡 Das Wichtigste auf einen Blick

  • Typen-Mix: Erlaubt unterschiedliche Datentypen (z. B. i32, bool, &str) in einem Container.
  • Runde Klammern: Erstellt mit (wert1, wert2).
  • Auslesen mit Punkt: Zugriff erfolgt über .0, .1, .2 etc.
  • Feste Größe: Nach der Erstellung können keine Elemente hinzugefügt oder gelöscht werden.
  • Anzeigen/Debuggen: Ein Tupel kann nicht normal mit {} gedruckt werden. Nutze dafür den Debug-Modus {:?} oder {:#?}.
fn main() {
    // 1. Tupel erstellen
    let person = ("Alex", 28, true); // (Text, Zahl, Bool-Wert)

    // 2. Einzeln auslesen (Punkt-Syntax)
    let alter = person.1; // 28

    // 3. Komplett entpacken (Destrukturieren)
    let (name, age, ist_aktiv) = person;

    // 4. Per Debug-Modus das ganze Tupel auf einmal anzeigen
    println!("{:?}", person); // Gibt aus: ("Alex", 28, true)
}

Zusammenfassung: Variablen & Datentypen in Rust

Dieses Kapitel bietet einen kompakten Überblick über die Grundlagen von Variablen und Datentypen in Rust.

1. Variablen und Veränderlichkeit (Mutability)

Standardmäßig sind Variablen in Rust unveränderlich (immutable). Das sorgt für maximale Sicherheit.

  • Unveränderlich (Standard): 
    let x = 5;
// x = 6; // ✘ FEHLER: Zuweisung an unveränderliche Variable nicht erlaubt!
  • Veränderlich machen mit mut: 
    let mut x = 5;
x = 6; // ✔ Erlaubt!

2. Konstanten (Constants)

Konstanten werden mit const definiert. Sie sind immer unveränderlich (kein mut erlaubt) und der Datentyp muss zwingend angegeben werden. Sie werden zur Kompilierzeit berechnet.

const DREI_STUNDEN_IN_SEKUNDEN: u32 = 60 * 60 * 3;

3. Shadowing (Überschatten)

In Rust kannst du eine Variable neu deklarieren und dabei denselben Namen wiederverwenden. Die neue Variable überschattet die alte.

  • Vorteil: Du kannst den Typ der Variable ändern, ohne einen neuen Namen erfinden zu müssen.
let x = 5;
let x = x + 1; // x ist jetzt 6

let spaces = "   "; // Typ: &str
let spaces = spaces.len(); // Typ: usize (Länge: 3)

4. Datentypen in Rust

Rust ist statisch typisiert. Der Compiler muss jeden Typ vor dem Start kennen (oft per Typinferenz automatisch ermittelt).

A. Skalare Datentypen (Einzeilige Werte)

  1. Ganzzahlen (Integers):
    • Mit Vorzeichen (Signed): i8, i16, i32, i64, i128, isize
    • Ohne Vorzeichen (Unsigned): u8, u16, u32, u64, u128, usize
    • Standard: i32
  2. Fließkommazahlen (Floats):
    • f32 (einfache Genauigkeit) und f64 (doppelte Genauigkeit)
    • Standard: f64
  3. Wahrheitswerte (Booleans):
    • bool (kann nur true oder false sein)
  4. Zeichen (Characters):
    • char (4 Bytes, Unicode für Emojis und Sonderzeichen, in einfachen Anführungszeichen: 'z')

B. Zusammengesetzte Datentypen (Compound Types)

  1. Das Tupel (Tuple):
    • Feste Länge, erlaubt unterschiedliche Datentypen.
    • Zugriff über Punkt-Notation (.0) oder Entpacken (Destrukturierung).
    • Leeres Tupel () wird Unit genannt (stellt leere Rückgabewerte dar).
    let tup: (i32, f64, u8) = (500, 6.4, 1);
let (x, y, z) = tup; // Destrukturieren
let fuenfhundert = tup.0; // Direktzugriff
  2. Das Array:
    • Feste Länge, alle Elemente müssen denselben Datentyp haben (homogen).
    • Zugriff über eckige Klammern (a[0]).
    • Bietet eingebaute Laufzeit-Sicherheitsprüfungen (Verhindert ungültigen Speicherzugriff durch sofortigen Abbruch/Panic).
    let a: [i32; 5] = [1, 2, 3, 4, 5];
let first = a[0];

💡 Merkzettel: Variablen & Datentypen

  • Standard: Variablen sind unveränderlich. Nutze mut für Veränderbarkeit.
  • Konstanten (const): Immer unveränderlich, Typangabe Pflicht, Großbuchstaben als Konvention.
  • Shadowing: Wiederverwendung desselben Variablennamens mit let. Typänderungen sind dabei erlaubt.
  • Zahlen: Standard für Ganzzahlen ist i32, für Fließkommazahlen f64.
  • Tupel vs. Array:
    • Tupel (): Verschiedene Typen erlaubt, Zugriff mit .index (z. B. .0).
    • Array []: Nur derselbe Typ erlaubt, Zugriff mit [index] (z. B. [0]).
  • Sicherheit: Rust bricht bei ungültigen Array-Zugriffen sofort ab (Panic), um Speicherfehler zu verhindern.

Nächste Lektion ist Funktion

Funktionen in Rust

Eine Funktion ist ein wiederverwendbarer Code-Block, der eine bestimmte Aufgabe erledigt. Du definierst sie einmal und kannst sie beliebig oft aufrufen. Das spart doppelten Code und hält dein Programm sauber.

1. Die main-Funktion und eigene Funktionen

Jedes Rust-Programm startet in der main-Funktion. Eigene Funktionen werden mit dem Schlüsselwort fn definiert.

  • Reihenfolge: Es ist egal, ob deine eigenen Funktionen vor oder nach der main-Funktion stehen. Rust findet sie überall in derselben Datei.
  • Definition vs. Aufruf: Das bloße Aufschreiben einer Funktion tut noch nichts. Erst wenn du sie mit () aufrufst, wird sie ausgeführt.
fn main() {
    gruss_schreiben(); // Aufruf der Funktion
}

fn gruss_schreiben() {
    println!("Hallo Welt!");
}

2. Parameter und Argumente (Eingaben)

Um Funktionen flexibel zu machen, kannst du ihnen Werte übergeben:

  • Parameter: Der Platzhalter in der Funktionsdefinition (z. B. name: &str). In Rust musst du für jeden Parameter einen Datentyp angeben.
  • Argument: Der tatsächliche Wert, den du beim Aufruf übergibst (z. B. "Anna").
  • Strikte Kontrolle: Der Compiler prüft genau, ob die Anzahl und die Typen der Argumente exakt mit den Parametern übereinstimmen.
fn main() {
    alter_anzeigen("Anna", 25); // Argumente
}

fn alter_anzeigen(name: &str, alter: i32) { // Parameter mit Typen
    println!("{} ist {} Jahre alt.", name, alter);
}

3. Rückgabewerte (Ausgaben)

Eine Funktion kann ein Ergebnis an den Aufrufer zurückgeben.

  1. Der Rückgabetyp (->): Wird mit einem Pfeil hinter den Klammern definiert.
  2. Die Rückgabe: In Rust gibt es zwei Wege, einen Wert zurückzugeben:
    • Mit return: Das Schlüsselwort return gibt den Wert zurück und beendet die Funktion sofort. Jede Codezeile danach ist unerreichbar.
    • Als Ausdruck (Expression): Wenn du die letzte Zeile einer Funktion ohne return und ohne Semikolon ; schreibst, wird dieser Wert automatisch zurückgegeben. Dies ist der typische Rust-Stil!
// Weg A: Mit return
fn addieren_a(a: i32, b: i32) -> i32 {
    return a + b;
}

// Weg B: Implizite Rückgabe (typischer Rust-Stil: kein return, kein Semikolon!)
fn addieren_b(a: i32, b: i32) -> i32 {
    a + b
}

💡 Merkzettel: Alles über Funktionen in Rust

  • Grundsyntax: 
    fn name(parameter: Typ) -> RueckgabeTyp {
    // Code
    ergebnis // ohne Semikolon für automatische Rückgabe
}
  • Namenskonvention: Funktionsnamen werden immer in snake_case geschrieben (z. B. berechne_preis).
  • Typzwang: Jeder Parameter braucht zwingend einen Typ (name: Typ). Der Rückgabetyp wird mit -> Typ definiert (fehlt der Pfeil, gibt die Funktion nichts zurück).
  • Return-Verhalten:
    • return wert; beendet die Funktion sofort.
    • Ein Ausdruck am Ende ohne Semikolon (wert) ist der implizite Rückgabewert (Standard in Rust).
  • Compiler-Sicherheit: Falsche Argument-Typen oder eine falsche Anzahl an Argumenten führen zu einem Kompilierfehler (rote Wellenlinie).

Die nächste Lektion wird Funktionen behandeln.

Funktionen

Funktionen sind im Rust-Code allgegenwärtig. Du hast bereits eine der wichtigsten Funktionen der Sprache kennengelernt: die main-Funktion, die den Einstiegspunkt vieler Programme darstellt. Du hast auch das Schlüsselwort fn gesehen, mit dem du neue Funktionen deklarieren kannst.

Rust-Code verwendet snake_case als Konvention für Funktions- und Variablennamen. Dabei sind alle Buchstaben klein und Wörter werden durch Unterstriche getrennt. Hier ist ein Programm, das eine beispielhafte Funktionsdefinition enthält:

Dateiname: src/main.rs

fn main() {
    println!("Hallo Welt!");

    andere_funktion();
}

fn andere_funktion() {
    println!("Eine andere Funktion.");
}

Wir definieren eine Funktion in Rust, indem wir fn gefolgt von einem Funktionsnamen und einer Reihe von runden Klammern eingeben. Die geschweiften Klammern teilen dem Compiler mit, wo der Funktionskörper beginnt und endet.

Wir können jede von uns definierte Funktion aufrufen, indem wir ihren Namen gefolgt von einer Reihe von runden Klammern eingeben. Da andere_funktion im Programm definiert ist, kann sie innerhalb der main-Funktion aufgerufen werden. Beachte, dass wir andere_funktion nach der main-Funktion im Quellcode definiert haben; wir hätten sie auch davor definieren können. Rust ist es egal, wo du deine Funktionen definierst, solange sie irgendwo in einem Bereich (Scope) definiert sind, der für den Aufrufer sichtbar ist.

Lass uns ein neues Binärprojekt namens functions erstellen, um Funktionen weiter zu erforschen. Platziere das Beispiel mit andere_funktion in src/main.rs und führe es aus. Du solltest die folgende Ausgabe sehen:

$ cargo run
   Compiling functions v0.1.0 (file:///projects/functions)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.28s
     Running `target/debug/functions`
Hallo Welt!
Eine andere Funktion.

Die Zeilen werden in der Reihenfolge ausgeführt, in der sie in der main-Funktion erscheinen. Zuerst wird die Nachricht „Hallo Welt!“ ausgegeben, und dann wird andere_funktion aufgerufen und deren Nachricht ausgegeben.

Parameter

Wir können Funktionen so definieren, dass sie Parameter haben. Dies sind spezielle Variablen, die Teil der Funktionssignatur sind. Wenn eine Funktion Parameter hat, kannst du ihr konkrete Werte für diese Parameter übergeben. Technisch gesehen heißen diese konkreten Werte Argumente, aber im alltäglichen Sprachgebrauch neigen Entwickler dazu, die Wörter Parameter und Argument synonym zu verwenden – sowohl für die Variablen in der Funktionsdefinition als auch für die konkreten Werte, die beim Aufruf übergeben werden.

In dieser Version von andere_funktion fügen wir einen Parameter hinzu:

Dateiname: src/main.rs

fn main() {
    andere_funktion(5);
}

fn andere_funktion(x: i32) {
    println!("Der Wert von x ist: {x}");
}

Führe dieses Programm aus; du solltest die folgende Ausgabe erhalten:

$ cargo run
   Compiling functions v0.1.0 (file:///projects/functions)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 1.21s
     Running `target/debug/functions`
Der Wert von x ist: 5

Die Deklaration von andere_funktion hat einen Parameter namens x. Der Typ von x ist als i32 angegeben. Wenn wir 5 an andere_funktion übergeben, setzt das println!-Makro die 5 an die Stelle der geschweiften Klammern mit x im Formatstring.

In Funktionssignaturen musst du den Typ jedes Parameters deklarieren. Dies ist eine bewusste Entscheidung im Design von Rust: Das Vorschreiben von Typannotationen in Funktionsdefinitionen bedeutet, dass der Compiler diese fast nie an anderer Stelle im Code benötigt, um herauszufinden, welchen Typ du meinst. Der Compiler ist außerdem in der Lage, hilfreichere Fehlermeldungen auszugeben, wenn er weiß, welche Typen die Funktion erwartet.

Wenn du mehrere Parameter definierst, trenne die Parameterdeklarationen durch Kommata, wie hier:

Dateiname: src/main.rs

fn main() {
    print_labeled_measurement(5, 'h');
}

fn print_labeled_measurement(value: i32, unit_label: char) {
    println!("Die Messung ist: {value}{unit_label}");
}

Dieses Beispiel erstellt eine Funktion namens print_labeled_measurement mit zwei Parametern. Der erste Parameter heißt value und ist vom Typ i32. Der zweite heißt unit_label und ist vom Typ char. Die Funktion gibt dann Text aus, der sowohl den value als auch das unit_label enthält.

Lass uns versuchen, diesen Code auszuführen. Ersetze das aktuelle Programm in der Datei src/main.rs deines functions-Projekts mit dem obigen Beispiel und führe es mit cargo run aus:

    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.31s
     Running `target/debug/functions`
Die Messung ist: 5h

Da wir die Funktion mit 5 als Wert for value und 'h' als Wert für unit_label aufgerufen haben, enthält die Programmausgabe diese Werte.

Anweisungen und Ausdrücke (Statements and Expressions)

Funktionskörper bestehen aus einer Reihe von Anweisungen (Statements), die optional mit einem Ausdruck (Expression) enden. Bisher enthielten die behandelten Funktionen keinen abschließenden Ausdruck, aber du hast einen Ausdruck als Teil einer Anweisung gesehen. Da Rust eine ausdrucksbasierte Sprache ist, ist dies eine wichtige Unterscheidung, die man verstehen muss. Andere Sprachen haben diese Unterscheidung nicht in derselben Weise. Lass uns also ansehen, was Anweisungen und Ausdrücke sind und wie sich ihre Unterschiede auf den Funktionskörper auswirken.

  • Anweisungen (Statements) sind Anweisungen, die eine Aktion ausführen und keinen Wert zurückgeben.
  • Ausdrücke (Expressions) werten zu einem Ergebniswert aus.

Lass uns einige Beispiele ansehen.

Wir haben tatsächlich bereits Anweisungen und Ausdrücke verwendet. Das Erstellen einer Variable und das Zuweisen eines Werts mit dem Schlüsselwort let ist eine Anweisung. In Codeblock 3-1 ist let y = 6; eine Anweisung.

Dateiname: src/main.rs

fn main() {
    let y = 6;
}

Codeblock 3-1: Eine main-Funktionsdeklaration, die eine Anweisung enthält

Auch Funktionsdefinitionen sind Anweisungen; das gesamte vorherige Beispiel ist an sich eine Anweisung. (Wie wir gleich sehen werden, ist der Aufruf einer Funktion jedoch keine Anweisung.)

Anweisungen geben keine Werte zurück. Daher kannst du eine let-Anweisung nicht einer anderen Variable zuweisen, wie es der folgende Code versucht; du erhältst einen Fehler:

Dateiname: src/main.rs

Dieser Code kompiliert nicht!

fn main() {
    let x = (let y = 6);
}

Wenn du dieses Programm ausführst, sieht der Fehler so aus:

Die Anweisung let y = 6 gibt keinen Wert zurück, daher gibt es nichts, woran x gebunden werden könnte. Dies unterscheidet sich von dem Verhalten in anderen Sprachen wie C und Ruby, in denen eine Zuweisung den Wert der Zuweisung zurückgibt. In diesen Sprachen kannst du x = y = 6 schreiben, sodass sowohl x als auch y den Wert 6 haben. In Rust ist das nicht der Fall.

Ausdrücke werten zu einem Wert aus und machen den größten Teil des restlichen Codes aus, den du in Rust schreiben wirst. Betrachte eine mathematische Operation wie 5 + 6, was ein Ausdruck ist, der zum Wert 11 auswertet. Ausdrücke können Teil von Anweisungen sein: In Codeblock 3-1 ist die 6 in der Anweisung let y = 6; ein Ausdruck, der zum Wert 6 auswertet. Der Aufruf einer Funktion ist ein Ausdruck. Der Aufruf eines Makros ist ein Ausdruck. Ein neuer Scope-Block, der mit geschweiften Klammern erstellt wird, ist ein Ausdruck, zum Beispiel:

Dateiname: src/main.rs

fn main() {
    let y = {
        let x = 3;
        x + 1
    };

    println!("Der Wert von y ist: {y}");
}

Dieser Ausdruck:

{
    let x = 3;
    x + 1
}

ist ein Block, der in diesem Fall zu 4 auswertet. Dieser Wert wird dann als Teil der let-Anweisung an y gebunden. Beachte die Zeile x + 1 ohne ein Semikolon am Ende, was sich von den meisten Zeilen unterscheidet, die du bisher gesehen hast. Ausdrücke enthalten kein abschließendes Semikolon. Wenn du am Ende eines Ausdrucks ein Semikolon hinzufügst, machst du daraus eine Anweisung, und sie gibt dann keinen Wert zurück. Behalte dies im Hinterkopf, wenn wir uns als Nächstes mit Funktionsrückgabewerten und Ausdrücken befassen.

Funktionen mit Rückgabewerten

Funktionen können Werte an den aufrufenden Code zurückgeben. Wir benennen Rückgabewerte nicht, aber wir müssen ihren Typ nach einem Pfeil (->) deklarieren. In Rust ist der Rückgabewert einer Funktion gleichbedeutend mit dem Wert des letzten Ausdrucks im Block des Funktionskörpers. Du kannst eine Funktion vorzeitig verlassen, indem du das Schlüsselwort return verwendest und einen Wert angibst, aber die meisten Funktionen geben den letzten Ausdruck implizit zurück. Hier ist ein Beispiel für eine Funktion, die einen Wert zurückgibt:

Dateiname: src/main.rs

fn five() -> i32 {
    5
}

fn main() {
    let x = five();

    println!("Der Wert von x ist: {x}");
}

In der Funktion five gibt es keine Funktionsaufrufe, Makros oder gar let-Anweisungen – nur die Zahl 5 für sich allein. Das ist eine vollkommen gültige Funktion in Rust. Beachte, dass auch der Rückgabetyp der Funktion als -> i32 angegeben ist. Versuche, diesen Code auszuführen; die Ausgabe sollte so aussehen:

$ cargo run
   Compiling functions v0.1.0 (file:///projects/functions)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.30s
     Running `target/debug/functions`
Der Wert von x ist: 5

Die 5 in five ist der Rückgabewert der Funktion, weshalb der Rückgabetyp i32 ist. Lass uns dies genauer untersuchen. Es gibt zwei wichtige Teile: Erstens zeigt die Zeile let x = five();, dass wir den Rückgabewert einer Funktion verwenden, um eine Variable zu initialisieren. Da die Funktion five eine 5 zurückgibt, ist diese Zeile dasselbe wie die folgende:

let x = 5;

Zweitens hat die Funktion five keine Parameter und definiert den Typ des Rückgabewerts, aber der Körper der Funktion ist eine einsame 5 ohne Semikolon, da es sich um einen Ausdruck handelt, dessen Wert wir zurückgeben wollen.

Lass uns ein weiteres Beispiel ansehen:

Dateiname: src/main.rs

fn main() {
    let x = plus_one(5);

    println!("Der Wert von x ist: {x}");
}

fn plus_one(x: i32) -> i32 {
    x + 1
}

Das Ausführen dieses Codes gibt Der Wert von x ist: 6 aus. Aber was passiert, wenn wir ein Semikolon am Ende der Zeile mit x + 1 setzen und sie damit von einem Ausdruck in eine Anweisung verwandeln?

Dateiname: src/main.rs

Dieser Code kompiliert nicht!

fn main() {
    let x = plus_one(5);

    println!("Der Wert von x ist: {x}");
}

fn plus_one(x: i32) -> i32 {
    x + 1;
}

Operatoren in Rust

In Rust sind Operatoren Symbole, die dem Compiler mitteilen, eine bestimmte mathematische, logische oder speicherbezogene Operation durchzuführen. Da Rust großen Wert auf Sicherheit und Effizienz legt, verhalten sich manche Operatoren etwas anders als in Sprachen wie C, C++ oder Java.

In diesem Kapitel schauen wir uns alle wichtigen Operatoren im Detail an. Zu jeder Gruppe findest du verständliche Erklärungen, Codebeispiele und eine genaue Beschreibung davon, was im Hintergrund passiert.

1. Arithmetische Operatoren

Arithmetische Operatoren werden für grundlegende mathematische Berechnungen verwendet.

OperatorBedeutungBeispiel
+Additionx + y
-Subtraktionx - y
*Multiplikationx * y
/Divisionx / y
%Modulo (Restwert)x % y

Beispielcode

Dateiname: src/main.rs

fn main() {
    let a = 10;
    let b = 3;

    // Ganzzahl-Operationen
    let summe = a + b;
    let differenz = a - b;
    let produkt = a * b;
    let quotient = a / b; // Ganzzahldivision schneidet den Rest ab!
    let rest = a % b;      // Modulo liefert den Rest der Division

    println!("Summe: {summe}");         // Ausgabe: 13
    println!("Differenz: {differenz}"); // Ausgabe: 7
    println!("Produkt: {produkt}");     // Ausgabe: 30
    println!("Quotient: {quotient}");   // Ausgabe: 3
    println!("Rest: {rest}");           // Ausgabe: 1

    // Fließkomma-Division für exakte Ergebnisse
    let x = 10.0;
    let y = 3.0;
    let exakter_quotient = x / y;
    println!("Exakter Quotient: {exakter_quotient}"); // Ausgabe: 3.3333333333333335
}

Was passiert hier?

  1. Ganzzahldivision (a / b): Da a und b vom Typ Ganzzahl (standardmäßig i32) sind, führt Rust eine Ganzzahldivision durch. Das Ergebnis ist 3, der Nachkommateil (0.333...) wird komplett abgeschnitten (Trunkierung).
  2. Modulo (a % b): Gibt den verbleibenden Rest zurück. Da 10 geteilt durch 3 gleich 3 Rest 1 ist, ist rest gleich 1.
  3. Fließkomma-Division: Um Nachkommastellen zu erhalten, müssen die Operanden Fließkommazahlen (z. B. f64) sein. Rust verlangt hier strikte Typübereinstimmung; du kannst keine Ganzzahl direkt durch eine Fließkommazahl teilen, ohne sie vorher umzuwandeln (dazu später mehr bei as).
  4. Überlauf-Schutz (Overflow): In Rust führt ein arithmetischer Überlauf (z.B. wenn eine u8-Variable den Wert 255 überschreitet) im Debug-Modus (cargo run) zu einem Programmabsturz (Panic). Im Release-Modus (cargo run --release) hingegen "wickelt" sich der Wert ohne Absturz um (Modulo-Arithmetik auf Hardwareebene).

2. Vergleichsoperatoren

Vergleichsoperatoren vergleichen zwei Werte und geben immer einen booleschen Wert (true oder false) zurück.

OperatorBedeutungBeispiel
==Gleichheitx == y
!=Ungleichheitx != y
<Kleiner alsx < y
>Größer alsx > y
<=Kleiner oder gleichx <= y
>=Größer oder gleichx >= y

Beispielcode

Dateiname: src/main.rs

fn main() {
    let alter = 18;
    let mindestalter = 18;

    let ist_volljaehrig = alter >= mindestalter;
    let ist_identisch = alter == mindestalter;
    let ist_ungleich = alter != 20;

    println!("Ist volljährig? {ist_volljaehrig}"); // Ausgabe: true
    println!("Ist identisch? {ist_identisch}");   // Ausgabe: true
    println!("Ist ungleich 20? {ist_ungleich}");  // Ausgabe: true
}

Was passiert hier?

  • Rust wertet die Ausdrücke von links nach rechts aus. alter >= mindestalter prüft, ob alter entweder größer oder genau gleich mindestalter ist. Da 18 >= 18 wahr ist, wird der Variable ist_volljaehrig der Wert true zugewiesen.
  • Rust erlaubt Vergleiche nur zwischen Variablen des exakt gleichen Typs. Ein Vergleich von einem i32 mit einem u8 oder einer Fließkommazahl führt zu einem Compilerfehler.

3. Logische Operatoren

Logische Operatoren verbinden boolesche Ausdrücke. Sie werden meist in if-Bedingungen und Schleifen eingesetzt.

OperatorBedeutungBeispiel
&&Logisches UND (beide müssen wahr sein)cond1 && cond2
``
!Logisches NICHT (Invertierung)!cond

Beispielcode

Dateiname: src/main.rs

fn main() {
    let hat_ticket = true;
    let hat_ausweis = false;
    let ist_mitarbeiter = true;

    // Logisches UND (&&)
    let darf_rein_standard = hat_ticket && hat_ausweis;

    // Logisches ODER (||)
    let darf_rein_vip = darf_rein_standard || ist_mitarbeiter;

    // Logisches NICHT (!)
    let zutritt_verweigert = !darf_rein_vip;

    println!("Standard-Zutritt: {darf_rein_standard}"); // Ausgabe: false
    println!("VIP/Mitarbeiter-Zutritt: {darf_rein_vip}"); // Ausgabe: true
    println!("Zutritt verweigert? {zutritt_verweigert}");  // Ausgabe: false
}

Was passiert hier?

  1. Short-Circuit-Evaluierung (Kurzschluss-Auswertung): Rust wertet logische Operatoren effizient aus.
    • Bei && (UND): Wenn die linke Seite false ist, kann das Gesamtergebnis niemals true werden. Rust spart sich daher die Auswertung der rechten Seite.
    • Bei || (ODER): Wenn die linke Seite true ist, steht das Gesamtergebnis (true) bereits fest. Rust wertet die rechte Seite nicht mehr aus.
  2. Invertierung (!): Dreht den Wahrheitswert um. Aus true wird false, aus false wird true.

4. Bitweise Operatoren

Bitweise Operatoren arbeiten direkt auf der binären Repräsentation (Bits 0 und 1) von Ganzzahlen.

OperatorBedeutungBeispiel
&Bitweises UND (AND)a & b
``Bitweises ODER (OR)
^Bitweises XOR (Exklusiv-Oder)a ^ b
!Bitweises NICHT (Komplement / Invertierung)!a
<<Links-Shift (Bits nach links verschieben)a << 1
>>Rechts-Shift (Bits nach rechts verschieben)a >> 1

Beispielcode

Dateiname: src/main.rs

fn main() {
    // Binär: 0b1100 (Dezimal: 12)
    let a: u8 = 0b1100;
    // Binär: 0b1010 (Dezimal: 10)
    let b: u8 = 0b1010;

    println!("a & b: {:04b} (Dezimal: {})", a & b, a & b); // UND: 0b1000 (8)
    println!("a | b: {:04b} (Dezimal: {})", a | b, a | b); // ODER: 0b1110 (14)
    println!("a ^ b: {:04b} (Dezimal: {})", a ^ b, a ^ b); // XOR: 0b0110 (6)
    println!("!a:    {:08b} (Dezimal: {})", !a, !a);       // NICHT: 0b11110011 (243)

    // Bit-Shifts
    println!("a << 1: {:04b} (Dezimal: {})", a << 1, a << 1); // Links-Shift: 0b11000 (24)
    println!("a >> 1: {:04b} (Dezimal: {})", a >> 1, a >> 1); // Rechts-Shift: 0b0110 (6)
}

Was passiert hier?

  • Bitweises UND (&): Vergleicht die Bits an jeder Position. Nur wenn beide Bits 1 sind, ist das Ergebnis-Bit 1 (z. B. 1100 & 1010 = 1000).
  • Bitweises ODER (|): Das Ergebnis-Bit ist 1, wenn mindestens eines der beiden Bits 1 ist (z. B. 1100 | 1010 = 1110).
  • Bitweises XOR (^): Das Ergebnis-Bit ist 1, wenn die Bits unterschiedlich sind (z. B. 1100 ^ 1010 = 0110).
  • Bitweises NICHT (!): Invertiert jedes einzelne Bit einer Zahl (aus 0 wird 1, aus 1 wird 0).
  • Links-Shift (<<): Verschiebt alle Bits nach links. Die leeren Stellen rechts werden mit 0 aufgefüllt. Mathematisch entspricht a << 1 einer Multiplikation mit 2 (aus 12 wird 24).
  • Rechts-Shift (>>): Verschiebt alle Bits nach rechts. Mathematisch entspricht a >> 1 einer Ganzzahldivision durch 2 (aus 12 wird 6).

5. Zuweisungsoperatoren

Der grundlegende Zuweisungsoperator ist =. Rust bietet zudem Abkürzungen für mathematische und bitweise Operationen kombiniert mit einer Zuweisung (Compound Assignments).

OperatorBedeutungEntspricht
=Zuweisungx = y
+=Addition & Zuweisungx = x + y
-=Subtraktion & Zuweisungx = x - y
*=Multiplikation & Zuweisungx = x * y
/=Division & Zuweisungx = x / y
%=Modulo & Zuweisungx = x % y
&=, `=, ^=`Bitweise Operation & Zuweisung
<<=, >>=Shift & Zuweisungx = x << y usw.

Beispielcode

Dateiname: src/main.rs

fn main() {
    let mut x = 5; // Muss als 'mut' deklariert werden!

    x += 10; // Gleichbedeutend mit: x = x + 10;
    println!("x nach += : {x}"); // Ausgabe: 15

    x *= 2; // Gleichbedeutend mit: x = x * 2;
    println!("x nach *= : {x}"); // Ausgabe: 30
}

Was passiert hier?

  • Der Compound-Zuweisungsoperator liest den aktuellen Wert der Variablen aus, führt die Operation mit dem rechten Operanden aus und schreibt das Ergebnis wieder in die Variable zurück.
  • Wichtig: Dies erfordert immer, dass die Variable mit dem Schlüsselwort mut (veränderlich) deklariert wurde.
  • Wichtiger Unterschied zu C/C++/Java: In Rust gibt es keine Inkrement- (++) oder Dekrement-Operatoren (--). Du musst stattdessen immer x += 1 oder x -= 1 schreiben. Dies verhindert Mehrdeutigkeiten bei der Auswertungsreihenfolge im Code.

6. Referenz- und Pointer-Operatoren

Rust hat ein einzigartiges Speichersicherheitskonzept (Ownership und Borrowing). Daher spielen Referenzoperatoren eine zentrale Rolle.

OperatorBedeutungBeispiel
&Erstellt eine unveränderliche Referenz (Leihen/Borrowing)let r = &x;
&mutErstellt eine veränderliche Referenzlet r = &mut x;
*Dereferenzierung (Zugriff auf den Wert hinter der Referenz)let y = *r;

Beispielcode

Dateiname: src/main.rs

fn main() {
    let mut zahl = 42;

    // 1. Unveränderliche Referenz (&) erstellen
    let ref1 = &zahl;
    println!("Wert über ref1 gelesen: {ref1}"); // Ausgabe: 42 (Rust dereferenziert hier automatisch)
    
    // 2. Dereferenzierung (*) zum Lesen
    let kopie = *ref1; // Kopiert den Wert 42 aus der Speicherstelle, auf die ref1 zeigt
    println!("Kopie: {kopie}"); // Ausgabe: 42

    // 3. Veränderliche Referenz (&mut) erstellen
    // Hinweis: Wir dürfen ref1 nicht mehr benutzen, da zeitgleich keine unveränderlichen 
    // und veränderlichen Referenzen existieren dürfen.
    let ref_mut = &mut zahl;

    // 4. Dereferenzierung (*) zum Schreiben
    *ref_mut += 8; // Ändert den Wert in der originalen Speicherstelle von 'zahl'
    
    println!("Zahl nach Änderung: {zahl}"); // Ausgabe: 50
}

Was passiert hier?

  1. &zahl: Erstellt einen Zeiger (eine Referenz), der auf die Speicheradresse zeigt, in der zahl liegt. Das ist eine "Leihgabe". Die Referenz ref1 besitzt die Daten nicht, darf sie aber lesen.
  2. *ref1: Der Dereferenzierungs-Operator * folgt dem Zeiger zur tatsächlichen Speicheradresse und greift auf den dort liegenden Wert (42) zu.
  3. &mut zahl: Erstellt eine veränderliche Referenz. Dies erlaubt uns, den Wert an der Speicheradresse direkt zu modifizieren.
  4. *ref_mut += 8: Wir greifen über * auf den eigentlichen Wert der Speicherstelle zu und addieren 8. Der Originalwert von zahl ändert sich dadurch von 42 auf 50.

7. Typumwandlung und Fehlerbehandlung (Spezialoperatoren)

Diese Operatoren sind spezifische Rust-Besonderheiten für die Typkonvertierung und das Fehlermanagement.

OperatorBedeutungBeispiel
asTypumwandlung (Type Casting)x as f64
?Fehler-Propagierung (Fehlerweiterleitung)funktion()?

Beispielcode für as (Typumwandlung)

Dateiname: src/main.rs

fn main() {
    let ganzzahl: i32 = 100;
    let komma: f64 = 5.5;

    // let ergebnis = ganzzahl + komma; // FEHLER! Rust erlaubt keine implizite Typkonvertierung.
    
    // Explizite Konvertierung mit 'as'
    let ergebnis = (ganzzahl as f64) + komma;
    println!("Ergebnis: {ergebnis}"); // Ausgabe: 105.5
}

Beispielcode für ? (Fehler-Propagierung)

Dateiname: src/main.rs

use std::fs::File;
use std::io::{self, Read};

fn lese_datei_inhalt() -> Result<String, io::Error> {
    // Der ?-Operator versucht die Datei zu öffnen. 
    // Wenn erfolgreich, wird das File-Objekt entpackt.
    // Wenn ein Fehler auftritt (z.B. Datei nicht vorhanden), bricht die 
    // Funktion sofort ab und gibt den Fehler als Rückgabewert zurück.
    let mut datei = File::open("info.txt")?;
    
    let mut inhalt = String::new();
    // Auch hier: Wenn read_to_string fehlschlägt, wird der Fehler sofort zurückgegeben.
    datei.read_to_string(&mut inhalt)?;
    
    Ok(inhalt) // Erfolgsfall
}

fn main() {
    match lese_datei_inhalt() {
        Ok(text) => println!("Dateiinhalt: {text}"),
        Err(e) => println!("Fehler aufgetreten: {e}"),
    }
}

Was passiert hier?

  • as: Rust führt im Gegensatz zu vielen anderen Sprachen niemals automatische (implizite) Typumwandlungen bei Berechnungen durch. Mit ganzzahl as f64 teilen wir dem Compiler explizit mit, dass wir den Wert der Ganzzahl im Fließkommaformat interpretieren möchten, damit die Addition durchgeführt werden kann.
  • ?: Dieser Operator wird an Ausdrücke angehängt, die ein Result (oder Option) zurückgeben. Er verkürzt den Code massiv:
    • Wenn das Ergebnis Ok(wert) ist, entpackt der Operator den wert und das Programm läuft in derselben Zeile weiter.
    • Wenn das Ergebnis Err(fehler) ist, entspricht das Verhalten einem vorzeitigen return Err(fehler) aus der aktuellen Funktion. Daher kann ? nur in Funktionen verwendet werden, deren Rückgabetyp mit dem zurückgegebenen Fehlertyp kompatibel ist.

8. Range-Operatoren (Bereiche)

Range-Operatoren erzeugen Sequenzen von Werten. Sie werden primär in for-Schleifen und beim Slicing (Zugriff auf Teilbereiche von Arrays/Vektoren) verwendet.

OperatorBedeutungBereich
..Exklusiver Bereichstart..ende (ohne ende)
..=Inklusiver Bereichstart..=ende (inklusive ende)

Beispielcode

Dateiname: src/main.rs

fn main() {
    println!("Exklusive Range (1..5):");
    // Schleife läuft für: 1, 2, 3, 4 (5 ist exkludiert)
    for i in 1..5 {
        print!("{i} ");
    }
    println!();

    println!("Inklusive Range (1..=5):");
    // Schleife läuft für: 1, 2, 3, 4, 5 (5 ist inkludiert)
    for i in 1..=5 {
        print!("{i} ");
    }
    println!();

    // Verwendung beim Slicing
    let array = [10, 20, 30, 40, 50];
    let slice = &array[1..4]; // Holt die Elemente an Index 1, 2 und 3
    println!("Slice: {:?}", slice); // Ausgabe: [20, 30, 40]
}

Was passiert hier?

  • 1..5: Erstellt einen Iterator, der bei 1 beginnt und stoppt, sobald der Wert 5 erreicht wird, bevor dieser Wert ausgegeben wird. Daher werden nur 1, 2, 3 und 4 durchlaufen.
  • 1..=5: Verhält sich analog, schließt jedoch die obere Grenze 5 mit ein.
  • Slicing (&array[1..4]): Wir nutzen die Range als Index-Auswahl. Das Slice enthält die Elemente ab Index 1 (inklusive) bis Index 4 (exklusive) – also die Indizes 1, 2 und 3 des Arrays.

Kapitel 13: Übungen zu Operatoren und Typumwandlung

In diesem Kapitel vertiefen wir das Gelernte über Operatoren und Typkonvertierungen in Rust anhand von fünf praktischen Übungen. Zu jeder Übung findest du eine genaue Erklärung der Problemstellung, die zugrundeliegende Theorie, eine ausführliche Schritt-für-Schritt-Erklärung der Lösung sowie den vollständigen Code.

Übung 1: Grundrechenarten (Der Klassiker)

Ziel: Die Anwendung grundlegender arithmetischer Operatoren (+, -, *, /, %) bei der Arbeit mit Ganzzahlen verstehen und deren Ausgaben formatieren.

1. Problemstellung und Erklärung

Du sollst zwei ganzzahlige Variablen a (Wert: 15) und b (Wert: 4) deklarieren. Berechne anschließend:

  • Die Summe (Addition)
  • Die Differenz (Subtraktion)
  • Das Produkt (Multiplikation)
  • Den Quotienten (Division)
  • Den Modulo-Rest (Restwert der Division)

2. Was passiert im Hintergrund?

Wenn Rust Operationen auf Ganzzahlen (standardmäßig i32) ausführt, verarbeitet die CPU diese direkt auf Hardwareebene.

  • Bei der Division / von zwei Ganzzahlen wird das Ergebnis automatisch abgeschnitten (Trunkierung). Aus 15 / 4 wird also 3 und nicht 3.75.
  • Der Modulo-Operator % gibt den Rest an, der bei dieser Ganzzahldivision übrig bleibt: 15 geteilt durch 4 ergibt 3 mit einem Rest von 3 (da 3 * 4 = 12 und 15 - 12 = 3).

3. Lösungscode

Dateiname: src/main.rs

fn main() {
    let a = 15;
    let b = 4;

    // Addition
    let summe = a + b;
    println!("Summe: {}", summe); // Ausgabe: 19

    // Subtraktion
    let differenz = a - b;
    println!("Differenz: {}", differenz); // Ausgabe: 11

    // Multiplikation
    let produkt = a * b;
    println!("Produkt: {}", produkt); // Ausgabe: 60

    // Ganzzahl-Division (Rest wird abgeschnitten)
    let quotient = a / b;
    println!("Quotient: {}", quotient); // Ausgabe: 3

    // Modulo (Restwert der Division)
    let rest = a % b;
    println!("Rest der Division (Modulo): {}", rest); // Ausgabe: 3
}

4. Detaillierte Beschreibung

  1. let a = 15; und let b = 4; reservieren Speicherplatz auf dem Stack für zwei vorzeichenbehaftete 32-Bit-Ganzzahlen (i32).
  2. let summe = a + b; addiert die Binärwerte von a und b und speichert das Ergebnis 19 in der neuen Variable summe.
  3. let quotient = a / b; führt die Division durch. Da beide Operanden Ganzzahlen sind, wird das Ergebnis 3.75 zur Ganzzahl 3 abgerundet.
  4. let rest = a % b; berechnet den Restwert. Das ist besonders nützlich, um beispielsweise zu prüfen, ob eine Zahl gerade oder ungerade ist (z.B. zahl % 2 == 0).

Übung 2: Die Ganzzahl-Falle bei der Division

Ziel: Verstehen, warum Ganzzahldivisionen Nachkommastellen abschneiden und wie man durch explizites Type-Casting mit as ein exaktes mathematisches Ergebnis erzielt.

1. Problemstellung und Erklärung

Gegeben sind die Variablen let x = 7; und let y = 2;. Wenn du versuchst, x / y zu rechnen, erhältst du das Ergebnis 3 statt 3.5. Modifiziere den Code so, dass die Division ein mathematisch exaktes Ergebnis liefert.

2. Was passiert im Hintergrund?

Da x und y als Ganzzahlen deklariert sind, führt der Compiler eine Ganzzahldivision aus. In Rust gibt es keine implizite (automatische) Typkonvertierung. Der Compiler wandelt Ganzzahlen nicht heimlich in Fließkommazahlen um. Um Nachkommastellen zu berechnen, müssen beide Operanden denselben Fließkommatyp (z. B. f64) besitzen. Wir müssen die Ganzzahlen manuell mit dem Operator as in f64 umwandeln (Casting).

3. Lösungscode

Dateiname: src/main.rs

fn main() {
    let x = 7;
    let y = 2;

    // Führt zur Ganzzahldivision
    let ergebnis_ganzzahl = x / y;
    println!("Ganzzahliges Ergebnis: {}", ergebnis_ganzzahl); // Ausgabe: 3

    // Lösung: Konvertierung in Gleitkommazahlen (f64)
    let x_float = x as f64;
    let y_float = y as f64;

    let ergebnis_exakt = x_float / y_float;
    println!("Exaktes Ergebnis: {}", ergebnis_exakt); // Ausgabe: 3.5
}

4. Detaillierte Beschreibung

  1. x as f64 konvertiert den ganzzahligen Wert 7 in den Fließkommawert 7.0.
  2. y as f64 konvertiert den ganzzahligen Wert 2 in den Fließkommawert 2.0.
  3. Der Division-Operator / sieht nun zwei Fließkommazahlen (f64) und führt eine Gleitkommadivision durch. Das Ergebnis 3.5 wird in ergebnis_exakt gespeichert.
  4. Ohne diese explizite Typumwandlung würde der Versuch, einen Ganzzahl-Typ durch einen Fließkomma-Typ zu teilen (z. B. x / y_float), zu einem Compilerfehler führen. Rust verlangt strikte Typübereinstimmung.

Übung 3: Typen mischen und explizite Typumwandlung

Ziel: Das Verhalten von Rust bei inkompatiblen Typen verstehen, Fehler gezielt beheben und die Konsequenzen von Datenverlust beim Abrunden (Casting von Float zu Integer) analysieren.

1. Problemstellung und Erklärung

Erstelle ein Programm mit let integer_wert: i32 = 10; und let float_wert: f64 = 3.14;.

  1. Zeige, dass die direkte Addition der beiden Variablen zu einem Compilerfehler führt.
  2. Löse den Fehler, indem du integer_wert in ein f64 konvertierst und addierst.
  3. Konvertiere umgekehrt float_wert in ein i32 und beschreibe den Effekt auf den Wert.

2. Was passiert im Hintergrund?

Der Rust-Compiler weigert sich, unterschiedliche Datentypen miteinander zu verrechnen, um Programmierfehler wie ungenaue Rundungen zu verhindern.

  • Das Konvertieren von einer Ganzzahl zu einer Fließkommazahl (i32 as f64) ist verlustfrei, da der Wertebereich vergrößert wird.
  • Das Konvertieren von einer Fließkommazahl zu einer Ganzzahl (f64 as i32) führt zu Datenverlust, da alle Nachkommastellen einfach abgeschnitten werden (aus 3.14 wird 3).

3. Lösungscode

Dateiname: src/main.rs

fn main() {
    let integer_wert: i32 = 10;
    let float_wert: f64 = 3.14;

    // 1. Dieser Code würde nicht kompilieren:
    // let fehler = integer_wert + float_wert; 

    // 2. Korrekte Addition (Verlustfreie Konvertierung von i32 zu f64)
    let summe = (integer_wert as f64) + float_wert;
    println!("Korrekt berechnete Summe: {}", summe); // Ausgabe: 13.14

    // 3. Konvertierung mit Datenverlust (f64 zu i32)
    let float_als_integer = float_wert as i32;
    println!("Fließkommazahl als Ganzzahl: {}", float_als_integer); // Ausgabe: 3
}

4. Detaillierte Beschreibung

  1. Der auskommentierte Code integer_wert + float_wert wirft den Compilerfehler E0308: mismatched types. Rust verlangt, dass beide Seiten der Addition denselben Typ haben.
  2. Mit integer_wert as f64 erstellen wir eine temporäre 64-Bit-Fließkommazahl mit dem Wert 10.0. Diese wird mit 3.14 addiert.
  3. Bei float_wert as i32 wird der Wert 3.14 in eine Ganzzahl umgewandelt. Rust schneidet dabei die .14 ab. Das Ergebnis ist 3. Es findet keine mathematische Rundung auf den nächsten Ganzzahlwert statt, sondern ein striktes Abschneiden.

Übung 4: Potenzierung und Wurzelziehen

Ziel: Nutzen von mathematischen Methoden der Standardbibliothek auf Fließkommazahlen (f64), um Potenzen und Wurzeln zu berechnen.

1. Problemstellung und Erklärung

Erstelle ein Programm, das:

  • Eine Basis base (Wert: 2.0 als f64) mit einem Exponenten exp (Wert: 3.0 als f64) potenziert (also $2^3 = 8$).
  • Die Quadratwurzel ($\sqrt{x}$) einer Zahl wurzel_zahl (Wert: 16.0) berechnet.

2. Was passiert im Hintergrund?

Da Potenzierung und Wurzelziehen komplexere Gleitkommaoperationen sind, stellt Rust hierfür Methoden auf dem Typ f64 bereit.

  • .powf(exponet) berechnet eine Zahl hoch eine andere Fließkommazahl.
  • .powi(exponent) berechnet eine Zahl hoch eine Ganzzahl (i32). Das ist oft schneller und effizienter, da es intern als wiederholte Multiplikation optimiert wird.
  • .sqrt() berechnet die Quadratwurzel der Gleitkommazahl unter Verwendung optimierter CPU-Befehle.

3. Lösungscode

Dateiname: src/main.rs

fn main() {
    let base: f64 = 2.0;
    let exp: f64 = 3.0;

    // Potenzierung (2.0 hoch 3.0)
    let ergebnis_potenz = base.powf(exp);
    println!("{} hoch {} = {}", base, exp, ergebnis_potenz); // Ausgabe: 2 hoch 3 = 8

    // Wurzelziehen (Quadratwurzel aus 16.0)
    let wurzel_zahl: f64 = 16.0;
    let ergebnis_wurzel = wurzel_zahl.sqrt();
    println!("Quadratwurzel von {} = {}", wurzel_zahl, ergebnis_wurzel); // Ausgabe: 4
}

4. Detaillierte Beschreibung

  1. base.powf(exp) ruft die Methode powf auf dem Objekt base auf. Sie nimmt als Argument den Exponenten exp entgegen. Da beide f64 sind, ist das Ergebnis ebenfalls ein f64.
  2. Hätten wir einen ganzzahligen Exponenten (z. B. 3), könnten wir stattdessen base.powi(3) aufrufen. Das spart Rechenzeit und benötigt weniger CPU-Ressourcen.
  3. wurzel_zahl.sqrt() berechnet die Quadratwurzel. Falls der Wert negativ wäre (z.B. -16.0), würde Rust das Ergebnis NaN (Not a Number) zurückgeben, da Quadratwurzeln aus negativen Zahlen im reellen Zahlenraum nicht definiert sind.

Übung 5: Praktisches Beispiel – Zinseszinsrechnung

Ziel: Die Kombination von arithmetischen Operatoren, Typumwandlung und Potenzierung zur Lösung eines praxisnahen finanzmathematischen Problems.

1. Problemstellung und Erklärung

Wir wollen den Endbetrag einer Zinseszins-Investition berechnen. Verwende folgende Vorgaben:

  • Startkapital (initial_capital): 1000.0 (als f64)
  • Jährlicher Zinssatz (annual_rate): 0.05 (entspricht 5% Zinsen, als f64)
  • Laufzeit in Jahren (years): 10 (als u32)

Die Formel zur Zinseszinsberechnung lautet: $$\text{Endbetrag} = \text{Startkapital} \times (1 + \text{Zinssatz})^{\text{Jahre}}$$

2. Was passiert im Hintergrund?

In dieser realen Anwendung müssen wir alle mathematischen Operationen kombinieren.

  • Zuerst addieren wir 1.0 zum Zinssatz (1.0 + annual_rate = 1.05).
  • Danach müssen wir dieses Ergebnis mit der Anzahl der Jahre potenzieren. Da years vom Typ u32 ist, die Methode powf aber ein f64 verlangt, müssen wir years as f64 konvertieren.
  • Zum Schluss multiplizieren wir das Ergebnis mit dem Startkapital.

3. Lösungscode

Dateiname: src/main.rs

fn main() {
    let initial_capital: f64 = 1000.0;
    let annual_rate: f64 = 0.05;
    let years: u32 = 10;

    // Zinseszinsberechnung
    // Zuerst 'years' von u32 in f64 umwandeln, da powf() f64 erwartet.
    let final_amount = initial_capital * (1.0 + annual_rate).powf(years as f64);

    // Ausgabe mit Formatierung auf zwei Nachkommastellen
    println!("Startkapital: {:.2} €", initial_capital);
    println!("Jährlicher Zinssatz: {:.2} %", annual_rate * 100.0);
    println!("Laufzeit: {} Jahre", years);
    println!("Endbetrag nach {} Jahren Zinseszins: {:.2} €", years, final_amount);
}

4. Detaillierte Beschreibung

  1. Die Laufzeit years ist als u32 typisiert (da Jahre immer positive Ganzzahlen sind). Die Potenzfunktion .powf() erwartet jedoch einen f64-Parameter. Wir casten daher years as f64.
  2. (1.0 + annual_rate) ergibt 1.05.
  3. 1.05.powf(10.0) berechnet $1.05^{10} \approx 1.628894$.
  4. Das Ergebnis wird mit dem Startkapital 1000.0 multipliziert, was zu 1628.8946 führt.
  5. In println! nutzen wir die Formatierungsoption {:.2}, um den Fließkommawert auf genau zwei Nachkommastellen gerundet auszugeben. Aus 1628.8946 wird in der Ausgabe 1628.89 €.

Kapitel 14: Das Antigravity CLI – Arbeiten mit KI-Agenten & Subagenten

Stell dir vor, du hättest einen virtuellen Co-Entwickler direkt in deiner Konsole sitzen, der auf Knopfdruck Dateien erstellt, Code schreibt und Fehler sucht. Genau das ist das Antigravity CLI (aufrufbar über den Befehl agy).

6. Leitplanken setzen: AGENTS.md & SKILLS.md

Damit der Agent nicht unkontrolliert Dateien in deinem Projekt ändert, kannst du ihm über zwei einfache Textdateien in deinem Projektordner feste Regeln und Fähigkeiten vorgeben.

Diese Datei legst du direkt im Hauptverzeichnis deines Projekts ab. Der Agent liest sie bei jedem Start automatisch.

  • Zweck: Du sagst dem Agenten, wie er Code formatieren soll, wo er schreiben darf und welche Verzeichnisbereiche für ihn tabu sind.

7. Subagenten: Arbeit im Team delegieren

Manche Aufgaben sind zu groß oder riskant für einen einzelnen Agenten. Deshalb kann der Hauptagent im Hintergrund Subagenten (Unter-Agenten) starten und ihnen Teilaufgaben übertragen.

7.1 Die 3 Workspace-Modi (Wo arbeitet der Subagent?)

Damit ein Subagent nicht versehentlich deinen Code überschreibt, während er etwas testet, gibt es drei Modi für seine Arbeitsumgebung:

  1. inherit (Vererben/Teilen):
    • Wie es funktioniert: Der Subagent arbeitet im selben Ordner wie du und der Hauptagent.
    • Ideal für: Schnelle Suchen oder kleine Dateiänderungen.
  2. branch (Kopie erstellen):
    • Wie es funktioniert: Es wird eine komplette, isolierte Kopie deines Projektordners erstellt.
    • Ideal für: Riskante Experimente. Der Subagent kann dort Code ändern und kompilieren, ohne dass deine Arbeitsdateien verändert werden.
  3. share (Geteiltes Arbeiten):
    • Wie es funktioniert: Ähnlich wie ein git worktree. Der Subagent arbeitet auf einem anderen Zweig (Branch) deines Git-Projekts im selben Speicherplatz.
    • Ideal für: Paralleles Arbeiten an verschiedenen Features ohne Datenmüll oder lange Kopierzeiten.

7.2 Regeln für Subagenten in AGENTS.md definieren

Du kannst in deiner AGENTS.md festlegen, was Subagenten dürfen. Hier ist ein konkretes Beispiel:

## Regeln für Subagenten (Subagent Policies)
- Alle Subagenten müssen standardmäßig im sicheren Modus 'branch' gestartet werden.
- Subagenten vom Typ 'Linter' dürfen Dateien nur LESEN, nicht schreiben.
- Subagenten vom Typ 'Refactoring' dürfen nur im Ordner '/src/helpers' schreiben.
- Die Ausführung von externen Netzwerkbefehlen (z. B. wget) ist für Subagenten deaktiviert.

Kapitel 15: Kontrollstrukturen – Bedingungen, Musterabgleich und Schleifen

Im echten Leben treffen wir ständig Entscheidungen: „Wenn es regnet, nehme ich einen Regenschirm, andernfalls gehe ich ohne.“ Oder wir wiederholen eine Tätigkeit: „Solange der Teller nicht leer ist, esse ich weiter.“

In der Programmierung nennen wir diese Mechanismen Kontrollstrukturen. Sie steuern den Ablauf deines Programms und sorgen dafür, dass dein Code auf unterschiedliche Situationen reagieren kann.

In diesem Kapitel gehen wir ganz genau ins Detail und schauen uns an, wie Rust Entscheidungen und Wiederholungen handhabt. Rust hat hier einige Besonderheiten und Sicherheitsgarantien, die sich von anderen Sprachen unterscheiden.

1. Warum brauchen wir Kontrollstrukturen? (Einsatzgebiete)

Ohne Kontrollstrukturen würde ein Computerprogramm stur Zeile für Zeile von oben nach unten ausführen. Es gäbe keine Interaktivität. In der Praxis nutzen wir Kontrollstrukturen für folgende typische Aufgaben:

Einsatzgebiete für Entscheidungen (if / else und match)

  • Benutzereingaben prüfen: Ist das eingegebene Passwort lang genug? Wenn ja, logge den Nutzer ein. Wenn nein, zeige eine Fehlermeldung (if-else).
  • Sicherheitsprüfungen: Hat der aktuelle Benutzer Admin-Rechte? Nur dann darf der sensible Lösch-Button gedrückt werden (if).
  • Zustandsmaschinen (Status-Steuerung): In einem Spiel befindet sich die Spielfigur im Zustand Laufen, Springen oder Fallen. Je nach Zustand werden andere Animationen abgespielt (match).
  • API-Antworten verarbeiten: Ein Webserver antwortet mit verschiedenen Statuscodes (z. B. 200 OK, 404 Not Found, 500 Server Error). Je nach Code reagiert das Programm anders (match).

Einsatzgebiete für Schleifen (loop, while und for)

  • Spiele-Schleifen (Game Loops): Jedes Computerspiel läuft in einer Endlosschleife. Sie liest die Tasten ein, berechnet die Physik und zeichnet das Bild auf den Monitor – und das 60-mal oder öfter pro Sekunde (loop).
  • Dienste im Hintergrund (Server): Ein Webserver muss permanent im Hintergrund laufen und auf Anfragen warten. Er darf sich niemals von alleine beenden (loop).
  • Dateien einlesen: Wenn du eine große Textdatei Zeile für Zeile ausliest, nutzt du eine Schleife, die so lange läuft, wie noch Text in der Datei übrig ist (while).
  • Datenverarbeitung (Listen & Tabellen): Du möchtest alle Preise in einem Warenkorb zusammenrechnen oder die Namen aller Schüler einer Klasse alphabetisch sortieren (for).

2. Ausdrücke (Expressions) vs. Anweisungen (Statements)

Um Rusts Kontrollstrukturen zu verstehen, müssen wir einen kurzen Blick auf den Unterschied zwischen Ausdrücken und Anweisungen werfen:

  1. Anweisungen (Statements): Sie führen eine Aktion aus, geben aber keinen Wert zurück. Sie enden in Rust fast immer mit einem Semikolon ;.
    • Beispiel: let x = 5; (weist einen Wert zu, gibt aber selbst nichts zurück).
  2. Ausdrücke (Expressions): Sie berechnen ein Ergebnis und geben einen Wert zurück. Sie haben kein Semikolon am Ende.
    • Beispiel: 5 + 5 (wertet sich zu 10 aus).

In Rust sind fast alle Kontrollstrukturen (wie if oder loop) Ausdrücke. Das bedeutet, sie liefern uns einen Wert zurück, den wir direkt verwenden können.

3. Entscheidungen mit if und else

Eine Bedingung prüft, ob eine Aussage wahr (true) oder falsch (false) ist.

3.1 Die Grundsyntax

fn main() {
    let alter = 18;

    if alter >= 18 {
        println!("Du bist volljährig!");
    } else {
        println!("Du bist noch minderjährig.");
    }
}
  • Keine Klammern: Du brauchst in Rust keine runden Klammern () um die Bedingung zu schreiben (also if alter >= 18 statt if (alter >= 18)).
  • Strikte Typen: Die Bedingung muss ein echter Wahrheitswert (bool) sein. Rust konvertiert Zahlen oder Texte nicht automatisch in Wahrheitswerte (es gibt kein „truthy“ oder „falsy“).

3.2 if als Ausdruck verwenden

Da if ein Ausdruck ist, kannst du das Ergebnis direkt einer Variablen zuweisen:

fn main() {
    let bedingung = true;

    // Weist 'nummer' den Wert 5 oder 6 zu
    let nummer = if bedingung { 5 } else { 6 };

    println!("Der Wert ist: {}", nummer); // Gibt 5 aus
}

[!IMPORTANT] Wenn du if als Ausdruck nutzt, müssen der if- und der else-Zweig den gleichen Datentyp zurückgeben! Ein Code wie let x = if bedingung { 5 } else { "Fehler" }; führt zu einem Kompilierfehler.

4. Musterabgleich mit match (Die Superkraft von Rust)

Wenn du viele verschiedene Fälle prüfen musst, werden if-else-Ketten schnell unübersichtlich. Rust bietet dafür eine der mächtigsten Kontrollstrukturen überhaupt: match (Musterabgleich).

Man kann sich match wie eine hochentwickelte Version des switch-Befehls aus anderen Sprachen vorstellen.

4.1 Grundlegender Aufbau von match

fn main() {
    let rolle = "Admin";

    match rolle {
        "Admin" => println!("Vollzugriff auf alle Systeme."),
        "Moderator" => println!("Beiträge bearbeiten und löschen."),
        "Nutzer" => println!("Beiträge lesen und schreiben."),
        _ => println!("Keine Rechte vorhanden."), // Der Auffang-Fall (Default)
    }
}
  • Der Zweig-Aufbau: Jeder Fall (Zweig) besteht aus einem Muster (z. B. "Admin"), gefolgt von dem Pfeil => und der auszuführenden Aktion. Die einzelnen Zweige werden durch Kommas getrennt.
  • Der Platzhalter _: Dies ist der „Auffang-Fall“ (ähnlich wie default in anderen Sprachen). Er fängt alle Werte ab, die nicht explizit darüber aufgelistet sind.

4.2 Die wichtigste Regel: Vollständigkeit (Exhaustiveness)

Der Rust-Compiler zwingt dich dazu, jeden einzelnen möglichen Fall abzudecken! Wenn du einen vergisst, kompiliert dein Programm nicht.

Ein Beispiel mit Zahlen:

fn main() {
    let wuerfel = 3;

    match wuerfel {
        1 => println!("Eins gewürfelt!"),
        2 => println!("Zwei gewürfelt!"),
        3 => println!("Drei gewürfelt!"),
        // Hier würde der Compiler meckern, weil 4, 5, 6 etc. fehlen.
        _ => println!("Andere Zahl gewürfelt!"), // Löst das Problem
    }
}

5. Schleifen – Code wiederholen

Schleifen wiederholen Code. Rust bietet drei Arten: loop, while und for.

5.1 loop und Schleifen-Labels (Loop Labels)

loop läuft unendlich lange weiter, bis wir break aufrufen.

Eine Besonderheit in Rust ist, dass wir Schleifen benennen können (Labels). Das ist extrem nützlich, wenn du Schleifen ineinander verschachtelst und die äußere Schleife aus der inneren Schleife heraus abbrechen willst:

fn main() {
    let mut x = 0;

    // Wir geben der äußeren Schleife den Namen 'aeusserer_kreis
    'aeusserer_kreis: loop {
        println!("Äußere Schleife startet");
        let mut y = 0;

        loop {
            println!("   Innere Schleife: x={}, y={}", x, y);
            if y == 2 {
                break; // Beendet nur die innere Schleife
            }
            if x == 2 {
                break 'aeusserer_kreis; // Beendet die äußere Schleife!
            }
            y += 1;
        }
        x += 1;
    }
    println!("Beide Schleifen beendet!");
}

Hinweis: Schleifen-Labels beginnen immer mit einem einfachen Anführungszeichen (z. B. 'name:).

5.2 while – Schleife mit Bedingung

Eine while-Schleife läuft so lange, wie eine Bedingung wahr (true) ist.

fn main() {
    let mut countdown = 3;

    while countdown > 0 {
        println!("{}...", countdown);
        countdown -= 1;
    }
    println!("Start!");
}

5.3 for – Iterieren über Sammlungen (Ranges & Iteratoren)

Die for-Schleife ist die sicherste und am häufigsten genutzte Schleife in Rust.

A) Über Bereiche laufen (Ranges)

  • 1..4 läuft von 1 bis 3 (die 4 ist exklusive).
  • 1..=4 läuft von 1 bis 4 (die 4 ist inklusive).
fn main() {
    // Gibt 1, 2, 3 aus
    for i in 1..4 {
        println!("i: {}", i);
    }
}

B) Über ein Array laufen mit .iter()

Um sicherzustellen, dass wir nicht außerhalb des Arrays zugreifen (Indexfehler), benutzen wir for in Kombination mit .iter():

fn main() {
    let zahlen = [10, 20, 30];

    for zahl in zahlen.iter() {
        println!("Wert: {}", zahl);
    }
}

Kapitel 17: Speicherverwaltung und das Ownership-System in Rust

Jedes laufende Programm benötigt Arbeitsspeicher (RAM), um temporäre Daten zu speichern. Da dieser Speicher begrenzt ist, muss er nach der Nutzung wieder freigegeben werden (Deallokation). Wie eine Programmiersprache diese Aufgabe bewältigt, unterscheidet sich fundamental. Rust nutzt hierfür ein einzigartiges Konzept namens Ownership (Eigentum).

1. Die drei Wege der Speicherverwaltung

Um zu verstehen, warum Rusts Ansatz so revolutionär ist, vergleichen wir ihn mit anderen bekannten Ansätzen:

Die drei goldenen Regeln des Ownerships

Das Ownership-System von Rust basiert auf drei einfachen, aber strikten Regeln:

  1. Jeder Wert in Rust hat einen Besitzer (meistens eine Variable).
  2. Es kann immer nur einen Besitzer gleichzeitig geben.
  3. Wenn der Besitzer den Gültigkeitsbereich (Scope) verlässt, wird der Wert automatisch gelöscht.

[!TIP] Die Haus-Analogie: Stell dir vor, du besitzt ein Haus. Du trägst die Verantwortung dafür. Du kannst das Haus an jemand anderen verkaufen (Besitzerwechsel/Move). Das Haus gehört jedoch niemals zwei Personen gleichzeitig auf dieselbe Weise. Wenn niemand mehr das Haus besitzt oder bewohnt, wird es sofort abgerissen (freigegeben), um Platz zu sparen.

Auch zusammengesetzte Datentypen wie Arrays oder Tupel funktionieren hierarchisch: Eine Variable besitzt das Array, und das Array wiederum besitzt die darin liegenden Werte.

2. Stack vs. Heap: Wo liegen deine Daten?

Wenn ein Rust-Programm läuft, nutzt es zwei verschiedene Bereiche im Arbeitsspeicher. Wo Daten abgelegt werden, entscheidet über die Geschwindigkeit und Flexibilität deines Programms.

1. Der Stack (Der Stapel)

  • Wie er funktioniert: Wie ein Stapel von Essenstabletts. Das neueste Element kommt oben drauf (Push), und das oberste Element wird als erstes heruntergenommen (Pop). Das Prinzip heißt LIFO (Last In, First Out).
  • Die Bedingung: Daten auf dem Stack müssen eine feste, dem Compiler im Voraus bekannte Größe haben (z. B. einfache Zahlen wie i32, Booleans oder fixierte Arrays).
  • Vorteil: Extrem schnell. Der Prozessor muss nicht nach freiem Speicher suchen, sondern greift einfach immer auf das oberste Element zu.

2. Der Heap (Der Haufen)

  • Wie er funktioniert: Wie ein riesiges Lagerhaus oder ein bewachter Parkplatz.
  • Die Bedingung: Für dynamische Daten, deren Größe sich zur Laufzeit verändern kann oder vorab unbekannt ist (z. B. Usereingaben, wachsende Listen).
  • Der Ablauf: Der Speicher-Manager (Allocator) sucht einen freien Platz auf dem Heap, legt die Daten dort ab und gibt eine Speicheradresse (Referenz/Zeiger) zurück.
  • Der Trick: Die eigentlichen Daten liegen auf dem Heap. Die kleine, feste Speicheradresse (der Zeiger) wird auf dem Stack abgelegt (wie ein Parkticket mit der Parkplatznummer).
  • Nachteil: Langsamer. Das Suchen nach freiem Speicherplatz beim Schreiben (Allokation) und das Verfolgen des Zeigers beim Lesen (Dereferenzierung) kosten Zeit.

Da Heap-Daten dynamisch groß sind, müssen sie exakt in dem Moment gelöscht werden, in dem ihre Stack-Variable (das "Parkticket") ungültig wird. So wird verhindert, dass der Heap mit Datenmüll vollgestellt wird.

3. Scopes, Blöcke und das automatische Löschen

In Rust steuern geschweifte Klammern { } die Lebensdauer von Variablen. Dieser Gültigkeitsbereich wird als Scope bezeichnet.

Verschachtelte Scopes

Sobald der Programmcode die schließende Klammer } erreicht, verlässt die Variable ihren Scope. In exakt diesem Moment wird ihr Wert automatisch aus dem Speicher gelöscht.

fn main() { // <-- Scope A startet
    let age = 33; // 'age' wird auf dem Stack angelegt

    { // <-- Scope B startet (innerer Block)
        let is_handsome = true; // 'is_handsome' wird auf dem Stack angelegt
        println!("Innerhalb: {}", is_handsome);
    } // <-- Scope B endet! 'is_handsome' wird SOFORT gelöscht!

    // println!("{}", is_handsome); // ❌ FEHLER! Variable existiert nicht mehr.
    println!("Außerhalb: {}", age); // ✅ Funktioniert, 'age' lebt noch.
} // <-- Scope A endet! 'age' wird gelöscht!

Die Lösch-Reihenfolge (LIFO)

Werden mehrere Variablen im selben Scope erstellt, räumt Rust sie am Ende in umgekehrter Reihenfolge ihrer Erstellung auf:

  1. Zuletzt erstellte Variable $\rightarrow$ wird als Erstes gelöscht.
  2. Zuerst erstellte Variable $\rightarrow$ wird als Letztes gelöscht.

4. Der Copy-Trait: Automatisches Duplizieren auf dem Stack

In Rust ist ein Trait wie eine Schnittstelle oder ein Vertrag: Er garantiert, dass ein Datentyp ein bestimmtes Verhalten beherrscht. Der Copy-Trait garantiert, dass ein Typ blitzschnell und automatisch im Speicher kopiert werden kann.

  • Wer hat ihn? Alle einfachen Datentypen mit fester Größe, die komplett auf dem Stack liegen (z. B. Zahlen wie i32, f64, sowie bool und char).
  • Was passiert bei einer Zuweisung? Wenn du den Wert einer Stack-Variablen einer neuen Variablen zuweist, wird der Wert im Speicher dupliziert. Beide Variablen sind danach unabhängig voneinander gültig.
fn main() {
    let time = 2026; // i32 liegt auf dem Stack
    let year = time; // Rust erstellt automatisch eine vollständige Kopie!

    // Beide Variablen sind unabhängig und voll funktionsfähig:
    println!("Time: {}, Year: {}", time, year); 
} // Am Ende werden beide Variablen unabhängig voneinander gelöscht.

Weil Stack-Daten winzig sind und eine feste Größe haben, kostet das Kopieren den Prozessor fast keinen Aufwand. Daher bleibt die ursprüngliche Variable time problemlos weiter nutzbar.

5. Die zwei String-Typen in Rust

Rust unterscheidet strikt zwischen Text, der fest im Programmcode eingebrannt ist, und Text, der zur Laufzeit dynamisch wachsen oder schrumpfen kann.

1. Das String-Literal: &str

  • Was es ist: Text direkt in doppelten Anführungszeichen: let pasta = "pasta";.
  • Wo er liegt: Weder auf dem Stack noch auf dem Heap. Er ist fest in die fertige ausführbare Programmdatei (Binärdatei) eingebettet.
  • Eigenschaft: Unveränderlich und starr. Du kannst nachträglich keine Zeichen anhängen oder ändern.

2. Der dynamische String: String

  • Was es ist: Ein flexibler, veränderbarer Text-Typ.
  • Wo er liegt: Die eigentlichen Textdaten liegen auf dem Heap, da ihre Größe flexibel ist.
  • Ownership: Die Variable auf dem Stack besitzt die Daten auf dem Heap. Verlässt die Variable ihren Scope, wird der Heap-Speicher automatisch freigegeben.

Wie erstellt man einen String auf dem Heap?

Es gibt zwei gängige Wege, um einen solchen String über den Namensraum String zu erstellen:

fn main() {
    // Weg 1: Erstellt einen komplett leeren String
    let mut text = String::new(); 
    
    // Weg 2: Wandelt ein starreres Literal (&str) in einen Heap-String um
    let candy = String::from("KitKat"); 
} // <-- Hier werden 'candy' und 'text' ungültig und ihr Heap-Speicher freigegeben!

[!NOTE] Die zwei Doppelpunkte :: bedeuten: "Suche im Namensraum von String nach der zugehörigen Funktion (new bzw. from)".

6. Strings verändern: Was passiert auf dem Heap?

Um einen String auf dem Heap zu manipulieren, muss die Variable mit mut als veränderbar deklariert werden. Mit der Methode push_str kannst du Text anhängen.

Das Innenleben eines Strings auf dem Stack

Auf dem Stack liegen für jeden Heap-String immer exakt drei Werte:

  1. Pointer (Verweis): Die Speicheradresse, an der der Text auf dem Heap beginnt.
  2. Len (Länge): Wie viele Bytes der Text aktuell verbraucht.
  3. Capacity (Kapazität): Wie viel Platz der Speicher-Manager auf dem Heap für diesen String insgesamt reserviert hat.

What happens during push_str?

fn main() {
    let mut name = String::from("Boris"); // Len: 5, Capacity: 5
    name.push_str(" Pasker");             // Text anhängen
}

Dabei entscheidet Rust im Hintergrund zwischen zwei Szenarien:

  • Szenario A (Genug Platz): Die neuen Zeichen passen in die vorhandene Capacity. Rust schreibt den Text einfach hinten an. Len erhöht sich, Pointer und Capacity bleiben gleich. (Sehr schnell).
  • Szenario B (Zu wenig Platz - Reallokation): Der Text überschreitet die Capacity. Rust sucht einen neuen, größeren Platz auf dem Heap, kopiert den alten Text dorthin, hängt den neuen Text an und gibt den alten Heap-Platz frei. Pointer, Len und Capacity auf dem Stack werden entsprechend aktualisiert.

7. Move-Semantik: Eigentumswechsel bei Heap-Daten

Wenn Daten einer neuen Variablen zugewiesen werden, unterscheidet Rust streng zwischen Stack und Heap:

  1. Stack-Daten (z. B. i32): Werden kopiert (Copy-Trait). Die Originalvariable bleibt gültig.
  2. Heap-Daten (z. B. String): Da das Kopieren von Heap-Daten teuer ist, kopiert Rust bei einer Zuweisung nur die drei Werte auf dem Stack (Pointer, Len, Capacity). Um zu verhindern, dass am Ende beide Variablen versuchen, denselben Heap-Speicher freizugeben (was zum fatalen Double-Free-Fehler führen würde), erklärt Rust die ursprüngliche Variable sofort für ungültig. Das Eigentum zieht um (Move).
fn main() {
    let person = String::from("Boris");
    let genius = person; // Eigentum zieht um (Move) von 'person' nach 'genius'

    // println!("{}", person); // ❌ COMPILER-FEHLER: 'person' ist nicht mehr gültig!
    println!("{}", genius);    // ✅ Erlaubt: 'genius' ist der neue Besitzer.
}

Visualisierung des Moves

VOR DEM MOVE:
person (Stack) ─────────► [ "Boris" ] (Heap)

NACH DEM MOVE:
person (Ungültig!)
genius (Stack) ─────────► [ "Boris" ] (Heap)

Durch diese Move-Semantik stellt Rust sicher, dass es immer genau einen aktiven Besitzer für jeden Speicher block auf dem Heap gibt.

8. Die Drop-Funktion: Automatisches und manuelles Löschen

1. Das automatische drop (Der Standard)

Sobald eine Variable ihren Scope verlässt (}), ruft Rust im Hintergrund automatisch die Funktion drop auf. Diese gibt den Heap-Speicher der Variable frei.

{
    let person = String::from("Boris"); // Heap-Speicher allokiert
} // <-- Scope-Ende! Rust ruft automatisch drop(person) auf. Der Heap-Speicher ist frei.

2. Das manuelle drop (Vorzeitiges Löschen)

Manchmal möchtest du Speicher oder Ressourcen (wie geöffnete Dateien) vor dem Ende eines Scopes freigeben. Hierzu kannst du die drop-Funktion manuell aufrufen:

fn main() {
    let person = String::from("Boris");

    drop(person); // Heap-Speicher wird SOFORT freigegeben.

    // Jede weitere Nutzung der Variable führt zu einem Compiler-Fehler:
    // println!("{}", person); // ❌ FEHLER!
}

9. Der .clone()-Befehl: Tiefe Kopien erzwingen

Wenn du Heap-Daten explizit duplizieren möchtest, anstatt sie zu verschieben (moven), musst du das mit der Methode .clone() tun. Dabei wird der gesamte Inhalt auf dem Heap dupliziert.

fn main() {
    let person = String::from("Boris");
    let genius = person.clone(); // Kopiert die tatsächlichen Daten auf dem Heap!

    println!("{}", person); // ✅ Erlaubt! 'person' behält ihr Eigentum.
    println!("{}", genius); // ✅ Erlaubt! 'genius' besitzt die neue Kopie.
}

[!TIP] Goldene Regel für Anfänger: Keine Angst vor .clone()! Es ist am Anfang völlig in Ordnung, .clone() zu nutzen, um den Compiler glücklich zu machen. Später lernst du mit Referenzen, wie du diese Kopien vermeidest. Hauptsache, dein Code läuft erst einmal!

10. Exkurs: Referenzen, der Dereferenzierungsoperator * und das Ausleihen

Um Daten nicht ständig klonen oder verschieben zu müssen, nutzt man Referenzen (&). Eine Referenz speichert lediglich die Speicheradresse eines Wertes (ein Verweis).

Der Dereferenzierungsoperator *

Der Dereferenzierungsoperator * ist das Gegenstück zur Referenz &. Er folgt der Adresse und holt den eigentlichen Wert hervor.

[!NOTE] Die Zettel-Analogie: Eine Referenz & ist wie ein Zettel, auf dem eine Hausadresse steht. Der Dereferenzierungsoperator * ist der Postbote, der physisch zu diesem Haus geht, um nachzusehen, wer dort wohnt.

fn main() {
    let wert = 2;
    let mein_verweis = &wert; // Referenz auf den Wert 2

    println!("{}", *mein_verweis); // ✅ Gibt 2 aus (folgt dem Zeiger)
}

Automatische Dereferenzierung

In der Praxis musst du das * selten schreiben. Rust dereferenziert Referenzen bei Operationen wie println! oder Methodenaufrufen oft automatisch im Hintergrund, da es weiß, dass du den eigentlichen Inhalt und nicht die Speicheradresse sehen möchtest.

Referenzen kopieren sich selbst

Da eine Referenz (&) nur eine kleine Adresse auf dem Stack ist, implementiert sie das Copy-Trait. Weist du eine Referenz einer neuen Variable zu, wird nur die Adresse kopiert, und das Eigentum der Daten bleibt unberührt.

fn main() {
    let ice_cream = "Cookies and Cream"; // Typ &str (eine Referenz)
    let dessert = ice_cream;             // Die Adresse wird kopiert

    // Beide Variablen zeigen auf denselben schreibgeschützten Text:
    println!("{}", ice_cream); 
    println!("{}", dessert);   
}

11. Die vier Text-Varianten im Vergleich (Deep Dive)

Für Anfänger ist die Unterscheidung der String-Typen oft verwirrend. Hier ist eine Übersicht der vier Varianten:

  1. String (Heap-String): Dynamischer, veränderbarer Text auf dem Heap. Besitzt die Daten.
  2. &String (Referenz auf Heap-String): Ein Zeiger auf einen String. Verhindert das Kopieren und den Move.
  3. str (Binär-Daten): Der rohe, unsortierte Text im Speicher. Da seine Größe vorab unbekannt ist, arbeitet man in Rust nie direkt damit.
  4. &str (String-Slice): Ein Zeiger auf einen schreibgeschützten Textbereich (z. B. auf Literale in der Binärdatei oder Ausschnitte eines String).

[!IMPORTANT] Entscheidungshilfe für die Praxis:

  • Sollen sich die Daten ändern? $\rightarrow$ Nutze String.
  • Sind es feste Texte im Code? $\rightarrow$ Nutze &str.
  • Als Funktionsparameter? $\rightarrow$ Nutze fast immer &str. Das macht deine Funktion maximal flexibel, da sie sowohl &str als auch Referenzen auf String (&String) akzeptieren kann.

12. Ownership bei Funktionen (Parameterübergabe)

Für Funktionen gelten dieselben Regeln wie bei Zuweisungen. Die Übergabe an eine Funktion verhält sich wie ein Eigentumsübergang.

Fall 1: Stack-Daten (i32, f64, bool) $\rightarrow$ Copy

Stack-Daten werden beim Funktionsaufruf automatisch kopiert. Die Originalvariable in main bleibt gültig.

fn print_integer(value: i32) {
    println!("Wert in Funktion: {}", value);
} // <-- 'value' verlässt den Scope und wird gelöscht.

fn main() {
    let apples = 6;
    print_integer(apples); // Übergibt eine Kopie von 'apples'
    println!("Äpfel in main: {}", apples); // ✅ Erlaubt!
}

Fall 2: Heap-Daten (String) $\rightarrow$ Move

Da Heap-Kopien teuer sind, wird das Eigentum an die Funktion übergeben. Die Originalvariable in main wird ungültig. Die Funktion "frisst" die Variable auf und löscht sie am Ende ihres Scopes.

fn print_string(value: String) {
    println!("Wert in Funktion: {}", value);
} // <-- 'value' verlässt den Scope. Heap-Speicher wird per 'drop' gelöscht!

fn main() {
    let oranges = String::from("Orangen");
    print_string(oranges); // Move! 'value' übernimmt das Eigentum.
    
    // println!("{}", oranges); // ❌ COMPILER-FEHLER: Daten wurden gelöscht!
}

13. Veränderbare Parameter in Funktionen (mut)

Parameter in Funktionen sind standardmäßig unveränderlich. Soll eine Funktion den übergebenen Wert verändern können, muss der Parameter mit mut markiert werden.

Dabei ist es egal, ob die Variable beim Aufrufer veränderlich war oder nicht. Durch den Move übernimmt die Funktion das alleinige Eigentum und bestimmt die Veränderbarkeit neu.

fn add_fries(mut meal: String) { // 'mut' erlaubt der Funktion, 'meal' zu verändern
    meal.push_str(" und Pommes");
    println!("Menü: {}", meal); // Ausgabe: "Burger und Pommes"
}

fn main() {
    let burger = String::from("Burger"); // Unveränderlich in main!
    add_fries(burger); // Move! 'meal' wird in der Funktion veränderbar.
}

14. Eigentum zurückgeben (Return)

Möchte die aufrufende Funktion den Wert nach dem Funktionsaufruf weiterverwenden, kann die aufgerufene Funktion das Eigentum per return (bzw. als Rückgabewert) wieder zurückgeben.

fn add_fries(mut meal: String) -> String {
    meal.push_str(" und Pommes");
    meal // Gibt das Eigentum am String zurück (kein Semikolon!)
}

fn main() {
    let burger = String::from("Burger");
    
    // burger zieht in die Funktion um; das Ergebnis wird in 'mein_menue' gespeichert:
    let mein_menue = add_fries(burger); 
    
    println!("{}", mein_menue); // ✅ Erlaubt: "Burger und Pommes"
    // println!("{}", burger);    // ❌ Verboten: 'burger' ist ungültig.
}

[!TIP] Variable überschreiben (Shadowing): Du kannst den zurückgegebenen Wert auch direkt wieder in der ursprünglichen Variable speichern, um den Namen wiederzuverwenden: let burger = add_fries(burger);

15. Das Problem mit dem "Eigentums-Ping-Pong"

Wenn du Daten ständig hin- und hergeben musst, um den Besitz nicht zu verlieren, führt das schnell zu unübersichtlichem Code.

fn add_flour(mut meal: String) -> String {
    meal.push_str("Mehl, ");
    meal
}

fn add_sugar(mut meal: String) -> String {
    meal.push_str("Zucker");
    meal
}

fn main() {
    let mut current_meal = String::new();
    
    // Umständliches Ping-Pong, um das Eigentum zu behalten:
    current_meal = add_flour(current_meal); 
    current_meal = add_sugar(current_meal); 
    
    println!("Rezept: {}", current_meal); // Ausgabe: "Mehl, Zucker"
}

Warum dieses Vorgehen nicht gut skalierbar ist:

  1. Blockade bei Lese-Funktionen: Selbst Funktionen, die Daten nur ausgeben (println!) und nicht verändern wollen, müssten die Daten zurückgeben, um sie nicht zu löschen.
  2. Mühsame Rückgaben: Müsste eine Funktion mehrere Strings verarbeiten, müsste sie am Ende alle Werte umständlich als Tupel (z. B. return (str1, str2, str3)) zurückgeben.

Im echten Leben gibst du dein Rezeptbuch auch nicht dauerhaft ab, wenn jemand ein Rezept lesen will – du leihst es ihm lediglich aus.

Genau dieses Problem löst Rust im nächsten Kapitel mit dem Konzept des Borrowings (Ausleihen) über Referenzen (&).

💡 Zusammenfassung

  • Ownership sorgt für speichersicheren Code zur Compile-Zeit, ohne Laufzeit-Overhead.
  • Stack speichert Daten mit fester Größe extrem schnell. Heap speichert dynamisch wachsende Daten über Zeiger (Pointer).
  • Move verschiebt das Eigentum an Heap-Daten bei Zuweisungen oder Funktionsaufrufen, um Double-Free-Fehler zu vermeiden.
  • Copy dupliziert Stack-Daten automatisch bei der Zuweisung.
  • .clone() erzwingt eine tiefe, manuelle Kopie von Heap-Daten.
  • Scopes { } begrenzen die Lebensdauer von Variablen. Beim Verlassen wird automatisch drop aufgerufen.

Kapitel 18: Das Ownership-System (Eigentum) im Detail

Das Ownership-System (Eigentum) ist das am meisten charakterisierende und einzigartigste Merkmal der Programmiersprache Rust. Es ermöglicht Rust-Programmen, absolute Speichersicherheit und maximale Ausführungsgeschwindigkeit (Zero-Cost Abstractions) zu garantieren, ohne auf ein Laufzeit-Hintergrundprogramm wie einen Garbage Collector angewiesen zu sein.

Dieses Kapitel befasst sich auf einer extrem tiefgehenden Ebene mit allen theoretischen und praktischen Aspekten des Ownership-Systems. Wir werden untersuchen, wie Rust den Arbeitsspeicher verwaltet, wie der Compiler den Code statisch analysiert, welche Konzepte der Hardware-Ebene (CPU-Register, Caches, Stack und Heap) eine Rolle spielen und wie du diese Regeln in realen Programmen anwendest.

1. Die historische Speicher-Krise in der Softwareentwicklung

Um zu verstehen, warum das Ownership-System von Rust eine der wichtigsten Innovationen in der Informatik der letzten Jahrzehnte darstellt, müssen wir uns die traditionellen Methoden der Speicherverwaltung und ihre schwerwiegenden Probleme ansehen.

Seit den Anfängen der Programmierung müssen Programme Arbeitsspeicher (RAM) vom Betriebssystem anfordern, um Daten während der Ausführung zu speichern. Wenn die Daten nicht mehr benötigt werden, muss dieser Speicher wieder freigegeben werden, um ihn dem Betriebssystem oder anderen Programmen zur Verfügung zu stellen. Historisch gesehen gibt es dafür zwei klassische Ansätze:

1.1 Die manuelle Speicherverwaltung (C, C++)

In Sprachen wie C oder C++ hat der Entwickler die absolute Kontrolle und Verantwortung über den Arbeitsspeicher.

  • Ablauf: Speicher wird explizit über Funktionen wie malloc() oder Operatoren wie new angefordert. Der Speicher-Manager sucht im Heap nach freiem Platz und gibt die Startadresse zurück. Nach der Nutzung muss der Speicher manuell über free() oder delete freigegeben werden.
  • Vorteile: Maximale Kontrolle, extrem geringer Overhead, keine unvorhersehbaren Pausen während der Programmausführung.
  • Nachteile (Die Speicher-Krise): Menschen machen Fehler. Das manuelle Speichermanagement führte zu den verheerendsten Sicherheitslücken und Systemabstürzen in der Geschichte der Softwareentwicklung:
    • Memory Leaks (Speicherlecks): Der Entwickler vergisst, den angeforderten Speicher freizugeben. Das Programm verbraucht im Laufe der Zeit immer mehr Arbeitsspeicher, bis das Betriebssystem den Prozess wegen Ressourcenmangel zwangsweise beendet (Out of Memory).
    • Double Free (Doppelte Freigabe): Der Entwickler versucht, denselben Speicherbereich zweimal freizugeben. Dies beschädigt die internen Datenstrukturen des Speicher-Managers und ermöglicht es Angreifern, Schadcode einzuschleusen (Heap Exploitation).
    • Dangling Pointers (Hängende Zeiger): Ein Speicherbereich wird freigegeben, aber ein Zeiger verweist weiterhin auf diese Adresse. Wird dieser Zeiger später wiederverwendet, greift das Programm auf undefinierte oder fremde Daten zu (Use-After-Free).
    • Buffer Overflows (Pufferüberläufe): Daten werden über die Grenzen eines zugewiesenen Speicherbereichs hinausgeschrieben, wodurch benachbarte Daten im Arbeitsspeicher überschrieben werden. Viele bekannte Sicherheitslücken wie Heartbleed gehen auf solche Fehler zurück.

1.2 Die automatische Speicherverwaltung mit Garbage Collector (Java, Python, C#, Go)

Als Reaktion auf die Fehleranfälligkeit der manuellen Speicherverwaltung wurden Sprachen mit einem Garbage Collector (GC) entwickelt.

  • Ablauf: Der Entwickler erstellt Objekte im Code, ohne sich um die Speicherfreigabe kümmern zu müssen. Ein im Hintergrund laufender Prozess (der GC) überwacht die Objekte im RAM. Sobald ein Objekt von keinem Teil des Programms mehr referenziert wird, markiert der GC diesen Speicherbereich als frei.
  • Vorteile: Hohe Sicherheit, komfortable Entwicklung, Ausschluss von Double-Free-Fehlern und hängenden Zeigern.
  • Nachteile:
    • Runtime Overhead: Der Garbage Collector benötigt selbst CPU-Leistung und Arbeitsspeicher, was die Performance mindert.
    • Stop-the-World Pausen: Um den Speicher konsistent zu analysieren, müssen viele Garbage Collector die Ausführung des Hauptprogramms kurzzeitig stoppen. Dies macht solche Sprachen ungeeignet für Echtzeitsysteme, Betriebssystem-Kernel oder hardwarenahe Programmierung.
    • Unvorhersehbarkeit: Wann der GC anspringt und wie lange er aufräumt, lässt sich zur Entwicklungszeit nicht exakt vorhersagen.

1.3 Der dritte Weg: Rusts Ownership

Rust löst dieses Dilemma, indem es das Beste aus beiden Welten kombiniert:

  • Es bietet die Sicherheit und Zuverlässigkeit einer Garbage-Collected-Sprache (keine Memory Leaks, Double Frees oder Dangling Pointers).
  • Es bietet die Performance und Vorhersehbarkeit von C und C++ (kein Hintergrundprogramm, keine Laufzeit-Pausen).

Dies gelingt, indem Rust die Speicherverwaltung komplett in die Kompilierzeit verlagert. Der Compiler analysiert deinen Code während des Übersetzens anhand strenger Eigentumsregeln. Wenn der Code die Regeln einhält, fügt der Compiler die exakten Freigabebefehle direkt in die Binärdatei ein. Zur Laufzeit verhält sich Rust somit wie ein manuell optimiertes C-Programm.

2. Die Anatomie des Arbeitsspeichers: Stack vs. Heap

Um die Regeln des Ownership-Systems und ihre Notwendigkeit zu verstehen, müssen wir die physischen Strukturen des Arbeitsspeichers analysieren. Wenn ein Programm ausgeführt wird, teilt das Betriebssystem dem Prozess einen Speicherbereich zu, der primär in zwei logische Bereiche unterteilt wird: den Stack (Stapel) und den Heap (Haufen).

2.1 Der Stack (Der Stapel)

Der Stack ist ein hochgradig strukturierter und extrem schneller Speicherbereich.

  • Das Funktionsprinzip: Er arbeitet nach dem LIFO-Prinzip (Last In, First Out). Das bedeutet, dass die Datenstruktur wie ein physikalischer Stapel von Büchern oder Tabletts funktioniert. Neue Daten werden oben auf den Stapel gelegt ("Push") und können nur von oben wieder entfernt werden ("Pop").
  • Die feste Größe: Jedes Element, das auf dem Stack gespeichert wird, muss eine feste, dem Compiler bereits zur Kompilierzeit bekannte Größe haben. Einfache Datentypen wie Ganzzahlen (i32), Fließkommazahlen (f64), Booleans (bool) und Zeichen (char) fallen in diese Kategorie.
  • Der Stack-Pointer: Die CPU besitzt ein spezielles Register (den Stack-Pointer, oft rsp genannt), das immer auf die aktuelle Spitze des Stapels zeigt. Beim Anlegen einer Variablen muss die CPU lediglich diesen Pointer verschieben (durch Subtraktion oder Addition), was in einem einzigen Taktzyklus geschieht.
  • Caches und Lokalität: Da die Daten auf dem Stack eng beieinanderliegen, werden sie vom Prozessor hervorragend in den schnellen L1/L2/L3-Caches der CPU zwischengespeichert. Dies sorgt für eine extrem hohe Zugriffsgeschwindigkeit, da kaum Speicherlatenzen auftreten.
  • Die Stack Frames: Jedes Mal, wenn dein Programm eine Funktion aufruft, wird ein sogenannter Stack Frame (Aktivierungsblock) auf den Stack gelegt. Dieser Frame enthält alle Argumente der Funktion sowie ihre lokalen Variablen. Sobald die Funktion beendet ist, wird der gesamte Stack Frame auf einmal vom Stack entfernt.

│ Rücksprungadresse (8 Bytes)   │
└───────────────────────────────┘  ◄── Stack Pointer (rsp) zeigt hierhin

2.2 Der Heap (Der Haufen)

Der Heap ist ein großer, unstrukturierter Speicherbereich, der für Flexibilität ausgelegt ist.

  • Das Funktionsprinzip: Wenn du Daten auf dem Heap speichern möchtest, deren Größe zur Kompilierzeit unbekannt ist (z. B. eine Benutzereingabe oder ein Text, der zur Laufzeit wächst), musst du Speicher auf dem Heap anfordern.
  • Der Allokationsprozess:
    1. Dein Programm bittet den Speicher-Manager (Allocator) um eine bestimmte Menge Speicher (in Bytes).
    2. Der Allocator sucht im Heap nach einem freien Block, der groß genug ist. Dies geschieht mithilfe von Algorithmen wie First Fit, Best Fit oder Buddy Allocation.
    3. Er markiert diesen Block als belegt und registriert die Allokation.
    4. Er gibt die Startadresse dieses Speicherblocks zurück. Diese Adresse nennen wir Pointer (Zeiger).
  • Die Rolle des Stack: Da der Pointer selbst eine feste Größe hat (unter 64-Bit-Systemen genau 8 Bytes bzw. 64 Bits), wird der Pointer auf dem Stack gespeichert. Er verweist lediglich auf die tatsächlichen Nutzdaten, die weit entfernt auf dem Heap liegen.
  • Der Performance-Nachteil:
    • Allokation: Das Suchen nach freiem Speicher und das Verwalten der internen Tabellen durch den Allocator kostet Zeit und CPU-Zyklen.
    • Zugriff: Um auf die Daten zuzugreifen, muss der Prozessor zuerst den Pointer auf dem Stack lesen und dann an die Speicheradresse auf dem Heap springen. Diese Indirektion kann zu Cache-Misses führen, da die Daten im Heap kreuz und quer verstreut liegen können.

3. Die drei goldenen Regeln des Ownership-Systems

Das gesamte Speichermanagement von Rust basiert auf drei fundamentalen Regeln. Diese Regeln werden vom Compiler bei jedem Übersetzungsvorgang rigoros geprüft.

                  ┌───────────────────────────────┐
                  │ Die 3 Regeln des Ownerships   │
                  └───────────────┬───────────────┘
                                  │
         ┌────────────────────────┼────────────────────────┐
         ▼                        ▼                        ▼
┌─────────────────┐      ┌─────────────────┐      ┌─────────────────┐
│ Wert hat genau  │      │ Nur ein Besitzer│      │ Scope-Ende:     │
│ einen Besitzer  │      │   gleichzeitig  │      │ Wert wird drop  │
└─────────────────┘      └─────────────────┘      └─────────────────┘

Regel 1: Jeder Wert in Rust hat einen Besitzer (Owner)

Der Besitzer eines Wertes ist in den allermeisten Fällen eine Variable oder ein Funktionsparameter. Sobald ein Wert erzeugt wird (z. B. eine Zahl oder ein String), wird er an einen Besitzer gebunden. Ohne Besitzer kann kein Wert im Speicher existieren.

Regel 2: Es kann immer nur einen Besitzer gleichzeitig geben

Diese Regel ist der Kern von Rusts Speichersicherheit. Sie schließt aus, dass zwei Variablen unabhängig voneinander die Verantwortung für denselben Speicherbereich auf dem Heap tragen. Dies verhindert den fatalen Double-Free-Fehler. Wenn du den Wert einer Variablen einer anderen Variablen zuweist, wird das Eigentum übertragen (Move) und die alte Variable wird ungültig.

Regel 3: Wenn der Besitzer den Scope verlässt, wird der Wert automatisch gelöscht

Sobald das Programm den Gültigkeitsbereich (Scope) einer Variablen verlässt, gibt Rust den Speicher dieser Variablen unverzüglich und ohne Verzögerung wieder frei. Dafür nutzt Rust die Spezialfunktion drop.

4. Scopes und die automatische Speicherfreigabe mit drop

Ein Scope (Gültigkeitsbereich) ist der Lebensraum einer Variablen. In Rust wird er durch geschweifte Klammern { } definiert. Jedes Mal, wenn du geschweifte Klammern öffnest, erstellst du einen neuen, isolierten Gültigkeitsbereich.

4.1 Verschachtelte Scopes

Variablen, die in einem äußeren Scope deklariert wurden, sind auch in inneren Scopes gültig. Variablen, die in einem inneren Scope deklariert wurden, können jedoch nicht nach außen dringen.

fn main() { // <-- Äußerer Scope beginnt
    let x = 10;

    { // <-- Innerer Scope beginnt
        let y = 20;
        println!("x: {}, y: {}", x, y); // ✅ Gültig! x und y sind sichtbar.
    } // <-- Innerer Scope endet! y verlässt den Scope und wird gelöscht.

    println!("x: {}", x); // ✅ Gültig!
    // println!("y: {}", y); // ❌ COMPILER-FEHLER: y existiert nicht mehr!
} // <-- Äußerer Scope endet! x verlässt den Scope und wird gelöscht.

4.2 Wie drop im Hintergrund arbeitet

Wenn ein Besitzer den Scope verlässt, muss der Speicher bereinigt werden. Rust löst dies über ein Konzept namens Destruktoren.

Der Compiler analysiert den Code während des Kompilierens und fügt exakt an der Stelle, an der eine Variable ungültig wird (oft an der schließenden geschweiften Klammer }), einen Aufruf der Funktion std::ops::Drop::drop ein. Diese Funktion gibt den Heap-Speicher über den System-Allocator wieder frei.

{
    let s = String::from("hallo");
    // Tu etwas mit s
} // ◄── Der Compiler fügt hier implizit `drop(s)` ein.

Das RAII-Prinzip (Resource Acquisition Is Initialization)

Dieses Verhalten entspricht dem RAII-Muster aus C++. Der Erwerb einer Ressource (z. B. Speicherallokation, Öffnen einer Datei oder Herstellen einer Netzwerkverbindung) ist direkt an die Lebensdauer des Objekts gekoppelt. Wenn das Objekt stirbt, wird die Ressource automatisch freigegeben. In Rust is dies tief in die Sprache integriert.

Im Gegensatz zu Sprachen wie Java (wo die Speicherbereinigung durch den Garbage Collector asynchron und unvorhersehbar geschieht) oder Python (wo die Destruktoren __del__ durch Referenzzählung aufgerufen werden, was zu zirkulären Referenzproblemen führen kann), ist die Zerstörung in Rust deterministisch: Sie geschieht genau an der Stelle, die der Compiler im Voraus bestimmt hat.

5. Das Speicher-Layout von Strings im Heap

Um die Auswirkungen von Zuweisungen, Moves und Clones zu verstehen, müssen wir das genaue Speicher-Layout von Strings analysieren. Rust unterscheidet zwischen String-Literalen (&str) und dem dynamischen Typ String.

5.1 &str (String-Literale)

Wenn du let s = "hallo"; schreibst, verweist s auf ein String-Literal.

  • Speicherort: Die Zeichen 'h', 'a', 'l', 'l', 'o' sind direkt in die ausführbare Binärdatei des Programms (das Datensegment) eingebrannt.
  • Eigenschaft: Da sie im schreibgeschützten Datensegment des Programms liegen, können sie niemals zur Laufzeit verändert werden. Sie haben eine feste Länge und leben für die gesamte Programmlaufzeit (haben die Lifetime 'static).

5.2 String (Der Heap-String)

Wenn du Text manipulieren oder zur Laufzeit laden willst, nutzt du String::from("hello").

  • Stack-Daten (Die Fernbedienung): Die Variable auf dem Stack belegt exakt 24 Bytes (auf einem 64-Bit-System) und besteht aus drei Feldern:
    1. Pointer (8 Bytes / 64 Bits): Die Speicheradresse auf dem Heap, an der die Textdaten beginnen.
    2. Length (8 Bytes / 64 Bits): Die Anzahl der Bytes, die der Text aktuell belegt.
    3. Capacity (8 Bytes / 64 Bits): Die Gesamtgröße des reservierten Heap-Speichers.
  • Heap-Daten: Der tatsächliche Text wird in einem zusammenhängenden Block auf dem Heap gespeichert.
STACK (Variable 's')                  HEAP
┌──────────┬──────────────┐          ┌───────────────────────┐
│ Pointer  │ 0x01a3f5f8 ──┼─────────►│ h │ e │ l │ l │ o │   │
├──────────┼──────────────┤          └───────────────────────┘
│ Length   │ 5            │
├──────────┼──────────────┤
│ Capacity │ 5            │
└──────────┴──────────────┘

5.3 Was passiert bei push_str?

Wenn wir Text anhängen, wächst die Länge des Strings.

let mut s = String::from("hello");
s.push_str(", world!");

Der Speicher-Manager verarbeitet dies in zwei Szenarien:

  • Szenario A (Genug Kapazität): Wenn die Kapazität (Capacity) groß genug ist (z. B. Capacity = 20, Length = 5), schreibt Rust die neuen Zeichen einfach hinter die alten Zeichen auf den Heap und erhöht den Length-Wert auf dem Stack. Dies ist extrem schnell.
  • Szenario B (Zu wenig Kapazität - Reallokation): Wenn der neue Text die Kapazität überschreitet, muss der String "umziehen":
    1. Der Allocator sucht einen neuen, größeren freien Speicherblock auf dem Heap (meist das Doppelte der benötigten Größe, um zukünftige Allokationen zu amortisieren).
    2. Der alte Text wird in den neuen Block kopiert.
    3. Der angehängte Text wird dahinter geschrieben.
    4. Der alte Speicherblock auf dem Heap wird freigegeben.
    5. Der Pointer, die Länge und die Kapazität auf dem Stack werden aktualisiert.

6. Move-Semantik: Eigentumswechsel im Detail

Die Move-Semantik ist das Herzstück von Rusts Effizienz und Sicherheit. Sie regelt, was passiert, wenn wir eine Heap-Variable einer anderen Variablen zuweisen.

6.1 Die Gefahr von flachen Kopien (Shallow Copies)

In vielen Programmiersprachen führt eine Zuweisung wie let s2 = s1; zu einer flachen Kopie (Shallow Copy). Das bedeutet, dass die Stack-Daten (Pointer, Länge, Kapazität) kopiert werden, beide Variablen aber auf denselben Heap-Speicher verweisen.

s1 (Stack) ───┐
              ├─► [ "hello" ] (Heap)
s2 (Stack) ───┘

Wenn nun beide Variablen ihren Scope verlassen, passiert Folgendes:

  1. Der Scope endet.
  2. Rust ruft drop(s2) auf. Der Heap-Speicher an der Adresse 0x01a3f5f8 wird freigegeben.
  3. Rust ruft drop(s1) auf. Rust versucht, den Speicher an derselben Adresse erneut freizugeben.
  4. Double-Free-Fehler! Dies führt zu schwerwiegenden Abstürzen des Speicher-Managers oder ermöglicht Heap-Exploits.

6.2 Die Lösung: Der Move

Um dieses Problem zu verhindern, verlagert Rust den Besitz. Bei let s2 = s1; kopiert Rust die Stack-Daten von s1 nach s2, deklariert s1 jedoch sofort für ungültig.

VOR DEM MOVE:
s1 ─────────► [ "hello" ] (Heap)

NACH DEM MOVE:
s1 (Ungültig! Zugriff gesperrt)
s2 ─────────► [ "hello" ] (Heap)

Da s1 ungültig ist, wird für s1 am Scope-Ende auch kein drop-Aufruf generiert. Nur s2 gibt den Speicher frei. Es gibt keinen Double-Free-Fehler.

Compiler-Fehlermeldung E0382 verstehen

Wenn du versuchst, eine verschobene Variable zu verwenden, verweigert der Compiler den Dienst:

fn main() {
    let s1 = String::from("hello");
    let s2 = s1; // Move von s1 nach s2

    // println!("{}", s1); // ❌ COMPILER-FEHLER!
}

Die Fehlermeldung des Compilers ist präzise:

error[E0382]: borrow of moved value: `s1`
  --> src/main.rs:5:20
   |
 2 |     let s1 = String::from("hello");
   |         -- move occurs because `s1` has type `String`, which does not implement the `Copy` trait
 3 |     let s2 = s1;
   |              -- value moved here
 4 | 
 5 |     println!("{}", s1);
   |                    ^^ value borrowed here after move

Der Compiler erklärt dir genau:

  • Wo die Variable definiert wurde (let s1 = ...).
  • Warum sie verschoben wurde (Typ String implementiert nicht den Copy-Trait).
  • Wo der Move stattfand (let s2 = s1;).
  • Wo der illegale Zugriffsversuch stattfand (println!("{}", s1);).

7. Kopieren auf dem Stack: Der Copy-Trait

Nicht alle Zuweisungen führen zu einem Move. Rust besitzt ein System, um einfache Datenstrukturen automatisch zu kopieren. Dieses Verhalten wird über den Copy-Trait gesteuert.

7.1 Was ist ein Trait?

Ein Trait in Rust ist eine Schnittstelle oder ein Vertrag. Er legt fest, welche Fähigkeiten ein Datentyp besitzt. Der Copy-Trait ist ein spezieller Marker-Trait: Er enthält keine Methoden, sondern signalisiert dem Compiler lediglich: "Dieser Typ darf bei Zuweisungen byteweise kopiert werden."

7.2 Wann wird ein Typ kopiert?

Wenn ein Datentyp das Copy-Trait implementiert, führt eine Zuweisung wie let y = x; dazu, dass der Wert im Speicher byteweise dupliziert wird. Da diese Typen komplett auf dem Stack liegen, ist dies eine sehr schnelle Operation. Beide Variablen bleiben unabhängig voneinander gültig.

fn main() {
    let x = 42; // i32 liegt auf dem Stack
    let y = x;  // Byteweise Kopie auf dem Stack

    println!("x: {}, y: {}", x, y); // ✅ Beide Variablen sind gültig!
}

Folgende Typen implementieren das Copy-Trait standardmäßig:

  • Alle Ganzzahl-Typen (wie i32, u64, usize, etc.)
  • Alle Fließkommazahl-Typen (wie f32, f64)
  • Der boolesche Typ (bool)
  • Der Zeichen-Typ (char)
  • Tupel, wenn sie ausschließlich Typen enthalten, die selbst Copy sind (z. B. (i32, f64) ist Copy, aber (i32, String) ist nicht Copy).
  • Arrays, wenn ihr Element-Typ Copy implementiert.

7.3 Die Ausschlussregel: Copy vs. Drop

Rust verbietet es, einen Typ gleichzeitig mit dem Copy-Trait und dem Drop-Trait zu deklarieren.

  • Warum? Wenn ein Typ Drop implementiert, bedeutet das, dass er spezielle Ressourcen freigeben muss (z. B. Heap-Speicher oder Datei-Handles).
  • Das Problem: Würde dieser Typ gleichzeitig Copy erlauben, könnten wir den Wert unkontrolliert duplizieren. Am Ende würden mehrere Variablen versuchen, dieselbe Ressource freizugeben (Double Free).
  • Die Regel: Alle Typen, die Heap-Speicher besitzen oder Ressourcen verwalten (wie String, Vec, File), dürfen niemals Copy implementieren.

8. Tiefe Kopien mit dem Clone-Trait

Wenn du Daten auf dem Heap duplizieren möchtest, musst du dies explizit tun. Dies wird über den Clone-Trait gesteuert.

Der Clone-Trait stellt die Methode .clone() zur Verfügung. Im Gegensatz zu Copy, das immer eine implizite, billige Stack-Kopie durchführt, ist Clone ein expliziter und potenziell teurer Vorgang.

fn main() {
    let s1 = String::from("hello");
    let s2 = s1.clone(); // Kopiert Stack-Daten UND Heap-Daten!

    // Beide Variablen zeigen nun auf getrennte Heap-Bereiche:
    println!("s1: {}, s2: {}", s1, s2); // ✅ Beide sind gültig!
}

Das Speicher-Layout beim Klonen

s1 (Stack) ─────────► [ "hello" ] (Heap-Block A)
s2 (Stack) ─────────► [ "hello" ] (Heap-Block B)

Da beide Variablen auf völlig unterschiedliche Speicherbereiche verweisen, können sie unabhängig voneinander verändert werden. Am Ende des Scopes rufen beide Variablen sicher drop auf ihrem jeweiligen Heap-Block auf.

9. Ownership im Kontext von Funktionen

Das Übergeben von Variablen an Funktionen und das Empfangen von Rückgabewerten unterliegt denselben strengen Eigentumsregeln wie Zuweisungen.

9.1 Parameterübergabe: Move vs. Copy

Wenn du eine Variable als Argument an eine Funktion übergibst, wird das Eigentum an den Parameter der Funktion übertragen:

  • Handelt es sich um einen Typ ohne Copy-Trait (z. B. String), findet ein Move statt. Die aufrufende Funktion verliert den Besitz und die Variable wird ungültig.
  • Handelt es sich um einen Typ mit Copy-Trait (z. B. i32), wird eine Kopie auf den Stack gelegt. Die aufrufende Funktion behält den Besitz der Originalvariablen.
main()                               Funktion(text: String)
┌────────────────────────┐           ┌────────────────────────┐
│ let s = String::from;  ├─ Move ───►│ (text übernimmt Besitz)│
│                        │           │                        │
│ s ist ungültig!        │◄── drop ──┤ text verlässt Scope!   │
└────────────────────────┘           └────────────────────────┘

9.2 Rückgabewerte und Eigentumsübertragung

Wenn eine Funktion einen Wert erzeugt und zurückgibt, überträgt sie das Eigentum an die aufrufende Funktion:

fn main() {
    let s1 = erzeuge_string(); // s1 übernimmt den Besitz des Rückgabewerts.
} // <-- s1 verlässt den Scope und wird gelöscht.

fn erzeuge_string() -> String {
    let temporaer = String::from("hallo");
    temporaer // Eigentum wird nach außen gegeben (kein drop von temporaer!)
}

10. Fortgeschrittene Ownership-Szenarien

Ownership beschränkt sich nicht nur auf einfache Variablen. Es beeinflusst jede Struktur in Rust. Hier untersuchen wir, wie sich das System bei zusammengesetzten Daten verhält.

10.1 Ownership bei Structs (Strukturen)

Wenn du eine Struktur erstellst, besitzt die Struktur ihre Felder.

struct Benutzer {
    name: String,  // String ist kein Copy-Typ
    alter: u32,    // u32 ist ein Copy-Typ
}
  • Wenn du eine Instanz von Benutzer erstellst, übernimmt die Instanz das Eigentum an dem übergebenen name-String.
  • Wenn die Struktur instanziiert wird, verlässt sie am Scope-Ende den Gültigkeitsbereich, und Rust ruft drop für die Struktur auf. Der Destruktor der Struktur gibt rekursiv alle seine Felder frei (d.h. der Speicher von name wird freigegeben).
  • Teilweises Verschieben (Partial Move): Wenn du ein Feld aus einer Struktur herausbewegst (z.B. let n = benutzer.name;), wird dieses Feld verschoben und die Struktur kann danach nicht mehr als Ganzes verwendet werden, da sie unvollständig ist.

10.2 Ownership bei Enums

Ähnlich verhält es sich mit Enums. Wenn eine Enum-Variante Daten enthält (z. B. Option<String>), besitzt die Enum-Instanz diese Daten. Wenn du über match oder if let auf die Daten zugreifst, versucht Rust standardmäßig, diese zu verschieben (moven). Möchtest du das verhindern, musst du eine Referenz verwenden (dazu mehr im nächsten Kapitel).

10.3 Ownership bei Collections (z. B. Vektoren)

Ein Vektor (Vec<T>) verwaltet ein dynamisches Array auf dem Heap. Er besitzt alle Elemente, die in ihm gespeichert sind.

let mut liste = Vec::new();
let text = String::from("Element");
liste.push(text); // text wird in den Vektor verschoben!
// println!("{}", text); // ❌ FEHLER: text gehört nun dem Vektor.

Wenn der Vektor am Ende seines Scopes zerstört wird, ruft er automatisch drop für jedes einzelne Element auf, das er enthält.

11. Didaktische Praxisbeispiele mit detaillierter Speicheranalyse

Um die Theorie des Ownership-Systems vollständig zu verinnerlichen, analysieren wir nun dreizehn praxisnahe, detailliert ausformulierte Programmbeispiele. Jedes Beispiel zeigt exakt, was bei jeder Zeile im Speicher (Stack und Heap) passiert.

🛠️ Praxisbeispiel 1: Einfaches Ownership bei Integers vs. Strings

Dieses Beispiel demonstriert den grundlegenden Unterschied zwischen Stack-Daten und Heap-Daten bei einer Zuweisung.

fn main() {
    // Zeile 1
    let x = 100; 
    // Zeile 2
    let y = x;   

    // Zeile 3
    let s1 = String::from("Rust"); 
    // Zeile 4
    let s2 = s1;                         
}

Schritt-für-Schritt-Ablauf & Speicherzustand:

  1. Nach Zeile 1 (let x = 100;):
    • Stack: Ein Speicherplatz für x (vom Typ i32, 4 Bytes) wird auf dem Stack angelegt und mit dem Wert 100 belegt.
    • Heap: Leer.
  2. Nach Zeile 2 (let y = x;):
    • Stack: Da i32 das Copy-Trait implementiert, wird der Wert von x byteweise kopiert. Es entsteht ein neuer Eintrag y auf dem Stack mit dem Wert 100. Beide Variablen sind unabhängig voneinander gültig.
    • Speicherzustand Stack: 
      x = 100 (i32)
y = 100 (i32)
  3. Nach Zeile 3 (let s1 = String::from("Rust");):
    • Stack: Die Variable s1 (24 Bytes) wird angelegt. Sie enthält:
      • ptr -> Zeigt auf eine Adresse im Heap (z.B. 0x55aa01)
      • len -> 4
      • cap -> 4
    • Heap: An Adresse 0x55aa01 liegen die Bytes [R, u, s, t].
    • Speicherzustand: 
      STACK                     HEAP
s1 [ptr: 0x55aa01] ───►  0x55aa01: ['R', 'u', 's', 't']
   [len: 4       ]
   [cap: 4       ]
  4. Nach Zeile 4 (let s2 = s1;):
    • Stack: Die Metadaten von s1 (Pointer, Länge, Kapazität) werden kopiert und in die neue Stackvariable s2 geschrieben.
    • Das entscheidende Ereignis: Da String nicht Copy ist, findet ein Move statt. s1 wird vom Compiler als ungültig markiert. Jedes Lesen von s1 ist ab hier verboten.
    • Speicherzustand: 
      STACK                     HEAP
s1 [UNGÜLTIG     ]
s2 [ptr: 0x55aa01] ───►  0x55aa01: ['R', 'u', 's', 't']
   [len: 4       ]
   [cap: 4       ]
    • Am Scope-Ende wird nur für s2 die drop-Funktion aufgerufen, welche den Heap-Speicher an Adresse 0x55aa01 freigibt.

🛠️ Praxisbeispiel 2: Scopes und verschachtelte Datenstrukturen

Dieses Beispiel veranschaulicht, wie geschweifte Klammern die Lebensdauer von Objekten begrenzen und wann Speicher freigegeben wird.

fn main() {
    // Zeile 1
    let a = String::from("Aussen");
    {
        // Zeile 2
        let b = String::from("Innen");
        // Zeile 3
        println!("{}, {}", a, b);
    } 
    // Zeile 4
    println!("{}", a);
}

Schritt-für-Schritt-Ablauf & Speicherzustand:

  1. Nach Zeile 1:
    • a wird auf dem Stack erzeugt und zeigt auf den Heap-Speicher mit dem Text "Aussen".
  2. Nach Zeile 2:
    • Ein neuer Scope beginnt. Die Variable b wird auf dem Stack angelegt und zeigt auf den Heap-Speicher mit dem Text "Innen".
    • Speicherzustand: 
      STACK                     HEAP
a [ptr: 0x111] ────────►  0x111: "Aussen"
b [ptr: 0x222] ────────►  0x222: "Innen"
  3. Zeile 3: Beide Variablen sind sichtbar, da a im übergeordneten Scope liegt und b im aktuellen Scope.
  4. Nach Zeile 4 (Austritt aus dem inneren Scope):
    • Die geschweifte Klammer schließt sich. b verlässt den Scope.
    • Der Compiler hat an dieser Stelle drop(b) eingefügt. Der Heap-Speicher an Adresse 0x222 wird freigegeben.
    • b wird vom Stack entfernt.
    • a bleibt unberührt, da es zum äußeren Scope gehört.
    • Speicherzustand: 
      STACK                     HEAP
a [ptr: 0x111] ────────►  0x111: "Aussen"
(b ist gelöscht)          (0x222 ist freigegeben)

🛠️ Praxisbeispiel 3: Custom Drop-Implementierung zur Ablaufverfolgung

Wir implementieren den Drop-Trait für eine eigene Datenstruktur, um die automatische Zerstörungsreihenfolge im Terminal zu protokollieren.

struct SpeicherDetektiv {
    name: String,
}

impl Drop for SpeicherDetektiv {
    fn drop(&mut self) {
        println!(">>> Zerstörung von: {}", self.name);
    }
}

fn main() {
    let d1 = SpeicherDetektiv { name: String::from("Detektiv 1") };
    {
        let d2 = SpeicherDetektiv { name: String::from("Detektiv 2") };
    } // ◄── Ort A
    println!("Zwischenschritt erreicht.");
} // ◄── Ort B

Schritt-für-Schritt-Ablauf & Terminalausgabe:

  1. Instanziierung: d1 wird im Haupt-Scope angelegt, d2 im inneren Scope.
  2. Erreichen von Ort A (} des inneren Scopes):
    • d2 verlässt seinen Scope. Der Compiler ruft die Methode drop(&mut d2) auf.
    • Terminalausgabe: >>> Zerstörung von: Detektiv 2
    • Der Speicher von d2 ist freigegeben.
  3. Erreichen von println!:
    • Terminalausgabe: Zwischenschritt erreicht.
  4. Erreichen von Ort B (Ende von main):
    • d1 verlässt den Scope. Der Compiler ruft drop(&mut d1) auf.
    • Terminalausgabe: >>> Zerstörung von: Detektiv 1

Didaktischer Hinweis: Man sieht deutlich, dass Variablen in einer exakten, deterministischen Reihenfolge abgebaut werden – immer genau dann, wenn ihr Scope endet.

🛠️ Praxisbeispiel 4: Der Speicher-Umzug bei String-Wachstum

Dieses Beispiel macht das Innenleben eines Strings sichtbar. Wir simulieren, wie sich die Werte verändern, wenn neuer Speicher allokiert werden muss.

fn main() {
    // Zeile 1
    let mut text = String::with_capacity(3);
    text.push_str("Hi");

    // Zeile 2
    text.push_str("! Jetzt wächst der Text.");
}

Schritt-für-Schritt-Ablauf & Speicherzustand:

  1. Nach Zeile 1 (with_capacity(3) und push_str("Hi")):
    • Es wird Speicher auf dem Heap für 3 Bytes reserviert. "Hi" belegt 2 Bytes.
    • Stack: ptr = 0x500, len = 2, cap = 3.
    • Heap: 0x500 -> ['H', 'i', '']
  2. Nach Zeile 2 (push_str(...)):
    • Der neue Text ist 24 Bytes lang. Die Gesamtlänge beträgt nun 26 Bytes.
    • Da die Kapazität von 3 nicht ausreicht, findet eine Reallokation statt:
      1. Der Allocator sucht einen neuen Block auf dem Heap mit ausreichender Kapazität (z.B. 52 Bytes).
      2. Der alte Inhalt ("Hi") wird an den Anfang des neuen Blocks kopiert.
      3. Der neue Inhalt wird angehängt.
      4. Der alte Speicherbereich (0x500) wird freigegeben.
      5. Die Stack-Metadaten werden aktualisiert.
    • Speicherzustand: 
      STACK                     HEAP
text [ptr: 0x900] ───►   0x900: "Hi! Jetzt wächst der Text." (26 Bytes belegt)
     [len: 26   ]
     [cap: 52   ]        (0x500 ist wieder frei gegeben)

🛠️ Praxisbeispiel 5: Move-Verhalten und Behebung des Fehlers E0382

Wir analysieren den klassischen Fehler, wenn wir eine verschobene Variable weiterverwenden wollen, und wie wir ihn durch Klonen lösen.

fn main() {
    let original = String::from("Wichtige Daten");

    // ❌ FALSCHER WEG (erzeugt E0382):
    // let fehlerhafte_kopie = original;
    // println!("{}", original); 

    // ✅ KORREKTER WEG:
    let echte_kopie = original.clone();

    println!("Original: {}", original);  
    println!("Kopie:    {}", echte_kopie); 
}

Schritt-für-Schritt-Ablauf & Speicherzustand:

  1. Initialisierung: original besitzt den Heap-Speicher an Adresse 0x300.
  2. Zuweisung mit .clone():
    • Rust führt eine tiefe Kopie (Deep Copy) durch:
      1. Es wird neuer Speicher auf dem Heap allokiert (Adresse 0x400).
      2. Der Inhalt "Wichtige Daten" wird von 0x300 nach 0x400 kopiert.
      3. Auf dem Stack wird echte_kopie mit dem Pointer 0x400 angelegt.
  3. Zustand nach dem Klonen:
    • Speicherzustand: 
      original   [ptr: 0x300] ───► 0x300: "Wichtige Daten"
echte_kopie [ptr: 0x400] ───► 0x400: "Wichtige Daten"
    • Beide Variablen sind unabhängig voneinander gültig und können gelesen und manipuliert werden.

🛠️ Praxisbeispiel 6: Stack-Kopieren mit dem Copy-Trait

Wir demonstrieren, wie sich Zuweisungen bei selbstdefinierten Strukturen verhalten und wie man den Copy-Trait anwendet.

#[derive(Debug, Copy, Clone)]
struct Koordinaten {
    x: f64,
    y: f64,
}

fn main() {
    // Zeile 1
    let k1 = Koordinaten { x: 10.0, y: 20.0 };
    // Zeile 2
    let k2 = k1;

    println!("k1: {:?}, k2: {:?}", k1, k2); 
}

Schritt-für-Schritt-Ablauf & Speicherzustand:

  1. Nach Zeile 1:
    • Die Variable k1 wird auf dem Stack angelegt. Da f64 8 Bytes groß ist, belegt k1 genau 16 Bytes auf dem Stack.
  2. Nach Zeile 2 (let k2 = k1;):
    • Da Koordinaten über das Attribut #[derive(Copy, Clone)] verfügt und alle Felder (x und y) ebenfalls das Copy-Trait besitzen, kopiert Rust die 16 Bytes von k1 direkt an eine neue Stelle auf dem Stack für k2.
    • Es findet kein Move statt! k1 bleibt voll funktionsfähig.
    • Speicherzustand Stack: 
      k1 = { x: 10.0, y: 20.0 } (16 Bytes Stack)
k2 = { x: 10.0, y: 20.0 } (16 Bytes Stack)

🛠️ Praxisbeispiel 7: Tiefe Kopien mit Clone und Performance-Überlegungen

Wir zeigen, wie teuer Klonen sein kann, wenn große Datenstrukturen auf dem Heap liegen, und vergleichen dies mit der Move-Semantik.

fn main() {
    // Zeile 1: Vektor mit 1 Million Nullen auf dem Heap erstellen
    let daten = vec![0; 1_000_000];

    // Zeile 2: Move
    let start_move = std::time::Instant::now();
    let daten_move = daten;
    let dauer_move = start_move.elapsed();

    // Zeile 3: Clone
    let start_clone = std::time::Instant::now();
    let daten_clone = daten_move.clone();
    let dauer_clone = start_clone.elapsed();

    println!("Move Dauer:  {:?}", dauer_move);
    println!("Clone Dauer: {:?}", dauer_clone);
}

Speicher- und Performance-Analyse:

  1. Zeile 1: daten besitzt einen großen Heap-Speicherbereich von ca. 8 Megabytes (1.000.000 * 8 Bytes für i64).
  2. Zeile 2 (Move):
    • Rust kopiert lediglich die 24 Bytes Stack-Daten (Pointer, Länge, Kapazität) von daten nach daten_move. Der Heap-Speicher wird nicht angefasst.
    • Zeitkomplexität: $O(1)$ (Konstante Zeit, extrem schnell, meist unter 50 Nanosekunden).
  3. Zeile 3 (Clone):
    • Rust muss einen neuen Heap-Speicherbereich von 8 Megabytes anfordern und die 1.000.000 Ganzzahlen einzeln dorthin kopieren.
    • Zeitkomplexität: $O(N)$ (Linear zur Datenmenge, deutlich spürbar, oft mehrere Millisekunden).

🛠️ Praxisbeispiel 8: Funktionen, die Werte verschlingen (Move)

Wir untersuchen, wie sich Ownership verhält, wenn wir eine Variable als Parameter an eine Funktion übergeben.

fn main() {
    let text = String::from("Hallo"); // Zeile 1
    konsumiere(text);                 // Zeile 2
    // println!("{}", text);          // ❌ Fehler! text wurde verschoben.
}

fn konsumiere(s: String) {            // Zeile 3
    println!("Erhalten: {}", s);
}                                     // Zeile 4

Schritt-für-Schritt-Ablauf & Speicherzustand:

  1. Nach Zeile 1: text ist der Besitzer des Strings "Hallo" auf dem Heap (z.B. Adresse 0x777).
  2. Zeile 2 (Funktionsaufruf):
    • Die Variable text wird als Argument übergeben. Es findet ein Move statt.
    • Die Stack-Metadaten von text werden in den Stack Frame der Funktion konsumiere kopiert (in den Parameter s).
    • text in main ist ab sofort ungültig.
    • Speicherzustand Stack: 
      [Stack Frame: main]       text [UNGÜLTIG]
[Stack Frame: konsumiere] s    [ptr: 0x777, len: 5, cap: 5] ──► Heap: "Hallo"
  3. Nach Zeile 4 (Ende von konsumiere):
    • Der Stack Frame von konsumiere wird abgebaut.
    • Die Variable s verlässt den Scope. Der Compiler ruft drop(s) auf und gibt den Heap-Speicher an Adresse 0x777 frei.
  4. Rückkehr zu main:
    • main läuft weiter, aber text ist nicht mehr lesbar und der zugehörige Heap-Speicher existiert nicht mehr.

🛠️ Praxisbeispiel 9: Shadowing und Return-Werte

Wir zeigen, wie wir eine Variable an eine Funktion übergeben, modifizieren und das Eigentum per Rückgabewert wieder zurückerhalten – gelöst über Shadowing.

fn main() {
    // Zeile 1
    let status = String::from("Aktiv");
    // Zeile 2
    let status = bearbeite(status);

    println!("Neuer Status: {}", status);
}

fn bearbeite(mut s: String) -> String {
    // Zeile 3
    s.push_str(" und Geprüft");
    // Zeile 4
    s
}

Schritt-für-Schritt-Ablauf & Speicherzustand:

  1. Nach Zeile 1: status (Version 1) wird deklariert und zeigt auf den Text "Aktiv".
  2. Zeile 2 (Aufruf und Shadowing):
    • status (Version 1) wird in bearbeite verschoben.
    • In bearbeite wird der Parameter s als veränderbar (mut) markiert.
  3. Nach Zeile 3: " und Geprüft" wird an s angehängt. Der Heap-Inhalt wächst.
  4. Zeile 4: Die Funktion gibt s zurück. Das Ownership wird aus der Funktion heraus an den Empfänger übergeben. Da die Funktion beendet wird, wird ihr Stack Frame abgebaut, aber es wird kein drop auf s aufgerufen, da der Wert zurückgegeben wurde.
  5. Zurück in main:
    • Das zurückgegebene Ownership wird an eine neue Variable gebunden. Durch die Deklaration let status = ... überschreiben wir den Namen der alten, ohnehin ungültigen Variablen status (Shadowing).
    • Speicherzustand: 
      status (Version 2) [ptr: 0x888] ───► Heap: "Aktiv und Geprüft"

🛠️ Praxisbeispiel 10: Der Ausweg aus dem Ping-Pong-Dilemma mit Tupeln

Wenn wir mehrere Daten an eine Funktion übergeben, müssen wir auch alle Daten wieder zurückgeben, um sie in main nicht zu verlieren. Wir zeigen, wie das mit Tupeln funktioniert.

fn main() {
    let t = String::from("Rust");
    let count = 1;

    // Eigentumsübergabe und Rückerhalt als Tupel
    let (t, count) = verarbeite_beide(t, count);

    println!("{} ({})", t, count);
}

fn verarbeite_beide(s: String, c: i32) -> (String, i32) {
    println!("Verarbeite String '{}' zum {}. Mal", s, c);
    (s, c + 1) // Rückgabe als Tupel
}

Analyse:

Dieses Muster nennt man das "Ping-Pong-Dilemma": Da wir den Besitz von t abgeben mussten, müssen wir t am Ende der Funktion wieder zurückgeben, um es in main weiterverwenden zu können. Dies führt zu unleserlichem Code, weshalb Rust für solche Fälle das Konzept der Referenzen (Borrowing) anbietet (siehe Kapitel 19).

🛠️ Praxisbeispiel 11: Ownership in Collections (Vektoren von Strings)

Dieses neue Beispiel zeigt im Detail, wie Vektoren das Eigentum an ihren Elementen verwalten und was beim Schleifendurchlauf passiert.

fn main() {
    // Zeile 1
    let mut namen: Vec<String> = Vec::new();
    
    // Zeile 2
    let n1 = String::from("Alice");
    namen.push(n1); // n1 wird in den Vektor verschoben!
    
    // Zeile 3
    // for name in namen {
    //     println!("{}", name);
    // }
}

Schritt-für-Schritt-Ablauf & Speicherzustand:

  1. Nach Zeile 1: Ein leerer Vektor namen wird auf dem Stack angelegt. Er belegt dort 24 Bytes (Pointer, Kapazität, Länge).
  2. Nach Zeile 2:
    • n1 wird auf dem Stack erzeugt und zeigt auf "Alice" im Heap.
    • Bei namen.push(n1) werden die Stack-Daten von n1 in den Heap-Bereich des Vektors kopiert.
    • Der Move: n1 ist in main nicht mehr nutzbar. Der Vektor besitzt nun den String.
    • Speicherzustand: 
      STACK                               HEAP
namen [ptr: 0xaa1] ────────► 0xaa1: [ ptr: 0xbb1, len: 5, cap: 5 ] (Vektor-Daten)
      [len: 1    ]                     │
      [cap: 4    ]                     ▼
                             0xbb1: ['A', 'l', 'i', 'c', 'e'] (Nutzdaten)
n1 [UNGÜLTIG]
  3. Das Verhalten bei Schleifen (Zeile 3):
    • Würden wir die auskommentierte Schleife aktivieren (for name in namen), würde die Schleife den Vektor konsumieren (Move). Das bedeutet, bei jedem Schleifendurchlauf wird das Eigentum an dem jeweiligen String aus dem Vektor heraus an die Schleifenvariable name übertragen. Am Ende der Schleife wird jeder String einzeln zerstört. Der Vektor ist danach komplett leer und ungültig!
    • Lösung: Auch hier behilft man sich in der Praxis mit Referenzen (for name in &namen), um den Vektor nur auszuleihen.

🛠️ Praxisbeispiel 12: Teilweises Verschieben (Partial Move) aus Strukturen

Dieses Beispiel zeigt, was passiert, wenn wir nur ein einzelnes Feld einer Struktur verschieben, und wie der Compiler die Integrität der gesamten Struktur überwacht.

struct Buch {
    titel: String,
    jahr: u32,
}

fn main() {
    // Zeile 1
    let mein_buch = Buch {
        titel: String::from("Rust Handbuch"),
        jahr: 2026,
    };

    // Zeile 2
    let t = mein_buch.titel; // titel (String) wird herausbewegt!

    // Zeile 3
    // println!("Jahr: {}", mein_buch.jahr); // ✅ Erlaubt! (jahr ist u32/Copy)
    // println!("Buch: {:?}", mein_buch);    // ❌ Verboten! (Struktur ist unvollständig)
}

Schritt-für-Schritt-Ablauf & Speicherzustand:

  1. Nach Zeile 1: Die Instanz mein_buch wird auf dem Stack erzeugt. Das Feld titel liegt im Heap (Adresse 0xf00).
  2. Nach Zeile 2 (let t = mein_buch.titel;):
    • Da String kein Copy-Typ ist, wird das Eigentum am Feld titel auf die Variable t übertragen (Move).
    • Das Feld jahr (vom Typ u32, ein Copy-Typ) verbleibt in der Struktur.
    • Teilweiser Speicherzustand: 
      mein_buch.titel = [UNGÜLTIG]
mein_buch.jahr  = 2026
t               = [ptr: 0xf00] ──► Heap: "Rust Handbuch"
  3. Die Auswirkung auf Zeile 3:
    • Der Compiler erlaubt den Zugriff auf das verbleibende Feld jahr, da dieses noch intakt ist.
    • Der Zugriff auf mein_buch als Ganzes (z. B. beim Drucken der gesamten Struktur) wird jedoch blockiert, da mein_buch durch das Verschieben des Titels in einen unvollständigen ("teilweise verschobenen") Zustand versetzt wurde.
    • Am Scope-Ende wird drop nur auf die intakten Teile von mein_buch angewendet (in diesem Fall passiert nichts, da u32 kein Drop benötigt). Der String von t wird durch drop(t) freigegeben.

🛠️ Praxisbeispiel 13: Komplexe Datenstrukturen (Vektoren von Strukturen mit Enums)

Dieses Beispiel zeigt die Eigentumsverhältnisse, wenn wir benutzerdefinierte Strukturen, Enums und Vektoren kombinieren. Wir analysieren, wie das Ownership-System verschachtelte Werte absichert.

#[derive(Debug)]
enum ServerStatus {
    Aktiv,
    Wartung,
}

#[derive(Debug)]
struct Server {
    id: u32,
    name: String,
    status: ServerStatus,
}

fn main() {
    // Zeile 1: Erstellen des Vektors
    let mut server_liste = Vec::new();

    // Zeile 2: Erstellen einer Server-Instanz
    let s = Server {
        id: 101,
        name: String::from("Database-Server"),
        status: ServerStatus::Aktiv,
    };

    // Zeile 3: Hinzufügen zum Vektor
    server_liste.push(s);

    // Zeile 4: Versuchter Zugriff
    // println!("Servername: {}", s.name); // ❌ FEHLER! s wurde in den Vektor verschoben.
}

Schritt-für-Schritt-Ablauf & Speicheranalyse:

  1. Nach Zeile 1 (let mut server_liste = Vec::new();):
    • Stack: Der Vektor-Header server_liste (24 Bytes) wird auf dem Stack angelegt (Pointer, Kapazität, Länge = 0).
    • Heap: Bisher keine Zuweisung für Elemente.
  2. Nach Zeile 2 (let s = Server { ... };):
    • Stack: Das Objekt s wird auf dem Stack erzeugt. Da es ein u32 (4 Bytes), einen String (24 Bytes) und ein ServerStatus Enum (in der Regel 4 oder 8 Bytes durch Speicher-Alignment) enthält, belegt s ca. 32 Bytes auf dem Stack.
    • Heap: Der Name "Database-Server" wird auf dem Heap gespeichert. Der String-Pointer in s zeigt auf diese Adresse (z.B. 0xbb00).
  3. Nach Zeile 3 (server_liste.push(s);):
    • Der Transfer: Die 32-Byte-Struktur s wird vom Stack in den Heap-Bereich des Vektors server_liste verschoben (Move). Der Vektor besitzt nun das gesamte Server-Objekt inklusive des Strings auf dem Heap.
    • Das Schicksal von s: Die Stack-Variable s wird für ungültig erklärt.
    • Speicherzustand: 
      STACK                                  HEAP
server_liste [ptr: 0xaa00] ──────► 0xaa00: [ Server-Daten: id: 101, status: Aktiv, ]
             [len: 1     ]                 [ name: ptr 0xbb00, len: 15, cap: 15    ] ──┐
             [cap: 4     ]                                                             │
                                                                                       ▼
s [UNGÜLTIG]                               0xbb00: ['D','a','t','a','b','a','s','e',...]
  4. Zeile 4 (Auskommentiert): Der Zugriff auf s.name schlägt fehl, da s kein Eigentümer der Daten mehr ist. Wenn wir den Server-Namen ausgeben wollen, müssen wir über den Vektor darauf zugreifen (z.B. mittels einer Referenz: &server_liste[0].name), um das Eigentum nicht zu verletzen.

12. Häufige Compiler-Fehler zu Ownership verstehen und beheben

Der Rust-Compiler ist berühmt für seinen strengen Borrow Checker. Hier analysieren wir die zwei häufigsten Fehlermeldungen im Detail und zeigen konkrete Lösungswege auf.

Fehler 1: E0382 - Use of moved value

Dieser Fehler tritt auf, wenn du versuchst, auf eine Variable zuzugreifen, nachdem ihr Besitz bereits abgegeben wurde.

Fehlerhafter Code:

fn main() {
    let s = String::from("Hallo");
    verarbeite(s);
    println!("Text ist: {}", s); // ❌ Compiler-Fehler E0382!
}

fn verarbeite(daten: String) {
    println!("Länge: {}", daten.len());
}

Erklärung:

Bei verarbeite(s) zieht der Inhalt auf dem Stack in den Parameter daten der Funktion um. In der darauffolgenden Zeile existiert s in main nicht mehr. Da der Heap-Speicher nun dem Parameter daten gehört und am Ende von verarbeite freigegeben wird, darf main unter keinen Umständen mehr auf s zugreifen. Der Borrow Checker verhindert dies statisch während der Kompilierung.

Lösungen:

  • Lösung A: Klonen (wenn du eine Kopie brauchst): 
    verarbeite(s.clone()); // Übergibt eine tiefe Kopie, s bleibt in main gültig.
  • Lösung B: Rückgabewert nutzen (Ping-Pong): 
    let s = verarbeite_und_rueckgabe(s);
  • Lösung C: Referenz verwenden (Best Practice für Kapitel 19): Übergib den Wert als Referenz (&s), sodass die Funktion den Wert nur ausleiht, statt ihn zu besitzen.

Fehler 2: E0507 - Cannot move out of borrow

Dieser Fehler tritt auf, wenn du eine Referenz (eine Leihgabe) auf ein Objekt hast, aber versuchst, das Eigentum an diesem Objekt oder an Teilen davon zu verschieben.

Fehlerhafter Code:

struct Person {
    name: String,
}

fn zeige_name(p: &Person) {
    // ❌ Compiler-Fehler E0507: 'p' ist nur eine Referenz, wir besitzen sie nicht!
    let name_kopie = p.name; 
    println!("Name: {}", name_kopie);
}

Erklärung:

Da p eine Referenz vom Typ &Person ist, besitzt die Funktion zeige_name das Person-Objekt nicht. Sie darf daher auch nicht das Feld name (welches ein String und kein Copy-Typ ist) aus der Struktur herausbewegen. Andernfalls bliebe das Originalobjekt hinter der Referenz in einem beschädigten Zustand zurück. Ein Zugriff durch andere Teile des Programms würde dann in undefiniertes Verhalten münden.

Lösungen:

  • Lösung A: Den Wert klonen: 
    let name_kopie = p.name.clone(); // Kopiert den String, Original bleibt intakt.
  • Lösung B: Eine Referenz auf das Feld nutzen: 
    let name_ref = &p.name; // Nur eine Referenz auf den String ausleihen.

13. Die feinen Unterschiede: Ownership vs. Lifetimes vs. Borrowing

Um dich optimal auf das nächste Kapitel vorzubereiten, werfen wir einen kurzen Blick auf das Zusammenspiel der drei Säulen von Rusts Speicherverwaltung:

  1. Ownership (Eigentum): Bestimmt, wer für die Bereinigung des Speichers verantwortlich ist. Es kann immer nur einen Besitzer geben.
  2. Borrowing (Ausleihen): Ermöglicht es uns, Zeiger (Referenzen) auf Daten zu erstellen, ohne das Eigentum zu übernehmen. Referenzen werden mit dem &-Symbol gekennzeichnet (z.B. &String).
  3. Lifetimes (Lebensdauern): Sind statische Analysen des Compilers, die garantieren, dass keine Referenz länger lebt als die Daten, auf die sie verweist. Sie verhindern "hängende Zeiger" (Dangling Pointers) vollständig.

Das Ownership-System ist das Fundament. Erst durch das darauf aufbauende Ausleihen wird Rust zu einer extrem flexiblen und komfortabel zu programmierenden Sprache.

💡 Zusammenfassung & Merkzettel

  • Ownership verlagert die Speicherverwaltung vollständig in die Kompilierzeit.
  • Stack-Daten haben eine feste Größe und werden bei Zuweisungen byteweise kopiert (Copy-Trait).
  • Heap-Daten haben eine dynamische Größe. Bei Zuweisungen findet ein Move (Besitzwechsel) statt, wodurch die Quellvariable ungültig wird.
  • Ein Wert hat immer exakt einen Besitzer. Verlässt dieser seinen Scope (Gültigkeitsbereich), wird der Speicher automatisch über drop freigegeben (RAII-Prinzip).
  • Clone führt eine tiefe Kopie der Heap-Daten durch, was jedoch spürbare Leistungseinbußen mit sich bringt.
  • Funktionen übernehmen beim Aufruf standardmäßig das Eigentum an ihren Argumenten. Das Eigentum kann über Rückgabewerte (oder als Tupel) wieder an den Aufrufer zurückgegeben werden.
