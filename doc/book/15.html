Kapitel 15: Kontrollstrukturen – Bedingte Ausdrücke und Schleifensysteme

Kontrollstrukturen bilden das logische Nervensystem jeder Programmiersprache. Ohne sie würden Programme deterministisch und linear Zeile für Zeile abgearbeitet werden. Erst durch Verzweigungen und Schleifen erlangt Software die Fähigkeit, dynamisch auf unterschiedliche Daten, Benutzereingaben und Systemzustände zu reagieren.

In Rust sind Kontrollstrukturen jedoch nicht nur einfache Ablaufanweisungen wie in C, C++ oder Java. Sie sind tief in das Typsystem und das Ownership-Modell integriert. Die Trennung zwischen Anweisungen (Statements) und wertabgebenden Ausdrücken (Expressions) führt dazu, dass Verzweigungen und Schleifen Werte zurückliefern können. In diesem Kapitel werden wir die theoretischen Grundlagen, die hardwarenahen Auswirkungen und die fortgeschrittenen Steuerungsmuster von Bedingungen und Schleifen in Rust detailliert analysieren.

2. Die Definition

  • Bedingter Ausdruck (Conditional Expression): Eine Struktur, die den Kontrollfluss eines Programms basierend auf dem Wahrheitswert (bool) einer Bedingung in verschiedene Pfade verzweigt. Da es sich in Rust um einen Ausdruck (Expression) handelt, wertet sich der ausgeführte Zweig zu einem konkreten Wert aus, der einer Variablen zugewiesen oder als Argument übergeben werden kann.
  • Statements vs. Expressions:
    • Statements (Anweisungen): Führen eine Aktion aus (z. B. eine Bindung via let oder eine Funktionsdefinition) und liefern keinen Wert zurück. Sie enden mit einem Semikolon ; (ausgenommen Block-Statements). Ihr impliziter Rückgabetyp ist das leere Tupel (), auch Unit-Typ genannt.
    • Expressions (Ausdrücke): Evaluieren zu einem Wert. Fast alles in Rust ist ein Ausdruck (z. B. mathematische Berechnungen, Funktionsaufrufe, Blöcke {} und if-Konstrukte). Sie haben kein abschließendes Semikolon, wenn ihr Wert zurückgegeben werden soll.
  • Endlosschleife (loop): Ein Kontrollfluss-Konstrukt, das einen Codeblock unendlich oft wiederholt. Es kann nur durch explizite Kontrollanweisungen wie break oder das Beenden des Threads verlassen werden. Rusts Compiler weiß, dass nachfolgender Code ohne ein erreichbares break unerreichbar ist, was weitreichende Garantien bei der statischen Analyse bietet.
  • Bedingte Schleife (while): Wiederholt die Ausführung eines Codeblocks, solange eine explizite boolesche Bedingung vor jedem Durchlauf zu true evaluiert.
  • Zählschleife (for): Iteriert über eine Sequenz von Werten, die durch einen Iterator oder einen Bereich (Range) bereitgestellt wird. Sie ist das sicherste Schleifenkonstrukt in Rust, da sie Zeiger-Arithmetik und manuelle Index-Validierungen überflüssig macht.
  • Schleifen-Labels (Loop Labels): Mit einem Apostroph eingeleitete Bezeichner (z. B. 'outer), die einer Schleife vorangestellt werden. Sie erlauben es den Anweisungen break und continue, sich explizit auf eine bestimmte äußere Schleife in einer verschachtelten Struktur zu beziehen.

Alltagsnahe Metaphern

Note

Die Bahngleis-Weiche (Bedingter Ausdruck): Stellen Sie sich eine Schienenweiche vor, auf die ein Zug (der Kontrollfluss) zufährt. Die Weiche wird durch einen Sensor (die Bedingung) gesteuert. Zeigt der Sensor “Grün” (true), fährt der Zug auf Gleis A ein. Zeigt er “Rot” (false), fährt er auf Gleis B. Am Ende der Gleise wartet ein Bahnhof, der den Zug entlädt. Egal welchen Weg der Zug genommen hat, er bringt am Bahnhof eine Ladung (den Rückgabewert) an. Wichtig ist: Beide Gleise müssen im selben Bahnhof enden (Typkonsistenz) – es ist physikalisch unmöglich, dass Gleis A einen Güterzug im Hamburger Hafen entlädt, während Gleis B ein U-Boot im Bodensee absetzt.

Tip

Der Kreisverkehr mit Ausfahrt-Tickets (Schleifen und Labels): Eine Schleife ist wie ein Kreisverkehr. Eine einfache while-Schleife prüft bei jeder Runde an der Einfahrt, ob noch Benzin im Tank ist. Ein loop fährt einfach so lange im Kreis, bis der Beifahrer ruft: “Halt! Hier ist unsere Ausfahrt!” (break). Wenn Sie nun mehrere Kreisverkehre ineinander verschachtelt haben (z. B. ein innerer Kreisel zur Verteilung in einem Industriegebiet, das wiederum in einem großen Autobahn-Verteilerkreisel liegt), können Sie mithilfe von Schildern (Labels) festlegen, dass ein Ausfahrt-Ticket an der innersten Kreuzung Sie direkt aus dem gesamten äußeren Autobahnkreisel herausleitet, anstatt Sie nur eine Ebene höher zu befördern.

3. Das Problem & Die Motivation

In traditionellen, imperativen Programmiersprachen wie C oder C++ bergen Kontrollstrukturen erhebliche Risiken für die Code-Sicherheit und Lesbarkeit:

  1. Das Problem der uninitialisierten Variablen: Wenn eine Variable basierend auf einer Bedingung initialisiert werden soll, deklariert man sie in C meist vor der Verzweigung ohne Wert. Wird in einem Zweig vergessen, die Variable zu initialisieren, greift das Programm später auf undefinierten Speicher zu. 
    // Gefährlicher C-Code:
int daten;
if (bedingung) {
    daten = 42;
} // Was passiert im else-Fall? "daten" enthält zufälligen Stack-Müll!
printf("%d", daten); // Undefined Behavior!
  2. Die Notwendigkeit künstlicher Mutabilität: Selbst wenn der Entwickler diszipliniert ist, muss die Variable vorab als veränderbar deklariert werden, um ihr innerhalb des if- oder else-Blocks einen Wert zuzuweisen. Das verletzt das Prinzip der kleinstmöglichen Rechte (Least Privilege).
  3. Die Flag-Hölle bei verschachtelten Schleifen: Möchte man in verschachtelten Schleifen (z. B. bei der Suche in einer 2D-Matrix) bei einem Treffer alle Schleifen abbrechen, muss man in Sprachen ohne Labels komplizierte Hilfsvariablen (Boolean-Flags) einführen und diese auf jeder Ebene abfragen, was den Code unleserlich und fehleranfällig macht: 
    bool gefunden = false;
for (int i = 0; i < 100 && !gefunden; i++) {
    for (int j = 0; j < 100; j++) {
        if (matrix[i][j] == ziel) {
            gefunden = true;
            break; // Beendet nur die innere Schleife
        }
    }
} // Die äußere Schleife muss 'gefunden' im Schleifenkopf abprüfen
  4. Fehlende Optimierungsgarantien bei Schleifen: Manuelle Index-Iterationen (wie for (int i = 0; i < len; i++)) zwingen den Compiler bei jedem Zugriff auf ein Array-Element zu prüfen, ob der Index innerhalb der Speichergrenzen liegt. Das kostet wertvolle CPU-Zyklen.

Rust löst diese Probleme durch ein konsequentes Redesign:

  • Da if ein Ausdruck ist, kann eine Variable direkt unveränderlich mit dem Ergebnis der Verzweigung initialisiert werden.
  • Schleifen-Labels erlauben den direkten Ausbruch aus beliebig tief verschachtelten Strukturen.
  • for-Schleifen arbeiten mit sicheren Iteratoren, wodurch der Compiler das speichergefährdende Bounds Checking zur Laufzeit vollständig wegoptimieren kann.

4. Der naive Versuch

Wir betrachten zwei naive Implementierungen, die typische Fallstricke beim Umgang mit Rusts Kontrollstrukturen aufzeigen.

Naiver Versuch 1: Typinkonsistenz in bedingten Ausdrücken

Hier versucht ein Programmierer, eine Variable basierend auf einer Konfigurationsprüfung entweder mit einer Ganzzahl oder mit einer Fehlermeldung zu initialisieren.

fn main() {
    let system_aktiv = true;

    // Der Compiler soll das Ergebnis direkt zuweisen
    let status_code = if system_aktiv {
        100 // Ein Integer-Wert
    } else {
        "System inaktiv" // Ein String-Literal
    };

    println!("Systemstatus: {:?}", status_code);
}

Naiver Versuch 2: Verschachtelter Schleifenabbruch mit Boolean-Flags

Hier wird versucht, einen Wert in einer Matrix zu suchen. Um aus beiden Schleifen auszubrechen, wird ein veränderbares Flag auf dem Stack verwaltet.

fn main() {
    let matrix = [
        [1, 2, 3],
        [4, 5, 6],
        [7, 8, 9]
    ];
    let zielwert = 5;
    let mut gefunden = false;

    // Wir durchsuchen die Zeilen und Spalten
    for zeile in 0..3 {
        for spalte in 0..3 {
            if matrix[zeile][spalte] == zielwert {
                gefunden = true;
                break; // Beendet nur die Spalten-Schleife!
            }
        }
        if gefunden {
            break; // Beendet die Zeilen-Schleife erst nach einer Extra-Prüfung
        }
    }

    println!("Wert gefunden: {}", gefunden);
}

5. Die Anatomie des Fehlers

Anatomie zu Naiver Versuch 1 (Typinkonsistenz)

Wenn wir versuchen, den ersten naiven Code zu kompilieren, verweigert der Compiler den Dienst mit folgender Fehlermeldung:

error[E0308]: `if` and `else` have incompatible types
 --> src/main.rs:8:9
  |
5 |       let status_code = if system_aktiv {
  |  _______________________-
6 | |         100
  | |         --- expected because of this
7 | |     } else {
8 | |         "System inaktiv"
  | |         ^^^^^^^^^^^^^^^^ expected integer, found `&str`
9 | |     };
  | |_____- `if` and `else` have incompatible types

Der Blick hinter die Kulissen (Speicherlayout & Stack-Frame)

Um zu verstehen, warum der Compiler diesen Code blockiert, müssen wir das Speicherlayout betrachten. Rust ist eine statisch typisierte Systemsprache. Zur Compilezeit muss die exakte Größe jeder Variablen auf dem Stack bekannt sein, um den Stack-Frame für die Funktion main im Maschinencode zu reservieren.

  • Ein Wert vom Typ i32 belegt auf dem Stack genau 4 Bytes.
  • Ein String-Literal &str ist ein Fat Pointer und belegt auf einem 64-Bit-System genau 16 Bytes (8 Bytes Startadresse im Datensegment + 8 Bytes Länge).
Szenario A (system_aktiv = true):
Stack-Zuweisung für `status_code`:
+---------+
|   100   |  -> 4 Bytes (i32)
+---------+

Szenario B (system_aktiv = false):
Stack-Zuweisung für `status_code`:
+-------------------+-------------------+
| Pointer auf Text  | Länge (14 Bytes)  | -> 16 Bytes (&str)
+-------------------+-------------------+

Da der Compiler zur Compilezeit nicht vorhersagen kann, welcher Pfad zur Laufzeit genommen wird, müsste er eine Variable deklarieren, deren Typ und Größe dynamisch fluktuieren. Dies würde das statische Speicherlayout des Stacks aufbrechen und aufwändige Laufzeitprüfungen erfordern. Rust erzwingt daher absolute Typkonsistenz über alle Zweige eines bedingten Ausdrucks hinweg.

Anatomie zu Naiver Versuch 2 (Flag-basierter Schleifenabbruch)

Dieser Code kompiliert zwar fehlerfrei, stellt jedoch ein schwerwiegendes Anti-Pattern dar:

  1. Instruktions-Overhead: Bei jedem Durchlauf der äußeren Schleife muss der Prozessor das Flag gefunden prüfen (if gefunden). Das führt zu zusätzlichen Verzweigungsbefehlen im Maschinencode. Die CPU-Pipeline muss Branch Prediction betreiben; schlägt diese fehl, kommt es zu Pipeline-Stalls (Verzögerungen bei der Instruktionsverarbeitung).
  2. Kognitive Komplexität: Der Code wird unübersichtlich. Wenn drei oder vier Schleifenebenen verschachtelt sind, bläht sich das Abprüfen der Flags extrem auf.
  3. Fehlende Ownership-Garantien: Das Flag gefunden muss mutable sein (mut gefunden). Dadurch besteht die Gefahr, dass es an anderer Stelle im Schleifenkörper versehentlich verändert wird, was schwer zu findende logische Laufzeitfehler (Bugs) provoziert.

6. Die Lösung

Wir beheben die Probleme des naiven Versuchs auf elegante, sichere und idiomatische Weise.

Lösung für 1: Typkonsistente Verzweigung und strukturierte Rückgabe

Wir nutzen ein Enum, um die unterschiedlichen Zustände typisiert abzubilden. Dadurch bleibt die Typkonsistenz des if-Ausdrucks gewahrt, während wir semantisch reichhaltige Daten zurückgeben.

// Wir definieren einen sauberen, typisierten Zustand
#[derive(Debug)]
enum SystemStatus {
    Aktiv(i32),       // Code bei Erfolg
    Inaktiv(&'static str), // Fehlermeldung bei Inaktivität
}

fn main() {
    let system_aktiv = true;

    // Beide Zweige geben nun denselben Typ 'SystemStatus' zurück!
    let status = if system_aktiv {
        SystemStatus::Aktiv(100)
    } else {
        SystemStatus::Inaktiv("System inaktiv")
    };

    // Strukturierte Verarbeitung
    match status {
        SystemStatus::Aktiv(code) => println!("System läuft mit Code: {}", code),
        SystemStatus::Inaktiv(msg) => println!("Warnung: {}", msg),
    }
}

Lösung für 2: Direkter Schleifenabbruch mit Loop-Labels

Wir verwenden ein Schleifen-Label 'suche, um direkt aus der inneren Schleife die äußere Schleife abzubrechen. Es ist kein Boolean-Flag und keine zusätzliche Prüfung mehr nötig.

fn main() {
    let matrix = [
        [1, 2, 3],
        [4, 5, 6],
        [7, 8, 9]
    ];
    let zielwert = 5;
    let mut koordinaten = None;

    // Wir benennen die äußere Schleife mit dem Label 'suche
    'suche: for zeile in 0..3 {
        for spalte in 0..3 {
            if matrix[zeile][spalte] == zielwert {
                koordinaten = Some((zeile, spalte));
                break 'suche; // Bricht sofort die gesamte, gelabelte Schleife ab!
            }
        }
    }

    match koordinaten {
        Some((z, s)) => println!("Wert {} bei Koordinate ({}, {}) gefunden.", zielwert, z, s),
        None => println!("Wert nicht gefunden."),
    }
}

Zeile-für-Zeile-Erklärung nach dem EVA-Prinzip

Für die Enum-Lösung (Lösung 1):

  • Eingabe (Input): Die boolesche Variable system_aktiv dient als Eingabe für die Bedingungsprüfung.
  • Verarbeitung (Processing):
    • Der if-Ausdruck wertet die Bedingung system_aktiv aus.
    • Trifft sie zu, wird die Variante SystemStatus::Aktiv(100) erzeugt.
    • Trifft sie nicht zu, wird SystemStatus::Inaktiv("System inaktiv") erzeugt.
    • Da beide Varianten dem gemeinsamen Datentyp SystemStatus angehören, ist die Typkonsistenz gewahrt. Der Compiler reserviert auf dem Stack genau die Größe der größten Enum-Variante plus Tag-Byte (Discriminant) zur Unterscheidung der Varianten.
  • Ausgabe (Output): Das Ergebnis wird der unveränderlichen Variablen status zugewiesen und über ein match-Pattern-Matching auf der Konsole ausgegeben.

Für die Label-Lösung (Lösung 2):

  • Eingabe (Input): Die 2D-Matrix und der zielwert dienen als Datenbasis.
  • Verarbeitung (Processing):
    • Die äußere Schleife wird mit 'suche: markiert.
    • Die Schleifen durchlaufen die Indizes. Sobald matrix[zeile][spalte] == zielwert zutrifft, wird die Koordinate in der Variable koordinaten gespeichert.
    • Der Befehl break 'suche weist die CPU an, den Befehlszeiger (Instruction Pointer) direkt hinter das Ende der mit 'suche markierten Schleife zu setzen.
  • Ausgabe (Output): Das Programm führt die darauffolgende Match-Verzweigung aus und gibt das Ergebnis aus. Es wurde kein einziges Hilfs-Flag benötigt.

7. Kleines Tutorial: Die Steuerung einer Fertigungsanlage

In diesem Tutorial entwickeln wir die Firmware-Simulation einer Fertigungsanlage. Das System steuert eine Temperaturüberwachung und das sequentielle Befüllen von Behältern. Wir nutzen hierbei wertrückgebende if-Ausdrücke, Endlosschleifen mit Wertrückgabe bei Abbruch, bedingte while-Schleifen für Füllvorgänge und Zählschleifen zur Qualitätskontrolle.

Schritt 1: Das Projekt anlegen

Erstellen Sie ein neues Cargo-Projekt im Workspace:

cargo new --bin fertigungs_steuerung

Schritt 2: Die Steuerungslogik implementieren

Ersetzen Sie den Inhalt von src/main.rs mit folgendem Code:

// main.rs - Steuerung einer virtuellen Fertigungsanlage

#[derive(Debug, PartialEq)]
enum MaschinenStatus {
    Bereit,
    Ueberhitzt,
    Notaus,
}

fn main() {
    let mut temperatur = 75.0;
    let mut anzahl_werkstuecke = 0;
    let max_werkstuecke = 5;

    println!("=== Fertigungssteuerung gestartet ===");

    // 1. Die Haupt-Kontrollschleife (Endlosschleife mit loop)
    // Sie läuft so lange, bis sie durch einen Zustand einen Wert per break zurückgibt.
    let finaler_status: MaschinenStatus = 'hauptschleife: loop {
        println!("\n[Status] Temperatur: {}°C, Werkstücke: {}", temperatur, anzahl_werkstuecke);

        // 2. Bedingter Ausdruck (if-else als Expression)
        let status = if temperatur >= 100.0 {
            MaschinenStatus::Ueberhitzt
        } else if anzahl_werkstuecke >= max_werkstuecke {
            // Wir beenden die Hauptschleife und geben den Status Bereit zurück
            break 'hauptschleife MaschinenStatus::Bereit;
        } else {
            MaschinenStatus::Bereit
        };

        // Reagieren auf den ermittelten Status
        match status {
            MaschinenStatus::Ueberhitzt => {
                println!("[CRITICAL] Überhitzung detektiert! Notabschaltung wird eingeleitet.");
                break 'hauptschleife MaschinenStatus::Notaus;
            }
            MaschinenStatus::Bereit => {
                println!("[Info] Maschine arbeitet... Starte Füllzyklus.");
                
                // 3. Bedingte Schleife (while) für den Füllvorgang
                let mut fuellstand = 0;
                while fuellstand < 100 {
                    fuellstand += 25;
                    println!("  -> Befülle Behälter: {}%", fuellstand);
                }

                // 4. Zählschleife (for) zur Qualitätskontrolle (Sensoren auslesen)
                println!("  -> Starte Sensorprüfung:");
                let sensoren = [true, true, true, false, true];
                let mut fehler_gefunden = false;

                'sensor_check: for (index, &sensor_ok) in sensoren.iter().enumerate() {
                    if !sensor_ok {
                        println!("     [FEHLER] Sensor {} meldet Defekt!", index + 1);
                        fehler_gefunden = true;
                        break 'sensor_check; // Bricht nur die Sensorprüfung ab
                    }
                    println!("     Sensor {}: OK", index + 1);
                }

                // Wenn Sensoren defekt sind, erhöhen wir die Temperatur als Verschleiß-Simulation
                if fehler_gefunden {
                    println!("[Warnung] Sensorfehler führt zu thermischer Belastung!");
                    temperatur += 15.0;
                } else {
                    anzahl_werkstuecke += 1;
                    temperatur += 5.0; // Normale Erwärmung im Betrieb
                }
            }
            MaschinenStatus::Notaus => {
                // Dieser Pfad ist logisch über den if-Ausdruck gesperrt,
                // muss aber zur Vollständigkeit des Matchings aufgeführt werden.
                break 'hauptschleife MaschinenStatus::Notaus;
            }
        }
    };

    // 5. Systemauswertung nach dem Schleifenabbruch
    println!("\n=== System gestoppt ===");
    match finaler_status {
        MaschinenStatus::Bereit => {
            println!("Status: Erfolgreich abgeschlossen. Soll-Stückzahl erreicht.");
        }
        MaschinenStatus::Notaus => {
            println!("Status: NOT-AUS aktiv. Techniker rufen!");
        }
        _ => {}
    }
}

Schritt 3: Ausführen und Überprüfen

Starten Sie das Programm in Ihrem Terminal:

cargo run

Das Programm simuliert den Durchlauf, befüllt die Behälter und bricht bei Auftreten des simulierten Sensorfehlers (Sensor 4 meldet false) die Sensorprüfung vorzeitig ab. Durch die thermische Belastung steigt die Temperatur, bis das System im vierten Durchlauf die 100°C-Marke überschreitet, in die Überhitzung läuft und die Hauptschleife mit MaschinenStatus::Notaus abbricht.

8. Mentale Modelle & Deep Dive

15.1 Bedingte Ausdrücke

15.1.1 if-Verzweigungen und die Eliminierung des ternären Operators

In vielen C-basierten Sprachen existiert zur schnellen Zuweisung der ternäre Operator: x = bedingung ? a : b;. In Rust gibt es diesen Operator nicht. Er ist syntaktisch redundant, da if in Rust ein vollständiger Ausdruck ist:

#![allow(unused)]
fn main() {
let x = if bedingung { a } else { b };
}

Diese Syntax ist weitaus lesbarer und lässt sich nahtlos auf mehrere Zweige (else if) erweitern, ohne an Lesbarkeit zu verlieren.

Typkonsistenz und Divergenz

Wenn ein if-Ausdruck einen Wert zurückgibt, müssen alle Pfade denselben Typ evaluieren. Was passiert jedoch, wenn ein Pfad die Ausführung abbricht (z. B. durch panic!, return oder break)?

#![allow(unused)]
fn main() {
let divisor = 0;
let ergebnis = if divisor != 0 {
    100 / divisor
} else {
    panic!("Division durch Null!"); // Welchen Typ gibt panic! zurück?
};
}

Dieser Code kompiliert einwandfrei. Der Grund liegt im sogenannten Never-Type ! (auch Divergenz-Typ genannt). Ausdrücke, die das Programm beenden, den aktuellen Thread einfrieren oder den Kontrollfluss umleiten (wie panic!, exit oder return), evaluieren zum Typ !.

Der Compiler erlaubt es, den Typ ! implizit in jeden beliebigen anderen Typ umzuwandeln (Coercion). Dadurch ist die Typkonsistenz des if-Ausdrucks formal gewahrt.

Hardware-Ebene: Branch Prediction und Branchless Programming

Moderne CPUs nutzen Pipelines, um Instruktionen parallel vorzubereiten. Trifft die CPU auf eine Verzweigung (if), versucht die eingebaute Branch Prediction (Sprungvorhersage) zu raten, welcher Pfad als nächstes ausgeführt wird, um die Pipeline vorab zu befüllen.

  • Erfolgreiche Vorhersage: Die Ausführung läuft mit maximaler Geschwindigkeit weiter.
  • Fehlvorhersage (Branch Misprediction): Die CPU muss die bereits geladenen Instruktionen verwerfen (Pipeline Flush) und die Instruktionen des tatsächlichen Pfades neu laden. Das kostet ca. 10 bis 20 CPU-Zyklen.

Der Rust-Compiler und das LLVM-Backend versuchen daher, einfache if-else-Zuweisungen in Branchless Code (sprungfreien Code) zu übersetzen. Statt eines Sprungsbefehls (jmp in x86-Assembler) nutzt der Compiler CPU-Instruktionen wie cmov (Conditional Move) oder bitweise Arithmetik.

#![allow(unused)]
fn main() {
// Rust-Code:
let x = if a < b { a } else { b };
}

Wird vom Compiler oft in eine einzige x86-Instruktion übersetzt:

cmp eax, ebx
cmovg eax, ebx  ; Wenn eax > ebx, kopiere ebx in eax

Es findet kein Sprung statt, wodurch Pipeline-Stalls hardwareseitig komplett ausgeschlossen werden.

15.2 Schleifensysteme

15.2.1 Die Endlosschleife (loop) und statische Analyse

Ein häufiges Muster in der Systemprogrammierung ist die Endlosschleife. In C schreibt man meist while (1) oder for (;;). Rust bietet hierfür das explizite Schlüsselwort loop.

Loop vs. While True

Für den Programmierer scheinen loop und while true identisch zu sein. Für den Rust-Compiler besteht jedoch ein fundamentaler Unterschied im Bereich der Kontrollfluss-Analyse (Control Flow Analysis):

#![allow(unused)]
fn main() {
// Beispiel A: loop
let x: i32;
loop {
    x = 42;
    break;
}
println!("{}", x); // Kompiliert! Der Compiler weiß, dass x garantiert initialisiert wurde.

// Beispiel B: while true
let y: i32;
while true {
    y = 42;
    break;
}
println!("{}", y); // FEHLER! Compiler meldet: "use of possibly-uninitialized variable: `y`"
}

Warum scheitert while true? Die Bedingung einer while-Schleife wird zur Laufzeit ausgewertet. Der Compiler führt bei while keine statische Analyse der Wahrheitswerte durch (er optimiert sie zwar später weg, aber die Typprüfung findet davor statt). Für den Compiler besteht bei while immer die theoretische Möglichkeit, dass die Schleife niemals betreten wird (falls die Bedingung direkt false ist). Daher gilt die Variable y nach der Schleife als “möglicherweise uninitialisiert”. loop hingegen ist syntaktisch als Endlosschleife definiert. Der Compiler garantiert, dass der Block mindestens einmal durchlaufen wird. Daher gilt x nach dem Ausbruch per break als sicher initialisiert.

Loop als wertrückgebender Ausdruck

In Rust kann loop einen Wert über das break-Schlüsselwort zurückgeben:

#![allow(unused)]
fn main() {
let mut counter = 0;
let ergebnis = loop {
    counter += 1;
    if counter == 10 {
        break counter * 2; // Wertübergabe bei Schleifenabbruch!
    }
}; // ergebnis ist nun 20
}

Dies ist besonders nützlich bei Retry-Operationen (z. B. das Abfragen eines Netzwerk-Sockets, bis Daten eintreffen).

15.2.2 Die bedingte Schleife (while)

Die while-Schleife ist die klassische Schleife mit Eintrittsbedingung. Sie gibt im Gegensatz zu loop niemals Werte zurück. Ihr Rückgabetyp ist immer ().

#![allow(unused)]
fn main() {
while bedingung {
    // Code
}
}

Wichtig: Da die Bedingung vor jedem Durchlauf geprüft wird, kann die Schleife auch 0-mal ausgeführt werden. Aus diesem Grund kann kein benutzerdefinierter Typ zurückgegeben werden, da im Falle von 0 Durchläufen kein Wert zur Zuweisung existieren würde.

15.2.3 Die Zählschleife (for) und die Magie der Iteratoren

Die for-Schleife in Rust is syntaktischer Zucker für die Arbeit mit Iteratoren. Es gibt in Rust keine klassische C-Schleife der Form for (int i = 0; i < 10; i++).

Syntax und Ranges

Rust stellt über die Standardbibliothek Range-Typen zur Verfügung:

  • a..b (Exklusive Range: von a bis b-1, Typ std::ops::Range)
  • a..=b (Inklusive Range: von a bis b, Typ std::ops::RangeInclusive)
#![allow(unused)]
fn main() {
for i in 0..5 {
    // i nimmt nacheinander die Werte 0, 1, 2, 3, 4 an
}
}
Der Blick unter die Haube: Das IntoIterator-Trait

Wenn Sie schreiben:

#![allow(unused)]
fn main() {
for element in kollektion { ... }
}

Übersetzt der Compiler dies im Hintergrund in ein Konstrukt, das den Iterator konsumiert:

#![allow(unused)]
fn main() {
let mut iterator = IntoIterator::into_iter(kollektion);
while let Some(element) = iterator.next() {
    // Schleifenkörper
}
}

Das bedeutet, dass for-Schleifen direkt mit dem Ownership-System verknüpft sind. Je nachdem, wie Sie die Kollektion übergeben, ändern sich die Besitzverhältnisse:

  1. for item in &kollektion: Ruft .iter() auf. Leiht die Elemente unveränderlich aus.
  2. for item in &mut kollektion: Ruft .iter_mut() auf. Leiht die Elemente veränderlich aus.
  3. for item in kollektion: Ruft into_iter() auf. Konsumiert die Kollektion (Verschiebung/Move). Die Kollektion ist danach nicht mehr verwendbar.
Performance: Eliminierung des Bounds Checkings und Loop Unrolling

In klassischen Sprachen führt ein Schleifenzugriff auf ein Array mittels Index immer zu einer Sicherheitsüberprüfung zur Laufzeit:

// C++ oder Java
for (int i = 0; i < array.length(); i++) {
    print(array[i]); // Prüft bei jedem Durchlauf: Ist i < length?
}

In Rust wird bei der Nutzung von for element in array.iter() der Iterator direkt vom Compiler analysiert. Da der Iterator die Länge des Arrays exakt kennt und sich nicht von außen manipulieren lässt, garantiert der Compiler zur Compilezeit, dass kein Index-Zugriff außerhalb der Grenzen stattfinden kann.

Die Folge: Der LLVM-Compiler entfernt alle Laufzeit-Grenzprüfungen (Bounds Checks) vollständig aus der Schleife. Das macht Rust-Schleifen in vielen Fällen performanter als äquivalenten C++-Code.

Zusätzlich wendet LLVM Optimierungen wie Loop Unrolling (Schleifenentrollung) an. Dabei wird der Schleifenkörper bei bekannten, kleinen Ranges im Maschinencode dupliziert, um die Sprunginstruktionen komplett einzusparen:

#![allow(unused)]
fn main() {
// Rust-Code:
for i in 0..3 {
    mach_etwas(i);
}
}

Wird im Maschinencode zu:

; Entrollte Schleife ohne Sprung-Instruktionen:
call mach_etwas(0)
call mach_etwas(1)
call mach_etwas(2)

15.2.4 Labels & Schleifensteuerung

Schleifen-Labels ermöglichen es, komplexe Sprungstrukturen flach und verständlich abzubilden. Ein Label wird mit einem einfachen Anführungszeichen eingeleitet und mit einem Doppelpunkt abgeschlossen. Es wird direkt vor der jeweiligen Schleife deklariert.

#![allow(unused)]
fn main() {
'aeussere_schleife: loop {
    'innere_schleife: for x in 0..10 {
        if x == 5 {
            // Beendet nicht 'innere_schleife, sondern die äußere loop!
            break 'aeussere_schleife; 
        }
        if x == 2 {
            // Springt zum nächsten Durchlauf der äußeren Schleife
            continue 'aeussere_schleife;
        }
    }
}
}
Syntaktische Regeln
  • Labels folgen den Benennungsregeln für Bezeichner (Schlangenschrift, lowercase).
  • Ein Label kann nur auf direkt darauf folgende Schleifen (loop, while, for) angewendet werden. Es kann nicht für freistehende Codeblöcke {} genutzt werden.
  • break mit Rückgabewert kann mit Labels kombiniert werden: break 'label wert;.

Exhaustive API-Reference (Lückenlos)

In diesem Abschnitt werden alle relevanten Standardbibliotheks-Methoden für Iteratoren und Ranges dokumentiert, die zur Steuerung und Auswertung von Schleifen in Rust unerlässlich sind.

1. std::iter::Iterator::next

  • Signatur: fn next(&mut self) -> Option<Self::Item>
  • Parameter: &mut self (veränderliche Referenz auf den Iterator-Zustand).
  • Rückgabetyp: Option<Self::Item>. Gibt Some(item) zurück, wenn ein weiteres Element existiert, andernfalls None.
  • Sicherheitsaspekte & Panics: Panikt nie. Mutiert den internen Zustand des Iterators (erhöht den internen Index).
  • Kurzbeispiel: 
    #![allow(unused)]
fn main() {
let mut iter = [10, 20].iter();
assert_eq!(iter.next(), Some(&10));
assert_eq!(iter.next(), Some(&20));
assert_eq!(iter.next(), None);
}

2. std::iter::Iterator::enumerate

  • Signatur: fn enumerate(self) -> Enumerate<Self>
  • Parameter: self (konsumiert den ursprünglichen Iterator).
  • Rückgabetyp: Ein Iterator vom Typ Enumerate, der Tupel der Form (usize, Self::Item) liefert.
  • Sicherheitsaspekte & Panics: Panikt nie. Der Index beginnt bei 0 und erhöht sich um 1 bei jedem Aufruf.
  • Kurzbeispiel: 
    #![allow(unused)]
fn main() {
let elemente = ["a", "b"];
let mut iter = elemente.iter().enumerate();
assert_eq!(iter.next(), Some((0, &"a")));
assert_eq!(iter.next(), Some((1, &"b")));
}

3. std::iter::Iterator::step_by

  • Signatur: fn step_by(self, step: usize) -> StepBy<Self>
  • Parameter: self (konsumiert den Iterator), step (usize, die Schrittweite).
  • Rückgabetyp: Ein neuer Iterator, der nur jedes step-te Element ausgibt.
  • Sicherheitsaspekte & Panics: Panikt, wenn step == 0.
  • Kurzbeispiel: 
    #![allow(unused)]
fn main() {
let mut iter = (0..10).step_by(3);
assert_eq!(iter.next(), Some(0));
assert_eq!(iter.next(), Some(3));
assert_eq!(iter.next(), Some(6));
assert_eq!(iter.next(), Some(9));
}

4. std::iter::Iterator::rev

  • Signatur: fn rev(self) -> Rev<Self> where Self: DoubleEndedIterator
  • Parameter: self.
  • Rückgabetyp: Ein umgekehrter Iterator. Erfordert, dass der zugrundeliegende Iterator das Trait DoubleEndedIterator implementiert (z. B. Ranges oder Array-Iteratoren).
  • Sicherheitsaspekte & Panics: Panikt nie.
  • Kurzbeispiel: 
    #![allow(unused)]

5. std::iter::Iterator::zip

  • Signatur: fn zip<U>(self, other: U) -> Zip<Self, <U as IntoIterator>::IntoIter> where U: IntoIterator
  • Parameter: self, other (eine beliebige Kollektion oder ein Iterator, der in einen Iterator umgewandelt werden kann).
  • Rückgabetyp: Ein Iterator, der Paare (A, B) liefert, bis einer der beiden Iteratoren erschöpft ist.
  • Sicherheitsaspekte & Panics: Panikt nie.

9. Drei praktische Übungen

Übung 1: FizzBuzz-Modifikation (Leicht)

Problembeschreibung: Schreiben Sie ein Programm, das die Zahlen von 1 bis 50 durchläuft.

  • Wenn eine Zahl durch 3 teilbar ist, geben Sie "Fizz" aus.
  • Wenn eine Zahl durch 5 teilbar ist, geben Sie "Buzz" aus.
  • Wenn eine Zahl durch 3 und 5 teilbar ist, geben Sie "Fizz und Buzz" aus.
  • Nutzen Sie hierfür eine for-Schleife über eine Range und weisen Sie das Ergebnis der Fallprüfung in jeder Iteration einer unveränderlichen Variablen über einen if-else-Ausdruck zu, bevor Sie es ausgeben.

Anforderungen:

  • Exakte Signatur der Prüffunktion: fn fizzbuzz_status(zahl: i32) -> String
  • Keine Platzhalter im Code.

Lösungshinweis (Hint): Nutzen Sie den Modulo-Operator % für die Teilbarkeit. Denken Sie daran, dass der am stärksten einschränkende Fall (Teilbarkeit durch 3 und 5) als erster Fall im if-Ausdruck geprüft werden muss.

Übung 2: Optimierte Matrix-Suche mit Labels (Mittel)

Problembeschreibung: Gegeben ist eine quadratische 4x4-Matrix mit Ganzzahlen. Schreiben Sie eine Funktion suche_in_matrix, die nach einer Zielzahl sucht. Sobald die Zahl gefunden wird, soll die Suche augenblicklich über ein Schleifen-Label abgebrochen werden. Die Funktion soll ein Option<(usize, usize)> zurückgeben, das die Zeilen- und Spaltenkoordinaten enthält.

Anforderungen:

  • Signatur: fn suche_in_matrix(matrix: &[[i32; 4]; 4], ziel: i32) -> Option<(usize, usize)>
  • Nutzen Sie verschachtelte for-Schleifen und ein Loop-Label für den Abbruch.

Lösungshinweis (Hint): Versehen Sie die äußere Schleife mit dem Label 'zeilen_suche. Nutzen Sie im inneren Schleifenkörper ein break 'zeilen_suche, sobald der Wert matched, um das vorzeitige Verlassen beider Schleifen einzuleiten.

Übung 3: Run-Length-Encoding (RLE) Kompressor (Schwer)

Problembeschreibung: Implementieren Sie einen einfachen Kompressionsalgorithmus (Lauflängenkodierung) für Strings. Das Programm soll eine Zeichenkette (z. B. "AAAAABBBCC") komprimieren und als codierten String zurückgeben ("A5B3C2"). Nutzen Sie hierbei eine while let- oder eine gesteuerte for-Schleife über die Zeichen des Strings und verarbeiten Sie die Übergänge mithilfe von bedingten Ausdrücken und Schleifensteuerung.

Anforderungen:

  • Signatur: fn rle_encode(input: &str) -> String
  • Sonderfall: Ist der Eingabestring leer, geben Sie einen leeren String zurück.
  • Verwenden Sie keine externen Crates, sondern nur Standard-Iteratoren.

Lösungshinweis (Hint): Iterieren Sie über die Zeichen. Speichern Sie das aktuelle Zeichen und einen Zähler. Vergleichen Sie im Schleifenkörper das jeweils nächste Zeichen mit dem aktuellen Zeichen. Bei Übereinstimmung erhöhen Sie den Zähler, andernfalls schreiben Sie das Zeichen und den Zähler in ein Ergebnis-Buffer und setzen den Zähler zurück.

Active Recall (Selbsttest-Fragen)

  1. Frage: Warum kann eine while-Schleife in Rust im Gegensatz zu einer loop-Schleife niemals einen benutzerdefinierten Wert über break zurückgeben?
    • Antwort: Da eine while-Schleife eine Bedingung prüft, kann es sein, dass sie gar nicht ausgeführt wird (0 Durchläufe). In diesem Szenario gäbe es keinen Rückgabewert. Daher ist ihr Rückgabetyp prinzipiell auf () festgelegt.
  2. Frage: Welchen Typ besitzt ein if-Ausdruck, der keinen else-Zweig deklariert?
    • Antwort: Ein if-Ausdruck ohne else-Zweig gibt standardmäßig den Unit-Typ () zurück. Daher muss auch der if-Block zu () evaluieren (z. B. eine Zuweisung oder ein println!).
  3. Frage: Was ist der Never-Type ! und warum ist er für if-else-Zuweisungen wichtig?
    • Antwort: Der Never-Type repräsentiert Ausdrücke, die niemals zum normalen Kontrollfluss zurückkehren (wie panic! oder return). Da ! in jeden Typ umgewandelt werden kann, blockiert ein panic! in einem Zweig nicht die Typkonsistenz des Gesamtausdrucks.

Gezielte Fehlerprovokation (Compiler-Guided Learning)

Führen Sie absichtlich folgende Fehler in Ihren Code ein, um die Reaktionen des Compilers kennenzulernen:

  1. Schreiben Sie ein if-Expression-Zuweisung, bei der Sie im else-Zweig das abschließende Semikolon setzen, im if-Zweig jedoch nicht. Analysieren Sie die Fehlermeldung bezüglich des Unit-Typs ().
  2. Versuchen Sie, ein Label 'label an einen normalen Scope-Block anzuhängen (z. B. 'block: { let x = 5; }) und mittels break 'block daraus auszubrechen. Stellen Sie fest, dass Rust-Labels exklusiv für Schleifen reserviert sind.

11. Zusammenfassung

  • Ausdrucksorientierung: Rust ist eine primär ausdrucksbasierte Sprache. Bis auf Deklarationen und Semikolon-Statements geben fast alle Konstrukte (inklusive if und Blöcke) Werte zurück.
  • Typkonsistenz: Da Variablen zur Compilezeit eine feste Größe auf dem Stack haben müssen, müssen alle Pfade eines wertabgebenden if-Ausdrucks denselben Datentyp liefern.
  • Der Divergenz-Typ !: Erlaubt es dem Compiler, Ausdrücke, die das Programm beenden (wie panic!), typunabhängig in Verzweigungen zu integrieren.
  • Loop-Garantien: loop garantiert im Gegensatz zu while mindestens einen Durchlauf. Das erlaubt dem Compiler zu erkennen, dass darin deklarierte Variablen danach sicher initialisiert sind. Zudem kann loop Werte über break wert; zurückgeben.
  • Sichere Iteration: for-Schleifen nutzen das IntoIterator-Trait. Sie machen manuelle Indizes überflüssig, verhindern standardmäßig Out-of-Bounds-Fehler und ermöglichen dem LLVM-Compiler signifikante Optimierungen durch Wegfall von Sicherheitsprüfungen.
  • Labels: Schleifen-Labels ('name:) brechen mit break 'name oder continue 'name gezielt aus verschachtelten Schleifenstrukturen aus, wodurch unübersichtliche Flag-Zustände vermieden werden.
