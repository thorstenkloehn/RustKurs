# Kapitel 27: Eigene Datentypen mit Structs (Strukturen) strukturieren

Strukturen, kurz **Structs**, bilden das Fundament der Datenmodellierung in Rust. Sie ermöglichen es Ihnen, mehrere zusammengehörige Werte unterschiedlicher Typen zu einer logischen Einheit zusammenzufassen. Während in vielen objektorientierten Sprachen Daten und Verhalten in Klassen verschmolzen sind, trennt Rust diese Aspekte strikt: Structs definieren das reine Speicherlayout der Daten, während das Verhalten über `impl`-Blöcke (Implementierungen) nachträglich an die Typen gebunden wird.

Dieses Kapitel bietet eine allumfassende, lückenlose Referenz über alle Facetten von Rust-Strukturen – von den syntaktischen Grundlagen für Anfänger über fortgeschrittene Speicherverwaltungs- und Kapselungstechniken bis hin zu systemnahen Details wie Byte-Alignment, Compiler-Layout-Optimierungen, Thread-Sicherheit und manuellen Trait-Implementierungen auf Profi-Niveau.

## 2. Die Definition

Ein **Struct** ist ein zusammengesetzter Datentyp, der es Ihnen erlaubt, mehrere Werte unterschiedlicher Typen zu einer neuen, benannten Einheit zu kombinieren. In Rust sind Structs reine Datencontainer ohne inhärentes Verhalten. Verhalten wird ausschließlich außerhalb der Datenstruktur über das Schlüsselwort `impl` definiert.

Rust bietet drei verschiedene syntaktische Ausprägungen von Strukturen:

### 1. Klassisches Struct (Named-Field Struct)
Besitzt benannte Felder. Jedes Feld ist über einen Bezeichner (Identifier) und einen expliziten Typ definiert. Dies ist das Standardwerkzeug für komplexe Domänenmodelle, da der Zugriff über den Feldnamen maximale Klarheit bietet.
```rust
struct User {
    username: String,
    email: String,
    sign_in_count: u64,
    active: bool,
}
```

### 2. Tuple-Struct
Besitzt einen Namen für den Gesamttyp, aber die einzelnen Felder sind namenlos. Die Felder werden über ihre Position (Index `0`, `1`, `2` etc.) angesprochen. Tuple-Structs sind ideal, um einfache Datenstrukturen abzubilden, bei denen die Bedeutung der Felder aus ihrer Reihenfolge hervorgeht, oder um das *Newtype-Pattern* zu realisieren (Erstellung eines typsicheren Wrappers um einen primitiven Typ).
```rust
struct Color(i32, i32, i32); // RGB-Farbwert
struct Point(f64, f64, f64); // 3D-Koordinate
struct Inches(f64);          // Newtype-Pattern zur Verhinderung von Einheiten-Verwechslung
```

### 3. Unit-Like Struct
Besitzt keinerlei Felder und verbraucht im fertigen Programm 0 Bytes Speicherplatz (Zero-Sized Type, ZST). Es verhält sich syntaktisch wie das leere Tupel `()`. Unit-Like Structs werden verwendet, um Zustände abzubilden (z. B. in Zustandsautomaten/State Pattern) oder um Traits auf einem Typ zu implementieren, der selbst keinen internen Zustand benötigt.
```rust
struct AlwaysEqual; // Repräsentiert eine logische Regel für Testzwecke
struct JsonFormatter; // Reine Struktur zur Gruppierung von Formatierungs-Methoden
```

### Alltagsnahe Analogien

> [!NOTE]
> **Die Schablonen-Metapher (Klassisches Struct)**: Ein Steuerformular ist ein klassisches Struct. Es enthält feste, vorgedruckte Felder wie „Steuernummer“, „Bruttoeinkommen“ und „Kirchensteuer“. Jedes Feld verlangt einen bestimmten Datentyp. Solange das Formular leer ist, entspricht es der **Struct-Definition**. Sobald Sie Ihre konkreten Daten eintragen, halten Sie eine **Instanz** des Formulars in den Händen, die Sie einreichen (Ownership übertragen) oder kopieren können.

> [!TIP]
> **Die Briefumschlag-Metapher (Tuple-Struct / Newtype)**: Stellen Sie sich vor, Sie stecken eine Zahl (z. B. `150.0`) in einen Umschlag, auf dem draußen in großen Buchstaben „Euro“ steht, und eine andere Zahl in einen Umschlag, auf dem „US-Dollar“ steht. Obwohl sich in beiden Umschlägen gewöhnliches Papiergeld (Gleitkommazahlen) befindet, können Sie die Umschläge nicht versehentlich zusammenzählen oder verwechseln. Das Tuple-Struct ist der schützende Briefumschlag um Ihre Rohdaten.

> [!IMPORTANT]
> **Die Stempel-Metapher (Unit-Like Struct)**: Ein Unit-Like Struct verhält sich wie ein physischer Stempel. Der Stempel selbst enthält keine variablen Daten, aber er hinterlässt einen Abdruck (eine Typinformation) auf einem Dokument. Er dient dem Compiler als reines Signal: „Dieses Objekt existiert und verhält sich nach der Regel X“.

## 3. Das Problem & Die Motivation

Warum reichen uns primitive Typen und Tupel in der Softwareentwicklung nicht aus? Um dies zu verdeutlichen, vergleichen wir drei Ansätze zur Modellierung einer geografischen Position.

### 1. Lose Variablen
Wir speichern die Koordinaten und den Namen der Position in einzelnen Variablen:
```rust
let pos_latitude = 48.8584;
let pos_longitude = 2.2945;
let pos_name = String::from("Eiffelturm");
```
* **Mangelnde Kohäsion**: Der Compiler weiß nicht, dass diese Variablen zusammengehören. Sie können versehentlich `pos_latitude` mit der Geometrie eines anderen Ortes kombinieren.
* **API-Explosion**: Beim Übergeben der Daten an Funktionen wächst die Parameterliste unkontrolliert an:
  `fn calculate_distance(lat1: f64, lon1: f64, lat2: f64, lon2: f64) -> f64`

### 2. Tupel
Wir gruppieren die Werte in einem namenlosen Tupel:
```rust
let position = (48.8584, 2.2945, String::from("Eiffelturm"));
```
* **Unleserlichkeit**: Der Zugriff erfolgt über `position.0` und `position.1`. Ohne Dokumentation ist unklar, ob Index `0` die Breite oder die Länge repräsentiert.
* **Keine Typsicherheit**: Ein Tupel vom Typ `(f64, f64, String)` ist strukturell identisch mit einem Tupel, das das Gewicht, den Preis und die Marke eines Kaffees beschreibt: `(250.0, 4.99, String::from("Arabica"))`. Eine Funktion zur Distanzberechnung würde das Kaffee-Tupel annehmen und mathematisch unsinnige Werte berechnen.

### Detaillierter Vergleich der Datenstrukturen

| Kriterium | Lose Variablen | Tupel (`(T, U)`) | Structs (`struct`) |
| :--- | :--- | :--- | :--- |
| **Typidentität** | Nein (nur Basis-Typen) | Nein (nur strukturelle Identität) | **Ja** (eindeutiger, neuer Typ) |
| **Feld-Semantik** | Nein | Nein (Zugriff über numerischen Index) | **Ja** (Zugriff über Bezeichner) |
| **Kapselung (Kapselbar)** | Nein | Nein | **Ja** (über Sichtbarkeit `pub`) |
| **Methodenbindung** | Nein | Nein | **Ja** (über `impl`-Blöcke) |
| **Speicher-Overhead** | Keiner | Keiner | **Keiner** (Zero-Cost) |

## 4. Drei naive Versuche

Wir betrachten drei typische Fehlermuster, die Entwickler beim Entwurf von Strukturen in Rust machen.

### Versuch 1: Referenzen ohne Lebensdauer-Annotationen
Ein Programmierer möchte Heap-Allokationen vermeiden und speichert String-Slices (`&str`) direkt im Struct, um auf String-Literale oder externe Daten zu zeigen.
```rust
// Filename: src/main.rs
// Dieser Code kompiliert NICHT!
struct User {
    username: &str, 
    email: &str,
    active: bool,
}

fn main() {
    let user1 = User {
        username: "admin",
        email: "admin@server.com",
        active: true,
    };
}
```

### Versuch 2: Deklaration von partieller Mutabilität
Ein Entwickler möchte sicherstellen, dass der Benutzername unveränderlich bleibt, die E-Mail-Adresse jedoch geändert werden darf. Er versucht, das Feld im Struct als veränderbar zu markieren.
```rust
// Filename: src/main.rs
// Dieser Code kompiliert NICHT!
struct User {
    username: String,
    mut email: String, // Versuch der partiellen Mutabilität
    active: bool,
}
```

### Versuch 3: Das selbst-referenzierende Struct
Ein Entwickler möchte ein Struct erstellen, das einen String besitzt, und gleichzeitig eine Referenz auf einen Teil dieses Strings im selben Struct speichern (z. B. für einen Parser).
```rust
// Filename: src/main.rs
// Dieser Code kompiliert NICHT!
struct Parser {
    source: String,
    current_token: &str, // Zeigt auf einen Teilbereich von "source"
}
```

## 5. Die Anatomie der Fehler

### 1. Analyse von Versuch 1 (Fehlende Lifetimes)
Der Compiler verweigert die Arbeit mit folgender Meldung:
```text
error[E0106]: missing lifetime specifier
 --> src/main.rs:4:15
  |
4 |     username: &str,
  |               ^ expected named lifetime parameter
```
* **Erklärung**: Ein String-Slice `&str` ist eine Referenz (ein Zeiger auf Speicher). Rust muss zur Kompilierzeit garantieren, dass die Daten, auf die gezeigt wird, mindestens so lange leben wie das Struct selbst. Ohne explizite **Lifetimes** (z. B. `User<'a>`) kann der Compiler diese Garantie nicht prüfen. Wenn das Struct die Daten besitzen soll, müssen Sie den besitzenden Typ `String` nutzen.

### 2. Analyse von Versuch 2 (Partielle Mutabilität)
Der Compiler meldet einen Syntaxfehler:
```text
error: expected identifier, found keyword `mut`
 --> src/main.rs:5:5
  |
5 |     mut email: String,
  |     ^^^ expected identifier
```
* **Erklärung**: Mutabilität ist in Rust keine Eigenschaft des *Typs* (der Struct-Definition), sondern eine Eigenschaft der *Bindung* (der Variablendeklaration). Ein Struct ist im Speicher ein zusammenhängender Block. Entweder ist der gesamte Block beschreibbar (mutabel) oder schreibgeschützt (unmutabel). Dies wird bei der Instanziierung über `let mut` gesteuert. 
* **Ausnahme**: Möchte man Mutabilität erzwingen, obwohl die Instanz unmutabel ist, muss man auf Typen mit *Interior Mutability* (wie `Cell<T>` oder `RefCell<T>`) zurückgreifen.

### 3. Analyse von Versuch 3 (Selbst-Referenzierung)
Der Compiler verfängt sich in einem unlösbaren Lebensdauer-Konflikt:
```text
error[E0506]: cannot move out of `source` because it is borrowed
  --> src/main.rs:10:12
   |
10 |     let p = Parser {
   |             ^^^^^^
11 |         source: my_string,
   |                 --------- borrow of `my_string` occurs here
```
* **Erklärung**: Würde Rust selbst-referenzierende Structs ohne Weiteres erlauben, würde eine Speicherkatastrophe drohen. Wenn das Struct `Parser` im Speicher verschoben wird (z. B. durch Übergabe an eine Funktion oder Rückgabe aus einer Funktion), ändert sich seine physische Adresse im Stack. Der Zeiger `current_token` würde jedoch weiterhin auf die alte, nun ungültige Stack-Adresse zeigen. Dies würde zu einem schweren Speicherfehler (Use-After-Free) führen. Rusts Borrow Checker verhindert dies fundamental.

## 6. Die Lösung

Wir präsentieren die korrekten, sicheren Lösungsansätze für die drei typischen Fehlerszenarien.

### Didaktischer Pseudocode

```text
1. LÖSUNG FÜR REFERENZEN:
   Verwende besitzenden Datentypen (String), damit das Struct Herr über seinen Speicher ist.
   ODER: Deklariere explizit die Lebensdauer 'a, sodass das Struct weiß: "Ich darf nicht länger leben als meine Quelle".

2. LÖSUNG FÜR MUTABILITÄT:
   Definiere das Struct ganz normal.
   Mache die Instanz veränderbar: let mut meine_instanz = ...

3. LÖSUNG FÜR SELBST-REFERENZIERUNG:
   Speichere keine Zeiger auf eigene Felder.
   Nutze stattdessen Indizes (z. B. usize für Start- und Endposition) als relative Verweise.
```

### Rust-Implementierung

```rust
// Lösung 1: Benutzung von Lifetimes für referenzierende Structs
struct BorrowedUser<'a> {
    username: &'a str, // Das Struct darf nicht länger leben als diese Referenz
    active: bool,
}

// Lösung 3: Auflösung von Selbst-Referenzierung über Indizes
struct SafeParser {
    source: String,
    token_start: usize, // Relative Position statt physischer Zeiger
    token_end: usize,
}

impl SafeParser {
    // Liefert das Token dynamisch zurück, ohne selbst-referenzierend zu sein
    fn get_current_token(&self) -> &str {
        &self.source[self.token_start..self.token_end]
    }
}

fn main() {
    // Lösung 2: Steuerung der Mutabilität über die Variablenbindung (let mut)
    let mut user1 = BorrowedUser {
        username: "admin",
        active: true,
    };
    user1.active = false; // Erlaubt, da user1 als "mut" deklariert wurde

    let parser = SafeParser {
        source: String::from("LET x = 10;"),
        token_start: 4,
        token_end: 5,
    };
    println!("Aktuelles Token: {}", parser.get_current_token()); // Gibt "x" aus
}
```

### Zeile-für-Zeile-Erklärung des Speicherverhaltens (EVA)

* **Eingabe (Input)**:
  * Wir erstellen das Struct `SafeParser` im Stack-Frame von `main`.
  * Das Feld `source` erhält die Ownership des alloziierten Heap-Strings `"LET x = 10;"` (24 Bytes Stack-Struktur: Pointer, Länge, Kapazität).
  * Die Felder `token_start` und `token_end` erhalten die numerischen Werte `4` und `5` direkt auf dem Stack.
* **Verarbeitung (Processing)**:
  * Beim Aufruf von `parser.get_current_token()` wird eine unveränderliche Referenz `&self` übergeben.
  * Die Methode berechnet den Slice-Zugriff über die Stack-Variablen `self.token_start` und `self.token_end` (relative Indizes).
  * Es wird eine temporäre Slice-Referenz (`&str`) auf den Heap-Speicherbereich von `source` erzeugt.
* **Ausgabe (Output)**:
  * Das generierte String-Slice wird an `println!` übergeben und auf der Konsole ausgegeben. Da wir keine feste Referenz im Struct gespeichert haben, kann das Struct im Speicher gefahrlos verschoben werden – die Indizes bleiben stets relativ und damit gültig.

## 7. Kleines Tutorial: Entwicklung einer 2D-Physik-Engine

In diesem Tutorial entwickeln wir ein modulares Physik-System für eine 2D-Simulation. Wir demonstrieren dabei die Konzepte der Komposition (Structs in Structs), Methodenimplementierung, Datenkapselung und die Anwendung von assoziierten Konstruktoren.

### Schritt 1: Definition der geometrischen Basistypen (Tuple-Structs)
Wir erstellen zwei Tuple-Structs für Koordinaten und Geschwindigkeiten. Durch die separaten Typen verhindern wir, dass Positionen und Geschwindigkeiten versehentlich verwechselt werden.

```rust
#[derive(Debug, Clone, Copy)]
struct Point2D(f64, f64); // X- und Y-Koordinate

#[derive(Debug, Clone, Copy)]
struct Velocity2D(f64, f64); // Vx- und Vy-Geschwindigkeit (m/s)
```

### Schritt 2: Komposition des Hauptobjekts (Klassisches Struct)
Wir erstellen ein Struct `Particle`, das die zuvor definierten Tuple-Structs enthält. Das ist ein klassisches Beispiel für **Komposition** (Zusammensetzung komplexer Typen aus einfachen Bausteinen).

```rust
#[derive(Debug, Clone)]
struct Particle {
    name: String,
    position: Point2D,
    velocity: Velocity2D,
    mass: f64,
}
```

### Schritt 3: Konstruktor und Datenkapselung im `impl`-Block
Wir binden das Verhalten an unser `Particle`. Wir deklarieren den Konstruktor `new` als assoziierte Funktion. Aus Sicherheitsgründen machen wir die Felder des Particles privat und erlauben den Zugriff nur über kontrollierte Methoden.

```rust
impl Particle {
    // Assoziierte Funktion (Konstruktor)
    // Nutzt Field Init Shorthand für mass
    fn new(name: String, position: Point2D, velocity: Velocity2D, mass: f64) -> Self {
        // Validierung der Masse zur Laufzeit
        let validated_mass = if mass <= 0.0 { 1.0 } else { mass };
        
        Self {
            name,
            position,
            velocity,
            mass: validated_mass,
        }
    }

    // Getter-Methode für die Position (Kapselung)
    fn position(&self) -> Point2D {
        self.position
    }

    // Getter-Methode für die Masse
    fn mass(&self) -> f64 {
        self.mass
    }
}
```

### Schritt 4: Implementierung von verändernden Methoden
Wir fügen eine Methode `update_position` hinzu, die die Position des Partikels basierend auf seiner Geschwindigkeit und einem Zeitschritt `dt` verändert. Da sich die Position ändert, benötigen wir eine veränderliche Ausleihe (`&mut self`).

```rust
impl Particle {
    // Simuliert einen Zeitschritt (dt in Sekunden)
    fn update_position(&mut self, dt: f64) {
        let new_x = self.position.0 + (self.velocity.0 * dt);
        let new_y = self.position.1 + (self.velocity.1 * dt);
        
        self.position = Point2D(new_x, new_y);
    }

    // Wendet eine Kraft auf das Partikel an (Beschleunigung a = F / m)
    fn apply_force(&mut self, force_x: f64, force_y: f64, dt: f64) {
        let accel_x = force_x / self.mass;
        let accel_y = force_y / self.mass;
        
        let new_vx = self.velocity.0 + (accel_x * dt);
        let new_vy = self.velocity.1 + (accel_y * dt);
        
        self.velocity = Velocity2D(new_vx, new_vy);
    }
}
```

### Schritt 5: Integration und Simulation in `main`
Wir führen nun eine kurze physikalische Simulation in der `main`-Funktion aus. Dabei nutzen wir auch die Struct-Update-Syntax (`..`), um ein schwereres Klon-Partikel zu erstellen.

```rust
fn main() {
    // 1. Initialisierung der Physik-Objekte
    let start_pos = Point2D(0.0, 0.0);
    let start_vel = Velocity2D(10.0, 5.0);
    
    let mut p1 = Particle::new(
        String::from("Partikel Alpha"),
        start_pos,
        start_vel,
        2.5
    );

    // 2. Erstellung eines Klons mit modifizierten Werten über Update-Syntax
    // Da String nicht Copy implementiert, müssen wir name klonen, um user1 nicht zu entwerten!
    let mut p2 = Particle {
        name: String::from("Partikel Beta (Schwer)"),
        mass: 10.0,
        ..p1.clone() // Nutzt die geklonten Positions- und Geschwindigkeitswerte
    };

    println!("Ausgangszustand p1: {:?}", p1);
    println!("Ausgangszustand p2 (Masse {} kg): {:?}", p2.mass(), p2);

    // 3. Simulation eines Zeitschritts von 2.0 Sekunden mit Krafteinwirkung
    let dt = 2.0;
    
    p1.apply_force(5.0, 0.0, dt); // Kraft von 5 Newton in X-Richtung
    p1.update_position(dt);
    
    p2.update_position(dt); // Bewegt sich träger ohne Krafteinwirkung

    println!("Nach Simulation p1 (Position): {:?}", p1.position());
    println!("Nach Simulation p2 (Position): {:?}", p2.position());
}
```

## 8. Mentale Modelle & Deep Dive

### 8.1 Speicherlayout & Repräsentation

Wie genau ordnet Rust Ihre Datenstrukturen physisch im RAM an? Dies wird durch die Datenausrichtung (Alignment) und die vom Compiler gewählte Repräsentation gesteuert.

#### Alignment & Padding
Jeder Datentyp besitzt ein Alignment (Ausrichtungsanforderung), das angibt, an welchen Speicheradressen er liegen darf. Ein Verstoß führt auf manchen CPUs zu Hardware-Ausnahmen (Bus-Errors) und auf allen CPUs zu drastischen Performanceeinbußen.

* **Alignment-Regel**: Ein Typ mit der Ausrichtung $N$ Bytes darf nur an Speicheradressen abgelegt werden, die ohne Rest durch $N$ teilbar sind (z. B. Adressen wie `0x00`, `0x08`, `0x10`).
* **Padding**: Um diese Ausrichtung einzuhalten, fügt der Compiler ungenutzte Füllbytes (Padding) ein.

#### Repräsentations-Attribute (`#[repr(...)]`)
Sie können das Speicherlayout Ihres Structs über Attribute direkt beeinflussen:

##### 1. `#[repr(Rust)]` (Standard)
Der Compiler darf die Reihenfolge der Felder frei vertauschen, um das Padding zu minimieren.
```rust
struct RustLayout {
    a: u8,   // 1 Byte
    b: u64,  // 8 Bytes
    c: u16,  // 2 Bytes
}
```
*Speichergröße*: **16 Bytes** (optimiert durch Umsortierung zu `b` -> `c` -> `a` + 5 Bytes Padding).

##### 2. `#[repr(C)]`
Zwingt den Compiler, die Felder exakt in der Reihenfolge abzubringen, in der sie im Code deklariert wurden. Unverzichtbar für FFI (Foreign Function Interface) beim Aufruf von C-Bibliotheken.
```rust
#[repr(C)]
struct CLayout {
    a: u8,   // 1 Byte
    // 7 Bytes Padding
    b: u64,  // 8 Bytes
    c: u16,  // 2 Bytes
    // 6 Bytes Padding am Ende (für Array-Alignment)
}
```
*Speichergröße*: **24 Bytes** (Ineffizient, aber kompatibel mit C).

##### 3. `#[repr(packed)]`
Entfernt jegliches Padding. Alle Felder liegen ohne Lücken hintereinander im Speicher.
```rust
#[repr(packed)]
struct PackedLayout {
    a: u8,   // 1 Byte
    b: u64,  // 8 Bytes (liegt unaligned im Speicher!)
    c: u16,  // 2 Bytes
}
```
*Speichergröße*: **11 Bytes** ($1 + 8 + 2$).
> [!CAUTION]
> **Hohes Risiko!** Der Zugriff auf unaligned Felder (wie `b`) kann zu CPU-Ausnahmen führen. Zudem ist es in Rust **strengstens verboten** und gilt als *Undefined Behavior*, eine Referenz (`&b`) auf ein unaligned Feld in einem gepackten Struct zu erstellen, da Referenzen in Rust zwingend aligned sein müssen!

##### 4. `#[repr(transparent)]`
Erlaubt es, ein Struct zu definieren, das genau ein nicht-Zero-Sized-Feld besitzt. Es garantiert, dass das Struct im Speicher exakt dieselbe Repräsentation und Größe aufweist wie das innenliegende Feld. Ideal für typsichere Wrapper.
```rust
#[repr(transparent)]
struct Wrapper(u32); // Garantiert exakt dieselbe Repräsentation wie u32
```

#### Zero-Sized Types (ZSTs)
Unit-Like Structs (wie `struct Empty;`) belegen **0 Bytes** Speicher.
* Der Compiler allokiert keinen Speicher für sie.
* Ein Array von 10.000 `Empty`-Objekten (`[Empty; 10000]`) belegt ebenfalls exakt 0 Bytes im RAM.
* Der Compiler optimiert alle Zugriffe weg. Interne Zeiger auf ZSTs zeigen stets auf einen virtuellen, gut ausgerichteten Zeiger (in der Regel auf den Wert des Alignments, z. B. `0x08`).

#### Nischen-Optimierung (Null Pointer Optimization)
Rust nutzt ungenutzte Bitmuster (Nischen) von Typen zur Speicheroptimierung. Besitzt ein Struct ein Feld, das keinen Nullwert annehmen darf (z. B. `NonNull<T>` oder `Box<T>`), und verpacken Sie dieses Struct in ein `Option`, nutzt der Compiler den Wert `0` für das `None`-Element.
```rust
struct MyNode {
    next: Box<MyNode>, // Box ist ein Non-Null-Zeiger
}
```
Die Größe von `Option<MyNode>` ist physisch identisch mit der Größe von `MyNode` allein (8 Bytes). Es wird kein zusätzliches Tag-Byte für das `Option` benötigt.

### 8.2 Generische Structs, Lifetimes & PhantomData

Wenn Strukturen flexibel auf verschiedene Datentypen oder temporäre Speicherbereiche reagieren müssen, kommen Generics und Lifetimes zum Einsatz.

#### Generische Strukturen
Sie können Typparameter in spitzen Klammern definieren:
```rust
struct Wrapper<T> {
    value: T,
}

impl<T> Wrapper<T> {
    fn new(value: T) -> Self {
        Self { value }
    }
}
```
* **Monomorphisierung**: Rust erzeugt beim Kompilieren für jede konkrete Instanziierung (z. B. `Wrapper<i32>`, `Wrapper<String>`) eine eigene Kopie des Maschinencodes. Dies bedeutet: Keine Performanceverluste zur Laufzeit (Zero-Cost).

#### Structs mit Lebensdauern (Lifetimes)
Soll ein Struct temporäre Referenzen halten, müssen Sie die Lebensdauer über Parameter deklarieren:
```rust
struct Preview<'a> {
    content: &'a str, // Das Struct darf nicht länger leben als diese Textquelle
}
```

#### PhantomData
Manchmal müssen Sie einen generischen Typ oder eine Lebensdauer im Struct deklarieren, obwohl das Feld diesen Typ nicht direkt nutzt (z. B. bei der Interaktion mit Rohzeigern im Systemcode). Da Rust ungenutzte Generics verbietet, müssen Sie `std::marker::PhantomData` verwenden:
```rust
use std::marker::PhantomData;

struct RawWrapper<T> {
    ptr: *mut u8,       // Unbemaßter Speicherbereich
    _marker: PhantomData<T>, // Weist dem Compiler an, den Typ T logisch zu binden
}
```
`PhantomData` belegt physisch **0 Bytes** im Speicher, steuert jedoch die logische Ownership-Prüfung des Compilers und bestimmt die sogenannte **Varianz** des Typs.

### 8.3 Fortgeschrittene Entwurfsmuster

#### 1. Das Builder-Pattern
Wenn Strukturen viele optionale Felder besitzen oder die Konstruktion komplex ist, ist ein Konstruktor mit 15 Parametern unleserlich. Das Builder-Pattern löst dies durch eine fließende Schnittstelle (Fluent API).

```rust
// Das eigentliche Struct (Felder sind privat)
#[derive(Debug)]
struct Connection {
    host: String,
    port: u16,
    timeout: u32,
    keep_alive: bool,
}

// Der Builder zur schrittweisen Konfiguration
struct ConnectionBuilder {
    host: String,
    port: Option<u16>,
    timeout: Option<u32>,
    keep_alive: Option<bool>,
}

impl ConnectionBuilder {
    // Startet die Konfiguration
    fn new(host: String) -> Self {
        Self {
            host,
            port: None,
            timeout: None,
            keep_alive: None,
        }
    }

    // Setzt das Port-Feld
    fn port(mut self, port: u16) -> Self {
        self.port = Some(port);
        self
    }

    // Setzt das Timeout-Feld
    fn timeout(mut self, seconds: u32) -> Self {
        self.timeout = Some(seconds);
        self
    }

    // Setzt die Keep-Alive-Option
    fn keep_alive(mut self, active: bool) -> Self {
        self.keep_alive = Some(active);
        self
    }

    // Konsumiert den Builder und baut das fertige Objekt
    fn build(self) -> Result<Connection, String> {
        let port = self.port.unwrap_or(80); // Standardport 80
        let timeout = self.timeout.unwrap_or(30); // Standardtimeout 30s
        let keep_alive = self.keep_alive.unwrap_or(true);

        if port == 0 {
            return Err(String::from("Ungültiger Port"));
        }

        Ok(Connection {
            host: self.host,
            port,
            timeout,
            keep_alive,
        })
    }
}
```

#### 2. Das Attribut `#[non_exhaustive]`
Wenn Sie eine Bibliothek schreiben und ein Struct veröffentlichen, dürfen Sie später keine neuen Felder hinzufügen, ohne den Code der Bibliotheksnutzer zu beschädigen (da deren Instanziierungen oder Pattern Matches dann unvollständig wären).

Über das Attribut `#[non_exhaustive]` verbieten Sie die direkte Instanziierung und das erschöpfende Pattern Matching außerhalb Ihres eigenen Crates:
```rust
#[non_exhaustive]
pub struct Config {
    pub api_key: String,
}
```
Nutzer der Bibliothek müssen dieses Struct nun zwingend über einen von Ihnen bereitgestellten Konstruktor erstellen und beim Pattern Matching einen Wildcard-Zweig (`_`) verwenden. Dies sichert die zukünftige Erweiterbarkeit (Abwärtskompatibilität).

#### 3. Das Type-State-Pattern (Zustandskontrolle zur Kompilierzeit)
Dies ist eines der mächtigsten Entwurfsmuster in Rust. Es nutzt das Typsystem, um sicherzustellen, dass Methoden nur in bestimmten logischen Zuständen aufgerufen werden können. Ein Verstoß führt zu einem Compilerfehler.

Wir modellieren einen `HttpRequest`:

```rust
// 1. Definition der logischen Zustände als Unit-Like Structs
struct Draft;
struct Configured;

// 2. Das Request-Struct besitzt einen generischen Zustandsparameter State
struct HttpRequest<State> {
    url: String,
    body: Option<String>,
    _state: std::marker::PhantomData<State>,
}

// 3. Methoden, die in JEDEM Zustand verfügbar sind
impl<State> HttpRequest<State> {
    fn url(&self) -> &str {
        &self.url
    }
}

// 4. Methoden, die NUR im Zustand Draft verfügbar sind
impl HttpRequest<Draft> {
    fn new(url: String) -> Self {
        Self {
            url,
            body: None,
            _state: std::marker::PhantomData,
        }
    }

    // Dieser Übergang konsumiert den Draft und gibt einen Configured-Request zurück
    fn set_body(self, body: String) -> HttpRequest<Configured> {
        HttpRequest {
            url: self.url,
            body: Some(body),
            _state: std::marker::PhantomData,
        }
    }
}

// 5. Methoden, die NUR im Zustand Configured verfügbar sind
impl HttpRequest<Configured> {
    // Ein Request kann nur abgesendet werden, wenn er konfiguriert wurde!
    fn send(self) {
        println!("Sende Request an {} mit Body: {:?}", self.url, self.body);
    }
}

fn main() {
    // Lauffähiger Code:
    let request = HttpRequest::new(String::from("https://api.com"));
    
    // FEHLER! request.send(); <-- Würde den Compiler abbrechen, da die Methode für Draft nicht existiert!

    let configured_request = request.set_body(String::from("{'data': 42}"));
    
    // Dies ist nun erlaubt:
    configured_request.send();
}
```

## 8.4 Interior Mutability in Structs

Normalerweise verbietet Rust jeglichen verändernden Zugriff auf Felder, wenn das übergeordnete Struct nicht als veränderbar (`mut`) deklariert ist. Über **Interior Mutability** (Innere Veränderlichkeit) können Sie diese Barriere gezielt durchbrechen. Dies ist nützlich für Caches, Lock-Verwaltungen oder interne Zähler.

#### Die Werkzeuge
* **`Cell<T>`**: Ermöglicht das Ändern von Werten durch Kopieren (`Copy`-Typen erforderlich). Verursacht keinerlei Laufzeit-Overhead.
* **`RefCell<T>`**: Verwaltet die Borrow-Regeln zur Laufzeit statt zur Kompilierzeit. Ermöglicht veränderliche Ausleihen auf Heap-Daten auch bei unmutablen Objekten. Stürzt bei Missbrauch zur Laufzeit ab (Panic).

```rust
use std::cell::RefCell;

struct Cache {
    data: String,
    // Dieser Zähler soll bei jedem Lesezugriff erhöht werden,
    // auch wenn das Cache-Objekt selbst unveränderlich (&self) ist.
    access_count: RefCell<usize>,
}

impl Cache {
    fn get_data(&self) -> &str {
        // Erhöhung des Zählers trotz unveränderlichem &self
        let mut count = self.access_count.borrow_mut();
        *count += 1;
        
        &self.data
    }
}
```

## 8.5 Destrukturierung & Pattern Matching

Sie können Structs über Pattern Matching zerlegen, um an die inneren Werte zu gelangen.

```rust
struct Point { x: i32, y: i32 }

fn main() {
    let p = Point { x: 10, y: 20 };

    // 1. Einfache Destrukturierung
    let Point { x, y } = p;

    // 2. Destrukturierung mit Variablen-Umbenennung
    let Point { x: x_coordinate, y: y_coordinate } = p;

    // 3. Ignorieren von Feldern über ".."
    let Point { x, .. } = p; // Ignoriert Y

    // 4. Binden über Referenzen im Pattern Matching (wichtig vor Edition 2018)
    let Point { ref x, ref mut y } = p;
}
```

## 8.6 Thread-Safety & Concurrency

Rust nutzt das Typsystem, um Concurrency-Fehler (Datenrennen / Data Races) zur Kompilierzeit zu verhindern. Die beiden Auto-Traits `Send` und `Sync` spielen dabei die entscheidende Rolle.

#### Automatische Ableitung (Auto-Traits)
`Send` und `Sync` sind Marker-Traits, die Sie nicht manuell implementieren müssen. Der Compiler leitet sie automatisch ab:
1. **`Send`**: Ein Struct ist `Send`, wenn alle seine Felder `Send` sind. Das Objekt darf in einen anderen Thread verschoben werden.
2. **`Sync`**: Ein Struct ist `Sync`, wenn alle seine Felder `Sync` sind. Das bedeutet, dass mehrere Threads gleichzeitig über Referenzen (`&T`) auf das Objekt zugreifen dürfen.

#### Shared Mutable State in Strukturen (Multi-Threading)
Wenn Sie Datenstrukturen zwischen Threads teilen und mutieren möchten, müssen Sie Thread-Safe Wrapper wie `Arc` (Atomarer Referenzzähler) und `Mutex` (Wechselseitiger Ausschluss) im Struct kombinieren.

```rust
use std::sync::{Arc, Mutex};
use std::thread;

struct ThreadSafeCounter {
    // Arc ermöglicht geteilten Besitz über Threadgrenzen hinweg.
    // Mutex garantiert exklusiven Schreibzugriff zur Laufzeit.
    value: Arc<Mutex<i32>>,
}

impl ThreadSafeCounter {
    fn new() -> Self {
        Self {
            value: Arc::new(Mutex::new(0)),
        }
    }

    fn increment(&self) {
        // Mutex sperren. lock() blockiert den Thread, bis Zugriff gewährt wird.
        let mut data = self.value.lock().unwrap();
        *data += 1;
    }

    fn get_value(&self) -> i32 {
        *self.value.lock().unwrap()
    }
}

fn main() {
    let counter = ThreadSafeCounter::new();
    let mut handles = vec![];

    for _ in 0..10 {
        // Wir klonen das Arc-Feld (erhöht den atomaren Referenzzähler)
        let counter_clone = Arc::clone(&counter.value);
        let handle = thread::spawn(move || {
            let mut data = counter_clone.lock().unwrap();
            *data += 1;
        });
        handles.push(handle);
    }

    for handle in handles {
        handle.join().unwrap();
    }

    println!("Finale Zählung: {}", counter.get_value()); // Gibt 10 aus
}
```

### 8.7 Performance & CPU-Architektur

Der Aufbau Ihrer Datenstrukturen hat massiven Einfluss auf die CPU-Cache-Effizienz und die Ausnutzung von Registern.

#### Cache Locality: AoS vs. SoA
CPUs lesen Daten nicht byteweise, sondern in sogenannten Cache-Lines (meist 64 Bytes am Stück). Liegen Daten, die nacheinander verarbeitet werden, hintereinander im Speicher, profitiert das Programm von der Cache-Lokalität.

##### 1. AoS (Array of Structures) - Klassischer Rust-Ansatz
```rust
struct Point { x: f32, y: f32, z: f32 }
let points: Vec<Point> = vec![Point { x: 1.0, y: 2.0, z: 3.0 }; 1000];
```
* **Verhalten im Speicher**:
  `[x1, y1, z1, x2, y2, z2, x3, y3, z3, ...]`
* **Einsatzbereich**: Ideal, wenn Sie immer alle Koordinaten eines einzelnen Punktes gleichzeitig verarbeiten müssen.

##### 2. SoA (Structure of Arrays) - Datenorientierter Ansatz (DOP)
```rust
struct Points {
    x: Vec<f32>,
    y: Vec<f32>,
    z: Vec<f32>,
}
```
* **Verhalten im Speicher**:
  Drei separate Speicherbereiche: `[x1, x2, x3, ...]`, `[y1, y2, y3, ...]`, `[z1, z2, z3, ...]`
* **Einsatzbereich**: Wenn Sie eine Operation durchführen möchten, die beispielsweise nur die X-Koordinaten aller Punkte berechnet (z. B. in Physik-Engines oder Grafik-Rendering). Die CPU-Cache-Line wird nicht mit unbenutzten Y- und Z-Werten verstopft. Das ermöglicht dem Compiler zudem die automatische Vektorisierung (SIMD-Befehle).

#### CPU-Register-Mapping
Kleine Structs (z. B. ein Tuple-Struct wie `struct Point(f32, f32)`) belegen genau 8 Bytes Speicher. Der Rust-Compiler ist intelligent genug, um beim Aufruf von Funktionen eine solche Struktur nicht auf den Stack zu legen, sondern sie direkt in ein einzelnes 64-Bit-Register der CPU zu mappen. Der Methodenaufruf ist somit physisch identisch mit der Übergabe einer primitiven Ganzzahl – es entsteht keinerlei Speicher-Overhead.

### 8.8 Exhaustive API-Reference & Manuelle Trait-Implementierung

#### 3. Trait `PartialEq`

Ermöglicht die typsichere Umwandlung eines Fremdtyps in Ihr Struct. Rust implementiert automatisch das Gegenstück `Into<T>` für Sie, sobald Sie `From` deklarieren.

Wir konvertieren ein einfaches Byte-Array in ein `CustomBuffer`.
```rust
impl From<Vec<u8>> for CustomBuffer {
```

#### 5. Traits `Deref` und `DerefMut` (Smart Pointer Verhalten)
Ermöglichen es Ihrem Struct, sich wie ein Smart Pointer zu verhalten. Wenn Sie den Dereferenzierungs-Operator `*` anwenden oder Methoden des inneren Typs aufrufen, leitet Rust den Aufruf automatisch weiter.

```rust
use std::ops::{Deref, DerefMut};

impl Deref for CustomBuffer {
    type Target = Vec<u8>; // Zieltyp der Dereferenzierung

    // Liefert eine Referenz auf den inneren Typ
    fn deref(&self) -> &Self::Target {
        &self.data
    }
}

impl DerefMut for CustomBuffer {
    // Liefert eine veränderliche Referenz auf den inneren Typ
    fn deref_mut(&mut self) -> &mut Self::Target {
        &mut self.data
    }
}
```

#### 7. Traits `PartialOrd` & `Ord` (Manuelle Sortierung & Vergleich)
Erlauben es, Objekte der Größe nach zu vergleichen und zu sortieren (z. B. für Sortieralgorithmen).
Wir implementieren dies für ein Struct `Player`, das nach seiner Punktzahl sortiert werden soll.

```rust
struct Player {
    name: String,
    score: u32,
}

// 1. PartialEq implementieren (Voraussetzung für PartialOrd)
impl PartialEq for Player {
    fn eq(&self, other: &Self) -> bool {
        self.score == other.score
    }
}

// 2. Eq implementieren (Voraussetzung für Ord). Eq ist ein leeres Marker-Trait.
impl Eq for Player {}

// 3. PartialOrd implementieren. Vergleicht die Punktzahlen.
impl PartialOrd for Player {
    fn partial_cmp(&self, other: &Self) -> Option<std::cmp::Ordering> {
        Some(self.cmp(other))
    }
}

// 4. Ord implementieren (Totale Ordnung)
impl Ord for Player {
    fn cmp(&self, other: &Self) -> std::cmp::Ordering {
        self.score.cmp(&other.score) // Nutzt die eingebaute Sortierung von u32
    }
}
```

##### Anwendung im Code:
```rust
let mut lobby = vec![
    Player { name: String::from("Alice"), score: 50 },
    Player { name: String::from("Bob"), score: 120 },
    Player { name: String::from("Charlie"), score: 10 },
];

lobby.sort(); // Sortiert die Spieler aufsteigend nach ihrer score!
assert_eq!(lobby[0].name, "Charlie");
```

### Übung 2 (Mittel): Bankkonto mit Transaktionshistorie

#### Aufgabenstellung
Entwickeln Sie ein System zur Verwaltung eines Bankkontos.
* **Struct**: `BankAccount` mit den Feldern `owner` (String), `balance` (f64) und `transactions` (`Vec<f64>`).
* **Anforderungen**:
  1. Konstruktor `new(owner: String) -> Self` (Masse startet bei `0.0`, leere Historie).
  2. Methode `deposit(&mut self, amount: f64)`: Fügt den Betrag zum Guthaben hinzu und protokolliert den Betrag als positiven Wert in `transactions`.
  3. Methode `withdraw(&mut self, amount: f64) -> Result<(), String>`: Zieht den Betrag ab, falls genug Guthaben vorhanden ist. Protokolliert den Betrag als negativen Wert in `transactions`. Falls das Guthaben nicht ausreicht, wird ein `Err` zurückgegeben und die Historie bleibt unverändert.
  4. Methode `transaction_count(&self) -> usize`: Gibt die Anzahl der getätigten Transaktionen zurück.

#### API-Vorgabe
```rust
struct BankAccount {
    owner: String,
    balance: f64,
```

```rust
// 1. Deklaration der drei Varianten

// 4. impl-Block mit verschiedenen self-Empfängern
impl Classic {
    // Konstruktor (Assoziierte Funktion)
    fn new(x: i32) -> Self { Self { x } }
    
    // Methode (Lesen)
    fn get_x(&self) -> i32 { self.x }
    
    // Methode (Schreiben)
    fn set_x(&mut self, new_x: i32) { self.x = new_x; }
    
    // Methode (Besitz konsumieren)
    fn consume(self) { println!("Weg ist x: {}", self.x); }
}
```

## 11. Zusammenfassung

1. **Structs** dienen zur Gruppierung logisch zusammengehöriger Daten in benannten Typen.
2. Rust bietet **klassische Structs** (benannte Felder), **Tuple-Structs** (nummerierte Indizes) und **Unit-Like Structs** (feldlos, für Trait-Implementierungen).
3. Mutabilität ist in Rust **keine Eigenschaft der Definition**, sondern wird über die Deklaration der Instanz (`let mut`) gesteuert.
4. Speicher-Optimierung: Rust sortiert Felder im RAM standardmäßig um (`repr(Rust)`), um durch **Padding** ungenutzten Speicherplatz zu minimieren. `repr(C)` erzwingt die C-Kompatibilität.
5. Verhalten wird in **`impl`-Blöcken** definiert. Methoden nutzen `self` (Wert), `&self` (unveränderlich) oder `&mut self` (veränderlich). Assoziierte Funktionen haben kein `self` und dienen meist als Konstruktoren.
6. Der Compiler optimiert Methodenaufrufe über **Inlining** und CPU-Register-Mapping vollständig weg (Zero-Cost-Abstractions).
7. Die **Struct-Update-Syntax (`..`)** erlaubt das partielle Übernehmen von Feldern. Sie verschiebt jedoch die Ownership bei Typen ohne `Copy`-Trait, wodurch die Quelle ungültig wird.
8. Geteilter, mutabler Zustand von Structs wird in Multithreading-Umgebungen über `Arc<Mutex<T>>` gelöst.
9. Über **Generics** und **Lifetimes** werden Strukturen wiederverwendbar und können sichere Referenzen halten. Ungenutzte Typparameter werden über `PhantomData` gebunden.
10. Fortgeschrittene Strukturen nutzen das **Builder-Pattern** für komplexe Instanziierungen, das **`#[non_exhaustive]`-Attribut** für stabile Bibliotheks-APIs und das **Type-State-Pattern** zur Zustandskontrolle zur Kompilierzeit.
11. Über **Interior Mutability** (`Cell`, `RefCell`) kann die Unveränderbarkeit von Structs in sicheren Nischen kontrolliert durchbrochen werden.
12. Standard-Traits können über `#[derive]` generiert werden. Wichtige Traits wie `Default`, `Clone`, `From` oder `Deref`, `Ord`, `Hash` können aber auch für feineres Verhalten manuell implementiert werden.
