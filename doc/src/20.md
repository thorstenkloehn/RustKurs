# Kapitel 20: Referenzen und Borrowing (Ausleihen) – Der ultimative Guide

In Kapitel 18 haben wir das Ownership-System (Besitzsystem) von Rust kennengelernt. Wir haben gesehen, dass die Übergabe einer Variable an eine Funktion standardmäßig das Eigentum (Ownership) verschiebt. Wenn wir den Wert danach im Hauptprogramm weiterverwenden wollen, müssten wir ihn mühsam von der Funktion als Rückgabewert zurückgeben lassen.

Rust bietet für dieses Problem eine elegante Lösung: **Referenzen (References)** und das Prinzip des **Ausleihens (Borrowing)**. In diesem Kapitel lernen wir auf einer tiefgehenden theoretischen und praktischen Ebene, wie wir Daten sicher teilen können, ohne das Eigentum zu übertragen, und welche strengen Regeln der Compiler dabei durchsetzt.

---

## 1. Deep Dive: Speicherverwaltung auf Hardware-Ebene

Um zu verstehen, warum Rusts Referenzen so sicher und performant sind, müssen wir einen Blick auf die Hardware und den Arbeitsspeicher (RAM) werfen.

### Was ist eine Speicheradresse?
Der Arbeitsspeicher deines Computers ist wie eine riesige Reihe von durchnummerierten Speicherzellen (Bytes) organisiert. Jedes Byte hat eine eindeutige Nummer – die **Speicheradresse** (z. B. `0x7ffdd92f4`).
* Wenn du eine Variable wie `let x: i32 = 42;` deklarierst, reserviert das Betriebssystem 4 Byte im Stack und speichert den Wert `42` an einer bestimmten Adresse.
* Eine **Referenz** ist nichts anderes als eine Variable, die als Wert eine solche Speicheradresse speichert. Auf einem 64-Bit-Prozessor belegt eine Referenz immer genau 8 Byte (64 Bit), da dies die Breite einer Speicheradresse ist.

### Der Weg über den Zeiger (Indirektion)
Wenn wir eine Referenz dereferenzieren (also auf den Wert zugreifen, auf den sie zeigt), muss der Prozessor eine sogenannte **Indirektion** ausführen: Er liest die Adresse aus der Referenz und springt dann im Speicher an diese Adresse, um die echten Daten zu lesen.

```text
[ Referenz s ] (auf dem Stack)
  ├─ Wert: 0x1000 (Speicheradresse von s1)
  └─ Größe: 8 Byte
       │
       ▼
[ Variable s1 ] (auf dem Stack)
  ├─ Zeiger auf Heap: 0x5000
  ├─ Länge: 5
  └─ Kapazität: 5
       │
       ▼
[ Heap-Daten ] (auf dem Heap an Adresse 0x5000)
  └─ [ 'H', 'a', 'l', 'l', 'o' ]
```

### Warum Referenzen performant sind
Wenn wir eine große Struktur (wie einen langen Text oder ein großes Array) an eine Funktion übergeben, kopiert Rust bei einer Referenz lediglich die 8 Byte lange Speicheradresse auf den Stack. Die eigentlichen Daten auf dem Heap müssen nicht kopiert, verschoben oder neu allokiert werden. Das spart Zeit und Arbeitsspeicher.

## 2. Ausführliche Merkzettel zu Referenzen & Borrowing

Nutze diese detaillierten Spickzettel, um die Funktionsweise des Ausleihens im Detail zu verstehen.

### 📌 Merkzettel A: Die Syntax-Übersicht

1. **Warum dieses Konzept? (Motivation):**
   Um mit Referenzen arbeiten zu können, müssen wir dem Compiler mitteilen, ob wir eine Referenz erstellen (Referenzieren) oder den Wert hinter der Referenz lesen bzw. schreiben wollen (Dereferenzieren).
2. **Schlüsselbegriffe (Definitions):**
   - **`&` (Referenzieren):** Erzeugt eine Adresse auf eine Variable.
   - **`*` (Dereferenzieren):** Folgt der Adresse, um auf den eigentlichen Wert zuzugreifen (wird bei vielen Operationen von Rust automatisch im Hintergrund gemacht).
3. **Praktische Visualisierung & Code-Beispiel:**
   ```rust
   let x = 42;
   let r = &x; // r zeigt auf x
   
   println!("Wert von x: {}", x);
   println!("Wert auf den r zeigt: {}", *r); // Manuelles Dereferenzieren mit *
   ```
4. **Häufiger Anfängerfehler:**
   *Fehlerhafter Code:*
   ```rust
   let mut x = 5;
   let r = &mut x;
   r = 10; // ❌ FEHLER: Wir versuchen, die Speicheradresse in r zu überschreiben, nicht den Wert!
   ```
   *Compiler-Fehler:*
   ```text
   error[E0308]: mismatched types: expected `&mut i32`, found `integer`
   ```
   *Korrektur:*
   Nutze den Dereferenzierungs-Operator `*`, um den Wert hinter der Adresse zu manipulieren:
   ```rust
   let mut x = 5;
   let r = &mut x;
   *r = 10; // 🟢 Korrekt: Wert von x wird auf 10 geändert!
   ```
5. **Die goldene Merkregel / Eselsbrücke (Mnemonic):**
   *„Mit `&` baust du die Brücke (Adresse), mit `*` gehst du rüber zum Wert (Dereferenzierung).“*

---

### 📌 Merkzettel B: Lese-Referenzen (`&T`) – Die unbegrenzte Ausleihe

1. **Warum dieses Konzept? (Motivation):**
   Wenn mehrere Teile deines Programms Daten gleichzeitig lesen müssen, gibt es keinen Konflikt, da niemand die Daten verändert. Rust erlaubt daher beliebig viele Lese-Ausleihen gleichzeitig.
2. **Schlüsselbegriffe (Definitions):**
   - **Immutable Reference (`&T`):** Eine unveränderliche Ausleihe. Sie erlaubt nur Lesezugriff auf das Original.
3. **Praktische Visualisierung & Code-Beispiel:**
   ```rust
   let text = String::from("Rust");
   let r1 = &text;
   let r2 = &text;
   let r3 = &text; // Beliebig viele Leser sind erlaubt
   
   println!("r1: {}, r2: {}, r3: {}", r1, r2, r3);
   ```
4. **Häufiger Anfängerfehler:**
   *Fehlerhafter Code:*
   ```rust
   fn ausgabe(s: &String) {
       s.push_str("!"); // ❌ FEHLER: Eine Lese-Referenz darf keine Daten schreiben!
   }
   ```
   *Compiler-Fehler:*
   ```text
   error[E0596]: cannot borrow `*s` as mutable, as it is behind a `&` reference
   ```
   *Korrektur:*
   Wenn die Funktion den Text verändern soll, muss sie eine veränderliche Referenz (`&mut String`) verlangen.
5. **Die goldene Merkregel / Eselsbrücke (Mnemonic):**
   *„Lesen tut nicht weh. Beliebig viele Gäste dürfen in das Buch schauen, solange niemand einen Stift zückt.“*

---

### 📌 Merkzettel C: Schreib-Referenzen (`&mut T`) – Die exklusive Ausleihe

1. **Warum dieses Konzept? (Motivation):**
   Wenn eine Funktion Daten verändern muss, muss sichergestellt sein, dass kein anderer Codepfad währenddessen dieselben Daten liest oder schreibt, da es sonst zu Inkonsistenzen kommt.
2. **Schlüsselbegriffe (Definitions):**
   - **Mutable Reference (`&mut T`):** Eine veränderliche Ausleihe, die exklusiven Schreib- und Lesezugriff gewährt.
3. **Praktische Visualisierung & Code-Beispiel:**
   ```rust
   let mut zahl = 10;
   let r = &mut zahl;
   *r += 5;
   println!("Wert: {}", r); // Ausgabe: 15
   ```
4. **Häufiger Anfängerfehler:**
   *Fehlerhafter Code:*
   ```rust
   let mut x = 5;
   let r1 = &mut x;
   let r2 = &mut x; // ❌ FEHLER: Zwei Schreiber gleichzeitig verboten!
   *r1 += 1;
   *r2 += 1;
   ```
   *Compiler-Fehler:*
   ```text
   error[E0499]: cannot borrow `x` as mutable more than once at a time
   ```
   *Korrektur:*
   Nutze Scopes oder beende die Nutzung der ersten Referenz, bevor die zweite deklariert wird:
   ```rust
   let mut x = 5;
   {
       let r1 = &mut x;
       *r1 += 1; // r1 wird hier letztmalig genutzt
   } // r1 verlässt den Scope -> Ausleihe beendet
   let r2 = &mut x; // 🟢 Erlaubt!
   *r2 += 1;
   ```
5. **Die goldene Merkregel / Eselsbrücke (Mnemonic):**
   *„Schreiben ist einsam. Nur ein einziger Handwerker darf am Werkstück arbeiten – alle anderen müssen den Raum verlassen.“*

---

### 📌 Merkzettel D: Die Aliasing-Regeln (Niemals Mischen!)

1. **Warum dieses Konzept? (Motivation):**
   Wenn Leser und Schreiber gleichzeitig auf dieselben Daten zugreifen, lesen die Leser eventuell veraltete oder halbe Daten (Datenkonflikt / Data Race). Rust verbietet das Mischen von Lese- und Schreibreferenzen komplett.
2. **Schlüsselbegriffe (Definitions):**
   - **Aliasing:** Wenn dieselbe Speicheradresse über verschiedene Variablen (Referenzen) erreichbar ist.
3. **Praktische Visualisierung & Code-Beispiel:**
   ```rust
   let mut wert = 100;
   let leser = &wert; // Leser aktiv
   // let schreiber = &mut wert; // ❌ Verboten, solange leser existiert!
   println!("Leser sieht: {}", leser);
   ```
4. **Häufiger Anfängerfehler:**
   *Fehlerhafter Code:*
   ```rust
   let mut name = String::from("Alice");
   let r1 = &name;
   let r2 = &mut name; // ❌ FEHLER: Mischung aus Leser und Schreiber
   println!("r1: {}, r2: {}", r1, r2);
   ```
   *Compiler-Fehler:*
   ```text
   error[E0502]: cannot borrow `name` as mutable because it is also borrowed as immutable
   ```
   *Korrektur:*
   Drucke den Wert der Lese-Referenz aus, *bevor* du die veränderliche Referenz deklarierst:
   ```rust
   let mut name = String::from("Alice");
   let r1 = &name;
   println!("r1: {}", r1); // Letzte Nutzung von r1 -> Lesezugriff erlischt!
   
   let r2 = &mut name; // 🟢 Erlaubt, da kein Leser mehr aktiv ist.
   r2.push_str(" Cooper");
   ```
5. **Die goldene Merkregel / Eselsbrücke (Mnemonic):**
   *„Entweder viele Leser ODER ein Schreiber. Niemals beide am selben Tisch!“*

---

### 📌 Merkzettel E: Der Borrow Checker und Non-Lexical Lifetimes (NLL)

1. **Warum dieses Konzept? (Motivation):**
   Früher waren Referenzen bis zum Ende des geschweiften Blocks `{}` gesperrt, in dem sie deklariert wurden. Das führte zu viel unnötigem Code. Der moderne Compiler prüft die Ausleihen zeilenbasiert und gibt sie sofort frei, wenn sie nicht mehr benutzt werden.
2. **Schlüsselbegriffe (Definitions):**
   - **Borrow Checker:** Das Compiler-Modul, das die Ausleihregeln prüft.
   - **Non-Lexical Lifetimes (NLL):** Zeilenbasierte Analyse der Lebensdauer von Referenzen statt rein blockbasierter Analyse.
3. **Praktische Visualisierung & Code-Beispiel:**
   ```rust
   let mut s = String::from("Rust");
   let r1 = &s; // r1 beginnt
   println!("{}", r1); // r1 endet hier (letzte Zeile der Nutzung)
   
   let r2 = &mut s; // 🟢 Erlaubt dank NLL!
   r2.push_str(" Kurs");
   ```
4. **Häufiger Anfängerfehler:**
   *Fehlerhafter Code:*
   ```rust
   let mut s = String::from("Rust");
   let r1 = &s;
   let r2 = &mut s; // ❌ FEHLER: r1 wird weiter unten noch einmal genutzt!
   r2.push_str(" Kurs");
   println!("{}", r1); // r1 ist hier noch aktiv!
   ```
   *Compiler-Fehler:*
   ```text
   error[E0502]: cannot borrow `s` as mutable because it is also borrowed as immutable
   ```
   *Korrektur:*
   Verschiebe den Zugriff auf `r1` vor die Deklaration von `r2`:
   ```rust
   let mut s = String::from("Rust");
   let r1 = &s;
   println!("{}", r1); // r1 beendet
   
   let r2 = &mut s; // 🟢 Erlaubt!
   r2.push_str(" Kurs");
   ```
5. **Die goldene Merkregel / Eselsbrücke (Mnemonic):**
   *„Wer fertig ist, gibt ab. Benutzt du die Referenz nicht mehr, gibt der Compiler den Speicher frei.“*

---

### 📌 Merkzettel F: Speicher-Moves vs. Referenz-Zuweisung

1. **Warum dieses Konzept? (Motivation):**
   Einsteiger verwechseln oft das Kopieren von Werten mit dem Erstellen von Referenzen. Zu verstehen, was auf Stack und Heap passiert, schützt vor Verwirrung beim Aufruf von Funktionen.
2. **Schlüsselbegriffe (Definitions):**
   - **Move:** Der Besitz eines Heap-Werts wird komplett übertragen. Die alte Variable wird ungültig.
   - **Referenzierung:** Es wird nur ein Zeiger (Adresse) auf den Wert übergeben. Der Besitzer bleibt unverändert.
3. **Praktische Visualisierung & Code-Beispiel:**
   ```rust
   let s1 = String::from("Daten");
   
   let s2 = s1; // MOVE! s1 ist ab hier ungültig!
   
   let s3 = &s2; // REFERENZIERUNG! s2 bleibt weiterhin voll gültig.
   ```
4. **Häufiger Anfängerfehler:**
   *Fehlerhafter Code:*
   ```rust
   fn verarbeite(s: String) {
       println!("{}", s);
   }
   
   fn main() {
       let text = String::from("Hallo");
       verarbeite(text); // Move!
       println!("{}", text); // ❌ FEHLER: text wurde verschoben!
   }
   ```
   *Compiler-Fehler:*
   ```text
   error[E0382]: borrow of moved value: `text`
   ```
   *Korrektur:*
   Übergib eine Referenz (`&String` bzw. `&str`), statt das Eigentum zu übergeben:
   ```rust
   fn verarbeite(s: &String) {
       println!("{}", s);
   }
   
   fn main() {
       let text = String::from("Hallo");
       verarbeite(&text); // 🟢 Nur ausgeliehen
       println!("{}", text); // 🟢 text ist weiterhin gültig!
   }
   ```
5. **Die goldene Merkregel / Eselsbrücke (Mnemonic):**
   *„Schenken (Move) macht dich arm, Ausleihen (Referenz) lässt dich reich bleiben.“*

---

### 📌 Merkzettel G: Dangling References erkennen und verhindern

1. **Warum dieses Konzept? (Motivation):**
   Ein Zeiger darf niemals auf einen Speicherbereich zeigen, der bereits freigegeben wurde. Rusts Compiler garantiert, dass keine Referenz länger lebt als die Daten, auf die sie verweist.
2. **Schlüsselbegriffe (Definitions):**
   - **Dangling Reference (Totzeiger):** Eine Referenz auf bereits gelöschten Arbeitsspeicher.
3. **Praktische Visualisierung & Code-Beispiel:**
   ```rust
   let r;
   {
       let x = 5;
       r = &x; // ❌ FEHLER: x lebt nur in diesem Block!
   } // x stirbt hier
   // println!("{}", r); // r würde auf gelöschtes x verweisen!
   ```
4. **Häufiger Anfängerfehler:**
   *Fehlerhafter Code:*
   ```rust
   fn erzeuge_daten() -> &String {
       let text = String::from("Temporär");
       &text // ❌ FEHLER: text wird am Funktionsende gelöscht!
   }
   ```
   *Compiler-Fehler:*
   ```text
   error[E0515]: cannot return reference to local variable `text`
   ```
   *Korrektur:*
   Gib das Eigentum (den Wert selbst) zurück:
   ```rust
   fn erzeuge_daten() -> String {
       let text = String::from("Temporär");
       text // 🟢 Eigentum wird nach außen verschoben
   }
   ```
5. **Die goldene Merkregel / Eselsbrücke (Mnemonic):**
   *„Gib den Vogel selbst frei (Eigentum zurückgeben), statt auf den leeren Käfig zu zeigen (Referenz auf lokale Daten).“*

## 3. Coding-Challenges & Praxisaufgaben

### 📝 Challenge 1: Der String-Verdoppler
* **Ziel:** Schreibe eine Funktion `verdopple`, die eine veränderliche Referenz auf einen `String` nimmt und den Text verdoppelt (z. B. aus `"Ja"` wird `"JaJa"`).
* **Lerneffekt:** Verwendung von `&mut String` und Modifikation des Originals.

#### Fehlerhafter Code (Dein Ausgangspunkt):
```rust
fn verdopple(s: String) {
    s.push_str(&s); 
}

fn main() {
    let mut text = String::from("Rust");
    verdopple(text);
    println!("Ergebnis: {}", text); 
}
```

#### Warum dieser Code scheitert (Compiler-Fehler):
1. Die Funktion `verdopple` übernimmt den Besitz von `s` (Move). In `main` ist `text` danach ungültig und darf nicht gedruckt werden.
2. `s.push_str(&s)` ist verboten, da wir `s` verändern wollen (Schreiber), aber gleichzeitig eine Referenz auf sich selbst (`&s` als Leser) übergeben. Das verletzt die Aliasing-Regel!

#### Korrekte Lösung:
```rust
fn verdopple(s: &mut String) {
    // Wir müssen den aktuellen Text clonen, um die Aliasing-Regel zu umgehen
    let kopie = s.clone();
    s.push_str(&kopie); 
}

fn main() {
    let mut text = String::from("Rust");
    verdopple(&mut text); // Wir übergeben eine veränderliche Referenz
    println!("Ergebnis: {}", text); // Ausgabe: RustRust
}
```

### 📝 Challenge 3: Die lokale Rückgabe-Falle
* **Ziel:** Behebe den Lifetime-Fehler in der folgenden Funktion, die versucht, eine Referenz auf ein lokal erstelltes Array zurückzugeben.
* **Lerneffekt:** Vermeidung von Dangling References.

#### Fehlerhafter Code:
```rust
fn erstelle_koordinaten() -> &[i32; 2] {
    let punkte = [10, 20];

}

    let k = erstelle_koordinaten();
```


```rust

    punkte // Wert wird kopiert/verschoben
}

fn main() {
    let k = erstelle_koordinaten();
    println!("X: {}, Y: {}", k[0], k[1]); // Ausgabe: X: 10, Y: 20
}
```

### 📝 Challenge 4: Das Array-Element-Austausch-Rätsel
* **Ziel:** Schreibe eine Funktion `tausche_werte`, die ein veränderliches Array von 3 Zahlen und zwei Indizes nimmt, und die Werte an diesen Indizes vertauscht.
* **Lerneffekt:** Sicheres Verändern von Array-Inhalten über Referenzen.

```rust
fn tausche_werte(arr: &mut [i32; 3], idx1: usize, idx2: usize) {

    arr[idx2] = temp;
}

    tausche_werte(&mut daten, 0, 2);

}
```

### 📝 Challenge 5: Der Scope-Trenner
* **Ziel:** Behebe den Fehler im folgenden Code, indem du einen expliziten geschweiften Block `{}` nutzt, um die Lebensdauer der veränderlichen Referenz künstlich zu begrenzen.
* **Lerneffekt:** Manuelle Scope-Steuerung.

#### Fehlerhafter Code:
```rust
fn main() {
    let mut text = String::from("Rust");
    
    let r_mut = &mut text;
    r_mut.push_str(" Sprache");
    
    let r_leser = &text;
    println!("Text: {} (Länge: {})", r_leser, r_mut.len()); // ❌ FEHLER!
}
```

#### Compiler-Fehler:
```text
error[E0502]: cannot borrow `text` as immutable because it is also borrowed as mutable
```

#### Korrekte Lösung:
```rust
fn main() {
    let mut text = String::from("Rust");
    
    {
        let r_mut = &mut text;
        r_mut.push_str(" Sprache");
        // r_mut verlässt hier den inneren Scope und wird ungültig!
    } 
    
    let r_leser = &text; // 🟢 Erlaubt, da kein Schreiber mehr existiert!
    println!("Text: {} (Länge: {})", r_leser, r_leser.len());
}
```

## 4. Lernnotizen & Mitschriften (Deine Lern-Ecke)

Nutze diese Vorlagen und Fragen, um dein Wissen zu festigen.

### 📝 Mitschriften-Template:
> #### 💡 Mein persönlicher Aha-Moment zu Referenzen:
> * *Ich habe verstanden, dass eine Referenz im Speicher...*
> * *Die Aliasing-Regel ("Viele Leser oder ein Schreiber") macht für mich Sinn, weil...*
> * *Mein Trick, um Dangling References zu vermeiden:*

### 🔍 Häufig gestellte Fragen (FAQ):

1. **Frage:** Kostet das Dereferenzieren mit `*` Performance?
   * **Antwort:** Nein. Für die CPU ist das Folgen einer Speicheradresse eine der grundlegendsten Operationen (Indirektion). Rust kompiliert diese zu extrem effizientem Maschinencode. Es gibt keinen Laufzeit-Overhead im Vergleich zu C.
   
2. **Frage:** Warum braucht man überhaupt unveränderliche Referenzen, wenn man Daten auch kopieren könnte?
   * **Antwort:** Bei kleinen Stack-Werten (wie `i32`) ist Kopieren oft schneller. Bei Heap-Daten (wie einem `String` mit 1 MB Text) wäre das Kopieren der Daten extrem langsam. Referenzen erlauben es, auf diese Daten zuzugreifen, ohne sie zu duplizieren.

3. **Frage:** Kann eine veränderliche Referenz (`&mut`) auf eine unveränderliche Variable (`let`) verweisen?
   * **Antwort:** Nein. Wenn das Original nicht veränderbar ist, darf es auch keine veränderliche Ausleihe geben. Der Compiler blockiert das mit der Meldung `cannot borrow as mutable`.

4. **Frage:** Was ist der Unterschied zwischen `&String` und `&str`?
   * **Antwort:** `&String` ist eine Referenz auf die Variable auf dem Stack, die den String besitzt. `&str` ist ein String-Slice, der direkt auf ein Stück Text verweist (entweder auf dem Heap oder im Programmspeicher). In Funktionsparametern ist `&str` flexibler, da man ihm sowohl Slices als auch Referenzen auf `String` übergeben kann.

5. **Frage:** Kann man Referenzen ineinander verschachteln (z. B. eine Referenz auf eine Referenz)?
   * **Antwort:** Ja, das geht (z. B. `&&i32`). In der Praxis vereinfacht Rust den Zugriff darauf jedoch meistens automatisch (Auto-Dereferenzierung), sodass man selten manuell mehrere Sterne (`**r`) schreiben muss.

6. **Frage:** Was passiert, wenn ich versuche, eine Referenz über einen Thread hinweg zu teilen?
   * **Antwort:** Rusts Compiler prüft auch hier streng, ob die Lebensdauer der Daten ausreicht. Wenn die Daten gelöscht werden könnten, während der Thread noch läuft, blockiert der Compiler den Code. Das macht Multithreading in Rust absolut sicher.

7. **Frage:** Warum kann ich nicht einfach einen Vektor oder ein Struct nutzen, um Daten auszutauschen?
   * **Antwort:** Structs und Vektoren sind komplexere Datenstrukturen. Zu lernen, wie man Referenzen auf Arrays und Tupel anwendet, zwingt dich dazu, die fundamentalen Speicherregeln sauber zu verstehen, bevor du fortgeschrittene Container nutzt.

8. **Frage:** Gibt es Situationen, in denen der Borrow Checker irrt?
   * **Antwort:** Ja, manchmal ist der Compiler "zu konservativ". Er blockiert Code, der logisch eigentlich sicher wäre, aber die statischen Regeln verletzt. Für solche Spezialfälle gibt es fortgeschrittene Konzepte (wie `Unsafe Rust` oder spezielle Typen), die wir aber erst viel später lernen.

9. **Frage:** Was bedeutet das Wort "Aliasing" genau?
   * **Antwort:** Aliasing bedeutet, dass derselbe Speicherbereich über verschiedene Namen (Aliase) im Code erreichbar ist. Wenn mindestens ein Name Schreibzugriff hat, führt das ohne Absicherung zu Datenkonflikten.

10. **Frage:** Wie merke ich mir am besten den Unterschied zwischen `&` und `*`?
    * **Antwort:** `&` ist der Adress-Operator ("Gib mir die Adresse von..."). `*` ist der Wert-Operator ("Gib mir den Wert an der Adresse...").
