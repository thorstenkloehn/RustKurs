# Kapitel 19: Referenzen & Borrowing – Ausleihen ohne Besitz

> [!IMPORTANT]
> Dieses Kapitel behandelt eines der grundlegendsten und gleichzeitig mächtigsten Konzepte in Rust: das **Borrowing** (Ausleihen). Sie lernen, wie Sie Werte vorübergehend nutzen können, ohne deren Ownership zu übernehmen – und warum Rust dafür ein strenges Regelwerk durchsetzt, das Data Races zur Compilezeit ausschließt.

## 19.1 Lernziele & Lernplan

### Lernziele

Nach Abschluss dieses Kapitels werden Sie in der Lage sein:

1. **Unveränderliche Referenzen (`&T`)** korrekt zu erstellen und zu verwenden – Sie werden verstehen, dass eine Referenz im Speicher ein einfacher Zeiger (8 Bytes auf einem 64-Bit-System) ist, der auf den Originalwert verweist, ohne dessen Ownership zu übernehmen.

2. **Veränderliche Referenzen (`&mut T`)** sicher einzusetzen – Sie werden die Einschränkung verstehen, dass zu einem gegebenen Zeitpunkt stets nur eine einzige veränderliche Referenz auf einen Wert existieren darf, und warum diese Regel Data Races vollständig verhindert.

3. **Den Dereferenzierungs-Operator (`*`)** gezielt zu nutzen – Sie werden erklären können, wann Rust automatisch dereferenziert und wann Sie selbst den `*`-Operator einsetzen müssen.

4. **Deref-Coercion** zu erkennen und anzuwenden – Sie werden verstehen, wie Rust `&String` automatisch zu `&str` und `&Vec<T>` automatisch zu `&[T]` umwandelt, und wie Sie diesen Mechanismus für eigene Typen implementieren.

5. **Dangling References** zu vermeiden – Sie werden verstehen, warum Rust zur Compilezeit verhindert, dass eine Referenz länger lebt als der Wert, auf den sie verweist.

6. **Referenzen in Structs** grundlegend einzuordnen – Sie erhalten eine erste Vorschau auf Lifetime-Annotationen und warum diese notwendig werden, sobald Structs Referenzfelder enthalten.

## 19.2 Die Definition

### Was ist eine Referenz?

Eine **Referenz** in Rust ist ein Zeiger auf einen Wert, der von jemandem anderen besessen (owned) wird. Eine Referenz ist garantiert gültig, solange sie existiert – der Rust-Compiler stellt dies zur Compilezeit sicher.

Die formale Definition lautet:

> Eine Referenz ist ein nicht-besitzender Zeiger auf einen Wert. Rust garantiert zur Compilezeit, dass die Referenz stets auf einen gültigen Wert zeigt.

In der Rust-Terminologie spricht man von zwei eng verwandten Konzepten:

- **Borrowing (Ausleihen)**: Der Vorgang, eine Referenz auf einen Wert zu erstellen. Man „leiht" den Wert aus, ohne seine Ownership zu übernehmen.
- **Referenz**: Das Ergebnis des Borrowings – ein Zeiger-ähnlicher Wert, der den geliehenen Wert repräsentiert.

### Referenzen im Speicher

Auf einem modernen 64-Bit-System ist eine Referenz in Rust genau **8 Bytes** groß – denn sie ist im Kern nichts anderes als eine Speicheradresse (ein Zeiger). Dieser Zeiger liegt auf dem **Stack** und enthält die Adresse des Wertes, auf den er verweist. Dieser Wert kann sich auf dem Stack oder auf dem Heap befinden.

```
Stack                       Heap
┌────────────────┐          ┌─────────────────────────┐
│ s1: String     │          │  "Hallo, Welt!"          │
│  ptr ──────────┼─────────►│  (UTF-8-Bytes)           │
│  len: 12       │          │                          │
│  cap: 12       │          └─────────────────────────┘
├────────────────┤
│ r: &String     │
│  ptr ──────────┼──────────► (zeigt auf s1 auf Stack) │
└────────────────┘
```

In diesem Diagramm:
- `s1` ist ein `String`-Wert auf dem Stack. Er enthält einen Zeiger auf den Heap (wo die eigentlichen Zeichen gespeichert sind), die aktuelle Länge und die Kapazität.
- `r` ist eine Referenz auf `s1`. Sie liegt ebenfalls auf dem Stack und enthält die Adresse von `s1`.

### Was ist Borrowing?

Das Konzept des Borrowings stammt aus der Metapher der Bibliothek: Wenn Sie ein Buch aus der Bibliothek ausleihen, gehört das Buch Ihnen nicht – Sie können es lesen (unveränderliche Referenz) oder, wenn die Bibliothek es erlaubt, darin schreiben (veränderliche Referenz). Am Ende geben Sie das Buch zurück. Der Besitzer bleibt stets die Bibliothek.

In Rust gilt dasselbe Prinzip:

- Sie können einen Wert **ausleihen**, indem Sie eine Referenz darauf erstellen.
- Der ursprüngliche Besitzer (Owner) behält die Ownership.
- Wenn die Referenz außer Gültigkeitsbereich gerät (out of scope), gibt sie nichts frei – denn sie besitzt den Wert nicht.

### Die zwei Arten von Referenzen

Rust kennt zwei grundlegende Arten von Referenzen:

| Art | Syntax | Zugriffsart | Gleichzeitige Instanzen |
|-----|--------|-------------|------------------------|
| Unveränderliche Referenz | `&T` | Nur lesen | Beliebig viele |
| Veränderliche Referenz | `&mut T` | Lesen und schreiben | Genau eine |

Diese Asymmetrie ist kein Zufall: Sie ist das Herzstück von Rusts Speichersicherheit zur Compilezeit.

> [!NOTE]
> In der Rust-Dokumentation und in englischsprachigen Quellen werden unveränderliche Referenzen oft als **shared references** (geteilte Referenzen) und veränderliche Referenzen als **exclusive references** (exklusive Referenzen) bezeichnet. Diese Begriffe beschreiben die Semantik präziser: `&T` kann geteilt werden, `&mut T` ist exklusiv.

## 19.3 Das Problem & Die Motivation

### Warum überhaupt Referenzen?

Um die Notwendigkeit von Referenzen zu verstehen, muss man zunächst das Problem begreifen, das sie lösen.

Erinnern Sie sich an Kapitel 18: Wenn eine Funktion einen Wert als Parameter erhält, übernimmt sie standardmäßig die Ownership dieses Wertes. Nach dem Funktionsaufruf ist der ursprüngliche Wert verschoben (moved) und kann vom Aufrufer nicht mehr verwendet werden.

Dies erzeugt ein praktisches Problem: Was, wenn eine Funktion einen Wert nur lesen soll, ohne ihn zu „verbrauchen"?

Betrachten Sie folgendes Szenario: Sie haben einen langen Text in einem `String` gespeichert und möchten seine Länge von einer Hilfsfunktion berechnen lassen. Ohne Referenzen hätten Sie zwei unbefriedigende Optionen:

**Option 1: Wert übergeben und Ownership verlieren**

```rust
fn berechne_laenge(s: String) -> usize {
    s.len()
}

fn main() {
    let mein_text = String::from("Hallo, Welt!");
    let laenge = berechne_laenge(mein_text);
    // mein_text ist jetzt moved – Sie können ihn nicht mehr verwenden!
    // println!("{}", mein_text); // FEHLER: use of moved value
    println!("Die Länge ist: {}", laenge);
}
```

Nach dem Aufruf von `berechne_laenge(mein_text)` ist `mein_text` verschoben. Sie können ihn danach nicht mehr verwenden. Das ist unpraktisch.

**Option 2: Wert zurückgeben und Ownership zurückerhalten**

```rust
fn berechne_laenge(s: String) -> (String, usize) {
    let laenge = s.len();
    (s, laenge) // Ownership zurückgeben
}

fn main() {
    let mein_text = String::from("Hallo, Welt!");
    let (mein_text, laenge) = berechne_laenge(mein_text);
    println!("Der Text '{}' hat {} Zeichen.", mein_text, laenge);
}
```

Das funktioniert, ist aber umständlich und unelegant. Die Funktion muss einen Tupel zurückgeben, nur damit der Aufrufer seinen Wert zurückbekommt. Bei komplexen Funktionen mit vielen Parametern wird dieses Muster schnell unpraktisch.

### Die Motivation: Ausleihen statt Übergeben

Die Lösung ist **Borrowing**: Anstatt den Wert zu übergeben, leihen Sie ihn der Funktion aus. Die Funktion erhält eine Referenz auf den Wert, kann ihn lesen (oder schreiben, wenn es eine veränderliche Referenz ist), und gibt ihn am Ende automatisch zurück – da sie ihn nie besessen hat.

```rust
fn berechne_laenge(s: &String) -> usize {
    s.len()
}

fn main() {
    let mein_text = String::from("Hallo, Welt!");
    let laenge = berechne_laenge(&mein_text);
    // mein_text ist noch verfügbar!
    println!("Der Text '{}' hat {} Zeichen.", mein_text, laenge);
}
```

Dies ist die elegante Lösung. Die Funktion `berechne_laenge` nimmt eine Referenz `&String` als Parameter, kann den String lesen, und wenn die Funktion endet, endet auch die Lebensdauer der Referenz – aber der String selbst bleibt intakt im Besitz des Aufrufers.

> [!IMPORTANT]
> Borrowing löst das fundamentale Spannungsfeld zwischen **Sicherheit** und **Praktikabilität** in Rust. Ohne Borrowing wäre die Ownership-Semantik so restriktiv, dass viele alltägliche Programmieraufgaben sehr umständlich wären. Mit Borrowing können Funktionen Werte effizient nutzen, ohne Ownership-Übertragungen zu erzwingen.

## 19.4 Der naive Versuch (fehlerhafter Code)

### Versuch 1: Referenz nach ihrem Wert verwenden

Beginnen wir mit einem häufigen Anfängerfehler: dem Versuch, eine veränderliche und eine unveränderliche Referenz gleichzeitig zu verwenden.

```rust
fn main() {
    let mut s = String::from("Hallo");

    let r1 = &s;       // unveränderliche Referenz
    let r2 = &s;       // noch eine unveränderliche Referenz

    let r3 = &mut s;   // FEHLER: veränderliche Referenz

    println!("{}, {}, und {}", r1, r2, r3);
}
```

Dieser Code wird **nicht kompilieren**. Der Compiler gibt eine Fehlermeldung aus, die wir in Abschnitt 19.5 detailliert analysieren werden.

### Versuch 2: Mehrere veränderliche Referenzen

```rust
fn main() {
    let mut s = String::from("Hallo");

    let r1 = &mut s;
    let r2 = &mut s;   // FEHLER: zweite veränderliche Referenz

    println!("{} und {}", r1, r2);
}
```

Auch dieser Code kompiliert nicht. Rust erlaubt zu einem gegebenen Zeitpunkt nur eine einzige veränderliche Referenz auf einen Wert.

### Versuch 3: Dangling Reference – Referenz auf einen nicht mehr existierenden Wert

```rust
fn erstelle_referenz() -> &String {   // FEHLER: fehlende Lifetime
    let s = String::from("Hallo");
    &s  // s wird am Ende der Funktion dropped – die Referenz würde auf ungültige Daten zeigen
}

fn main() {
    let referenz_auf_nichts = erstelle_referenz();
}
```

Dieser Code würde eine **Dangling Reference** erzeugen – eine Referenz auf Speicher, der bereits freigegeben wurde. In C oder C++ wäre dies ein undefiniertes Verhalten (undefined behavior). Rust verhindert dies zur Compilezeit.

### Versuch 4: Falscher Einsatz des Dereferenzierungsoperators

```rust
fn main() {
    let x = 5;
    let y = &x;

    // Versuch, einen Wert direkt mit der Referenz zu vergleichen
    if y == 5 {          // FEHLER: mismatched types
        println!("y ist 5");
    }
}
```

Hier versucht der Code, eine Referenz `&i32` mit einem Integer `i32` zu vergleichen. Das sind unterschiedliche Typen. Wir müssen entweder dereferenzieren oder Rust lässt automatisch dereferenzieren (in bestimmten Kontexten).

> [!WARNING]
> Diese vier Fehlermuster sind die häufigsten Stolpersteine für Rust-Einsteiger im Umgang mit Referenzen. Der Rust-Compiler gibt für jeden dieser Fehler eine präzise, erklärende Fehlermeldung aus. Lesen Sie die Fehlermeldungen sorgfältig – sie enthalten in der Regel auch konkrete Lösungsvorschläge.

## 19.5 Die Anatomie des Fehlers

### Fehleranalyse: Gleichzeitige unveränderliche und veränderliche Referenz

Wenn Sie den fehlerhaften Code aus Versuch 1 kompilieren:

```rust
fn main() {
    let mut s = String::from("Hallo");
    let r1 = &s;
    let r2 = &s;
    let r3 = &mut s;
    println!("{}, {}, und {}", r1, r2, r3);
}
```

Gibt der Compiler folgende Fehlermeldung aus:

```
error[E0502]: cannot borrow `s` as mutable because it is also borrowed as immutable
 --> src/main.rs:5:14
  |
3 |     let r1 = &s;
  |              -- immutable borrow occurs here
4 |     let r2 = &s;
5 |     let r3 = &mut s;
  |              ^^^^^^ mutable borrow occurs here
6 |     println!("{}, {}, und {}", r1, r2, r3);
  |                                -- immutable borrow later used here
```

**Lesen der Fehlermeldung:**

- `error[E0502]`: Dies ist der Fehlercode. Sie können mit `rustc --explain E0502` eine ausführliche Erklärung abrufen.
- `cannot borrow 's' as mutable because it is also borrowed as immutable`: Der Kern des Problems.
- Die Fehlermeldung zeigt genau, **wo** die unveränderliche Ausleihe beginnt (Zeile 3), **wo** die veränderliche Ausleihe versucht wird (Zeile 5), und **wo** die unveränderliche Ausleihe zuletzt benutzt wird (Zeile 6).

### Warum diese Fehlermeldung?

Das Regelwerk von Rust lautet:

**Zu jedem Zeitpunkt kann ein Wert entweder:**
- **Beliebig viele unveränderliche Referenzen (`&T`)** haben, **ODER**
- **Genau eine veränderliche Referenz (`&mut T`)** haben.

Diese beiden Zustände schließen sich gegenseitig aus. Es ist nicht möglich, gleichzeitig eine unveränderliche und eine veränderliche Referenz auf denselben Wert zu haben.

### Die Begründung: Data-Race-Prävention

Ein **Data Race** (Datenwettlauf) tritt auf, wenn:
1. Zwei oder mehr Zeiger gleichzeitig auf denselben Speicherbereich zugreifen,
2. Mindestens einer der Zugriffe schreibend ist,
3. Kein Synchronisationsmechanismus verwendet wird.

Data Races sind undefiniertes Verhalten und führen zu schwer reproduzierbaren, gefährlichen Bugs. Sprachen wie C und C++ können Data Races erst zur Laufzeit (oder gar nicht) entdecken.

Rust eliminiert Data Races vollständig zur **Compilezeit** durch das Borrow-Checker-Regelwerk. Die Logik ist einfach:

- **Mehrere unveränderliche Referenzen**: Sicher, weil niemand den Wert verändert. Alle Leser sehen denselben, konsistenten Wert.
- **Genau eine veränderliche Referenz**: Sicher, weil es keine anderen Referenzen gibt. Der einzige Schreiber hat exklusiven Zugriff.
- **Unveränderliche und veränderliche Referenz gleichzeitig**: Unsicher! Der Schreiber könnte den Wert ändern, während der Leser ihn liest. Das ist ein Data Race.

### Fehleranalyse: Mehrere veränderliche Referenzen

```rust
fn main() {
    let mut s = String::from("Hallo");
    let r1 = &mut s;
    let r2 = &mut s;
    println!("{} und {}", r1, r2);
}
```

```
error[E0499]: cannot borrow `s` as mutable more than once at a time
 --> src/main.rs:4:14
  |
3 |     let r1 = &mut s;
  |              ------ first mutable borrow occurs here
4 |     let r2 = &mut s;
  |              ^^^^^^ second mutable borrow occurs here
5 |     println!("{} und {}", r1, r2);
  |                           -- first borrow later used here
```

Hier gilt dasselbe Prinzip: Zwei veränderliche Referenzen würden bedeuten, dass zwei verschiedene Programmteile gleichzeitig schreibend auf denselben Wert zugreifen könnten – ein klassischer Data Race.

### Die Non-Lexical Lifetimes (NLL)

Ein wichtiges Detail, das vielen Anfängern nicht bekannt ist: Referenzen enden in modernem Rust nicht am Ende des Blocks (`}`), sondern an dem Punkt, wo sie **zuletzt verwendet** werden. Dieses Feature heißt **Non-Lexical Lifetimes (NLL)** und wurde in Rust 2018 eingeführt.

Das bedeutet: Dieser Code ist **gültig**:

```rust
fn main() {
    let mut s = String::from("Hallo");

    let r1 = &s;
    let r2 = &s;
    println!("{} und {}", r1, r2);
    // r1 und r2 werden ab hier nicht mehr verwendet – ihre Lebenszeit endet hier

    let r3 = &mut s;   // Jetzt ist eine veränderliche Referenz erlaubt
    println!("{}", r3);
}
```

Dieser Code kompiliert erfolgreich, weil `r1` und `r2` zum Zeitpunkt, wo `r3` erstellt wird, bereits nicht mehr in Verwendung sind. Die Lebenszeiten überschneiden sich nicht.

> [!NOTE]
> Non-Lexical Lifetimes sind ein Beispiel dafür, wie Rust kontinuierlich verbessert wird. In frühen Versionen von Rust endeten Referenz-Lebenszeiten am Ende des lexikalischen Blocks (`{}`), was zu unnötig strikten Fehlern führte. Mit NLL analysiert der Borrow-Checker den tatsächlichen Datenfluss und ist dadurch gleichzeitig präziser und benutzerfreundlicher.

## 19.6 Die Lösung

### 19.6.1 Unveränderliche Referenzen (`&T`) korrekt verwenden

Die Syntax für eine unveränderliche Referenz ist das einfache `&`-Zeichen vor einer Variable oder einem Wert:

```rust
fn berechne_laenge(s: &String) -> usize {
    s.len()
}

fn main() {
    let s1 = String::from("Hallo, Welt!");

    let laenge = berechne_laenge(&s1);

    println!("Die Länge von '{}' ist {}.", s1, laenge);
}
```

**Zeile-für-Zeile-Erklärung:**

```rust
fn berechne_laenge(s: &String) -> usize {
```
- `fn berechne_laenge`: Deklaration einer Funktion namens `berechne_laenge`.
- `s: &String`: Der Parameter `s` ist vom Typ `&String` – eine unveränderliche Referenz auf einen `String`.
- `-> usize`: Die Funktion gibt einen `usize`-Wert zurück (vorzeichenloser Integer, plattformabhängige Größe).
- Die Funktion besitzt `s` **nicht** – sie leiht ihn nur aus.

```rust
    s.len()
```
- Ruft die Methode `.len()` auf der Referenz `s` auf.
- Rust dereferenziert die Referenz automatisch, um auf die Methode zugreifen zu können (automatische Dereferenzierung, mehr dazu in Abschnitt 19.8).
- Der Rückgabewert ist die Anzahl der Bytes im String (nicht Zeichen, da Rust UTF-8 verwendet).

```rust
fn main() {
    let s1 = String::from("Hallo, Welt!");
```
- `s1` ist ein `String`-Wert. `s1` besitzt (owns) den String.

```rust
    let laenge = berechne_laenge(&s1);
```
- `&s1` erstellt eine unveränderliche Referenz auf `s1`.
- Diese Referenz wird an `berechne_laenge` übergeben.
- `s1` selbst wird **nicht** verschoben – `s1` behält seine Ownership.
- Das `&` hier und das `&String` in der Funktionssignatur korrespondieren miteinander.

```rust
    println!("Die Länge von '{}' ist {}.", s1, laenge);
```
- `s1` ist immer noch gültig und kann hier verwendet werden, weil seine Ownership nie übertragen wurde.

**ASCII-Speicherdiagramm:**

```
Stack                          Heap
┌──────────────────────┐       ┌──────────────────────────┐
│ s1: String           │       │ "Hallo, Welt!"            │
│   ptr ───────────────┼──────►│ H a l l o ,   W e l t !  │
│   len: 12            │       └──────────────────────────┘
│   cap: 12            │
├──────────────────────┤
│ s (Parameter in      │
│   berechne_laenge):  │
│   &String            │
│   ptr ───────────────┼──────► (zeigt auf s1 auf Stack)
└──────────────────────┘
```

Die Referenz `s` in der Funktion zeigt auf `s1` auf dem Stack. `s1` seinerseits zeigt auf die eigentlichen Zeichendaten im Heap. Wenn `berechne_laenge` endet, wird `s` verworfen (der Zeiger verschwindet), aber der Heap-Speicher bleibt intakt, weil `s1` noch lebt und den Speicher besitzt.

### 19.6.2 Veränderliche Referenzen (`&mut T`) korrekt verwenden

Um eine veränderliche Referenz zu erstellen, müssen Sie:
1. Die Variable selbst als `mut` deklarieren.
2. Das `&mut`-Schlüsselwort verwenden, um eine veränderliche Referenz zu erstellen.
3. Den Parametertyp in der Funktion als `&mut T` angeben.

```rust
fn text_hinzufuegen(s: &mut String) {
    s.push_str(", Welt!");
}

fn main() {
    let mut mein_text = String::from("Hallo");

    text_hinzufuegen(&mut mein_text);

    println!("{}", mein_text);
}
```

**Zeile-für-Zeile-Erklärung:**

```rust
fn text_hinzufuegen(s: &mut String) {
```
- `s: &mut String`: Der Parameter ist eine **veränderliche Referenz** auf einen `String`.
- Die Funktion kann den String modifizieren, den `s` referenziert.
- Die Ownership wird nicht übertragen.

```rust
    s.push_str(", Welt!");
```
- `push_str` ist eine Methode auf `String`, die einen String-Slice anhängt.
- Durch die veränderliche Referenz `&mut String` hat die Funktion Schreibzugriff auf den Originalwert.
- Der Original-String in `main` wird tatsächlich modifiziert.

```rust
    let mut mein_text = String::from("Hallo");
```
- `mut` ist hier zwingend notwendig. Nur eine als `mut` deklarierte Variable kann durch eine veränderliche Referenz modifiziert werden.

```rust
    text_hinzufuegen(&mut mein_text);
```
- `&mut mein_text` erstellt eine veränderliche Referenz auf `mein_text`.
- Diese Referenz wird an die Funktion übergeben.

```rust
    println!("{}", mein_text);
```
- Gibt `"Hallo, Welt!"` aus – der Originalwert wurde durch die Funktion modifiziert.

**Ausgabe:**
```
Hallo, Welt!
```

### 19.6.3 Die Regeln des Borrowings im Überblick

Rust erzwingt zur Compilezeit folgende Regeln für Referenzen:

**Regel 1: Exklusivität veränderlicher Referenzen**
Zu einem gegebenen Zeitpunkt darf es auf einem Wert entweder beliebig viele unveränderliche Referenzen (`&T`) **oder** genau eine veränderliche Referenz (`&mut T`) geben – nicht beides gleichzeitig.

**Regel 2: Gültigkeit**
Referenzen müssen stets gültig sein. Der Compiler stellt sicher, dass eine Referenz nicht länger lebt als der Wert, auf den sie zeigt (keine Dangling References).

> [!IMPORTANT]
> Diese zwei Regeln sind das vollständige Regelwerk des Borrow-Checkers für Referenzen (abgesehen von Lifetimes, die in einem späteren Kapitel behandelt werden). Alles, was der Borrow-Checker erzwingt, leitet sich aus diesen zwei einfachen Prinzipien ab.

## 19.7 Kleines Tutorial

In diesem Tutorial bauen wir Schritt für Schritt ein kleines Programm, das verschiedene Aspekte von Referenzen und Borrowing demonstriert. Wir implementieren einen einfachen Textanalysator.

### Schritt 1: Projektstruktur anlegen

Erstellen Sie ein neues Rust-Projekt:

```bash
cargo new textanalyse
cd textanalyse
```

### Schritt 2: Grundstruktur der `main.rs`

Ersetzen Sie den Inhalt von `src/main.rs` mit:

```rust
fn main() {
    let text = String::from(
        "Rust ist eine Systemprogrammiersprache. \
         Sie bietet Speichersicherheit ohne Garbage Collector. \
         Rust ist schnell und zuverlässig."
    );
```

## 19.8 Mentale Modelle & Deep Dive

### 19.8.1 Der Dereferenzierungs-Operator (`*`)

#### Was macht der `*`-Operator?

Der `*`-Operator (Dereferenzierungsoperator) erlaubt den Zugriff auf den Wert, auf den eine Referenz zeigt. Er „dereferenziert" die Referenz – er folgt dem Zeiger und gibt den Wert zurück, auf den der Zeiger zeigt.

```rust
fn main() {
    let x = 5;
    let y = &x;      // y ist eine Referenz auf x

    println!("x = {}", x);      // Direkter Zugriff
    println!("y = {}", y);      // Rust dereferenziert automatisch für println!
    println!("*y = {}", *y);    // Explizite Dereferenzierung: 5

    // Vergleich:
    assert_eq!(5, x);
    assert_eq!(5, *y);    // *y == 5, weil *y den Wert ergibt, auf den y zeigt
    // assert_eq!(5, y); // FEHLER: Typ-Mismatch: i32 != &i32
}
```

**Zeile-für-Zeile-Erklärung:**

```rust
    let x = 5;
```
- `x` ist ein `i32` mit dem Wert `5`. Auf dem Stack gespeichert.

```rust
    let y = &x;
```
- `y` ist eine Referenz `&i32`, die auf `x` zeigt. `y` enthält die Speicheradresse von `x`.

```rust
    println!("*y = {}", *y);
```
- `*y` folgt dem Zeiger in `y` und ergibt den `i32`-Wert `5`.

```rust
    assert_eq!(5, *y);
```
- `*y` ergibt `5`, also ist diese Assertion erfolgreich.

#### Wann wird der `*`-Operator benötigt?

In der Praxis wird der explizite `*`-Operator in Rust seltener benötigt als in C oder C++, weil Rust in vielen Kontexten **automatisch dereferenziert**. Konkret benötigen Sie `*` in folgenden Situationen:

1. **Beim Vergleich von Referenzen mit Werten** (wenn Rust nicht automatisch coerciert):

```rust
fn main() {
    let wert = 42;
    let referenz = &wert;

    // Manuell dereferenzieren:
    if *referenz == 42 {
        println!("Der Wert ist 42");
    }
}
```

2. **Beim Schreiben über eine veränderliche Referenz**:

```rust
fn main() {
    let mut zahl = 10;
    let r = &mut zahl;

    *r = 20;    // Schreibe den Wert 20 an die Stelle, auf die r zeigt

    println!("zahl = {}", zahl);  // Ausgabe: 20
}
```

**Erklärung dieser Schreiboperation:**

```rust
    let mut zahl = 10;
```
- `zahl` ist ein veränderlicher `i32` auf dem Stack.

```rust
    let r = &mut zahl;
```
- `r` ist eine veränderliche Referenz auf `zahl`.

```rust
    *r = 20;
```
- `*r` dereferenziert `r` und greift auf den Wert zu, auf den `r` zeigt.
- `= 20` schreibt den Wert `20` an diese Stelle.
- Nach dieser Zeile hat `zahl` den Wert `20`.

3. **Bei der Verwendung von Smart Pointern**:

```rust
fn main() {
    let boxed_wert = Box::new(42);

    println!("Wert in Box: {}", *boxed_wert);  // Explizite Dereferenzierung

    let summe = *boxed_wert + 10;
    println!("Summe: {}", summe);
}
```

**Erklärung:**

```rust
    let boxed_wert = Box::new(42);
```
- `Box::new(42)` alloziert den Wert `42` auf dem Heap und gibt einen `Box<i32>` zurück.
- `boxed_wert` ist auf dem Stack und enthält einen Zeiger auf den Heap.

```rust
    println!("Wert in Box: {}", *boxed_wert);
```
- `*boxed_wert` dereferenziert den `Box<i32>` und ergibt den `i32`-Wert `42`.

```rust
    let summe = *boxed_wert + 10;
```
- `*boxed_wert` ergibt `42`, dann wird `10` addiert. `summe` ist `52`.

#### Vergleich mit C/C++

In C und C++ ist der `*`-Operator ebenfalls der Dereferenzierungsoperator:

```c
// C-Äquivalent:
int x = 5;
int *y = &x;    // y ist ein Zeiger auf x
int wert = *y;  // Dereferenzierung: wert == 5
*y = 10;        // Schreibzugriff über den Zeiger
```

Der wesentliche Unterschied in Rust:

- In **C/C++** gibt es keine Garantien über die Gültigkeit eines Zeigers. Ein C-Zeiger kann `NULL` sein, auf freigegebenen Speicher zeigen oder auf einen falschen Typ zeigen. All das ist undefiniertes Verhalten.
- In **Rust** garantiert der Borrow-Checker, dass eine Referenz stets gültig ist. Eine Rust-Referenz ist niemals `NULL`, zeigt nie auf freigegebenen Speicher, und der Typ ist stets korrekt. Diese Garantien werden zur Compilezeit geprüft.

> [!NOTE]
> In Rust gibt es auch **rohe Zeiger** (`*const T` und `*mut T`), die ähnlich wie C-Zeiger funktionieren und keine Sicherheitsgarantien bieten. Diese werden in `unsafe`-Blöcken verwendet und sind für Systemprogrammierung auf niedrigster Ebene vorgesehen. Im normalen Rust-Code verwenden Sie ausschließlich Referenzen.

### 19.8.2 Automatische Dereferenzierung

Rust führt in bestimmten Kontexten eine automatische Dereferenzierung durch. Diese Regel heißt **method call deref coercion** für Methodenaufrufe. Wenn Sie eine Methode auf einer Referenz aufrufen und die Methode einen anderen Typ erwartet, dereferenziert Rust automatisch so oft wie nötig.

```rust
fn main() {
    let s = String::from("Hallo");
    let r = &s;

    // Beide Aufrufe sind äquivalent:
    println!("{}", r.len());    // Rust dereferenziert r automatisch
    println!("{}", (*r).len()); // Manuelle Dereferenzierung
}
```

Beide Zeilen sind identisch. Rust sieht, dass `r` eine `&String` ist, und `String` eine `.len()`-Methode hat. Also dereferenziert Rust `r` automatisch zu `String` und ruft `.len()` auf.

### 19.8.3 Deref-Coercion (Automatische Umwandlung)

#### Was ist Deref-Coercion?

**Deref-Coercion** ist ein Mechanismus in Rust, der automatisch einen Typ in einen anderen umwandelt, wenn der erwartete Typ nicht exakt passt. Diese Umwandlung erfolgt durch wiederholte Anwendung des `Deref`-Traits.

Die wichtigste Anwendung ist die automatische Umwandlung von:
- `&String` → `&str`
- `&Vec<T>` → `&[T]`
- `&Box<T>` → `&T`

#### Das Deref-Trait

Das `Deref`-Trait ist in der Standardbibliothek definiert:

```rust
pub trait Deref {
    type Target: ?Sized;
    fn deref(&self) -> &Self::Target;
}
```

**Erklärung:**

```rust
pub trait Deref {
```
- `Deref` ist ein öffentliches Trait in `std::ops`.

```rust
    type Target: ?Sized;
```
- `Target` ist ein zugeordneter Typ – der Typ, auf den dereferenziert wird.
- `?Sized` bedeutet, dass `Target` auch dynamisch-dimensionierte Typen (DSTs) wie `str` oder `[T]` sein darf.

```rust
    fn deref(&self) -> &Self::Target;
```
- `deref` gibt eine unveränderliche Referenz auf den `Target`-Typ zurück.
- Dies ist die einzige Methode, die implementiert werden muss.

#### Wie `String` das `Deref`-Trait implementiert

`String` implementiert `Deref<Target = str>`. Das bedeutet: Eine `&String` kann automatisch zu `&str` umgewandelt werden.

```rust
// Vereinfachte Implementierung aus der Standardbibliothek:
impl Deref for String {
    type Target = str;

    fn deref(&self) -> &str {
        unsafe {
            std::str::from_utf8_unchecked(&self.as_bytes())
        }
    }
}
```

In der Praxis müssen Sie das nicht selbst implementieren – diese Implementierung existiert bereits. Sie profitieren automatisch davon.

#### Deref-Coercion in der Praxis: `&String` zu `&str`

```rust
fn gruss_ausgeben(name: &str) {
    println!("Hallo, {}!", name);
}

fn main() {
    let name = String::from("Thorsten");

    // Alle drei Aufrufe sind äquivalent:
    gruss_ausgeben(&name);           // &String wird automatisch zu &str
    gruss_ausgeben(&name[..]);       // Explizit: &str-Slice des gesamten Strings
    gruss_ausgeben(name.as_str());   // Explizit: .as_str()-Methode
}
```

**Zeile-für-Zeile-Erklärung:**

```rust
fn gruss_ausgeben(name: &str) {
```
- Die Funktion erwartet einen `&str` (String-Slice).

```rust
    gruss_ausgeben(&name);
```
- `name` ist ein `String`, `&name` ist eine `&String`.
- Rust sieht, dass `gruss_ausgeben` einen `&str` erwartet, aber `&String` übergeben wird.
- Rust wendet automatisch `Deref` auf `&String` an und erhält `&str`.
- Die Umwandlung erfolgt zur Compilezeit – kein Laufzeit-Overhead.

```rust
    gruss_ausgeben(&name[..]);
```
- `name[..]` ist eine explizite Slice-Syntax: alle Bytes des Strings.
- `&name[..]` ist eine `&str`.
- Diese Version macht die Umwandlung explizit sichtbar.

```rust
    gruss_ausgeben(name.as_str());
```
- `.as_str()` ist eine Methode auf `String`, die direkt eine `&str` zurückgibt.

> [!TIP]
> In modernem Rust-Code sollten Funktionen, die einen String-Text lesen wollen, den Parameter `&str` (und nicht `&String`) akzeptieren. Das macht die Funktion flexibler: Sie kann sowohl `&String` (durch Deref-Coercion) als auch String-Literale (`&'static str`) und andere `&str`-Werte akzeptieren.

#### Deref-Coercion: `&Vec<T>` zu `&[T]`

Genauso wie `String` implementiert `Vec<T>` das `Deref`-Trait:

```rust
fn summe_berechnen(zahlen: &[i32]) -> i32 {
    zahlen.iter().sum()
}

fn main() {
    let vektor = vec![1, 2, 3, 4, 5];

    // &Vec<i32> wird automatisch zu &[i32]
    let summe = summe_berechnen(&vektor);

    println!("Summe: {}", summe);  // Ausgabe: 15
}
```

**Zeile-für-Zeile-Erklärung:**

```rust
fn summe_berechnen(zahlen: &[i32]) -> i32 {
```
- Die Funktion erwartet einen Slice `&[i32]` (einen Verweis auf eine Folge von `i32`-Werten).

```rust
    zahlen.iter().sum()
```
- `.iter()` gibt einen Iterator über die Elemente des Slices zurück.
- `.sum()` addiert alle Elemente und gibt die Summe als `i32` zurück.

```rust
    let vektor = vec![1, 2, 3, 4, 5];
```
- `vec![...]` ist ein Macro, das einen `Vec<i32>` auf dem Heap erstellt.

```rust
    let summe = summe_berechnen(&vektor);
```
- `&vektor` ist eine `&Vec<i32>`.
- Rust wendet Deref-Coercion an: `&Vec<i32>` → `&[i32]`.
- Die Funktion erhält einen Slice der fünf Zahlen.

#### Die Deref-Coercion-Kette

Rust wendet Deref-Coercion mehrfach hintereinander an. Wenn `&T` in `&U` umgewandelt werden muss und `T: Deref<Target=V>` und `V: Deref<Target=U>`, dann wird die Kette `T → V → U` automatisch durchlaufen.

Beispiel mit `Box<String>`:

```rust
fn gruss_ausgeben(name: &str) {
    println!("Hallo, {}!", name);
}

fn main() {
    let name = Box::new(String::from("Erika"));

    // Deref-Coercion-Kette:
    // &Box<String> → &String (Box implementiert Deref<Target=String>)
    // &String → &str (String implementiert Deref<Target=str>)
    gruss_ausgeben(&name);
}
```

**Erklärung der Kette:**

1. `&name` ist vom Typ `&Box<String>`.
2. `Box<String>` implementiert `Deref<Target=String>`, also wird `&Box<String>` zu `&String`.
3. `String` implementiert `Deref<Target=str>`, also wird `&String` zu `&str`.
4. Die Funktion `gruss_ausgeben` erwartet `&str` – der finale Typ passt.

Rust erledigt diese gesamte Kette zur Compilezeit ohne Laufzeit-Overhead.

#### Die drei Regeln der Deref-Coercion

Der Rust-Compiler wendet Deref-Coercion in folgenden drei Situationen automatisch an:

**Regel 1:** Wenn `T: Deref<Target=U>` gilt, wird `&T` automatisch zu `&U`.

**Regel 2:** Wenn `T: DerefMut<Target=U>` gilt, wird `&mut T` automatisch zu `&mut U`.

**Regel 3:** Wenn `T: Deref<Target=U>` gilt, wird `&mut T` automatisch zu `&U`.

> [!NOTE]
> Regel 3 erlaubt die Umwandlung einer veränderlichen Referenz in eine unveränderliche Referenz (durch Deref-Coercion). Die umgekehrte Richtung (unveränderlich zu veränderlich) ist nicht erlaubt, weil sie das Borrowing-Regelwerk verletzen würde.

#### Implementierung von Deref für eigene Typen

Sie können das `Deref`-Trait für Ihre eigenen Typen implementieren, um Deref-Coercion zu ermöglichen:

```rust
use std::ops::Deref;

/// Ein einfacher Wrapper-Typ, der einen Wert kapselt.
struct MeinBox<T>(T);

impl<T> MeinBox<T> {
    fn new(x: T) -> MeinBox<T> {
        MeinBox(x)
    }
}

impl<T> Deref for MeinBox<T> {
    type Target = T;

    fn deref(&self) -> &Self::Target {
        &self.0
    }
}

fn gruss_ausgeben(name: &str) {
    println!("Hallo, {}!", name);
}

fn main() {
    let name = MeinBox::new(String::from("Max"));

    // Deref-Coercion-Kette:
    // &MeinBox<String> → &String (MeinBox implementiert Deref<Target=String>)
    // &String → &str (String implementiert Deref<Target=str>)
    gruss_ausgeben(&name);

    // Explizite Dereferenzierung:
    println!("Name: {}", *name);  // *name ergibt String
}
```

**Zeile-für-Zeile-Erklärung:**

```rust
struct MeinBox<T>(T);
```
- Ein **Tupel-Struct** mit einem generischen Typ-Parameter `T`.
- `MeinBox<i32>` enthält genau einen `i32`-Wert.
- Zugriff auf das erste (und einzige) Feld: `self.0`.

```rust
impl<T> MeinBox<T> {
    fn new(x: T) -> MeinBox<T> {
        MeinBox(x)
    }
}
```
- `impl<T> MeinBox<T>`: Implementierungsblock für `MeinBox<T>` mit generischem `T`.
- `fn new(x: T) -> MeinBox<T>`: Konstruktorfunktion.
- `MeinBox(x)`: Erstellt eine neue `MeinBox` mit dem Wert `x`.

```rust
impl<T> Deref for MeinBox<T> {
    type Target = T;
```
- Implementiert das `Deref`-Trait für `MeinBox<T>`.
- `type Target = T`: Dereferenzierung ergibt den inneren Typ `T`.

```rust
    fn deref(&self) -> &Self::Target {
        &self.0
    }
```
- `&self.0`: Gibt eine Referenz auf das erste Feld des Tupel-Structs zurück.
- Das ist der Wert, auf den `MeinBox` zeigt.

```rust
    gruss_ausgeben(&name);
```
- `name` ist `MeinBox<String>`, `&name` ist `&MeinBox<String>`.
- Rust wendet zweifach Deref-Coercion an: `&MeinBox<String>` → `&String` → `&str`.

#### Das DerefMut-Trait

Analog zu `Deref` gibt es `DerefMut` für veränderliche Dereferenzierung:

```rust
use std::ops::{Deref, DerefMut};

struct MeinBox<T>(T);

impl<T> MeinBox<T> {
    fn new(x: T) -> MeinBox<T> {
        MeinBox(x)
    }
}

impl<T> Deref for MeinBox<T> {
    type Target = T;
    fn deref(&self) -> &T {
        &self.0
    }
}

impl<T> DerefMut for MeinBox<T> {
    fn deref_mut(&mut self) -> &mut T {
        &mut self.0
    }
}

fn text_gross_machen(s: &mut String) {
    *s = s.to_uppercase();
}

fn main() {
    let mut name = MeinBox::new(String::from("max"));

    // &mut MeinBox<String> → &mut String (durch DerefMut)
    text_gross_machen(&mut name);

    println!("{}", *name);  // Ausgabe: MAX
}
```

**Erklärung:**

```rust
impl<T> DerefMut for MeinBox<T> {
    fn deref_mut(&mut self) -> &mut T {
        &mut self.0
    }
}
```
- `DerefMut` erfordert, dass `Deref` bereits implementiert ist.
- `fn deref_mut(&mut self) -> &mut T`: Gibt eine **veränderliche** Referenz auf das innere Feld zurück.

```rust
    text_gross_machen(&mut name);
```
- `&mut name` ist `&mut MeinBox<String>`.
- Durch `DerefMut`-Coercion wird dies zu `&mut String`.
- Die Funktion kann den String modifizieren.

### 19.8.4 Dangling References

#### Was ist eine Dangling Reference?

Eine **Dangling Reference** (baumelnde Referenz) ist eine Referenz auf Speicher, der bereits freigegeben wurde. In C und C++ können solche Referenzen entstehen, wenn ein Zeiger auf eine lokale Variable zurückgegeben wird, die beim Verlassen der Funktion ungültig wird.

Rust verhindert Dangling References zur Compilezeit durch den Borrow-Checker und das Lifetime-System.

#### Fehlerhafter Versuch: Referenz auf lokale Variable zurückgeben

```rust
fn erstelle_referenz() -> &String {    // FEHLER: fehlende Lifetime-Annotation
    let s = String::from("Hallo");
    &s    // s wird hier gedroppt – die Referenz würde auf ungültigen Speicher zeigen
}

fn main() {
    let r = erstelle_referenz();
    println!("{}", r);
}
```

**Compiler-Fehler:**

```
error[E0106]: missing lifetime specifier
 --> src/main.rs:1:30
  |
1 | fn erstelle_referenz() -> &String {
  |                            ^ expected named lifetime parameter
  |
  = help: this function's return type contains a borrowed value, but there is
    no value for it to be borrowed from
help: consider using the `'static` lifetime, but this is uncommon unless you're
      returning a borrowed value from a `const` or a `static`
  |
1 | fn erstelle_referenz() -> &'static String {
  |                            +++++++
```

**Analyse des Fehlers:**

- `error[E0106]`: Fehlende Lifetime-Spezifikation.
- `this function's return type contains a borrowed value, but there is no value for it to be borrowed from`: Der Rückgabewert ist eine Referenz, aber es gibt keinen Wert in der Funktion, der lang genug lebt, um ausgeliehen zu werden.
- Der Compiler schlägt `'static` vor, aber das ist hier falsch – der Wert `s` ist nicht `'static`.

**Was tatsächlich passieren würde (ohne Rust):**

```
Funktionsaufruf erstelle_referenz():
┌──────────────────────┐
│ s: String            │
│   ptr ─────────────► Heap: "Hallo"
│   len: 5             │
│   cap: 5             │
│                      │
│ Rückgabe: &s (Adresse│
│ von s auf Stack)     │
└──────────────────────┘
   ↓ Funktion endet: s wird gedroppt, Heap-Speicher wird freigegeben
   ↓
Die zurückgegebene Referenz zeigt jetzt auf ungültigen Speicher!
```

In C würde dieses Programm compilieren und zur Laufzeit undefiniertes Verhalten zeigen. Rust verhindert dies.

#### Die korrekte Lösung: Ownership zurückgeben

Wenn Sie aus einer Funktion einen `String` zurückgeben wollen, geben Sie den Wert selbst zurück (Ownership-Transfer), nicht eine Referenz:

```rust
fn erstelle_string() -> String {    // Ownership wird zurückgegeben
    let s = String::from("Hallo");
    s    // s wird zurückgegeben (moved), nicht gedroppt
}

fn main() {
    let s = erstelle_string();    // s übernimmt Ownership des Strings
    println!("{}", s);            // Gültig: s ist der Owner
}
```

**Erklärung:**

```rust
fn erstelle_string() -> String {
```
- Der Rückgabetyp ist `String` (nicht `&String`).
- Die Funktion gibt den Wert zurück, nicht eine Referenz.

```rust
    s    // s wird zurückgegeben (moved), nicht gedroppt
```
- `s` wird zurückgegeben. Die Ownership wird an den Aufrufer übertragen.
- `s` wird **nicht** gedroppt, weil sie bewegt (moved) wurde.

```rust
    let s = erstelle_string();
```
- `s` in `main` übernimmt die Ownership des zurückgegebenen Strings.
- Der String ist gültig für den gesamten Scope von `s` in `main`.

### 19.8.5 Referenzen in Structs (Vorschau auf Lifetimes)

#### Das Problem

Was passiert, wenn ein Struct ein Referenzfeld enthält?

```rust
struct Ausschnitt {
    text: &str,    // FEHLER: fehlende Lifetime-Annotation
}
```

Dies kompiliert nicht, weil Rust nicht weiß, wie lang die Referenz `&str` leben soll. Die Referenz muss mindestens so lang leben wie der `Ausschnitt`-Struct selbst.

**Compiler-Fehler:**

```
error[E0106]: missing lifetime specifier
 --> src/main.rs:2:11
  |
2 |     text: &str,
  |           ^ expected named lifetime parameter
```

#### Die Lösung: Lifetime-Annotationen

Um dieses Problem zu lösen, benötigen Sie **Lifetime-Annotationen** – eine Syntax, mit der Sie dem Compiler mitteilen, wie lange Referenzen leben müssen:

```rust
struct Ausschnitt<'a> {
    text: &'a str,    // 'a ist eine Lifetime-Annotation
}

impl<'a> Ausschnitt<'a> {
    fn ausgeben(&self) {
        println!("Ausschnitt: {}", self.text);
    }
}

fn main() {
    let roman = String::from(
        "Ruf mich Ismael. Vor einigen Jahren - genau kann ich nicht sagen, wie viele..."
    );

    let erster_satz;
    {
        let bytes = roman.as_bytes();
        let mut ende = roman.len();

        for (i, &zeichen) in bytes.iter().enumerate() {
            if zeichen == b'.' {
                ende = i;
                break;
            }
        }

        erster_satz = Ausschnitt {
            text: &roman[0..ende],
        };

        erster_satz.ausgeben();
    }
}
```

**Zeile-für-Zeile-Erklärung:**

```rust
struct Ausschnitt<'a> {
```
- `<'a>`: Deklariert einen Lifetime-Parameter namens `'a` (Apostroph + Name).
- Lifetime-Parameter beginnen konventionell mit einem Apostroph und sind kurze Namen wie `'a`, `'b`, `'text`.

```rust
    text: &'a str,
```
- `&'a str`: Eine Referenz auf einen `str`-Wert, die mindestens so lang wie `'a` lebt.
- Damit stellt der Compiler sicher, dass der `Ausschnitt` nicht länger lebt als der String, auf den `text` verweist.

```rust
impl<'a> Ausschnitt<'a> {
```
- `impl<'a>`: Der Implementierungsblock muss den Lifetime-Parameter ebenfalls deklarieren.

```rust
    erster_satz = Ausschnitt {
        text: &roman[0..ende],
    };
```
- `&roman[0..ende]` ist ein String-Slice: eine Referenz auf den Teil des Strings von Byte 0 bis Byte `ende`.
- Dieser Slice zeigt auf denselben Heap-Speicher wie `roman`.
- Der `Ausschnitt` enthält eine Referenz auf `roman` – daher muss `roman` länger leben als der `Ausschnitt`.

> [!NOTE]
> Lifetime-Annotationen sind ein fortgeschrittenes Thema und werden in einem späteren Kapitel ausführlich behandelt. An dieser Stelle genügt es, zu verstehen, **warum** sie notwendig sind: Um dem Compiler zu zeigen, dass Referenzen in Structs gültig bleiben, solange der Struct existiert. Die Syntax `'a` ist nur ein Name für eine Lebensdauer-Einschränkung.

> [!WARNING]
> Wenn Sie Structs mit Referenzfeldern definieren und die Lifetime-Annotationen weglassen, wird der Compiler einen `E0106`-Fehler ausgeben. Fügen Sie entweder Lifetime-Annotationen hinzu, oder erwägen Sie, den Wert statt einer Referenz im Struct zu speichern (was oft die einfachere Lösung ist).

```rust
fn text_statistik(s: &String) -> (usize, usize, usize, usize) {

        if c == ' ' {
```

### Übung 3: Deref-Coercion und eigener Smart Pointer

**Aufgabe:** Implementieren Sie einen einfachen `Stack<T>`-Typ (Stapel-Datenstruktur) mit folgenden Eigenschaften:
- Interne Speicherung in einem `Vec<T>`.
- Methoden: `push(wert: T)`, `pop() -> Option<T>`, `peek() -> Option<&T>`, `ist_leer() -> bool`, `groesse() -> usize`.
- Implementieren Sie das `Deref`-Trait so, dass `&Stack<T>` automatisch zu `&[T]` wird (Zugriff auf den internen Vec als Slice).
- Demonstrieren Sie die Deref-Coercion, indem Sie eine Funktion `slices_ausgeben(s: &[i32])` schreiben und diese mit einem `&Stack<i32>` aufrufen.

**Musterlösung:**

```rust
use std::ops::Deref;

struct Stack<T> {
    elemente: Vec<T>,
}

impl<T> Stack<T> {
    /// Erstellt einen neuen, leeren Stack.
    fn neu() -> Stack<T> {
        Stack {
            elemente: Vec::new(),
        }
    }

    /// Legt ein Element auf den Stack.
    fn push(&mut self, wert: T) {
        self.elemente.push(wert);
    }

    /// Entfernt und gibt das oberste Element des Stacks zurück.
    fn pop(&mut self) -> Option<T> {
        self.elemente.pop()
    }

    /// Gibt eine Referenz auf das oberste Element zurück, ohne es zu entfernen.
    fn peek(&self) -> Option<&T> {
        self.elemente.last()
    }

    /// Gibt true zurück, wenn der Stack leer ist.
    fn ist_leer(&self) -> bool {
        self.elemente.is_empty()
    }

    /// Gibt die Anzahl der Elemente im Stack zurück.
    fn groesse(&self) -> usize {
        self.elemente.len()
    }
}

impl<T> Deref for Stack<T> {
    type Target = [T];

    fn deref(&self) -> &[T] {
        &self.elemente
    }
}

fn slices_ausgeben(s: &[i32]) {
    print!("Slice-Inhalt: [");
    for (i, wert) in s.iter().enumerate() {
        if i > 0 {
            print!(", ");
        }
        print!("{}", wert);
    }
    println!("]");
}

fn main() {
    let mut stack: Stack<i32> = Stack::neu();

    println!("Stack leer? {}", stack.ist_leer());

    stack.push(10);
    stack.push(20);
    stack.push(30);
    stack.push(40);

    println!("Stack-Größe: {}", stack.groesse());
    println!("Oberstes Element (peek): {:?}", stack.peek());

    // Deref-Coercion: &Stack<i32> wird automatisch zu &[i32]
    slices_ausgeben(&stack);

    println!("Pop: {:?}", stack.pop());
    println!("Pop: {:?}", stack.pop());

    println!("Stack-Größe nach 2 Pops: {}", stack.groesse());

    // Deref-Coercion erlaubt auch den Zugriff auf Slice-Methoden:
    let summe: i32 = stack.iter().sum();
    println!("Summe der verbleibenden Elemente: {}", summe);
}
```

**Zeile-für-Zeile-Erklärung:**

```rust
struct Stack<T> {
    elemente: Vec<T>,
}
```
- Generischer Struct mit einem Vektor als internem Speicher.
- `T` ist der Typ der gespeicherten Elemente.

```rust
    fn peek(&self) -> Option<&T> {
        self.elemente.last()
    }
```
- `&self`: Unveränderliche Referenz auf den Stack.
- `.last()`: Gibt `Some(&T)` zurück (Referenz auf das letzte Element) oder `None`.
- Der Rückgabetyp `Option<&T>` enthält eine Referenz – das Element bleibt im Stack.

```rust
impl<T> Deref for Stack<T> {
    type Target = [T];

    fn deref(&self) -> &[T] {
        &self.elemente
    }
}
```
- `Target = [T]`: Dereferenzierung ergibt einen Slice `[T]` (nicht `Vec<T>`).
- `&self.elemente`: Da `Vec<T>` zu `[T]` coerciert werden kann, ist `&self.elemente` automatisch `&[T]`.
- Damit wird `&Stack<T>` zu `&[T]` – alle Slice-Methoden (`.iter()`, `.len()`, usw.) sind verfügbar.

```rust
    // Deref-Coercion: &Stack<i32> wird automatisch zu &[i32]
    slices_ausgeben(&stack);
```
- `&stack` ist `&Stack<i32>`.
- `slices_ausgeben` erwartet `&[i32]`.
- Rust wendet Deref-Coercion an: `&Stack<i32>` → `&[i32]`.

```rust
    let summe: i32 = stack.iter().sum();
```
- `stack.iter()`: Rust dereferenziert `Stack<i32>` automatisch zu `[i32]` und ruft `.iter()` auf dem Slice auf.
- `.sum()`: Addiert alle Elemente. Der Rückgabetyp `i32` wird durch die Typ-Annotation `summe: i32` angegeben.

**Erwartete Ausgabe:**
```
Stack leer? true
Stack-Größe: 4
Oberstes Element (peek): Some(40)
Slice-Inhalt: [10, 20, 30, 40]
Pop: Some(40)
Pop: Some(30)
Stack-Größe nach 2 Pops: 2
Summe der verbleibenden Elemente: 30
```

```
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  GLEICHZEITIG ERLAUBT:          GLEICHZEITIG VERBOTEN:          │
│  ✓ Beliebig viele &T            ✗ &T und &mut T zusammen        │
│  ✓ Genau eine &mut T            ✗ Mehrere &mut T                │
│  ✓ &T und der Owner             ✗ &mut T und &T                 │
│                                                                  │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  DEREF-COERCION-KETTE:                                           │
│  &Box<String> → &String → &str                                  │
│  &Vec<T> → &[T]                                                  │
│  &MeinBox<T> → &T (wenn Deref implementiert)                    │
│                                                                  │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  DEREFERENZIERUNGSOPERATOR (*):                                   │
│  *referenz       → Wert lesen                                    │
│  *ref_mut = wert → Wert schreiben                                │
│  Rust dereferenziert automatisch bei Methodenaufrufen            │
│                                                                  │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  DANGLING REFERENCES: Rust verhindert diese zur Compilezeit!     │
│  Lösung: Ownership zurückgeben statt Referenz                    │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### Merkzettel: Referenz-Syntax

| Situation | Syntax | Bedeutung |
|-----------|--------|-----------|
| Unveränderliche Referenz erstellen | `&variable` | Leiht `variable` unveränderlich aus |
| Veränderliche Referenz erstellen | `&mut variable` | Leiht `variable` veränderlich aus |
| Unveränderliche Referenz in Signatur | `fn f(x: &Typ)` | Nimmt eine unveränderliche Referenz |
| Veränderliche Referenz in Signatur | `fn f(x: &mut Typ)` | Nimmt eine veränderliche Referenz |
| Wert lesen über Referenz | `*referenz` | Dereferenzierung (oft automatisch) |
| Wert schreiben über Referenz | `*ref_mut = wert` | Schreiben durch veränderliche Referenz |
| Referenz auf Struct-Feld | `&instanz.feld` | Referenz nur auf ein Feld |
| Slice-Referenz | `&vektor[1..3]` | Referenz auf einen Teil des Vektors |

### Lernstrategie: Fehlerbasiertes Lernen

Eine besonders effektive Strategie beim Lernen von Rust ist das **fehlerbasierte Lernen**:

1. **Schreiben Sie absichtlich fehlerhaften Code.** Versuchen Sie, zwei veränderliche Referenzen zu erstellen, oder eine Referenz auf eine lokale Variable zurückzugeben. Lesen Sie die Fehlermeldungen sorgfältig.

2. **Nutzen Sie `rustc --explain <FEHLERCODE>`.** Jeder Rust-Fehler hat einen Code (z.B. `E0502`). Der Befehl `rustc --explain E0502` gibt eine ausführliche Erklärung mit Codebeispielen aus.

3. **Verwenden Sie Clippy.** Das Tool `cargo clippy` gibt zusätzliche Warnungen und Verbesserungsvorschläge. Besonders nützlich für Anfänger, da es häufige Antipattern erkennt.

4. **Machen Sie sich das mentale Modell zu eigen.** Stellen Sie sich immer vor, wie der Borrow-Checker denkt: „Kann dieser Zugriff zu einem Data Race führen?" Wenn ja, verbietet Rust ihn.

### Häufige Anfängerfehler und ihre Lösungen

| Fehler | Problem | Lösung |
|--------|---------|--------|
| Wert nach Move verwenden | Ownership wurde übertragen | Referenz statt Move verwenden |
| Zwei `&mut T` gleichzeitig | Verletzt Exklusivitätsregel | Einen Scope früher enden lassen |
| `&T` und `&mut T` gleichzeitig | Verletzt das Regelwerk | Unveränderliche Referenzen zuerst fertig nutzen |
| Referenz auf lokale Variable zurückgeben | Dangling Reference | Wert zurückgeben (Ownership-Transfer) |
| Fehlender `*` beim Schreiben | Typ-Mismatch | `*referenz = wert` verwenden |
| `&String` statt `&str` in Funktion | Zu restriktiv | Parameter als `&str` definieren |

> [!TIP]
> Wenn Sie nicht sicher sind, ob Sie eine Referenz oder eine Kopie verwenden sollen: Beginnen Sie mit einer Referenz. Falls der Compiler beschwert, überlegen Sie, ob Sie `.clone()` benötigen oder die Struktur des Codes anpassen müssen. In der Praxis ist `.clone()` oft unnötig und deutet auf eine suboptimale Programmstruktur hin.

> [!NOTE]
> Das Borrowing-System ist zunächst ungewohnt, besonders wenn Sie aus einer Sprache kommen, die Garbage Collection (Java, Python, JavaScript) oder manuelle Speicherverwaltung (C, C++) verwendet. Geben Sie sich Zeit – nach einigen Wochen aktiver Rust-Programmierung werden die Regeln zur zweiten Natur.

## 19.11 Zusammenfassung

In diesem Kapitel haben Sie das Konzept des **Borrowings** (Ausleihens) kennengelernt – eines der zentralen Konzepte in Rust, das die einzigartige Kombination aus Speichersicherheit ohne Garbage Collector ermöglicht.

### Was Sie gelernt haben

**Unveränderliche Referenzen (`&T`):**
- Eine Referenz ist ein 8-Byte-Zeiger (auf 64-Bit-Systemen), der auf den Originalwert verweist.
- Unveränderliche Referenzen erlauben nur Lesezugriff.
- Beliebig viele unveränderliche Referenzen können gleichzeitig existieren.
- Syntax: `&variable` zum Erstellen, `&Typ` in Funktionssignaturen.

**Veränderliche Referenzen (`&mut T`):**
- Erlauben Lese- **und** Schreibzugriff auf den referenzierten Wert.
- Zu jedem Zeitpunkt darf nur genau eine veränderliche Referenz auf einen Wert existieren.
- `&T` und `&mut T` auf denselben Wert dürfen nicht gleichzeitig existieren.
- Diese Einschränkungen eliminieren Data Races zur Compilezeit.

**Dereferenzierungsoperator (`*`):**
- Folgt einem Zeiger und gibt den Wert zurück, auf den er zeigt.
- Notwendig beim expliziten Lesen über eine Referenz oder beim Schreiben über eine veränderliche Referenz.
- Rust führt in vielen Kontexten automatische Dereferenzierung durch.

**Deref-Coercion:**
- Automatische Typumwandlung durch wiederholte Anwendung des `Deref`-Traits.
- `&String` wird automatisch zu `&str`.
- `&Vec<T>` wird automatisch zu `&[T]`.
- Eigene Typen können durch Implementierung von `Deref` an diesem Mechanismus teilnehmen.
- Drei Regeln: `&T → &U` (Deref), `&mut T → &mut U` (DerefMut), `&mut T → &U` (Deref).

**Dangling References:**
- Rust verhindert zur Compilezeit, dass eine Referenz auf freigegebenen Speicher zeigt.
- Lösung: Ownership zurückgeben statt Referenz, wenn der Wert die Funktion überleben soll.

**Referenzen in Structs:**
- Erfordern Lifetime-Annotationen (Vorschau auf das nächste Kapitel).
- Der Compiler stellt sicher, dass die Referenz mindestens so lang lebt wie der Struct.

### Die zwei goldenen Regeln des Borrowings

```
Regel 1: Zu jedem Zeitpunkt darf ein Wert entweder
         beliebig viele unveränderliche Referenzen (&T)
         ODER genau eine veränderliche Referenz (&mut T)
         haben – nicht beides gleichzeitig.

Regel 2: Referenzen müssen stets gültig sein.
         Sie dürfen nie länger leben als der Wert,
         auf den sie zeigen (keine Dangling References).
```

### Ausblick

Im nächsten Kapitel (Kapitel 20) werden Sie die **Grundlagen von Referenzen und Borrowing** vertiefen und weitere praktische Muster kennenlernen. Aufbauend darauf werden spätere Kapitel das **Lifetime**-System von Rust behandeln, das die Regeln des Borrowings auf komplexere Szenarien – insbesondere Structs mit Referenzfeldern und Funktionen mit mehreren Referenz-Parametern – ausdehnt.

> [!IMPORTANT]
> Die Konzepte aus diesem Kapitel – Referenzen, Borrowing, Deref-Coercion – werden in nahezu jedem Rust-Programm verwendet. Eine solide Beherrschung dieser Grundlagen ist die Voraussetzung für den Einstieg in alle fortgeschrittenen Rust-Themen: Traits, generische Programmierung, asynchrone Programmierung und Systemprogrammierung.
