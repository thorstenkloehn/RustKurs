# Kapitel 22: Der VS Code Planungs-Workflow

> [!IMPORTANT]
> In diesem Kapitel geht es nicht um eine neue Rust-Syntax, sondern um professionelles Arbeiten: planen, typisieren, prüfen, implementieren und gezielt verbessern.

## 22.1 Lernziele & Lernplan

Nach diesem Kapitel können Sie:

- ein Rust-Feature vor der Implementierung in kleine, überprüfbare Schritte zerlegen;
- `todo!()`, `unimplemented!()` und `unreachable!()` korrekt einordnen;

- Compilerfehler priorisieren, statt wahllos an mehreren Stellen gleichzeitig zu ändern;
- eine kleine CLI-Funktion mit Plan, Platzhaltern, Tests und Umsetzung entwickeln.

## 22.2 Die Definition

Der **VS Code Planungs-Workflow** ist eine iterative Arbeitsmethode für Rust-Projekte:

```text
Planen -> Signaturen schreiben -> Platzhalter setzen -> cargo check -> implementieren -> testen
```

Die wichtigsten Werkzeuge:

| Werkzeug | Zweck |
|---|---|
| VS Code | Editor, Navigation, Problems-Ansicht. |
| rust-analyzer | Sprachserver für Typinfos, Inline-Fehler und Refactorings. |
| `todo!()` | Kompilierbarer Platzhalter, der zur Laufzeit panikt. |
| `cargo check` | Schnelle statische Prüfung ohne vollständigen Build. |
| `cargo test` | Ausführung automatisierter Tests. |

> [!NOTE]
> `todo!()` ist kein fertiger Code. Es ist ein absichtlicher Marker: "Die Struktur stimmt, die Implementierung fehlt noch."

## 22.3 Das Problem & die Motivation

Viele Anfänger beginnen mit einer großen Funktion und schreiben sofort Logik hinein. Bei Rust führt das schnell zu einer Mischung aus Syntaxfehlern, Typfehlern, Borrowing-Problemen und unklarer Architektur. Der Compiler meldet dann viele Symptome, aber die eigentliche Ursache ist fehlende Struktur.

Ein guter Workflow reduziert die kognitive Last:

- Zuerst klären Sie Eingaben und Ausgaben.
- Dann schreiben Sie Signaturen.
- Danach prüfen Sie, ob das Programm strukturell zusammenpasst.
- Erst am Ende füllen Sie die Logik aus.

Das passt besonders gut zu Rust, weil Typen sehr viel Architektur ausdrücken.

## 22.4 Der naive Versuch

Ein Anfänger möchte einen Taschenrechner schreiben und beginnt direkt:

```rust
fn main() {
    let eingabe = "10 + 5";
    let ergebnis = berechne(eingabe);
    println!("{ergebnis}");
}

fn berechne(eingabe: &str) -> i32 {
    let teile = eingabe.split(" ");
    let links = teile[0].parse::<i32>().unwrap();
    let op = teile[1];
    let rechts = teile[2].parse::<i32>().unwrap();

    if op == "+" {
        links + rechts
    }
}
```

Zeile-für-Zeile:

| Zeile | Problem |
|---|---|
| `split(" ")` | Liefert einen Iterator, keinen indexierbaren Vektor. |
| `teile[0]` | Iteratoren unterstützen keine Indexsyntax. |
| `if op == "+" { ... }` | Der `else`-Fall fehlt, obwohl `i32` zurückgegeben werden muss. |
| `unwrap()` | Panikt bei ungültiger Eingabe. |

EVA-Analyse:

| Phase | Beschreibung |
|---|---|
| Eingabe | Ein Text wie `"10 + 5"`. |
| Verarbeitung | Parsing und Operatorauswertung sind vermischt. |
| Ausgabe | Ein `i32`, aber nicht jeder Codepfad liefert einen Wert. |

## 22.5 Die Anatomie des Fehlers

Typische Compilerhinweise:

```text
error[E0608]: cannot index into a value of type `Split<'_, &str>`
error[E0317]: `if` may be missing an `else` expression
```

Der technische Kern:

- `split` erzeugt eine faule Sequenz. Sie müssen iterieren oder sammeln.
- Eine Funktion mit Rückgabetyp `i32` muss auf jedem Pfad ein `i32` liefern.
- Der Code vermischt vier Verantwortlichkeiten: Eingabe zerlegen, Zahlen parsen, Operator prüfen, Ergebnis berechnen.

> [!WARNING]
> Wenn Sie Parsing, Validierung und Berechnung in einer Funktion vermischen, werden Compilerfehler schwerer lesbar. Trennen Sie Aufgaben früh.

## 22.6 Die Lösung

Erst planen, dann Signaturen:

```rust
#[derive(Debug, PartialEq)]
enum Operator {
    Add,
    Sub,
}

fn parse_operator(token: &str) -> Option<Operator> {
    match token {
        "+" => Some(Operator::Add),
        "-" => Some(Operator::Sub),
        _ => None,
    }
}

fn berechne(links: i32, rechts: i32, op: Operator) -> i32 {
    match op {
        Operator::Add => links + rechts,
        Operator::Sub => links - rechts,
    }
}

fn auswerten(eingabe: &str) -> Option<i32> {
    let teile: Vec<&str> = eingabe.split_whitespace().collect();
    if teile.len() != 3 {
        return None;
    }

    let links = teile[0].parse::<i32>().ok()?;
    let op = parse_operator(teile[1])?;
    let rechts = teile[2].parse::<i32>().ok()?;

    Some(berechne(links, rechts, op))
}

fn main() {
    match auswerten("10 + 5") {
        Some(ergebnis) => println!("Ergebnis: {ergebnis}"),
        None => println!("Ungueltige Eingabe"),
    }
}
```

Warum dies funktioniert:

- `parse_operator` kapselt Operatorlogik.
- `berechne` arbeitet nur mit bereits validierten Daten.
- `auswerten` gibt `Option<i32>` zurück, weil Parsing scheitern kann.
- `?` auf `Option` beendet die Funktion früh mit `None`.

EVA:

| Phase | Beschreibung |
|---|---|
| Eingabe | `&str`, eine nicht besitzende Sicht auf die Eingabe. |
| Verarbeitung | Zerlegen, Länge prüfen, Zahlen parsen, Operator parsen, rechnen. |
| Ausgabe | `Some(i32)` bei Erfolg oder `None` bei ungültiger Eingabe. |

## 22.7 Kleines Tutorial: Plan -> `todo!()` -> Implementierung

### Schritt 1: Pseudocode schreiben

```text
FUNKTION auswerten(eingabe):
    zerlege eingabe in drei Teile
    wenn nicht genau drei Teile vorhanden sind: None
    parse linke Zahl
    parse Operator
    parse rechte Zahl
    berechne Ergebnis
```

### Schritt 2: Gerüst mit Platzhaltern

```rust
#[derive(Debug, PartialEq)]
enum Operator {
    Add,
    Sub,
}

fn parse_operator(_token: &str) -> Option<Operator> {
    todo!("Operator aus Text lesen")
}

fn berechne(_links: i32, _rechts: i32, _op: Operator) -> i32 {
    todo!("Rechenoperation ausfuehren")
}

fn auswerten(_eingabe: &str) -> Option<i32> {
    todo!("Eingabe parsen und berechnen")
}

fn main() {
    println!("{:?}", auswerten("10 + 5"));
}
```

Dieser Code kompiliert mit `cargo check`, weil `todo!()` den Never-Typ `!` hat und sich in jeden erwarteten Rückgabetyp einfügen lässt.

### Schritt 3: Tests zuerst ergänzen

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn addition_funktioniert() {
        assert_eq!(auswerten("10 + 5"), Some(15));
    }

    #[test]
    fn ungueltige_eingabe_liefert_none() {
        assert_eq!(auswerten("10 mal 5"), None);
    }
}
```

### Schritt 4: Platzhalter einzeln ersetzen

Ersetzen Sie zuerst `parse_operator`, führen Sie `cargo test` aus, ersetzen Sie danach `berechne`, und erst zuletzt `auswerten`. So wissen Sie bei jedem Fehler, welcher Schritt ihn verursacht hat.

## 22.8 Mentale Modelle & Deep Dive

### Der Compiler als Checkliste

```mermaid
flowchart LR
    A[Plan] --> B[Signaturen]
    B --> C[todo!()]
    C --> D[cargo check]
    D --> E[Implementierung]
    E --> F[cargo test]
    F --> A
```

### Never-Typ `!`

`todo!()`, `panic!()` und `unimplemented!()` kehren nicht normal zurück. Deshalb haben sie den Typ `!`. Dieser Typ kann in Positionen stehen, an denen eigentlich `i32`, `String`, `Option<T>` oder ein anderer Typ erwartet wird.

```rust
fn zahl() -> i32 {
    todo!("spaeter implementieren")
}
```

Das ist für Planung nützlich, darf aber nicht in fertigen Pfaden verbleiben.

### Praktische VS-Code-Ansicht

| Anzeige | Nutzen |
|---|---|
| Problems | Liste aller aktuellen Compiler- und Analyzer-Hinweise. |
| Hover | Typ einer Variable oder Funktion anzeigen. |
| Go to Definition | Definition eines Symbols öffnen. |
| Rename Symbol | Umbenennen über mehrere Dateien hinweg. |
| Code Actions | Vorschläge wie Imports oder kleine Fixes anwenden. |

## 22.9 Drei praktische Übungen

### Übung 1: Leicht - Platzhalter setzen

Schreiben Sie ein Gerüst für:

```rust
fn ist_gerade(zahl: i32) -> bool
```

Nutzen Sie zuerst `todo!()`, prüfen Sie mit `cargo check`, und implementieren Sie danach `% 2 == 0`.

Lösungshinweis: Der Rückgabetyp ist `bool`; `todo!()` passt trotzdem.

### Übung 2: Mittel - Parser planen

Schreiben Sie:

```rust
fn parse_positiv(text: &str) -> Option<u32>
```

Anforderungen:

- `"42"` ergibt `Some(42)`.
- `"-1"` ergibt `None`.
- `"abc"` ergibt `None`.

Lösungshinweis: Nutzen Sie `parse::<u32>().ok()`.

### Übung 3: Schwer - Mini-Workflow dokumentieren

Erstellen Sie für ein kleines CLI-Werkzeug zuerst eine Planliste in Kommentaren:

- Eingabe lesen;
- Eingabe validieren;
- Ergebnis berechnen;
- Ergebnis ausgeben.

Schreiben Sie dann Signaturen mit `todo!()` und ersetzen Sie jeden Platzhalter einzeln.

Lösungshinweis: Jeder Schritt sollte mit `cargo check` überprüfbar bleiben.

## 22.10 Lernstrategie, Selbsteinschätzung & Merkzettel

### Cheat Sheet

| Aufgabe | Befehl oder Syntax |
|---|---|
| Schnell prüfen | `cargo check` |
| Tests ausführen | `cargo test` |
| Platzhalter | `todo!("Grund")` |
| Bewusst nicht implementiert | `unimplemented!("Grund")` |
| Logisch unerreichbar | `unreachable!("Grund")` |
| Typ anzeigen | VS Code Hover |
| Fehlerliste öffnen | Problems-Ansicht |

### Active Recall

1. Warum ist `cargo check` in frühen Phasen schneller als `cargo build`?
2. Warum kompiliert eine Funktion mit `todo!()` trotz Rückgabetyp?
3. Welche Aufgabe sollte eine Funktionssignatur vor der Implementierung erfüllen?
4. Warum sind kleine Tests Teil des Planungs-Workflows?

### Feynman-Methode

Erklären Sie den Workflow in drei Sätzen: Was planen Sie zuerst, was prüft der Compiler, wann schreiben Sie die konkrete Logik?

### Gezielte Fehlerprovokation

Entfernen Sie den `else`- oder `_`-Arm aus einem `match`, das einen Wert zurückgeben muss. Lesen Sie, wie Rust unvollständige Kontrollflüsse meldet.

### Selbsttest

Sie beherrschen das Kapitel, wenn Sie:

- ein Feature erst in Signaturen und dann in Code übersetzen;
- `todo!()` als temporäres Werkzeug nutzen;
- Compilerfehler nach Ursache sortieren;
- eine kleine Funktion testgetrieben vervollständigen.

## 22.11 Zusammenfassung

- Planen vor Implementieren reduziert Fehlerfluten.
- Rust-Typen sind ein Architekturwerkzeug.
- `todo!()` erlaubt kompilierbare Gerüste, panikt aber zur Laufzeit.
- `cargo check` ist die schnelle Feedbackschleife für Strukturarbeit.
- VS Code und rust-analyzer helfen am meisten, wenn der Code in kleinen Schritten wächst.
