# Kapitel 20: Referenzen & Borrowing - Grundlagen und Regeln

> [!IMPORTANT]
> Dieses Kapitel vertieft Kapitel 19. Sie sollten den Unterschied zwischen Ownership, Move, Copy und Referenz bereits sicher benennen können.

## 20.2 Die Definition

Eine **Referenz** ist ein nicht besitzender Zugriff auf einen Wert. Sie zeigt auf Daten, ohne deren Eigentum zu übernehmen. Eine **unveränderliche Referenz** hat den Typ `&T` und erlaubt lesenden Zugriff. Eine **veränderliche Referenz** hat den Typ `&mut T` und erlaubt schreibenden Zugriff.

Die zentrale Borrowing-Regel lautet:

> Zu einem Wert dürfen entweder beliebig viele unveränderliche Referenzen oder genau eine veränderliche Referenz aktiv sein.

Die wichtigsten Begriffe:

| Begriff | Bedeutung |
|---|---|
| Borrow | Das Ausleihen eines Wertes per Referenz. |
| Referent | Der Wert, auf den eine Referenz zeigt. |
| Dereferenzierung | Zugriff auf den Wert hinter einer Referenz mit `*` oder automatischer Deref-Koerzierung. |
| Aliasing | Mehrere Namen oder Referenzen zeigen auf denselben Speicher. |
| Borrow Checker | Compilerkomponente, die Referenzen und Lebensdauern prüft. |

> [!NOTE]
> Eine Referenz ist nicht "ein halber Besitz". Besitz bleibt beim Owner. Die Referenz ist nur eine zeitlich begrenzte Zugriffserlaubnis.

## 20.3 Das Problem & die Motivation

Ohne Borrowing müssten Funktionen Werte ständig übernehmen und zurückgeben. Das ist unpraktisch und bei Heap-Daten teuer. Gleichzeitig darf ein Programm keine Referenz verwenden, nachdem der Besitzer gelöscht wurde, und keine Daten lesen, während sie an anderer Stelle unkoordiniert verändert werden.

In C oder C++ kann ein Zeiger auf bereits freigegebenen Speicher zeigen. In Sprachen mit Garbage Collector wird dieses Problem anders gelöst, dafür entsteht Laufzeitverwaltung. Rust wählt einen dritten Weg: Die Regeln werden zur Compilezeit geprüft.

Typische Ziele von Borrowing:

- Daten lesen, ohne Ownership zu verschieben;
- Daten gezielt verändern, ohne Kopien zu erstellen;
- Seiteneffekte sichtbar und begrenzt halten;
- Iteratoren, Slices und APIs effizient gestalten;
- Speichersicherheit ohne Garbage Collector erreichen.

## 20.4 Der naive Versuch

Ein Anfänger möchte häufig einen `String` an eine Funktion übergeben und danach weiterverwenden:

```rust
fn laenge(text: String) -> usize {
    text.len()
}

fn main() {
    let name = String::from("Ferris");
    let anzahl = laenge(name);
    println!("Der Name hat {anzahl} Zeichen.");
    println!("Der Name lautet: {name}");
}
```

Zeile-für-Zeile:

| Zeile | Erklärung |
|---|---|
| `fn laenge(text: String)` | Die Funktion übernimmt Ownership an einem `String`. |
| `text.len()` | Die Länge wird gelesen; der Heap-Inhalt wird nicht verändert. |
| `let name = String::from("Ferris");` | `name` liegt als Steuerblock auf dem Stack und zeigt auf Heap-Bytes. |
| `laenge(name)` | Ownership wird von `name` nach `text` verschoben. |
| `println!(..., {name})` | `name` wird nach dem Move erneut verwendet. Das ist ungültig. |

EVA-Analyse:

| Phase | Beschreibung |
|---|---|
| Eingabe | Ein besitzender `String` wird an `laenge` übergeben. |
| Verarbeitung | Die Funktion liest nur die Länge, besitzt den Wert aber trotzdem. |
| Ausgabe | `usize` wird zurückgegeben; am Funktionsende wird `text` gedroppt. |

## 20.5 Die Anatomie des Fehlers

Der Compiler meldet sinngemäß:

```text
error[E0382]: borrow of moved value: `name`
  --> src/main.rs:8:32
   |
6  |     let anzahl = laenge(name);
   |                         ---- value moved here
8  |     println!("Der Name lautet: {name}");
   |                                ^^^^^^ value borrowed here after move
```

Was im Speicher passiert:

```text
Vor dem Aufruf:

Stack                         Heap
name: ptr,len,cap  -------->  "Ferris"

Beim Aufruf laenge(name):

Stack                         Heap
text: ptr,len,cap  -------->  "Ferris"
name: ungueltig

Nach Funktionsende:

text wird gedroppt, Heap-Speicher wird freigegeben.
name darf nicht mehr benutzt werden.
```

Der Fehler entsteht nicht, weil `len()` gefährlich wäre. Der Fehler entsteht, weil die Signatur `String` Ownership verlangt, obwohl die Funktion nur lesen möchte.

Ein zweiter typischer Fehler entsteht bei veränderlichen Referenzen:

```rust
fn main() {
    let mut text = String::from("Rust");
    let leser = &text;
    let schreiber = &mut text;
    schreiber.push_str(" lernen");
    println!("{leser}");
}
```

Der Compiler lehnt dies ab, weil `leser` eine aktive unveränderliche Referenz ist, während `schreiber` exklusiven veränderlichen Zugriff verlangt.

> [!WARNING]
> `mut` an der Variablen und `&mut` an der Referenz sind verwandt, aber nicht identisch. `let mut text` erlaubt Änderungen am Besitzer. `&mut text` erstellt eine exklusive veränderliche Ausleihe.

## 20.6 Die Lösung

Die Lesefunktion sollte eine Referenz annehmen:

```rust
fn laenge(text: &String) -> usize {
    text.len()
}

fn main() {
    let name = String::from("Ferris");
    let anzahl = laenge(&name);
    println!("Der Name hat {anzahl} Zeichen.");
    println!("Der Name lautet: {name}");
}
```

Zeile-für-Zeile:

| Zeile | Erklärung |
|---|---|
| `fn laenge(text: &String)` | Die Funktion leiht den `String` nur aus. |
| `text.len()` | Rust dereferenziert automatisch passend für den Methodenaufruf. |
| `laenge(&name)` | Es entsteht eine unveränderliche Referenz auf `name`. |
| `println!(..., {name})` | `name` besitzt die Daten weiterhin und bleibt gültig. |

Noch idiomatischer ist `&str`, weil damit sowohl `String` als auch String-Literale funktionieren:

```rust
fn laenge(text: &str) -> usize {
    text.len()
}

fn main() {
    let name = String::from("Ferris");
    let literal = "Rust";

    println!("{} Zeichen", laenge(&name));
    println!("{} Zeichen", laenge(literal));
}
```

Eine veränderliche Lösung:

```rust
fn haenge_ausrufezeichen_an(text: &mut String) {
    text.push('!');
}

fn main() {
    let mut sprache = String::from("Rust");
    haenge_ausrufezeichen_an(&mut sprache);
    println!("{sprache}");
}
```

EVA-Analyse:

| Phase | Beschreibung |
|---|---|
| Eingabe | `&mut String` ist eine exklusive Leihe auf einen mutablen Besitzer. |
| Verarbeitung | `push` kann den Heap-Puffer verändern oder vergrößern. |
| Ausgabe | Es wird kein Wert zurückgegeben; der Seiteneffekt ist die Mutation von `sprache`. |

## 20.7 Kleines Tutorial: Textstatistik ohne Ownership-Verlust

Ziel: Sie schreiben ein kleines Programm, das einen Text liest, analysiert und erweitert, ohne unnötige Moves zu erzeugen.

### Schritt 1: Reine Lesefunktion planen

Pseudocode:

```text
FUNKTION zaehle_woerter(text):
    teile text an Leerraum
    zaehle die Teile
    gib die Anzahl zurueck
```

Rust-Code:

```rust
fn zaehle_woerter(text: &str) -> usize {
    text.split_whitespace().count()
}

fn main() {
    let notiz = String::from("Rust prueft Referenzen statisch");
    let anzahl = zaehle_woerter(&notiz);
    println!("Woerter: {anzahl}");
    println!("Original: {notiz}");
}
```

Analyse:

- `&str` bindet die Funktion nicht an `String`.
- `split_whitespace()` erzeugt Iteratorwerte, die den Text nur ausleihen.
- `count()` verbraucht den Iterator, nicht den ursprünglichen `String`.

### Schritt 2: Mutation in eigener Phase

```rust
fn markiere_erledigt(text: &mut String) {
    text.push_str(" [ok]");
}

fn main() {
    let mut notiz = String::from("Borrowing ueben");
    let vorher = zaehle_woerter(&notiz);
    markiere_erledigt(&mut notiz);
    let nachher = zaehle_woerter(&notiz);

    println!("Vorher: {vorher}, nachher: {nachher}");
    println!("{notiz}");
}

fn zaehle_woerter(text: &str) -> usize {
    text.split_whitespace().count()
}
```

Die Leseausleihe endet nach der letzten Verwendung von `vorher`. Danach darf `notiz` veränderlich ausgeliehen werden.

### Schritt 3: Scopes bewusst einsetzen

```rust
fn main() {
    let mut text = String::from("Plan");

    {
        let leser = &text;
        println!("Aktueller Text: {leser}");
    }

    let schreiber = &mut text;
    schreiber.push_str(" fertig");

    println!("{text}");
}
```

Der innere Block beendet die Lebensdauer von `leser` sichtbar. Moderne Non-Lexical Lifetimes erkennen oft auch ohne Block das Ende, aber explizite Scopes sind für Anfänger hilfreich.

## 20.8 Mentale Modelle & Deep Dive

### Die Leihbibliothek als Analogie

Ein Besitzer besitzt das Buch. Eine unveränderliche Referenz ist ein Leserausweis: Viele Personen dürfen gleichzeitig lesen, aber niemand darf Seiten ändern. Eine veränderliche Referenz ist die Werkstattfreigabe: Genau eine Person darf Änderungen eintragen, während niemand sonst das Buch nutzt.

### Speicherlayout eines `String`

```text
Stack                                      Heap
+----------------------------+            +------------------+
| name.ptr  ------------------------------> Ferris           |
| name.len  = 6              |            +------------------+
| name.cap  = 6              |
+----------------------------+

&name:
+----------------------------+
| ref.ptr ---------------------> Stack-Adresse von name
+----------------------------+
```

In der Praxis optimiert der Compiler viele Details. Das mentale Modell bleibt: Der Owner verwaltet die Freigabe, Referenzen leihen nur Zugriff.

### Regeln in Kurzform

| Situation | Erlaubt? | Grund |
|---|---:|---|
| Mehrere `&T` | Ja | Nur Lesen, keine Mutation. |
| Eine `&mut T` | Ja | Exklusiver Zugriff. |
| `&T` und `&mut T` gleichzeitig | Nein | Leser könnten inkonsistente Daten beobachten. |
| Zwei `&mut T` auf denselben Wert | Nein | Zwei Schreibende verletzen Exklusivität. |
| Move während Borrow aktiv | Nein | Referenz könnte auf ungültige Daten zeigen. |

### Reborrowing

Rust kann aus einer veränderlichen Referenz kurzfristig eine kürzere Leihe bilden:

```rust
fn drucke(text: &String) {
    println!("{text}");
}

fn main() {
    let mut wert = String::from("reborrow");
    let mut_ref = &mut wert;
    drucke(mut_ref);
    mut_ref.push_str(" ok");
    println!("{mut_ref}");
}
```

Während `drucke(mut_ref)` wird `mut_ref` kurz als unveränderliche Referenz reborrowed. Danach darf die ursprüngliche veränderliche Referenz weiter genutzt werden.

## 20.9 Drei praktische Übungen

### Übung 1: Leicht - Lesefunktion schreiben

Schreiben Sie eine Funktion:

```rust
fn beginnt_mit_rust(text: &str) -> bool
```

Anforderungen:

- `"Rust ist schnell"` ergibt `true`.
- `"Ich lerne Rust"` ergibt `false`.
- Der Eingabetext darf nicht übernommen werden.

Lösungshinweis: Nutzen Sie die Methode `starts_with`.

### Übung 2: Mittel - Mutation begrenzen

Schreiben Sie:

```rust
fn normalisiere_name(name: &mut String)
```

Anforderungen:

- Entfernen Sie führende und abschließende Leerzeichen.
- Wandeln Sie den Namen in Kleinbuchstaben um.
- Speichern Sie das Ergebnis wieder in `name`.

Lösungshinweis: Erzeugen Sie zuerst einen neuen `String` aus `trim().to_lowercase()` und weisen Sie ihn danach mit `*name = ...` zu.

### Übung 3: Schwer - Borrow-Konflikt auflösen

Startcode:

```rust
fn main() {
    let mut daten = String::from("alpha beta");
    let erstes = daten.split_whitespace().next().unwrap();
    daten.push_str(" gamma");
    println!("{erstes}");
}
```

Aufgabe:

- Erklären Sie, warum der Code nicht kompiliert.
- Ändern Sie den Code so, dass zuerst das erste Wort ausgegeben und danach der String erweitert wird.
- Ändern Sie ihn anschließend so, dass `erstes` als eigener `String` unabhängig vom Original weiterlebt.

Lösungshinweis: Variante 1 nutzt Reihenfolge. Variante 2 nutzt `to_string()`.

## 20.10 Lernstrategie, Selbsteinschätzung & Merkzettel

### Cheat Sheet

| Ziel | Syntax |
|---|---|
| Unveränderlich ausleihen | `let r = &wert;` |
| Veränderlich ausleihen | `let r = &mut wert;` |
| Funktion liest Text | `fn f(text: &str)` |
| Funktion verändert String | `fn f(text: &mut String)` |
| Dereferenzieren | `*referenz` |
| Scope begrenzen | `{ let r = &wert; println!("{r}"); }` |

## 20.11 Zusammenfassung

- Referenzen erlauben Zugriff ohne Ownership-Transfer.
- `&T` steht für beliebig viele gleichzeitige Leser.
- `&mut T` steht für genau einen exklusiven Schreiber.
- Der Borrow Checker verhindert Use-after-free, Iterator-Invalidierung und Data Races bereits zur Compilezeit.
- Gute Rust-APIs nehmen so wenig Besitz wie möglich und so viel Besitz wie nötig.
- Scopes, Reihenfolge und kleinere Funktionen sind die wichtigsten Werkzeuge gegen Borrowing-Konflikte.
