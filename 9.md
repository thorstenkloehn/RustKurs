## 2. Die Definition

Um eine präzise Grundlage für die anschließende Syntaxgegenüberstellung und Speicheranalyse zu schaffen, etablieren wir zunächst die formalen Fachbegriffe:

* **Variable**: Eine benannte Speicherbindung (Binding) auf dem Stack. Standardmäßig sind Variablen in Rust unveränderlich (*immutable*). Die Mutabilität (*Veränderbarkeit*) muss explizit mit dem Schlüsselwort `mut` angefordert werden.
* **Konstante (`const`)**: Ein unveränderlicher Wert, der zur Kompilierzeit ausgewertet wird. Konstanten besitzen keinen festen Speicherort zur Laufzeit; ihr Wert wird an jeder Verwendungsstelle direkt in den Maschinencode einbetoniert (Inlining). Die Typ annotation ist zwingend erforderlich.
* **Shadowing (Überschattung)**: Die Deklaration einer neuen Variablen mit demselben Namen wie eine bereits existierende Variable im selben oder einem übergeordneten Scope. Dies ermöglicht eine Änderung des Datentyps und der Mutabilität, ohne einen neuen Bezeichner einführen zu müssen.
* **Skalarer Datentyp**: Ein primitiver Typ, der einen einzelnen, atomaren Wert repräsentiert. Dazu gehören Ganzzahlen (Integers), Fließkommazahlen (Floats), Booleans (`bool`) und Unicode-Zeichen (`char`).
* **Zusammengesetzter Datentyp (Compound Type)**: Ein Typ, der mehrere Werte in einer einzigen Struktur zusammenfasst.
  * **Array (`[T; N]`)**: Eine homogene Sammlung von Elementen des gleichen Typs `T` mit einer festen, zur Kompilierzeit bekannten Länge `N`. Das Array liegt flach und zusammenhängend auf dem Stack.
  * **Tupel (`(T1, T2, ...)`)**: Eine heterogene Sammlung von Elementen, die unterschiedliche Typen besitzen können. Die Länge ist fest. Die Elemente werden über ihre Position indiziert.
* **Unit-Typ (`()`)**: Ein spezielles Tupel ohne Elemente. Es repräsentiert das Fehlen eines Wertes (vergleichbar mit `void` in anderen Sprachen) und belegt physisch 0 Bytes im Speicher.

### Alltagsnahe Metapher

> [!NOTE]
> * **Der Pillen-Organizer (Array)**: Ein Array ist wie ein wöchentlicher Pillen-Organizer. Jedes Fach hat exakt dieselbe Größe, is fortlaufend nummeriert (Index 0 bis 6) und darf nur denselben Inhalt aufnehmen (z. B. Vitamintabletten). Sie können nicht spontan ein achtes Fach anbauen.
> * **Das Schweizer Taschenmesser (Tupel)**: Ein Tupel ist wie ein Schweizer Taschenmesser. Es enthält verschiedene Werkzeuge (eine Schere, eine Klinge, eine Feile). Jedes Werkzeug hat eine andere Form, Größe und Funktion (heterogene Typen). Die Zusammensetzung ist fest definiert und kann nicht im Nachhinein verändert werden.
> * **Der leere Briefumschlag (Unit-Typ `()`)**: Der Unit-Typ ist wie ein leerer Briefumschlag. Er ist da, um als Umschlag (Typ) zu existieren, enthält aber keine Nachricht (Daten). Er benötigt keinen physischen Platz, transportiert aber die Information: „Ich bin erfolgreich angekommen, aber ich bringe keine Daten mit.“

## 9.1 Syntaktisches Cheat-Sheet

Dieses Cheat-Sheet dient als schnelles Nachschlagewerk für den direkten Vergleich der verschiedenen Variablentypen und Datenstrukturen.

### 9.1.1 Gegenüberstellung

Die folgende Tabelle vergleicht die wichtigsten Eigenschaften der skalaren und zusammengesetzten Datentypen in Rust:

| Kriterium | Skalare Typen (`i32`, `f64`, `bool`, `char`) | Arrays (`[T; N]`) | Tupel (`(T1, T2, ...)`) |
| :--- | :--- | :--- | :--- |
| **Typ-Homogenität** | Ein einzelner Basistyp | Streng homogen (nur Elemente vom Typ `T`) | Heterogen (unterschiedliche Typen erlaubt) |
| **Größe zur Laufzeit** | Fest (1 bis 16 Bytes) | Fest (Anzahl $N \times$ Elementgröße) | Fest (Summe der Elementgrößen + Padding) |
| **Speicherort** | Stack (bzw. CPU-Register) | Stack (kontinuierlich) | Stack (kontinuierlich mit Lücken) |
| **Indexierungs-Syntax** | Nicht anwendbar | `array[index]` (Laufzeit-Bounds-Check) | `tupel.0`, `tupel.1` (Compilezeit-statisch) |
| **Zuweisungs-Semantik** | Immer `Copy` (Bit-Kopie auf dem Stack) | `Copy` nur, wenn Typ `T` den `Copy`-Trait besitzt | `Copy` nur, wenn alle Teil-Typen `Copy` sind |
| **Häufiger Einsatzzweck** | Mathematische Berechnungen, Flags | Puffer feste Größe, mathematische Vektoren | Rückgabe mehrerer Werte aus Funktionen |

### Syntaktischer Codevergleich

Der folgende Code zeigt die Deklaration, Initialisierung, Modifikation und das Entpacken der Typen im direkten Vergleich:

```rust
fn main() {
    // ==========================================
    // 1. Skalare Typen
    // ==========================================
    let integer_val: i32 = -42;
    let float_val: f64 = 3.14159;
    let boolean_val: bool = true;
    let character_val: char = '🦀'; // 4 Bytes Unicode

    // ==========================================
    // 2. Arrays (Homogen, feste Länge)
    // ==========================================
    // Deklaration mit Typ und Größe: [Typ; Größe]
    let mut temperatures: [f32; 3] = [18.5, 21.0, 19.2];
    
    // Kurzschreibweise für Initialisierung mit Standardwerten: [Wert; Größe]
    let byte_buffer: [u8; 1024] = [0; 1024]; // 1024 mal die 0

    // Elementzugriff über eckige Klammern
    temperatures[0] = 19.0; 
    let first_temp = temperatures[0];

    // ==========================================
    // 3. Tupel (Heterogen, feste Länge)
    // ==========================================
    // Deklaration mit expliziten Typen: (Typ1, Typ2, ...)
    let mut user_profile: (u32, String, bool) = (1001, String::from("Alice"), true);

    // Elementzugriff über die Punkt-Notation
    user_profile.0 = 1002; // ID ändern
    let username = &user_profile.1;

    // Destrukturierung (Entpacken) eines Tupels
    let (id, name, active) = &user_profile;
}
```

## 3. Das Problem & Die Motivation

In der hardwarenahen Systemprogrammierung ist der effiziente und korrekte Umgang mit dem Speicher von existenzieller Bedeutung. Werden Variablen und Datentypen unüberlegt eingesetzt, entstehen fundamentale Probleme:

1. **Speicherverschwendung & Cache-Misses**: CPUs lesen Daten nicht byteweise aus dem RAM, sondern in größeren Blöcken (Cache-Lines, meist 64 Bytes). Liegen Daten verstreut im Speicher oder sind sie unnötig groß, führt dies zu ständigen Cache-Misses. Die CPU muss auf den langsamen Hauptspeicher warten.
2. **Datenkorruption durch Integer-Overflows**: In sicherheitskritischen Bereichen (z. B. Flugsteuerungen oder Krypto grafie) kann ein einfacher Überlauf einer Zahl katastrophale Folgen haben. Wenn ein vorzeichenloser 8-Bit-Integer (`u8`) den Wert 255 erreicht und um 1 erhöht wird, fällt er im Release-Modus unbemerkt auf 0 zurück (*Wrapping*). Dies kann Schleifenbedingungen aushebeln oder falsche Sensorwerte simulieren.
3. **Laufzeitabstürze durch mangelnde Typen trennung**: Versucht ein Programmierer, heterogene Daten (wie Temperatur, Fehlermeldung und Sensor-ID) in ein einziges homogenes Array zu pressen, scheitert er entweder an den Typgrenzen des Compilers oder erzwingt unsichere Typkonvertierungen (`as`-Casts), die die Typ sicherheit aushebeln.

Rust zwingt Entwickler durch sein strenges Typsystem und die Compilezeit-Garantien, diese Aspekte bereits beim Entwurf der Software zu berücksichtigen.

## 4. Der naive Versuch

Im folgenden Code versucht ein Programmierer, ein einfaches Telemetriesystem zu schreiben. Er begeht dabei drei typische Anfängerfehler:
1. Er versucht, heterogene Sensordaten in ein homogenes Array zu zwingen.
2. Er verwendet für die Berechnung eines Offsets einen vorzeichenbehafteten 8-Bit-Integer (`i8`), wodurch ein unkontrollierter Überlauf provoziert wird.
3. Er greift über einen dynamisch berechneten Index ungesichert auf ein Array zu.

```rust
// Dieser Code lässt sich teilweise nicht kompilieren und stürzt zur Laufzeit ab!
fn main() {
    // FEHLER 1: Versuch, heterogene Daten in ein homogenes Array zu zwingen
    // Ein Sensor hat: ID (u8), Temperatur (f32), Status-Flag (bool)
    // Der Compiler wird diese Zuweisung verweigern!
    // let raw_sensor_data = [42, 23.5, true]; 

    // Wir weichen auf getrennte Variablen aus, um fortzufahren:
    let sensor_id: u8 = 42;
    let mut temperature: i8 = 120; // Maximale Betriebstemperatur nahe i8::MAX (127)
    let status_active: bool = true;

    // FEHLER 2: Unkontrollierter Integer-Overflow
    // Ein Kalibrierungs-Offset soll addiert werden
    let calibration_offset: i8 = 10;
    
    // Unter Debug-Bedingungen stürzt das Programm hier mit einer Panik ab!
    temperature = temperature + calibration_offset; 
    println!("Kalibrierte Temperatur: {}", temperature);

    // FEHLER 3: Ungesicherter Indexzugriff auf ein Array
    let readings = [15, 18, 20, 22, 19];
    
    // Der Index wird dynamisch berechnet (z. B. durch Sensoreingabe)
    let target_index = readings.len() + 1; 
    
    // Dieser Zugriff provoziert eine Laufzeit-Panik (Bounds Check Failure)
    let critical_reading = readings[target_index]; 
    println!("Kritischer Messwert: {}", critical_reading);
}
```

## 5. Die Anatomie des Fehlers

### 1. Compiler-Fehler bei der Array-Deklaration
Wenn Sie versuchen, die Zeile `let raw_sensor_data = [42, 23.5, true];` einzukommentieren, bricht der Compiler sofort mit folgendem Fehler ab:

```text
error[E0308]: mismatched types
 --> src/main.rs:5:32
  |
5 |     let raw_sensor_data = [42, 23.5, true];
  |                                ^^^^ expected integer, found float
  |
help: change the type of the numeric literal or remove the incompatible elements
```

**Ursache**: Ein Rust-Array vom Typ `[T; N]` erfordert absolute Homogenität. Der Compiler leitet aus dem ersten Element `42` ab, dass es sich um ein Array aus Integers handelt. Das zweite Element `23.5` (ein Float) bricht diese Regel fundamental.

---

### 2. Laufzeit-Absturz durch Integer-Overflow (Debug-Modus)
Wird der Array-Fehler behoben, übersetzt der Compiler das Programm im Debug-Profil problemlos. Beim Ausführen stürzt die Applikation jedoch bei der Addition ab:

```text
thread 'main' panicked at src/main.rs:17:19:
attempt to add with overflow
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
```

**Was im Speicher passiert**: 
Ein `i8` belegt genau 1 Byte (8 Bits) auf dem Stack. Der Wertebereich reicht von $-128$ bis $+127$. 
* Die Binärdarstellung für `120` ist `0111_1000`.
* Die Binärdarstellung für `10` ist `0000_1010`.
* Bei der Addition im CPU-Register entsteht der Wert `1000_0010`.
* Da das MSB (Most Significant Bit, das vorderste Bit) bei vorzeichenbehafteten Integers als Vorzeichen-Flag fungiert (`1` steht für negativ, kodiert im Zweierkomplement), wird dieser Wert als $-126$ interpretiert.
* Da Rust im **Debug-Modus** standardmäßig auf Überläufe prüft, erkennt es diese mathematische Inkonsistenz und löst eine kontrollierte Panik aus, um zu verhindern, dass die Logik mit korrupten Daten arbeitet.
* Im **Release-Modus** (`--release`) würde Rust diesen Check aus Performancegründen weglassen. Die Variable `temperature` würde lautlos auf `-126` umspringen (*Wrapping*). Ihr Sensor würde plötzlich frostige Temperaturen statt extremer Hitze melden – ein katastrophaler Logikfehler!

---

### 3. Laufzeit-Absturz durch Out-of-Bounds-Zugriff
Falls der Overflow umgangen wird, stürzt das Programm beim Zugriff `readings[target_index]` ab:

```text
thread 'main' panicked at src/main.rs:25:28:
index out of bounds: the len is 5 but the index is 6
```

**Was im Speicher passiert**:
Das Array `readings` liegt als kompakter Block von 5 Integers (`5 * 4 Bytes = 20 Bytes`) auf dem Stack. Ein Zugriff auf Index 6 würde bedeuten, dass das Programm die Startadresse des Arrays nimmt, um 24 Bytes nach vorne springt und dort liegenden Speicher liest. Dieser Speicher gehört jedoch zu anderen Variablen. Um Speicherverletzungen (wie Buffer Overflows, die in C/C++ als Sicherheitslücken ausgenutzt werden) unmöglich zu machen, führt Rust bei jedem Indexzugriff einen impliziten Grenzwert-Check durch (*Bounds Checking*) und stürzt lieber ab, als unautorisierten Speicher freizugeben.

## 6. Die Lösung

Um diese Schwachstellen sauber zu beseitigen, wenden wir folgende Techniken an:
1. **Tupel** für die Speicherung heterogener Datensätze.
2. **Sichere Arithmetik-Methoden** der Standardbibliothek zur Kontrolle von Überläufen.
3. **Sicherer Array-Zugriff** mittels der `.get()`-Methode, die ein `Option`-Objekt zurückgibt.

Hier ist die fehlerfreie Implementierung nach dem **EVA-Prinzip**:

```rust
fn main() {
    // =========================================================================
    // EINGABE (Input): Definition der Sensor-ID, des Rohwerts und des Offsets
    // =========================================================================
    let sensor_id: u8 = 42;
    let raw_temp: i8 = 120;
    let calibration_offset: i8 = 10;
    
    // Ein Tupel fasst die heterogenen Daten strukturiert zusammen
    let sensor_meta: (u8, bool) = (sensor_id, true);

    // =========================================================================
    // VERARBEITUNG (Processing): Sichere Addition und sicherer Array-Zugriff
    // =========================================================================
    
    // Option A: Sättigende Addition (Saturating) -> Bleibt am Maximum (127) kleben
    let calibrated_temp_saturating = raw_temp.saturating_add(calibration_offset);

    // Option B: Kontrollierter Überlauf (Checked) -> Gibt None zurück, wenn es überläuft
    let calibrated_temp_checked = match raw_temp.checked_add(calibration_offset) {
        Some(val) => val,
        None => {
            eprintln!("Warnung: Sensor-Temperaturüberlauf erkannt! Verwende Maximalwert.");
            i8::MAX // Ausfall-Sicherheitswert
        }
    };

    // Sicherer Zugriff auf das Messwert-Array
    let readings = [15, 18, 20, 22, 19];
    let target_index = 6; // Ungültiger Index

    // .get() gibt im Fehlerfall None zurück, anstatt abzustürzen
    let safe_reading = match readings.get(target_index) {
        Some(value) => *value,
        None => {
            eprintln!("Fehler: Index {} außerhalb des gültigen Bereichs!", target_index);
            -1 // Standard-Fehlercode
        }
    };

    // =========================================================================
    // AUSGABE (Output): Ausgabe der berechneten Werte auf der Konsole
    // =========================================================================
    println!("Sensor ID: {}, Aktiv: {}", sensor_meta.0, sensor_meta.1);
    println!("Saturating Temp: {} °C (Erwartet: 127)", calibrated_temp_saturating);
    println!("Checked Temp: {} °C (Erwartet: 127)", calibrated_temp_checked);
    println!("Sicherer Messwert: {}", safe_reading);
}
```

### Zeile-für-Zeile-Erklärung nach dem EVA-Prinzip

* **Eingabe (Input)**:
  * Wir deklarieren die Rohdaten (`sensor_id`, `raw_temp`, `calibration_offset`) auf dem Stack.
  * Wir erstellen das Tupel `sensor_meta`. Da dieses unterschiedliche Typen (`u8` und `bool`) aufnehmen kann, akzeptiert der Compiler die Definition anstandslos.
* **Verarbeitung (Processing)**:
  * Anstelle des mathematischen Operators `+` nutzen wir `saturating_add`. Wenn die Summe $120 + 10 = 130$ die Grenze von $127$ überschreitet, rundet Rust das Ergebnis nicht ab, sondern hält es exakt auf dem maximalen Grenzwert (`i8::MAX`, also $127$).
  * Alternativ verwenden wir `checked_add`. Diese Methode gibt ein `Option<i8>` zurück. Bei einem Überlauf ist das Ergebnis `None`. Über ein `match`-Konstrukt fangen wir diesen Fall explizit ab und setzen die Temperatur kontrolliert auf `i8::MAX`. Das Programm läuft stabil weiter.
  * Beim Array-Zugriff rufen wir `readings.get(target_index)` auf. Da der Index 6 außerhalb des Bereichs liegt, stürzt das System nicht ab. Es gibt `None` zurück, was wir im `match`-Block sicher behandeln.
* **Ausgabe (Output)**:
  * Die Ergebnisse werden formatiert ausgegeben. Es kommt zu keinerlei unkontrollierten Laufzeitabstürzen.

## 7. Kleines Tutorial: GPS- und Telemetrie-Decoder

In diesem Tutorial entwickeln wir einen einfachen Decoder für serielle GPS-Datensätze. Die eingehenden Daten bestehen aus einer festen Byte-Sequenz (Array) und sollen in strukturierte Geokoordinaten (Tupel aus Breitengrad, Längengrad und Satelliten anzahl) übersetzt werden. Dabei nutzen wir Shadowing und Konstanten zur Strukturierung.

### Schritt 1: Das Projekt anlegen
Erstellen Sie ein neues Cargo-Projekt auf Ihrem System (Sie können dies in Ihrem Terminal ausführen, nicht im Code block):
```bash
cargo new telemetry_decoder --bin
```

### Schritt 2: Konstanten und Datenstrukturen definieren
Öffnen Sie die Datei `src/main.rs` und definieren Sie die grundlegenden Systemparameter als Konstanten:

```rust
// Die erwartete Paketgröße in Bytes
const RAW_PACKET_SIZE: usize = 8;
// Der Skalierungsfaktor zur Umwandlung von Rohwerten in echte GPS-Koordinaten
const COORDINATE_SCALE: f64 = 10_000.0;
```

### Schritt 3: Die Dekodierungs-Logik implementieren
Wir schreiben eine Funktion `decode_gps_packet`, die ein rohes Byte-Array entgegennimmt und ein strukturiertes Tupel zurückgibt. Wir nutzen hierbei Bit-Shifting, um einzelne Bytes zu größeren Integers zusammenzusetzen:

```rust
// Dekodiert ein 8-Byte-Paket in (Latitude, Longitude, Satellites, Valid)
fn decode_gps_packet(packet: [u8; RAW_PACKET_SIZE]) -> (f64, f64, u8, bool) {
    // Byte 0-2: Breitengrad (Latitude) als u24 (simuliert über u32)
    let raw_lat = ((packet[0] as u32) << 16) | ((packet[1] as u32) << 8) | (packet[2] as u32);
    
    // Byte 3-5: Längengrad (Longitude) als u24
    let raw_lon = ((packet[3] as u32) << 16) | ((packet[4] as u32) << 8) | (packet[5] as u32);

    // Byte 6: Anzahl der Satelliten
    let satellites = packet[6];

    // Byte 7: Status-Flag (0 = ungültig, 1 = gültig)
    let is_valid = packet[7] == 1;

    // Umrechnung in Fließkommagrad unter Verwendung unserer Konstante
    let latitude = (raw_lat as f64) / COORDINATE_SCALE;
    let longitude = (raw_lon as f64) / COORDINATE_SCALE;

    (latitude, longitude, satellites, is_valid)
}
```

### Schritt 4: Die Integration in der `main`-Funktion
Jetzt fügen wir Testdaten ein und verarbeiten diese. Wir nutzen Shadowing, um die dekodierten Rohdaten für die Ausgabe aufzubereiten:

```rust
fn main() {
    // Ein simuliertes GPS-Rohdatenpaket
    // Latitude-Bytes: [0x07, 0xA1, 0x20] -> 500000 -> 50.0000°
    // Longitude-Bytes: [0x01, 0x86, 0xA0] -> 100000 -> 10.0000°
    // Satelliten: 9
    // Status: 1 (Gültig)
    let raw_data: [u8; RAW_PACKET_SIZE] = [0x07, 0xA1, 0x20, 0x01, 0x86, 0xA0, 9, 1];

    println!("Starte Dekodierung des Telemetriepakets...");

    // Aufruf des Decoders
    let decoded_gps = decode_gps_packet(raw_data);

    // Shadowing nutzen, um die Daten übersichtlich zu strukturieren und auszugeben
    let (lat, lon, sats, valid) = decoded_gps;

    if valid {
        println!("--- GPS-Signal erfasst ---");
        println!("Breitengrad: {:.4}° Nord", lat);
        println!("Längengrad:  {:.4}° Ost", lon);
        println!("Satelliten in Reichweite: {}", sats);
    } else {
        println!("--- Warnung: GPS-Signal ungültig! ---");
    }
}
```

## 8. Mentale Modelle & Deep Dive

Um die Speicherverwaltung von Rust-Typen wirklich zu durchdringen, müssen wir die Abstraktionsebene verlassen und uns ansehen, wie der Compiler die Daten im RAM anordnet.

### Heap vs. Stack bei Primitives
Im Gegensatz zu komplexen Typen wie `String` oder `Vec<T>`, die dynamisch wachsen und Zeiger auf den Heap besitzen, sind skalare Typen, Arrays und Tupel **reine Stack-Typen**.
* Sie besitzen keine Pointer auf den Heap.
* Sie implementieren alle implizit den `Copy`-Trait (sofern bei Arrays und Tupeln deren Elementtypen dies ebenfalls tun).
* Wenn Sie ein Array einer neuen Variablen zuweisen, kopiert Rust den gesamten Speicherblock auf den Stack. Es gibt keinen Move-Zwang, da kein Heap-Speicher doppelt freigegeben werden könnte.

```
Zuweisung eines Arrays (Copy-Semantik):
Stack (Variable a)       Stack (Variable b)
┌───┬───┬───┐            ┌───┬───┬───┐
│ 1 │ 2 │ 3 │   ====>    │ 1 │ 2 │ 3 │
└───┴───┴───┘            └───┴───┴───┘
(a bleibt voll einsatzfähig!)
```

### Thread-Safety: Die Auto-Traits `Send` und `Sync`
Im Systembereich ist Multithreading allgegenwärtig. Rust garantiert Thread-Safety durch zwei Compiler-eingebaute Traits, die automatisch vergeben werden (Auto-Traits):
* **`Send`**: Zeigt an, dass ein Typ sicher an einen anderen Thread übertragen werden darf.
* **`Sync`**: Zeigt an, dass mehrere Threads gleichzeitig über Referenzen auf denselben Wert zugreifen dürfen (`&T` is `Send`).

Da alle hier behandelten skalaren Typen, Arrays und Tupel reine Speicherbereiche ohne geteilte Zeiger oder veränderliche globale Zustände sind, sind sie **vollständig `Send` und `Sync`**. Sie können diese Daten bedenkenlos zwischen Threads teilen oder verschieben, solange die Standard-Borrowing-Regeln eingehalten werden.

## 9.2 Physischer Speicherbedarf

### 9.2.1 Datengrößen

Der physische Speicherbedarf eines Datentyps hängt maßgeblich von der Bitbreite der Zielplattform (32-Bit- vs. 64-Bit-CPU) ab. Die folgende Tabelle schlüsselt die exakten Bytegrößen auf:

| Datentyp | Größe auf 32-Bit CPUs | Größe auf 64-Bit CPUs | Alignment (64-Bit) |
| :--- | :--- | :--- | :--- |
| `i8` / `u8` / `bool` | 1 Byte | 1 Byte | 1 Byte |
| `i16` / `u16` | 2 Bytes | 2 Bytes | 2 Bytes |
| `i32` / `u32` / `f32` | 4 Bytes | 4 Bytes | 4 Bytes |
| `i64` / `u64` / `f64` | 8 Bytes | 8 Bytes | 8 Bytes |
| `i128` / `u128` | 16 Bytes | 16 Bytes | 8 oder 16 Bytes (OS-abhängig) |
| `char` | 4 Bytes | 4 Bytes | 4 Bytes |
| `isize` / `usize` | **4 Bytes** | **8 Bytes** | **8 Bytes** |
| `[T; N]` (Array) | $N \times \text{Größe}(T)$ | $N \times \text{Größe}(T)$ | Entspricht Alignment von $T$ |
| `(T1, T2, ...)` (Tupel) | Summe der Typen + Padding | Summe der Typen + Padding | Größtes Alignment der Teil-Typen |

---

### Deep Dive: Speicher-Alignment und Padding

Warum ist die Größe eines Tupels wie `(u8, u32)` nicht einfach 5 Bytes ($1 + 4$), sondern 8 Bytes? Die Antwort liegt im **Speicher-Alignment** (Speicherausrichtung).

CPUs lesen Daten nicht byteweise, sondern in Speicherworten (z. B. 4 Bytes auf 32-Bit-Systemen oder 8 Bytes auf 64-Bit-Systemen). Wenn ein 4-Byte-Integer (`u32`) an einer Speicheradresse liegt, die nicht durch 4 teilbar ist (z. B. `0x03`), muss die CPU zwei Lesezugriffe durchführen und die Bits verschieben. Das kostet Performance. Manche Architekturen (wie ARM) stürzen bei unaligned Zugriffen sogar ab.

Aus diesem Grund erzwingt der Rust-Compiler zwei Regeln:
1. **Alignment**: Jeder Typ hat eine Ausrichtungsanforderung. Ein Typ mit Alignment $A$ darf nur an einer Speicheradresse abgelegt werden, die ein Vielfaches von $A$ ist.
2. **Padding**: Um das Alignment zu garantieren, fügt der Compiler ungenutzte Füll-Bytes (*Padding*) ein.

#### Visualisierung des Layouts eines Tupels `(u8, u32)`:

Da `u32` ein Alignment von 4 Bytes benötigt, kann es im Speicher nicht direkt nach dem 1-Byte `u8` liegen. Der Compiler fügt 3 Padding-Bytes ein:

```
Adresse: 0x00      0x01      0x02      0x03      0x04   0x05   0x06   0x07
Wert:    [ u8 ]    [  PADDING-BYTE (x3)  ]       [       u32-Wert      ]
         └────┬───┘└──────────┬──────────┘       └──────────┬──────────┘
           1 Byte          3 Bytes                     4 Bytes
```

#### Wichtige Regel für Tupel:
Im Gegensatz zu Structs, bei denen der Rust-Compiler die Reihenfolge der Felder im Speicher frei optimieren darf (`repr(Rust)`), **behalten Tupel ihre definierte Reihenfolge im Speicher strikt bei**. 

Betrachten wir das Tupel `(u8, u32, u8)`:
* `u8` (1 Byte) an Adresse 0
* 3 Bytes Padding, um das Alignment von `u32` (Adresse 4) zu erfüllen
* `u32` (4 Bytes) belegt Adressen 4 bis 7
* `u8` (1 Byte) an Adresse 8
* Da die Gesamtgröße eines zusammengesetzten Typs immer ein Vielfaches seines maximalen Alignments (hier 4 Bytes) sein muss, werden am Ende weitere 3 Bytes Padding angehängt.
* **Gesamtgröße**: 12 Bytes (obwohl nur 6 Bytes echte Nutzdaten enthalten sind!).

## Exhaustive API-Reference

Um die Vorgaben für ein professionelles Lehrbuch zu erfüllen, dokumentieren wir an dieser Stelle die wichtigsten in der Standardbibliothek implementierten Methoden für unsere Kern-Typen lückenlos.

### 1. Integer-Methoden (`i32` / `u32` / `i8` etc.)

#### `checked_add`
* **Signatur**: `pub fn checked_add(self, rhs: Self) -> Option<Self>`
* **Parameter**: `rhs` (Right-Hand Side): Der zu addierende Wert des gleichen Typs.
* **Rückgabetyp**: `Option<Self>`: `Some(Ergebnis)` bei erfolgreicher Addition, `None` bei Überlauf.
* **Panics**: Keine.
* **Beispiel**:
  ```rust
  let x: u8 = 250;
  assert_eq!(x.checked_add(10), None);
  assert_eq!(x.checked_add(5), Some(255));
  ```

#### `saturating_add`
* **Signatur**: `pub fn saturating_add(self, rhs: Self) -> Self`
* **Parameter**: `rhs`: Der zu addierende Wert.
* **Rückgabetyp**: `Self`: Die Summe, gedeckelt auf das jeweilige Limit des Typs (`MAX` oder `MIN`).
* **Panics**: Keine.
* **Beispiel**:
  ```rust
  let x: u8 = 250;
  assert_eq!(x.saturating_add(20), 255); // Bleibt bei u8::MAX stehen
  ```

#### `wrapping_add`
* **Signatur**: `pub fn wrapping_add(self, rhs: Self) -> Self`
* **Parameter**: `rhs`: Der zu addierende Wert.
* **Rückgabetyp**: `Self`: Die Summe modulo Wertebereichsgröße (Überlauf-Wrapping).
* **Panics**: Keine (auch nicht im Debug-Modus).
* **Beispiel**:
  ```rust
  let x: u8 = 255;
  assert_eq!(x.wrapping_add(1), 0);
  ```

#### `overflowing_add`
* **Signatur**: `pub fn overflowing_add(self, rhs: Self) -> (Self, bool)`
* **Parameter**: `rhs`: Der zu addierende Wert.
* **Rückgabetyp**: `(Self, bool)`: Ein Tupel bestehend aus dem (ggf. gewrappten) Wert und einem Boolean, der anzeigt, ob ein Überlauf stattgefunden hat (`true`).
* **Panics**: Keine.
* **Beispiel**:
  ```rust
  let x: u8 = 255;
  assert_eq!(x.overflowing_add(1), (0, true));
  ```

#### `abs`
* **Signatur**: `pub fn abs(self) -> Self`
* **Parameter**: Keine.
* **Rückgabetyp**: `Self`: Der absolute Wert (ohne Vorzeichen).
* **Panics**: Stürzt ab, wenn der Wert `MIN` ist (da der positive Gegenpart von `MIN` außerhalb des Wertebereichs liegt).
* **Beispiel**:
  ```rust
  let x: i32 = -5;
  assert_eq!(x.abs(), 5);
  ```

#### `pow`
* **Signatur**: `pub fn pow(self, exp: u32) -> Self`
* **Parameter**: `exp`: Der Exponent als `u32`.
* **Rückgabetyp**: `Self`: Die Basis hoch `exp`.
* **Panics**: Stürzt im Debug-Modus ab bei mathematischem Überlauf.
* **Beispiel**:
  ```rust
  let base: i32 = 2;
  assert_eq!(base.pow(8), 256);
  ```

#### `to_be_bytes`
* **Signatur**: `pub fn to_be_bytes(self) -> [u8; N]`
* **Parameter**: Keine.
* **Rückgabetyp**: Ein Byte-Array der Größe `N` (entsprechend der Typgröße in Bytes) im Big-Endian-Format (wichtig für Netzwerkprotokolle).
* **Panics**: Keine.
* **Beispiel**:
  ```rust
  let val: u32 = 0x12345678;
  assert_eq!(val.to_be_bytes(), [0x12, 0x34, 0x56, 0x78]);
  ```

#### `from_le_bytes`
* **Signatur**: `pub fn from_le_bytes(bytes: [u8; N]) -> Self`
* **Parameter**: `bytes`: Ein Byte-Array der Größe `N` im Little-Endian-Format.
* **Rückgabetyp**: `Self`: Der rekonstruierte Integer-Wert.
* **Panics**: Keine.
* **Beispiel**:
  ```rust
  let bytes = [0x78, 0x56, 0x34, 0x12];
  assert_eq!(u32::from_le_bytes(bytes), 0x12345678);
  ```

## 10. Lernstrategie, Selbsteinschätzung & Merkzettel

### Spickzettel / Merkzettel (Cheat Sheet)

Hier ist die wichtigste Syntax für die Deklaration und Initialisierung auf einen Blick:

```rust
// Skalare Variablen
let mut steps: u64 = 0;             // Standard-Integer auf Stack
let price: f64 = 99.99;             // Fließkommazahl IEEE-754

// Arrays (Homogen)
let numbers: [i32; 5] = [1, 2, 3, 4, 5];
let count = numbers.len();          // Länge ermitteln
let first = numbers[0];             // Elementzugriff (Achtung: Panic-Gefahr!)
let safe_item = numbers.get(10);    // Sicherer Zugriff (gibt Option<&i32> zurück)

// Tupel (Heterogen)
let record: (u32, f32, char) = (42, 36.6, '🤒');
let sensor_id = record.0;           // Direktzugriff über Punkt-Syntax
let (id, temp, symbol) = record;    // Destrukturierung
```

### Active Recall (Selbsttestfragen)
1. **Frage**: Warum kann man ein Array in Rust nicht dynamisch während der Laufzeit vergrößern?
   * *Antwort*: Da Arrays flach auf dem Stack liegen, muss der Compiler ihre genaue Größe zur Kompilierzeit kennen, um den Stackframe-Pointer korrekt zu verschieben. Dynamische Vergrößerung würde den Stackframe beschädigen.
2. **Frage**: Was passiert bei einem Integer-Overflow im `--release`-Build im Vergleich zum Debug-Build?
   * *Antwort*: Im Debug-Build stürzt das Programm mit einer Panik ab. Im Release-Build wird das Ergebnis lautlos gewrappt (Modulo-Arithmetik), was zu schwer zu findenden Logikfehlern führen kann.
3. **Frage**: Warum ist die Bytegröße von `usize` nicht auf allen Systemen identisch?
   * *Antwort*: `usize` repräsentiert die Breite des Adressbusses der CPU. Auf einer 32-Bit-CPU werden 4 Bytes zur Adressierung benötigt, auf einer 64-Bit-CPU hingegen 8 Bytes.
4. **Frage**: Wie unterscheidet sich das Speicher-Alignment bei einem Struct von dem eines Tupels?
   * *Antwort*: Der Rust-Compiler darf Felder eines Structs umsortieren (`repr(Rust)`), um Padding-Bytes zu minimieren. Bei Tupeln hingegen ist die Reihenfolge der Elemente im Speicher fest vorgegeben.
5. **Frage**: Wann implementieren Arrays den `Copy`-Trait?
   * *Antwort*: Ein Array implementiert den `Copy`-Trait genau dann, wenn der Typ seiner Elemente `T` ebenfalls `Copy` implementiert. Ein `[i32; 10]` ist `Copy`, ein `[String; 10]` hingegen nicht.

## 11. Zusammenfassung

* **Skalare vs. Zusammengesetzte Typen**: Skalare Typen (`i32`, `f64`, `bool`, `char`) speichern Einzelwerte. Arrays (`[T; N]`) speichern homogene Daten fester Länge. Tupel (`(T1, T2, ...)`) speichern heterogene Datensätze fester Länge.
* **Sichere Arithmetik**: Nutzen Sie bei kritischen Berechnungen immer die `checked_` oder `saturating_` Methoden der Standardbibliothek anstelle der Standard-Operatoren, um unkontrollierte Laufzeitabstürze oder lautlose Überläufe zu verhindern.
* **Speicher-Alignment**: CPUs greifen am effizientesten auf ausgerichtete Adressen zu. Rust fügt automatisch Padding-Bytes ein, um dieses Alignment zu erzwingen. Tupel behalten ihre Definitionsreihenfolge im Speicher bei, was zu ungenutztem Speicherplatz (Padding) führen kann.
* **Sicherer Zugriff**: Der direkte Array-Zugriff mit `[index]` ist crash-gefährdet. Nutzen Sie `.get(index)` für den sicheren Zugriff, um ein `Option`-Ergebnis zu erhalten.
