## 2. Die Definition

* **Slice-Typ (`str` bzw. `[T]`)**: Ein Slice ist ein dynamisch dimensionierter Typ (Dynamically Sized Type, DST), der eine kontinuierliche Sequenz von Elementen in einer Kollektion repräsentiert. Da die Größe eines Slices zur Kompilierzeit unbekannt ist, kann er nicht direkt in einer Variablen auf dem Stack abgelegt werden. Slices existieren daher in der Praxis fast ausschließlich hinter einer Referenz.
* **String-Slice (`&str`)**: Eine unveränderliche Referenz auf eine gültige UTF-8-codierte Zeichensequenz. Sie zeigt entweder auf einen Teilbereich eines auf dem Heap alloziierten `String`-Objekts oder direkt auf ein statisches String-Literal (`&'static str`), das im schreibgeschützten Datensegment der Binärdatei gespeichert ist.
* **Slice-Referenz (`&[T]`)**: Eine generische, unveränderliche Referenz auf eine zusammenhängende Sequenz von Elementen des Typs `T`. Sie erlaubt das Ablesen von Teilausschnitten aus Arrays, Vektoren oder anderen sequentiellen Kollektionen, ohne dass Speicher kopiert oder alloziiert werden muss.
* **Fat Pointer (Fetter Zeiger)**: Die interne Repräsentation einer Slice-Referenz auf dem Stack. Ein Fat Pointer ist genau zwei Systemworte groß (16 Bytes auf 64-Bit-Systemen) und besteht aus:
  1. Einer Speicheradresse (Zeiger), die auf das erste Element des Ausschnitts zeigt.
  2. Einer Länge (Anzahl der Elemente bzw. Bytes bei `str`), die den gültigen Bereich des Slices definiert.

### Alltagsnahe Metapher

> [!NOTE]
> **Die Scheinwerfer-Metapher**: Stellen Sie sich einen Scheinwerferkegel auf einer Theaterbühne vor. Auf der Bühne stehen mehrere Schauspieler nebeneinander (die Kollektion im Heap). Der Scheinwerferkegel beleuchtet nun einen ganz bestimmten Teilausschnitt der Bühne – zum Beispiel genau drei Schauspieler (das Slice). Der Scheinwerfer besitzt die Schauspieler nicht und kann sie nicht verändern. Er zeigt dem Publikum lediglich diesen Teilausschnitt. Die Position des Scheinwerfers entspricht der Speicheradresse (Pointer), und die Breite des Lichtkegels (wie viele Schauspieler beleuchtet werden) entspricht der Länge. Wenn sich die Schauspieler von der Bühne entfernen (Speicher freigegeben wird), würde das Licht ins Leere scheinen. In Rust verhindert der Compiler dies, indem er sicherstellt, dass die Schauspieler auf der Bühne bleiben müssen, solange der Lichtkegel auf sie gerichtet ist.

## 3. Das Problem & Die Motivation

In der Softwareentwicklung kommt es häufig vor, dass man auf Teilausschnitte einer größeren Kollektion zugreifen möchte, beispielsweise auf das erste Wort eines Satzes oder einen bestimmten Datenblock in einem Byte-Stream.

Ohne Slices ist man gezwungen, diese Teilausschnitte über manuelle Indizes (zum Beispiel Start- und Endpositionen als `usize`-Variablen) zu verwalten. Dies führt in der Praxis zu schwerwiegenden Problemen:
1. **Out-of-Sync-Indizes**: Die Indizes werden getrennt von der eigentlichen Kollektion gespeichert. Ändert sich die Kollektion (wird sie geleert, gekürzt oder verschoben), bleiben die gespeicherten Index-Variablen unverändert auf dem Stack bestehen. Sie verweisen auf ungültige oder veraltete Positionen.
2. **Gefahr von Laufzeitfehlern (Panics)**: Greift das Programm später mit einem veralteten Index auf die Kollektion zu, stellt Rust zur Laufzeit fest, dass die Grenze überschritten wurde, und bricht das Programm abrupt mit einer Panik ab.
3. **Speicherfehler und Sicherheitsrisiken**: In Sprachen ohne Sicherheitsgarantien (wie C oder C++) führt ein solcher Zugriff zu Undefined Behavior, Speicherfehlern (Use-After-Free) oder Datenlecks. Rust verhindert dies zwar durch Laufzeitprüfungen, doch ein Absturz des Programms zur Laufzeit ist in produktiven Systemen dennoch unerwünscht.
4. **Fehlende Kopplung**: Der Compiler kann die logische Abhängigkeit zwischen der Kollektion und den Index-Variablen nicht erkennen, da `usize` ein eigenständiger primitiver Typ ist.

Slices lösen dieses Problem fundamental, indem sie die Referenz auf den Speicherbereich direkt mit seiner Länge koppeln und die Lebensdauer dieses Slices über den Borrow Checker an die Lebensdauer der zugrundeliegenden Kollektion binden.

## 4. Der naive Versuch

Der folgende Rust-Code zeigt den naiven Versuch eines Anfängers, das Ende des ersten Wortes eines Strings als einfachen `usize`-Index zu speichern. Dieser Index wird nach dem Leeren des Strings ungültig, was beim anschließenden Zugriff zu einer Laufzeit-Panik führt.

```rust
// Diese Funktion sucht nach dem ersten Leerzeichen und gibt dessen Index zurück.
// Gibt es kein Leerzeichen, wird die Gesamtlänge des Strings zurückgegeben.
fn first_word(s: &String) -> usize {
    let bytes = s.as_bytes(); // Umwandlung in ein Byte-Array zur zeichenweisen Prüfung

    for (i, &item) in bytes.iter().enumerate() {
        if item == b' ' {
            return i; // Leerzeichen gefunden -> Index zurückgeben
        }
    }

    s.len() // Kein Leerzeichen gefunden -> Gesamtlänge zurückgeben
}

fn main() {
    let mut s = String::from("hello world");
    let word_end = first_word(&s); // word_end erhält den Wert 5

    s.clear(); // Der String wird geleert. Seine Länge im Speicher ist nun 0!

    // word_end ist auf dem Stack immer noch 5!
    // Der Compiler kann diese logische Inkonsistenz nicht erkennen.
    println!("Das erste Wort endete bei Index: {}", word_end);

    // Der Versuch, mit dem veralteten Index auf den geleerten String zuzugreifen,
    // provoziert nun direkt eine Laufzeit-Panik.
    let first = &s[0..word_end];
    println!("Das erste Wort lautet: {}", first);
}
```

## 5. Die Anatomie des Fehlers

### Compiler-Akzeptanz & Laufzeit-Panik
Das obige Programm lässt sich problemlos kompilieren, da aus Sicht des Compilers alle Typregeln eingehalten wurden. Beim Ausführen des Programms stürzt es jedoch in der Zeile `let first = &s[0..word_end];` mit folgender Fehlermeldung ab:

```text
thread 'main' panicked at src/main.rs:25:19:
byte index 5 is out of bounds of ``
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
```

### Zeile-für-Zeile-Erklärung des Speicherverhaltens

1. **Deklaration von `s`**:
   `let mut s = String::from("hello world");`
   * **Stack**: Rust alloziiert eine 24-Byte-Struktur für `s`. Diese enthält einen Pointer (8 Bytes, zum Beispiel auf Heap-Adresse `0x10A0`), die Länge `11` (8 Bytes) und die Kapazität `11` (8 Bytes).
   * **Heap**: An der Adresse `0x10A0` liegen die 11 ASCII-Bytes für `"hello world"`.
2. **Aufruf von `first_word`**:
   `let word_end = first_word(&s);`
   * Die Funktion `first_word` erhält eine unveränderliche Referenz `&s`. Sie durchläuft die Bytes und findet das Leerzeichen (`b' '`) bei Index 5. Sie gibt `5` als `usize` zurück.
   * **Stack**: Die Variable `word_end` wird mit dem Wert `5` initialisiert. Dies ist eine einfache Zahl, die keinerlei Verknüpfung zu `s` aufweist.
3. **Leeren des Strings**:
   `s.clear();`
   * Die Methode `clear` erfordert eine veränderbare Referenz (`&mut s`). Da zum Zeitpunkt dieses Aufrufs keine aktiven Ausleihen auf `s` existieren (die Ausleihe für `first_word` endete beim Verlassen der Funktion), erlaubt der Compiler diese Operation.
   * **Speicheränderung**: Die Länge von `s` auf dem Stack wird auf `0` gesetzt. Der Heap-Speicher bleibt alloziiert, wird aber als leer deklariert.
4. **Der fatale Zugriff**:
   `let first = &s[0..word_end];`
   * Es wird versucht, eine Teilscheibe von `s` von Index `0` bis `5` zu erstellen.
   * Da die aktuelle Länge von `s` jedoch `0` ist, schlägt die interne Prüfung `5 <= s.len()` fehl.
   * Um einen ungültigen Speicherzugriff zu verhindern, führt Rust eine kontrollierte Laufzeit-Panik aus und beendet das Programm. Der Compiler konnte dies nicht verhindern, da `word_end` als primitives `usize` auf dem Stack völlig unabhängig von der Lebensdauer des Strings `s` existiert.

## 6. Die Lösung

Die Lösung besteht darin, anstelle eines losen Index ein echtes String-Slice (`&str`) zurückzugeben. Dadurch wird die Lebensdauer der zurückgegebenen Referenz direkt an die Lebensdauer des Strings gebunden, und der Compiler verhindert verändernde Operationen an der Datenquelle, solange das Slice existiert.

```rust
// Die Funktion gibt nun ein String-Slice (&str) zurück, das direkt
// auf den Speicherbereich des übergebenen String-Slices verweist.
fn first_word(s: &str) -> &str {
    let bytes = s.as_bytes();

    for (i, &item) in bytes.iter().enumerate() {
        if item == b' ' {
            return &s[0..i]; // Gibt das Slice vom Start bis zum Leerzeichen zurück
        }
    }

    &s[..] // Gibt den gesamten String als Slice zurück
}

fn main() {
    let mut s = String::from("hello world");
    
    // word ist ein Slice (&str), das direkt auf den Heap-Speicher von s zeigt.
    let word = first_word(&s); 

    // FEHLER! Dieser Aufruf wird nun vom Compiler verhindert.
    s.clear(); 

    // Hier wird word noch verwendet.
    println!("Das erste Wort lautet: {}", word);
}
```

### Die Compiler-Fehlermeldung

Wenn Sie versuchen, diesen Code zu kompilieren, meldet der Borrow Checker folgendes:

```text
error[E0502]: cannot borrow `s` as mutable because it is also borrowed as immutable
  --> src/main.rs:19:5
   |
16 |     let word = first_word(&s);
   |                           -- immutable borrow occurs here
17 | 
18 |     s.clear(); 
   |     ^^^^^^^^^ mutable borrow occurs here
19 | 
20 |     println!("Das erste Wort lautet: {}", word);
   |                                           ---- immutable borrow later used here
```

### Zeile-für-Zeile-Erklärung nach dem EVA-Prinzip

* **Eingabe (Input)**:
  Die Funktion `first_word` erwartet als Parameter ein String-Slice `s` vom Typ `&str`. In `main` übergeben wir eine Referenz auf den String (`&s`). Da `String` das `Deref`-Trait mit dem Zieltyp `str` implementiert, führt der Compiler eine automatische Typkonvertierung (Deref Coercion) durch.
* **Verarbeitung (Processing)**:
  * Mit `s.as_bytes()` erzeugen wir eine Byte-Ansicht des Strings, um ihn zeichenweise zu analysieren.
  * Über `bytes.iter().enumerate()` iterieren wir über die Bytes und erhalten in jedem Schritt den Byte-Index `i` sowie eine Referenz auf das Byte `&item`.
  * Sobald ein Leerzeichen (`b' '`) gefunden wird, verwenden wir die exklusive Range-Syntax `&s[0..i]`, um eine Referenz auf diesen spezifischen Teilbereich zu erstellen. Diese Referenz wird sofort zurückgegeben.
  * Wird kein Leerzeichen gefunden, erzeugt `&s[..]` eine Referenz auf den gesamten String und gibt diese zurück.
* **Ausgabe (Output)**:
  Die Funktion gibt ein String-Slice `&str` zurück. Nach den Regeln der Lifetime Elision wird die Lebensdauer dieses Rückgabe-Slices implizit an die Lebensdauer des Eingabe-Slices `s` gebunden: `fn first_word<'a>(s: &'a str) -> &'a str`. Der Compiler weiß somit, dass die Variable `word` in `main` eine aktive, unveränderliche Ausleihe von `s` darstellt.
* **Die Mutationssperre**:
  Der Aufruf von `s.clear()` erfordert eine veränderbare Ausleihe (`&mut String`). Rusts Speicherregeln verbieten es jedoch strengstens, ein objekt veränderbar auszuleihen, solange noch mindestens eine unveränderbare Ausleihe (`word`) im selben Gültigkeitsbereich aktiv ist. Da `word` in der darauffolgenden `println!`-Zeile verwendet wird, bleibt die Ausleihe aktiv, und der Compiler blockiert das Leeren des Strings bereits zur Kompilierzeit.

## 7. Kleines Tutorial: Entwicklung eines Log-Parsers

In diesem Tutorial erstellen wir Schritt für Schritt einen einfachen Log-Parser, der Log-Zeilen im Format `"[LEVEL] Nachricht"` analysiert. Er extrahiert das Log-Level sowie die Nachricht als Slices und demonstriert, wie Rust jegliche Modifikation der Quell-Logzeile während der Nutzung der Slices unterbindet.

### Schritt 1: Die Funktion deklarieren
Wir definieren eine Funktion namens `parse_log_line`. Sie nimmt eine Logzeile als String-Slice entgegen. Da die Zeile fehlerhaft formatiert sein könnte, geben wir ein `Option`-Tupel zurück, das die extrahierten Slices enthält.
```rust
fn parse_log_line(line: &str) -> Option<(&str, &str)> {
```

### Schritt 2: Die öffnende Klammer prüfen
Wir stellen sicher, dass die übergebene Zeile mit einer öffnenden eckigen Klammer beginnt. Ist dies nicht der Fall, geben wir `None` zurück.
```rust
    if !line.starts_with('[') {
        return None;
    }
```

### Schritt 3: Die schließende Klammer suchen
Wir suchen nach der Position der schließenden eckigen Klammer `]`. Der Operator `?` sorgt dafür, dass die Funktion sofort `None` zurückgibt, falls die Methode `.find()` kein Ergebnis liefert.
```rust
    let end_bracket = line.find(']')?;
```

### Schritt 4: Das Log-Level extrahieren
Wir schneiden das Log-Level aus. Es beginnt direkt nach der öffnenden Klammer (Index 1) und endet unmittelbar vor der schließenden Klammer (Index `end_bracket`).
```rust
    let log_level = &line[1..end_bracket];
```

### Schritt 5: Die Nachricht extrahieren
Die Nachricht beginnt zwei Zeichen nach der schließenden Klammer (nach der Klammer selbst und dem darauffolgenden Leerzeichen). Wir prüfen, ob dieser Index innerhalb der Grenzen der Zeile liegt, und extrahieren dann den Rest des Strings.
```rust
    let msg_start = end_bracket + 2;
    if msg_start > line.len() {
        return None;
    }
    let message = &line[msg_start..];

    Some((log_level, message))
}
```

### Schritt 6: Anwendung und Prüfung der Mutationssperre
Im Hauptprogramm wenden wir den Parser an und demonstrieren den Schutz vor Speicherfehlern.
```rust
fn main() {
    // Wir erstellen eine veränderbare Log-Zeile
    let mut log_entry = String::from("[WARNUNG] Verbindung wird neu aufgebaut");

    // Wir parsen die Zeile und erhalten die Slices
    if let Some((level, msg)) = parse_log_line(&log_entry) {
        println!("Level: {}", level);
        println!("Nachricht: {}", msg);

        // HINWEIS: Wenn Sie die folgende Zeile einkommentieren,
        // verweigert der Compiler den Dienst, da 'level' und 'msg' 
        // noch aktive Referenzen auf 'log_entry' halten.
        //
        // log_entry.push_str(" - Versuchter Anhang");

        // Verwendung der Slices, um ihre Lebensdauer zu verlängern
        println!("Erfolgreich geparst. Das Level war: {}", level);
    } else {
        println!("Fehler: Das Log-Format ist ungültig.");
    }
}
```

## 8. Mentale Modelle & Deep Dive

### Das Speicherlayout eines Slices (Fat Pointer)

Ein normaler Referenz-Pointer auf ein Datenobjekt (zum Beispiel `&i32`) speichert lediglich eine 8-Byte-Speicheradresse. Ein Slice hingegen ist ein **Fat Pointer**. Er belegt im Stack genau **16 Bytes** und setzt sich aus einem Zeiger auf die Daten und der Anzahl der Elemente (Länge) zusammen.

```text
       Struktur der Variable `s` (String) im Stack (24 Bytes)
       +-------------------+-------------------+-------------------+
       | Pointer (ptr)     | Länge (len)       | Kapazität (cap)   |
       | 8 Bytes (0x5000)  | 8 Bytes (11)      | 8 Bytes (11)      |
       +-------------------+-------------------+-------------------+
                 |
                 v
       Heap-Speicher an Adresse 0x5000:
       +---+---+---+---+---+---+---+---+---+---+---+
       | h | e | l | l | o |   | w | o | r | l | d |
       +---+---+---+---+---+---+---+---+---+---+---+
                             ^
                             |
       Struktur des String-Slices `word` (&str) im Stack (16 Bytes)
       +-------------------+-------------------+
       | Pointer (ptr)     | Länge (len)       |
       | 8 Bytes (0x5006)  | 8 Bytes (5)       |
       +-------------------+-------------------+
```

### Komposition & Lebensdauern

#### Slices in Datenstrukturen (Structs)
Da ein Slice die zugrundeliegenden Daten nicht besitzt, sondern nur ausleiht, müssen Strukturen, die Slices enthalten, explizit mit Lifetime-Annotationen deklariert werden. Dies garantiert dem Compiler, dass das Struct niemals länger lebt als die Daten, auf die seine Slices verweisen.

```rust
// Das Struct Book leiht den Titel aus. Die Lebensdauer 'a stellt sicher,
// dass eine Book-Instanz nicht länger existieren kann als die String-Referenz.
struct Book<'a> {
    title: &'a str,
    pages: &'a [u32],
}

fn main() {
    let title = String::from("Rust Grundlagen");
    let pages = [10, 20, 30, 40, 50];
    
    let book = Book {
        title: &title,
        pages: &pages[1..4],
    };
    
    println!("Buch: '{}', Seiten-IDs: {:?}", book.title, book.pages);
}
```

#### Slices in Arrays und Vektoren
Slices können flexibel auf Teilausschnitte von Arrays und Vektoren verweisen. Der Typ lautet dann `&[T]` für unveränderliche Referenzen beziehungsweise `&mut [T]` für veränderliche Referenzen.

```rust
let mut array: [i32; 5] = [1, 2, 3, 4, 5];
let slice: &[i32] = &array[1..4]; // Referenziert [2, 3, 4]

let mut vector: Vec<f64> = vec![1.1, 2.2, 3.3];
let vec_slice: &mut [f64] = &mut vector[..2]; // Veränderbares Slice auf [1.1, 2.2]
vec_slice[0] = 9.9; // Modifiziert den Vektor direkt im Heap
```

#### Slices in `Option` und `Result`
Rust optimiert Referenzen in Kombination mit Enums. Da eine Referenz niemals den Wert `0` (Nullpointer) annehmen darf, nutzt der Compiler die Bitkombination des Nullpointers für die Darstellung von `None` bei `Option<&str>`. Dadurch belegt `Option<&str>` im Speicher exakt dieselbe Größe wie `&str` (16 Bytes).

```rust
let text = "Daten";
let option_slice: Option<&str> = Some(&text[0..2]); // Belegt 16 Bytes
```

### Deref Coercion

Deref Coercion ist ein automatischer Konvertierungsmechanismus in Rust. Wenn ein Typ das Trait `Deref` implementiert, kann Rust eine Referenz dieses Typs implizit in eine Referenz des Zieltyps umwandeln.
* `String` implementiert `Deref<Target = str>`. Daher wird eine Referenz vom Typ `&String` automatisch in ein `&str` umgewandelt, wenn dies erforderlich ist.
* `Vec<T>` implementiert `Deref<Target = [T]>`. Eine Referenz vom Typ `&Vec<T>` wird somit automatisch zu einem `&[T]`.

**Warum Sie Funktionen immer mit Slices als Parameter deklarieren sollten**:
Wenn Sie eine Funktion wie folgt definieren:
```rust
fn verarbeite_text(s: &str) {
    println!("{}", s);
}
```
Können Sie diese Funktion mit extrem hoher Flexibilität aufrufen:
1. Mit einem String-Literal: `verarbeite_text("hallo");`
2. Mit einer String-Referenz: `let s = String::from("hallo"); verarbeite_text(&s);`
3. Mit einem echten String-Slice: `verarbeite_text(&s[1..3]);`

Hätten Sie die Funktion stattdessen mit `s: &String` deklariert, müssten String-Literale erst unter einer Heap-Allokation in ein `String`-Objekt umgewandelt werden, um sie an die Funktion übergeben zu können. Slices als Parameter machen Ihre APIs somit performanter und flexibler.

### Systemebene, Thread-Safety & Performance

* **Speichergröße**: Auf 64-Bit-Systemen belegt jede Slice-Referenz (`&str`, `&[T]`) exakt 16 Bytes. Sie besteht aus einem 8-Byte-Pointer und einer 8-Byte-Länge. Auf 32-Bit-Systemen beträgt die Größe dementsprechend 8 Bytes (4 Bytes Pointer + 4 Bytes Länge).
* **Thread-Safety**:
  * Unveränderliche Slices (`&str`, `&[T]`) implementieren die Auto-Traits `Send` und `Sync`, sofern der zugrundeliegende Typ `T` `Sync` implementiert. Da sie schreibgeschützt sind, können sie sicher über Thread-Grenzen hinweg geteilt werden.
  * Veränderliche Slices (`&mut [T]`) implementieren `Send` und `Sync`, sofern `T` `Send` implementiert. Da veränderliche Slices exklusiv ausgeliehen werden, garantiert Rust auch hier absolute Datenrennofreiheit (Data-Race-Safety).
* **Performance**:
  * **O(1) Komplexität**: Das Erstellen eines Slices benötigt konstante Zeit, da lediglich der Pointer und die Länge kopiert werden. Es findet keine Heap-Allokation und kein Kopiervorgang von Elementen statt.
  * **LLVM Optimierungen**: Da der Compiler garantiert, dass sich veränderliche und unveränderliche Referenzen niemals überlappen (Aliasing-Garantie), kann der LLVM-Backend-Compiler den Maschinencode extrem stark optimieren. Bei Schleifen über Slices führt dies häufig zu automatischer **Vektorisierung (SIMD)**, wodurch mehrere Elemente parallel in den CPU-Registern verarbeitet werden.

### Exhaustive API-Reference (Lückenlos)

#### Wichtige Methoden für String-Slices (`str`)

1. **`len`**
   * *Signatur*: `pub const fn len(&self) -> usize`
   * *Parameter*: `&self` (unveränderliche Referenz auf das String-Slice).
   * *Rückgabetyp*: `usize` (Länge des Slices in Bytes).
   * *Sicherheitsaspekte & Panics*: Panikt nie.
   * *Beispiel*:
     ```rust
     let length = "Rust".len(); // 4
     ```

2. **`is_empty`**
   * *Signatur*: `pub const fn is_empty(&self) -> bool`
   * *Parameter*: `&self`.

## 9. Drei praktische Übungen

### Übung 1 (Leicht - Syntax festigen)
Schreiben Sie eine Funktion `last_word(s: &str) -> &str`, die das letzte Wort in einem String-Slice zurückgibt. Wenn kein Leerzeichen vorhanden ist, soll das gesamte Wort/der gesamte String zurückgegeben werden.

* **Anforderungen**:
  * Eingabetyp: `&str`
  * Rückgabetyp: `&str`
  * Nutzen Sie keine Hilfsmethoden von Drittanbieter-Bibliotheken.
* **Lösungshinweis**: Suchen Sie rückwärts nach dem ersten Leerzeichen unter Verwendung der Methode `.rfind(' ')`. Nutzen Sie den zurückgegebenen Index `Some(idx)`, um mittels Range-Syntax `&s[idx + 1..]` den hinteren Teil auszuschneiden. Liefert `.rfind(' ')` den Wert `None`, geben Sie den gesamten String zurück.

### Übung 2 (Mittel - Logik erweitern)
Schreiben Sie eine Funktion `trim_spaces(s: &str) -> &str`, die führende und nachfolgende Whitespaces aus einem String-Slice abschneidet und den bereinigten Teilausschnitt zurückgibt. Verwenden Sie dabei **nicht** die eingebaute Methode `.trim()`.

* **Anforderungen**:
  * Eingabetyp: `&str`
  * Rückgabetyp: `&str`
  * Whitespaces sind Zeichen, die `.is_whitespace()` erfüllen.
* **Lösungshinweis**:
  * Nutzen Sie einen Iterator über die Zeichen oder Bytes, um die Position des ersten Zeichens zu ermitteln, das kein Whitespace ist (zum Beispiel mit `.position(|c| !c.is_whitespace())`).
  * Nutzen Sie denselben Ansatz rückwärts, um die Position des letzten Nicht-Whitespace-Zeichens zu finden (zum Beispiel mit `.rposition(|c| !c.is_whitespace())`).
  * Denken Sie an den Randfall, dass der gesamte String nur aus Leerzeichen besteht – in diesem Fall soll ein leeres Slice `""` zurückgegeben werden.

### Übung 3 (Schwer - Transferleistung)
Implementieren Sie eine generische Funktion `find_subslice<T: PartialEq>(data: &[T], pattern: &[T]) -> Option<usize>`, die das erste Vorkommen einer Musterscheibe (`pattern`) in einem größeren Array-Slice (`data`) sucht und den Startindex zurückgibt.

* **Anforderungen**:
  * Die Funktion muss generisch über den Typ `T` sein.
  * `T` implementiert das Trait `PartialEq` für Vergleiche.
  * Falls `pattern` leer ist, soll `Some(0)` zurückgegeben werden.
* **Lösungshinweis**: Verwenden Sie die Methode `.windows(pattern.len())` auf `data`, um Teilausschnitte der exakten Länge von `pattern` nacheinander mit dem Muster zu vergleichen. Nutzen Sie die Methode `.position()`, um den ersten übereinstimmenden Index zu ermitteln.

## 10. Lernstrategie, Selbsteinschätzung & Merkzettel

### Spickzettel (Cheat Sheet): Range-Syntax

| Syntax | Beschreibung | Beispiel (für `s = "hello"`) | Ergebnis |
| :--- | :--- | :--- | :--- |
| `&s[start..end]` | Inklusive `start`, exklusive `end` | `&s[1..4]` | `"ell"` |
| `&s[start..=end]` | Inklusive `start`, inklusive `end` | `&s[1..=3]` | `"ell"` |
| `&s[start..]` | Ab `start` bis zum Ende des Slices | `&s[2..]` | `"llo"` |
| `&s[..end]` | Vom Anfang des Slices bis exklusive `end` | `&s[..3]` | `"hel"` |
| `&s[..]` | Das gesamte Slice (Referenzkopie) | `&s[..]` | `"hello"` |

### Die Feynman-Methode
Erklären Sie einem Programmierer, der nur Java oder Python kennt, das Konzept der Slices in Rust in drei einfachen Sätzen. Konzentrieren Sie sich darauf, wie Rust Speicherallokationen einspart und gleichzeitig die Sicherheit zur Kompilierzeit garantiert, ohne einen Garbage Collector zu nutzen.

### Gezielte Fehlerprovokation: UTF-8-Boundary-Fehler

Deutsche Umlaute wie `"ä"`, `"ö"` oder `"ü"` benötigen in UTF-8 zwei Bytes (zum Beispiel `"ä"` = `0xC3 0xA4`), während normale ASCII-Zeichen nur ein Byte belegen. Wenn Sie versuchen, einen String mitten in einem Umlaut zu zerschneiden, stürzt Rust ab. Provozieren Sie diesen Fehler absichtlich:

1. Schreiben Sie folgendes Testprogramm:
   ```rust
   fn main() {
       let s = String::from("Bäume");
       // 'B' belegt 1 Byte. 'ä' belegt die Bytes 1 und 2.
       // Wir schneiden bei Index 2 ab - also genau in der Mitte von 'ä'!
       let slice = &s[0..2];
       println!("{}", slice);
   }
   ```
2. Kompilieren Sie das Programm und führen Sie es aus.
3. Sie erhalten folgende Fehlermeldung:
   ```text
   thread 'main' panicked at src/main.rs:5:19:
   byte index 2 is not a char boundary; it is inside 'ä' (bytes 1..3) of `Bäume`
   ```
4. **Erkenntnis**: Nutzen Sie bei Strings mit Multibyte-Zeichen immer sichere Methoden wie `.get(0..2)` (welches `None` statt einer Panik liefert) oder arbeiten Sie über Iteratoren wie `.chars()`, um Zeichengrenzen nicht manuell verletzen zu können.

## 11. Zusammenfassung

* **Slices** sind unveränderliche oder veränderliche Referenzen auf zusammenhängende Teilbereiche einer Kollektion (`&str`, `&[T]`), ohne diese zu besitzen.
* Sie werden auf Systemebene als **Fat Pointer** (8 Bytes Startadresse + 8 Bytes Länge = 16 Bytes) auf dem Stack abgebildet, was sie extrem leichtgewichtig und allokationsfrei macht.
* Sie verhindern **Out-of-Sync-Fehler** (ungültige Indizes), da der Borrow Checker Mutationen der zugrundeliegenden Kollektion blockiert, solange Slices aktiv verwendet werden.
* APIs sollten bevorzugt **Slices als Parameter** akzeptieren (zum Beispiel `&str` statt `&String`), um dank Deref Coercion maximale Kompatibilität und Performance zu erzielen.
